# Front end

- Status: accepted
- Date: 2026-10-09

## 1. Purpose and scope

This spec defines the front end of Silicon: the stages from a `.si` file to core IR. It covers build step 4 of [the architecture](../architecture.md), the source language and the elaborator.

The goal: a source design has one meaning, which a Lean reference elaborator defines. The Rust front end agrees with that meaning on each run. A mechanical oracle checks each stage.

The language is the v0.1 proposal in [`doc/reference/`](../reference/SILICON_SPEC.md). This spec keeps all its features. It orders them into slices (section 12). Each feature gets a Lean definition in the reference elaborator. Section 9 shows how the features with the highest risk get one.

These items are out of scope. Each item has a follow-up issue (section 15):

- More than one clock domain, domain maps, and asynchronous reset. Issue #11 blocks them.
- Synchronous read ports in the core IR. Issue #12 adds them. Section 7.6 lowers the source memory onto the current core memory.
- The design of contracts (`conforms`, `using`) and certificates. They come after packages. The parser reserves their syntax now.
- The LSP and `salsa`. They come in build step 5.

## 3. The meaning of a source design

A build has a `.si` file and a top selection. A top selection names a module and its static arguments, for example `Counter(8)`. The Lean function `elaborate` maps them to a core design or to an error:

```lean
elaborate : Source → TopSelection → Budgets → Except Error Core.Design
```

The meaning of a source design is the semantics of the core IR (core IR spec, section 5) of `canonicalize (elaborate src top budgets)`. The front end adds no second semantics. Elaboration exists only to produce core IR. The core IR then has its proven semantics, its interpreter, its reference lowering, and LEC.

These consequences follow:

- The Lean `Source` modules are the normative definition of the language. The prose of v0.1 is input for them, not a second authority. A disagreement between them is a bug in the Lean modules or a language decision for the human gate.
- A port schema maps each source port to its core port. Source vectors (section 11.2) and, later, contracts use it.
- Elaboration does no optimization. An optimization is a core-to-core pass, and LEC checks it.

## 4. Pipeline

```text
.si text
  │ syntax: lexer, rowan tree types                 Lean: Source.Lex
  │ parse: lossless tree with recovery, typed AST   Lean: Source.Parse, Source.Print
  │ resolve: item table, scopes, names               Lean: Source.Resolve
  │ typeck: generic pre-check                       Lean: Source.Check
  │ elab: static evaluator, instantiations,         Lean: Source.Value, Source.Eval,
  │       checks for each instantiation                   Source.Elab
  │ elab: lowering to core IR, names                Lean: Source.Flatten, Source.Layout,
  │                                                       Source.Names
  ▼
core IR (.sil) → existing chain: check, run, backend-circt, reference lowering, LEC
```

### 4.1 Stage interfaces

Each stage is a pure function of its inputs. Each stage reports the first error of its pass in the order of section 6.

| Stage     | Input                                | Output                                                                               |
| --------- | ------------------------------------ | ------------------------------------------------------------------------------------ |
| `syntax`  | Bytes                                | Tokens                                                                               |
| `parse`   | Tokens                               | A lossless syntax tree with errors, and an AST with source spans. Or `S001`, `S004`. |
| `resolve` | AST                                  | A resolved AST: each name points to its declaration. Or `S002`, `S003`.              |
| `typeck`  | Resolved AST                         | The same AST, or `S005` to `S008`                                                    |
| `elab`    | Resolved AST, top selection, budgets | A core design, or `S008` (section 9.1) or `S010` to `S020`. Slice 3 adds `S021`.     |

The resolved AST is the boundary between the stages that work on all code and the stages that work on instantiations. `elab` holds no syntax tree. It reads the resolved AST only.

### 4.2 The generic pre-check and the checks for each instantiation

A width such as `UInt[W + 1]` has no value before `W` has a value. A type check before elaboration thus cannot check widths. The work splits into two parts:

- **Generic pre-check (`typeck`).** These checks need no static values: the syntactic stage rule, placement, arity, and the aliasing rule of `mut` places. They run on each item, also on an item that no instantiation uses. An agent thus gets these errors without a top selection.
- **Checks for each instantiation (`elab`).** These checks need static values: types and widths, fit, the dynamic stage rule, effects, resources, and bindings. They run on the code that an instantiation executes. A `comptime if` checks only its selected branch, as v0.1 section 1 requires.

Lean has the same split: `Source.Check` and `Source.Elab`.

The modules are under `lean/Silicon/Source/`, in dependency order:

The crate `srcgen` is dev-only, as `testkit` is. Only `xtask` and `[dev-dependencies]` name it. It comes before `parse` in the layer order, so it cannot use the code of the stages that it tests. See [ADR 0018](../adr/0018-source-generator-crate.md).

These rules apply to the Rust front end:

- **Query shape.** Each stage is a pure function. Its key is a file and an item, or an `InstantiationId`. No stage has global mutable state. `salsa` replaces the plain calls when the LSP starts.
- **Determinism.** The crates `resolve`, `typeck`, and `elab` use no `std::collections::HashMap` and no `HashSet`. A clippy `disallowed-types` rule enforces this. An output order comes from the evaluation order or from a sort, never from an address or a hash.
- **Recovery.** The parser and the resolver continue after an error, for the LSP. The first error in the order of section 6 must equal the error of Lean. Later errors have no oracle.
- **Interfaces.** Each crate exports a small interface. `elab` exports `elaborate`, `eval`, `cost`, and the schema. Slice 2 adds `observe`.

### 4.5 Preparation for an Aeneas proof

The end goal is a proof of the Rust front end against the Lean reference elaborator. Aeneas translates Rust code to Lean, and a proof then relates the translation to the reference. Issue #10 plans the same proof for the core IR checker and interpreter. Until that proof exists, `silicon-check validate` on each run is the oracle.

Aeneas reads the MIR of the compiler through Charon. It supports a subset of safe Rust. These limits of Aeneas matter for the front end:

- No `unsafe` code, no interior mutability (`Cell`, `RefCell`), and no shared ownership with mutation (`Rc`, `Arc`).
- No trait objects (`dyn`). Support for closures, iterator adapters, and complex trait code is partial.
- Only a part of the standard library has a Lean model. `Vec` and `Box` have one. `HashMap`, external crates, and most iterator adapters do not.
- A loop becomes a recursive Lean function. A panic and an arithmetic overflow become an error result.
- Borrows inside data structures and nested mutable borrows have limited support.

The Rust front end thus follows these rules where they cost little:

- The **elaborator core** is the code of `elab` from the resolved AST to the core design: `Value`, `Eval`, `Elab`, `Flatten`, and `Names`. It uses plain `enum` data, `match`, `Vec`, `Box`, and indices into a `Vec` for arenas. It has no trait object, no interior mutability, no shared ownership, no thread of its own, no `HashMap`, and no external crate. It has no `FnMut`, which is a closure that captures a mutable value. A function that changes state gets the state as a parameter. The core can use iterator adapters, and the proof gives each adapter that the core uses a Lean model.
- The rule `elab-subset` parses each module of `elab` that `lib.rs` reaches, and it skips each item with the attribute `#[cfg(test)]`. It rejects these names in the other code: `Cell`, `RefCell`, `OnceCell`, `LazyCell`, `UnsafeCell`, `Rc`, `Arc`, `Weak`, `Mutex`, `RwLock`, `OnceLock`, `LazyLock`, each `Atomic` type, `FnMut`, `HashMap`, and `HashSet`. It also rejects `dyn`, `unsafe` (also on a trait, an impl, and an `extern` block), `static mut`, `std::thread`, and these macros: `thread_local!`, `include!`, `include_str!`, `include_bytes!`, and `macro_rules!`. It rejects `#[path]` on a module, a glob of a crate root such as `use std::*`, and an alias of a standard crate such as `use std as s`. Check: `cargo xtask check` (rule `elab-subset`).
- The rule cannot see a closure that captures a mutable value without the word `FnMut`, for example `.map(|x| { n += 1; x })`. It does not check external crates. The proof must handle both. The syntax tree and the parser are outside this rule, as the next list shows.
- The evaluator and the lowering recurse, so they run through `parse::NestedStack::nest` and `parse::on_stack`. Each can run its function on a new thread. The proof takes each as one call of the function, in place, with the same state and the same result, when the stack allocation succeeds. A `StackError` with no call is an error result. The proof trusts these assumptions, and `doc/trust.md` lists them.
- The elaborator core returns `Result` for each error and does not panic. It passes the fuel as an explicit argument, so its loops have a visible bound.
- The resolved AST is a plain owned tree. It holds no `rowan` node and no `salsa` handle.
- `salsa`, the LSP, the diagnostics, and the `driver` stay outside the elaborator core. They call it as a pure function.

These parts cost a lot to adapt. They stay outside the first proof, and validation keeps them covered:

- **The syntax tree and the parser.** `rowan` uses `Rc` and `unsafe` code. A parser for Aeneas needs a second, plain tree. The proof of the parser comes after the proof of the elaborator core, or the parser keeps validation as its oracle.
- **Static integers of any size.** The elaborator core uses an integer type of its own with a small interface. The proof can take a Lean model of this interface as an assumption, and `doc/trust.md` lists it.
- **The SHA-256 digest.** The proof takes it as an opaque function with the Lean `Sha256` as its model.
- **The ordered maps.** The elaborator core keeps its tables in `BTreeMap` and `BTreeSet`: the frames of locals, the core names, the versions, the instantiations, and the results of the scan. Aeneas has no Lean model of these types. A `Vec` costs more. A search takes a linear step at each look-up. A `Vec` with an index for each declaration takes a step for each declaration at each call. Thus the work of the elaboration grows with the square of the size of the program. Some keys are strings or tuples, so they are not dense indices. Thus the maps stay. The proof takes the few map operations that the core calls as an assumption, as for the integers. Their model is the Lean `Std.TreeMap`. `doc/trust.md` lists this assumption.

## 5. Elaboration

### 5.1 Values

A value of the evaluator has one of these forms:

- **Static value.** An integer (`Int`, and `Nat` as a checked `Int`), a Boolean, a string, a type, a named function, or a finite static integer of type `UInt[W]` or `SInt[W]`. Slice 2 adds the unit value `()`.
- **Container (slice 2).** An array, a tuple, a record, or a list. It holds a sequence of values, its elements.
- **Hardware value.** A typed tree of core operations over core names. Its source type is `Bool`, `UInt[W]`, or `SInt[W]`.
- **Handle.** A reference to a register, a wire, a memory, an instance, or a child input. Its identity is its structural path (section 7.3). A memory handle also holds the word type and the depth of the memory.

A finite static value uses the same `BitVec` function as the core operation. The Lean definitions share the function, so `static_op_agrees` (section 10.3) is nearly definitional.

Slice 2 adds these rules. The parser of slice 1 rejects their syntax with `S004`, so they do not change slice 1.

- **Shape.** The shape of a container is static: its length, its indices, and its field names. Each element keeps its own stage, so one container can hold static and hardware elements.
- **Leaf.** A leaf of a value is a part, at any depth, that is not a container and not `()`. A leaf is a static value or a hardware value. A **hardware leaf** is a leaf that is a hardware value. In slice 2, a leaf is never a handle: a handle as an element is `S010`, and the message names slice 3.
- **Array.** The type `[T; N]` has the fixed length `N` and one element type `T`. `[a, b]` makes an array. The element type is the common type of the elements, by the operand rule of slice 1. Thus a static integer converts to the finite type of another element. Elements with no common type give `S010`. The length `N` of `[T; N]` is a static position (`S005`). In an expression, `[T; N]` is a type, as in the v0.1 grammar. Its element `T` is a type expression, and its length `N` is an expression. The two syntax categories are thus mutually recursive. The parser decides at the `[`: a `;` at the depth of this bracket makes it `[T; N]`, and the `;` is a separator at this depth. The parser does not try again, so the parse stays linear. Thus the `0` of `[0; 4]` is not a type, and it gives `S001` at its first token.
- **Empty array.** `[]` gets its type `[T; 0]` only at a typed use: an annotation, an assignment, an argument, a return, a constant, or a module argument. As a module argument, `[]` takes the type of its parameter. Each module argument gets its typed use at its parameter type (section 5.3). That parameter type evaluates in the scope of the module, with each earlier parameter bound to its converted argument. The parent pays for this work. A struct argument does the same in the scope of the struct, before the key of the specialization exists. Thus `P[[]]` is valid when the parameter of `P` has the type `[Bool; 0]`. The type of a typed use also goes into each element of a nested literal. Thus `let a: [[Int; 0]; 1] = [[]];` is valid. A literal that holds `[]` without a typed use, for example `[[]]`, is `S010` at the first `[]`.
- **Index.** An index of a container is a static position. Its value is a static `Int` or `UInt`. An `SInt` index is `S010`. An index that names a port, a register, a wire, or an instance is `S005` in pass 4. Another hardware index is `S011` in pass 5.
- **Container equality.** `==` and `!=` on containers compare each pair of elements by the operand rule. A static integer thus converts to the finite type of its pair, and the conversion checks its fit (`S012`). In a static equality, this conversion has no charge of its own (section 5.4). A leaf pair of a hardware aggregate keeps the conversion charge of slice 1 (section 7.4). The length of a list is a value, not a part of its type. Two lists of different lengths are thus unequal, not `S010`.
- **Tuple.** The type `(T, U)` and the value `(a, b)`. A tuple with one element is `(a,)`. The selectors `.0`, `.1`, and so on select an element. The selector after `.` can be any number literal, and its value selects the element. Thus `t.0x1` and `t.0b1` select the element 1, as `t.1` does. This differs from the v0.1 grammar, which allows only a decimal selector.
- **Record.** A value of a `struct` type (section 5.6). Its type is nominal: its identity is the declaration and the static arguments. `P[8](a, b)` makes a record with the fields in declaration order.
- **List.** `List[T]` is a static type only. `list(T)` makes an empty list. `push`, `pop`, and `len` change and read it. A value with a hardware leaf in a list is `S011`.
- **String.** A static sequence of Unicode scalar values. `+` joins two strings. `s[i]` gives a string with the scalar `i` of `s`. `str(n)` gives the decimal form of an `Int` or a `Nat`. `len(s)` counts the scalars. `str` of a finite integer is `S010` by the type rule, also for a hardware `UInt`. An order operator on two strings is `S010`. A string is not a container, so an assignment to an index of a string is `S010` at the index.
- **Type.** A static value of type `Type`. Its forms are `Bool`, `Nat`, `Int`, `UInt[W]`, `SInt[W]`, `Unit`, `String`, `Type`, `[T; N]`, `(T, U)`, `List[T]`, a struct specialization, and `fn (T, mut U) -> V`. A `type` alias is transparent: it names the normalized type. Two types are equal when their normalized terms are equal.
- **Function type.** `fn (T, mut U) -> V` is a type expression. In an expression, it is a unary operand, as in the v0.1 grammar, so a postfix after it belongs to its result type. A parameter type can have the mark `mut`. A `comptime` mark there is `S001` at the mark. An index of a function type, for example `(fn () -> UInt)[8]`, is `S007` in pass 4.
- **Function value.** A named function that is not generic, also a `comptime fn`. A function is generic when it has a `comptime` parameter, or when a parameter type or its result type names one of its parameters, for example `fn d(T: Type, x: T) -> T`. The resolver knows this, so the check needs no evaluation. Its type is its signature, with the `mut` mark of each parameter. A named wrapper gives a function value for one specialization (v0.1, section 2).
- **Function name as a value.** A name of a function item gives a function value, except as the callee of a call (section 5.6). The name charges its node. A generic function or a builtin is then `S010` at the name. Then the signature evaluates in the scope of the function: each parameter type, then the result type, as type expressions. The function type then charges its recursive size, as a type constructor does. This evaluation is not a call, so it adds no call frame. It is a nested evaluation, so it adds one nesting level. A signature can name its own function, for example as an argument of a call in a parameter type. The nesting depth then ends this cycle with `S015` at the name. A value or a type of this evaluation above the nesting depth is `S015` at the name, as the function type is. A call, a constant, or a struct use in the signature nests, so its own checks keep their positions. The name makes the value, so a binding of it is not a copy.
- **Typed use of a function value.** A typed use of a function value needs its exact function type: equal parameter types, equal `mut` marks, and an equal result type. It converts nothing and charges no conversion, as a record at its struct type does. Another type is `S010`.
- **Function equality.** `==` and `!=` are `S010` at the operator when the type of an operand holds a function type at any depth. Examples are a function, a value of type `[fn () -> Bool; 0]`, and a value of type `List[fn () -> Bool]`. The check comes after both operands evaluate, before each join and each charge of the operator. It reads the type metadata (section 5.4), so it walks no value.
- **Hardware data.** `Bool`, `UInt[W]`, `SInt[W]`, and `Unit` are hardware data. An array, a tuple, or a record is hardware data when each element type is hardware data. `Int`, `Nat`, `String`, `Type`, `List[T]`, and a function type are not. A type that holds a function type at any depth is thus not hardware data, also `[fn () -> Bool; 0]`. A port, a `reg`, and a `wire` need a hardware data type (`S010`), and this type can be empty (section 7.5).
- **Leaf of a type.** A leaf of a hardware data type is a part of type `Bool`, `UInt[W]`, or `SInt[W]`. A type without a leaf, for example `Unit` or `[T; 0]`, is empty.
- **Hardware aggregate.** A container with at least one hardware leaf. Section 7.4 lowers it leaf by leaf ([ADR 0019](../adr/0019-aggregates-lower-to-leaves.md)). A container without a hardware leaf is a static value. A list never holds a hardware leaf (`S011`).
- **Aggregate form.** The evaluator holds a hardware aggregate as a tree. Each container node stores its recursive size, its depth, its type, and its number of hardware leaves. Thus no charge walks the tree. The nodes have six kinds:
  - A static part: a value without a hardware leaf. It is a static scalar, `()`, a list, or a container without a hardware leaf.
  - A hardware leaf: a hardware value.
  - A reference: a whole port, register, wire, or child output, or a static part of one, with its type. A reference does not expand into its leaves (section 5.4). The `data` field of a memory response is a reference to the word of the memory, with a bit offset (section 7.6).
  - An array, a tuple, and a record, with their elements.
- **Static positions of an aggregate.** A hardware aggregate at a static position is `S011`. A module argument, an element of a list, and the element of `push` are static positions for this rule.

Slice 3 adds these rules. The first part comes in slice 3a, and the second part comes in slice 3b (section 12.4).

- **Enum type (slice 3a).** An `enum` item declares a nominal type (section 5.6). Its identity is its declaration. An enum has no parameters in slice 3. Its tag type is `UInt[W]`. Each variant has a static tag value of this type and zero or more payload types.
- **Enum value.** A static enum value holds its tag and its packed payload bits. The payload of a variant packs its values as the tuple of its payload types, in packing order. The first leaf goes in the low bits, and the high bits are zero ([ADR 0025](../adr/0025-enum-payload-packs-its-leaves.md)). A static enum value can thus hold a tag that no variant declares, for example from `reinterpret` or `T()`.
- **One static form.** An enum value whose two parts are both static is a static enum value. A node of an enum type with only static parts thus normalizes to this form. Each enum value without a hardware leaf thus has one form. Its size, its serialization, and its equality do not depend on the operation that made it.
- **Enum leaves.** An enum has two parts: `tag` of type `UInt[W]` first, then `payload` of type `UInt[P]`. `P` is the largest `data_bits` of the payloads of its variants. The payload is empty when `P` is 0. An enum value with a hardware leaf is a hardware aggregate with these two parts. A constructor with a static tag thus gives a static `tag` leaf and a hardware `payload` leaf when a payload value is hardware. A hardware enum is a container node of the aggregate form, with the type of the enum and the parts `tag` and `payload`.
- **No fields.** `tag` and `payload` are leaves, not fields. Thus `e.tag` and `e.payload` are `S010`. Each other field or `.N` selector of an enum is `S010` too. Section 6.2 gives the text. Only `reinterpret` gives the bits of an enum (F26).
- **Enum as hardware data.** An enum is hardware data with `data_bits = W + P`. `T()` of an enum gives the tag 0 and the payload 0. `==` and `!=` are `S010` when the type of an operand holds an enum at any depth. The message of section 6.2 tells the user to compare with a `match`. The check reads the enum flag of the type metadata (section 5.4), so it walks no value. It comes after both operands evaluate and after the check of a function type. It comes before each join and each charge of the operator.
- **Typed use of an enum.** A typed use at an enum type needs a value of exactly this enum type. It converts nothing and charges no conversion, as a record at its struct type does. Another value is `S010`.
- **Handle leaf (slice 3b).** A handle is a third kind of leaf, next to a static leaf and a hardware leaf. A handle is not static, and it is not hardware data. Its identity is its structural path and its owner. A handle copies as an identity, so a copy refers to the same resource ([ADR 0026](../adr/0026-handles-copy-as-identities.md)).
- **Handle type.** `Reg[T]`, `Wire[T]`, `Mem[T, N]`, `Input[T]`, and `Instance[M, args]` are static values of type `Type` (section 5.6). A handle type is not hardware data. Thus a port, a `reg`, a `wire`, `T()`, and `data_bits` reject it with `S010`.
- **Typed use of a handle.** A typed use at a handle type needs a handle of exactly this type. No conversion applies, so another value is `S010`. A typed use at a data type reads a register or a wire (section 9.2). Thus `let a: Reg[UInt[8]] = r;` keeps the handle, and `let a: UInt[8] = r;` reads it.
- **Containers of handles.** An array, a tuple, a record, and a list can hold handle leaves. The rule of slice 2 that a handle as an element is `S010` goes away. A list still holds no hardware leaf (`S011`), but it can hold handles, as `bind_all` of v0.1 needs. A container with a handle leaf is not a static value.
- **Static positions of a handle.** A static position has no handle leaf (`S011`). These positions are a module argument, a `comptime` parameter, an argument of a `comptime fn`, and a `const`. A list of handles is thus not static, and a static position rejects it.
- **Aggregate form.** The nodes of section 5.1 get two more kinds: a handle leaf, and an enum with its `tag` part and its `payload` part.

Lean defines `Value` and `Ty` as nested inductive types. A Lean container uses `Array`, so an index and `len` of an array or a list take constant work. The Rust containers use `Vec` and `Box`, inside the subset of section 4.5.

### 5.2 Evaluation order

Elaboration executes statements in source order. The order of the operands, the arguments, and the branches is the order of v0.1, section 1. This order is normative. It fixes the first error, the cost, and the core names.

Slice 2 adds the order of an assignment `place = e` whose place has a step. A step of a place is an index, a `.N` selector, or a field `.f`. The steps of the place come first, from the root outward. Each step charges 1 before it applies, as an expression node does. Then the index expression of an index step evaluates, and the index gets its static check (`S011` and `S013`). Then `e` evaluates. The assignment then replaces the selected part of the root.

Each step reads the live value of the root after its index evaluates, and its range check uses that value. The assignment writes into the live value of the root after `e` evaluates. A `mut` actual resolves its place by the same steps (section 9.1). `S008` keeps the root unchanged in the window of the place, so each read gives the value of the root when it became pending.

An index, in a place or in an expression, does its checks in this order after it evaluates:

1. The index is static (`S011`).
2. The indexed value can take an index, for example an array or a tuple (`S010`).
3. The index is a static `Int` or `UInt` (`S010`). Thus an `SInt` index is `S010`.
4. The index is in range (`S013`).

### 5.3 Instantiations

An `instance u = M(args);` statement elaborates as follows:

1. Evaluate the arguments from left to right. Each argument is a recursively static value.
2. Give each argument its typed use at its parameter type. This work nests one level, in the scope of `M`, with a new frame of locals. For each parameter in order, its type evaluates as a type expression. A `[]` argument takes this type. The argument converts to this type. Then the recursive size of the converted argument charges, before the next parameter type evaluates. Then the parameter binds to the converted value. Thus a later parameter type can read an earlier parameter.
3. Make the `InstantiationId`: the `ModuleId` of `M` and the canonical serialization of the converted arguments (section 7.1).
4. If the `InstantiationId` is in progress, report `S019` at the statement.
5. If the `InstantiationId` is done, use its result. Nothing more charges.
6. Otherwise, mark it in progress, elaborate `M` with the converted arguments now, and mark it done. The parameters bind to the converted values. Their types do not evaluate again, and the child charges nothing for them.
7. Bind `u` to an instance handle in the parent.

Step 2 uses the typed use of section 5.4. A function, a type, or a record argument gets no conversion. Its type must equal the parameter type. A container converts each element. Take a parameter of the type `[UInt[8]; 2]`. Then `[1, 2]` and `[UInt[8](1), UInt[8](2)]` give one `InstantiationId`. A struct use makes the key of its specialization in the same way (section 5.6). The top selection runs steps 2 to 6 for its arguments too. Section 6.2 gives the order of the errors.

Slice 3 adds two rules. An enum argument needs its exact type, as a record argument does, and it gives the digest form of the emitted name (section 7.1). A module argument is a static position, so an argument with a handle leaf is `S011` at step 1 (section 5.1). The type `Instance[M, args]` gives its arguments the typed use of step 2 at the parameter types of `M` (section 5.6). Thus it has the same key as the `InstantiationId` of `instance u = M(args);`.

A repeat of a done `InstantiationId` runs steps 1 to 3 again. It thus pays again for each parameter type and each typed use. An error of step 2 occurs in the parent, so its backtrace (section 6.3) ends at the parent.

The table of instantiations is normative, as the table of constants is. The evaluation order fixes which use of an `InstantiationId` comes first. Both front ends thus elaborate and charge the same instantiations, and no implementation cache can change a result. A child elaborates before its parent continues. The first error is the first error in this depth-first order.

An instantiation elaborates in two steps:

1. It executes the module body.
2. It checks the bindings (`S018`) of its resources.

After the top instantiation, the elaborator lowers the design and runs the core checker on it (section 7.5).

### 5.4 Budgets and the cost model

One elaboration has two budgets. All parts of the elaboration share them, in the normative evaluation order: the top selection, each instantiation, and each constant. An `eval` command is its own elaboration. The defaults are normative. The budget values are build inputs, and the build record names them.

| Budget        | Unit                                                                                                | Default   | Flag      |
| ------------- | --------------------------------------------------------------------------------------------------- | --------- | --------- |
| Fuel          | Cost units                                                                                          | 100000000 | `--fuel`  |
| Nesting depth | Active calls, typed uses of module arguments, instantiations in progress, and constants in progress | 1000      | `--depth` |

From slice 2 on, the nesting depth also counts the struct specializations in progress (section 5.6). It also bounds the depth of each value and each type (section 5.5). It needs no budget of its own.

The parse stage has one budget of its own: the **syntax depth** N. It bounds the depth of brackets and the height of an expression or a type (section 6.2). Its default is 4096, and the flag `--syntax-depth` sets it to a value from 1 to 65536. Another value is a usage error with exit code 2. Like the other budgets, it is a build input, and the build record names it. Compilation and validation use the same value. The default is far above the depth of written or generated code, so it is not a limit of the language.

The syntax depth bounds the native stack of each front end:

- The lexer rejects a bracket above the depth N, so the recursion of a parser stays bounded for any input.
- A parser builds a chain of binary operators, unary operators, fields, calls, or `else if` branches in a loop.
- After the parse, each recursive pass over the AST goes at most about 2N deep: N for the blocks and N for an expression.
- The Rust front end runs on a thread with a stack for the depth N. When the machine cannot give this stack, the command fails with exit code 2 before it parses.
- Each front end has a test at the default limit, a test at the depth 65536, and a test with 1,000,000 open brackets. Each gives the expected result and no stack overflow.

The cost model:

- Elaboration charges one cost unit before it evaluates an expression node.
- It charges one cost unit before it executes a statement. A block is a statement.
- A `comptime for` charges its statement once, and the sum of the sizes of its two bounds for the range. Each iteration then charges the size of its loop value before it binds it, and its body block charges once.
- A call charges its expression node. The body block of the callee charges as a statement.
- A type expression charges as an expression.
- An operation that makes a value charges a bound on the recursive size of that value, known before the operation runs. The bound holds up to a constant factor: `2^32 * 2^32` charges one word and makes two. A unary operation charges the size of its operand. An addition, a subtraction, and a bitwise operation charge the sum of the operand sizes. A conversion charges the operand size plus the result size. An operation that reads a value in full, for example a comparison or a serialization, charges its recursive size.
- An operation that only refers to a value charges no size: a name, a field selection, a static index, and `len`. A string is the exception (slice 2, below).
- A static condition, a static `&&` or `||`, and a static `if` that selects a value charge only their node. An `if` or a name that selects an existing value passes the reference on, so a later binding of it is a copy.
- A typed use converts a static integer to a finite value. These are typed uses: an annotation, an assignment, an argument, a return, a constant, `T(n)`, and an operand next to a finite operand. The copy comes first, then the conversion charge. A module argument and a struct argument are the exception (sections 5.3 and 5.6). Their typed use comes first. Then the copy of the converted value charges its recursive size. A use of the same type charges no conversion.
- A typed use at `Nat` checks the sign before its charge. A typed use at a finite type checks the fit after its charge. Thus a negative integer at `Nat` is `S012` before the conversion charges. A typed use of a container checks the types and signs of all its elements before its charge. Thus a negative `Nat` element is `S012` before the charge, also after an earlier element that does not fit its finite type.
- A call of a builtin or of a constructor `T(x)` charges the sizes of its arguments as copies, before the type check and the conversion. The builtins are `resize`, `reinterpret`, `static_assert`, and `error`, and from slice 2 on `str` and `list`. `len` only refers to its argument, so it charges no copy.
- An explicit block `{ ... }` is one statement and charges once. The body of a call, each `comptime if` branch, and each loop iteration charge once each. The root name of an assignment target charges nothing. Each step of the target charges 1 (section 5.2).
- A copy charges the recursive size of the value. These are copies: a binding of an existing value, an argument, a return, a `mut` write-back, a `push`, and a `pop`. A binding of a value that its expression just made is not a copy.
- A serialization charges its length in bytes, and the decimal form of an integer charges the square of its size. The emitted name of an instantiation charges its length in bytes too.
- A multiplication, a division, and a remainder of static integers charge the product of the operand sizes. A left shift charges the size of its result. A right shift charges the size of its operand, because it reads the operand in full.
- An `instance` statement charges the recursive size of each converted argument right after its typed use, before the next parameter type evaluates. This charge also occurs when the `InstantiationId` is done. Each `instance` statement charges its parameter types and its typed uses again.
- A hardware operation makes one node and charges 1 plus the number of its operands. Its operand trees are shared, not copied. `&&`, `||`, and `if` on hardware values are hardware operations.
- The `cost` command attributes each charge to one instantiation. The parent pays for an `instance` statement and the typed uses of its arguments, with each parameter type (section 5.3). It also pays for the serialization and the emitted name of a new child. The child pays nothing for its parameters. The units of an instantiation do not include those of its children. The charges of the top selection belong to no instantiation, so `total` can exceed the sum of the lines.

The recursive size of a value counts each node and each payload, over all nested values:

- An integer has the size 1 for each 64-bit word of its magnitude, and at least 1. A finite value of type `UInt[w]` or `SInt[w]` has the size 1 for each 64-bit word of its width `w`, and at least 1. A Boolean, a handle, and a named function have the size 1.
- A string has the size 1 plus its number of characters.
- An array, a list, a tuple, and a record have the size 1 plus the recursive sizes of their elements.
- A type has the number of nodes of its normalized term, plus the size of each integer in it: `UInt[8]` has the size 2. A hardware value has the number of nodes of its tree without names.
- A hardware value that refers to a core name has the size of a finite value of its type. Such a value is a reference to a port, a register, a wire, a named binding, or a child output. A reference aggregate (section 5.1) thus has the zero size of its type, and the type metadata gives this size.
- A mark of a shared operand (below) has the size of a finite value of its type. Its operand does not count, because the mark paid for it once.
- Slice 2 gives the terms of the new types. The unit value `()` and the types `Unit`, `String`, and `Type` have the size 1. `[T; N]` is a node with `T` and the integer `N`. `List[T]` is a node with `T`.
- A tuple type is a node with each element type. A function type is a node with each parameter type and the result type, and each `mut` mark is one more node.
- A struct type is a node with its static arguments as values. Its field types do not count, because its identity is nominal. Thus `P[8]` has the size 2.

An implementation can share immutable parts of a value. The charge is the recursive size all the same, so acceptance does not depend on the sharing.

- The lowering charges one cost unit for each core node that it emits. A core node is a design, a module, a port, a statement, a reset, a connection, or an expression node.
- The lowering runs in this order, which fixes the position of an `S015`: the instantiations in the order in which they finish. In a module, the order is the module, the domain ports, the ports, and the registers. Then come the memories (slice 2), the named `let` values, each `:=` binding with its connections, and the instances. The ports and the memories lower in declaration order. Section 7.6 gives the order in the block of one memory.
- The lowering units of a module count toward its instantiation. The design node and the name of the top count toward no instantiation.
- The design node and the name of the top charge last, at the position of the top selection. The top selection is a text of its own, so this position is line 1, column 1. Thus a fuel one unit below the total of `cost` gives `S015` at `1:1`.
- The lowering charges one cost unit for each core node that it emits. Each field of a core name charges its length in bytes, at least 1. A made field that holds an integer charges the square of the size of the integer, at least 1.

Slice 2 adds these charges. Each charge is known before its work, by the principle above:

- **Construction.** An array literal, a tuple literal, and a record constructor charge the recursive size of the result. The charge comes after the elements evaluate and before the construction. An element that refers to an existing value thus pays its copy here and nowhere else. `T(x)` of a scalar type keeps the rule of slice 1.
- **Zero.** `T()` charges its node and the recursive size of the result, before it builds the result. The type metadata below gives this size, so no walk measures it. Thus `[[UInt[8]; 1048576]; 1048576]()` fails with `S015` before any work.
- **`data_bits`.** `data_bits(T)` charges its node and the size of the width that it gives, because it copies the width. The type metadata below gives the width, so the size of `T` does not count.
- **Types.** A type constructor charges the recursive size of the type that it makes: `[T; N]`, a tuple type, `List[T]`, and a function type. A struct specialization has its own rule below. A type equality charges the sum of the two sizes.
- **Join.** The join of two types is their common type by the operand rule (section 5.1). An array literal joins the type of each element after the first with the join of the earlier elements, from left to right. `==` and `!=` on two arrays join their element types. A join walks both types together. It charges 1 for each pair of container types that it visits, before it visits the pair. A pair that is not two container types charges nothing. Thus `[1, 2]` charges no join, and `[[1], [2]]` charges 1. A join of two tuple types thus charges 1 for each pair of container types and nothing for its scalar pairs. The work stays bounded, because each tuple type paid for its parts, and a front end keeps the join of each pair of types. A pair of two struct types charges as a type equality, the sum of the two sizes, instead of 1, and compares the identities. A pair of two function types charges in the same way, and it needs two equal types, also in their `mut` marks. A pair of two container types of different kinds, for example an array and a tuple, charges 1 and then fails. A failed pair stops the walk. A pair of two list types charges 1 and joins the element types, as a pair of two array types does. From slice 3 on, a pair of two enum types charges as a type equality, 1 plus 1, and compares the identities. Two different enums, or an enum and another type, have no join (`S010`). `String` is not a container type, so a pair of two `String` types charges nothing.
- **Selection.** A static index, a field selection, and `len` of an array or a list only refer to a value. They charge no size.
- **References.** An implicit read of an aggregate port, register, or wire, and a child output `u.q` of an aggregate type, give a reference (section 5.1). The read charges no size. A static index, a `.N` selector, or a field of a reference gives a reference to the part. Its work is in proportion to the number of steps, and it charges no size. A hardware index of a reference is `S011`. `len` of a reference gives a static `Int`. A typed use of a handle reads it. A copy of such a read charges the size 1 of the handle, then the zero size of the type.
- **Empty parts of a reference.** A selected part without a hardware leaf is a static value, for example `r.z` with the field type `[Unit; 1048576]`. The selection charges the zero size of the type of the part, from the type metadata, before the static value exists. A read of a whole port, register, or wire of an empty type follows the same rule. It gives a new static value, and it charges the zero size of the type at each read. An empty input port charges nothing at its declaration.
- **Strings.** `len(s)` and `s[i]` charge the size of `s` before the scan, because a UTF-8 string needs a scan. `s[i]` charges it after the checks 1 to 3 of section 5.2 and before the range check. `+` charges the sum of the two sizes before it joins the strings. `str(n)` charges the copy of `n`, then the square of the size of `n` before the conversion, then the size of the result before the string value exists. A string that an operation just made binds without a copy, so a step `s = s + t` charges only its nodes and the sum.
- **Lists.** `list(T)` charges the copy of `T`, plus 1 for the empty list. `push` and `pop` charge the recursive size of the element. They change the live list place directly: they do not copy the list in, and they have no write-back. `S008` excludes an alias of the place, so the result equals the rule of section 9.1 for a `mut` actual. A loop that pushes `n` elements thus charges in proportion to the sum of the element sizes.
- **`push` and `pop` order.** Both charge their node and their function name, then resolve the steps of the place (section 5.2). `push` then runs in this order:
  1. The element evaluates.
  2. The place holds a list, else `S010`.
  3. The mutation rule of section 9.4 (`S016`).
  4. The element has no hardware leaf, else `S011` at the element. Then the typed use of the element at the element type of the list.
  5. The depth check. Then the charge of the element, the charge of a list part (below), and the change of the list.
  6. The result is `()`, with no charge.
- **`pop` order.** After the steps of the place, the place holds a list, else `S010`. Then `pop` checks for an empty list (`S013`), then the mutation rule (`S016`). Then it charges the element and the list part (below), and it changes the list. Its result is a new value, so a binding of it is not another copy.
- **`push` depth.** `push` reads only the depth of the element. The root of the place is in the nesting depth, so only the path to the new element can go above it. The check thus counts the steps of the place, plus 1, plus the depth of the element. A depth above the nesting depth is `S015` at the call, before the list changes.
- **Receiver calls.** A receiver call charges as the call that it binds to. Its node charges first. Its function name then charges 1, as the callee name of a call does. The receiver and the explicit arguments then evaluate in their order (section 5.6). After all arguments run, the copies charge in the binding order of the parameters. Thus `x.m(a)` and `m(x, a)` charge the same units when the receiver binds to the first parameter.
- **Waiting results.** A node evaluates its operands in order. The result of an earlier operand waits while the later operands evaluate. The left operand of a binary operator other than `&&` and `||` waits, and so does the first arm of a hardware `if`. Each argument of a call, of an instance, of a type family, and of a struct use waits. The callee of a call that evaluates its callee waits too (section 5.6). Each element of a literal, the base of an index, and the lower bound of a `comptime for` wait too. The place of a `mut` actual or of an assignment target does not wait, because `S008` keeps its root unchanged in its window.
- **Held roots.** A waiting result **holds** a local when it refers to a static value in that local. Such a result is a name of the local, or an index, a selector, a field, or a static `if` that selects a part of it. A local is a **held root** while at least one waiting result holds it. A call runs in a new frame, so a waiting result of the caller holds no local of the callee.
- **Mutation of a held root.** The mutations are an assignment, a `push`, a `pop`, and a `mut` write-back. A mutation of a held root charges the recursive size of the root before the change. This charge comes after all other checks and charges of the mutation, immediately before the change. A mutation charges it once, also when more than one waiting result holds the root. A mutation of a root that is not held has no such charge. The charge pays for a copy of each waiting result that refers to the root. Thus an implementation can keep the value that each waiting result read. For example, `let y = xs[xs.pop()];` charges the size of `xs` at the `pop`, because the base `xs` waits while the index evaluates.
- **Changed root of an index.** An index `b[i]` of a value reads its result from the value that `b` gave before `i` evaluates. When `b` refers to a local, that local is the root of the read. The local can hold a static value or a hardware aggregate. The read **changes its root** when a mutation of that local runs during the evaluation of `i`. The mutations are those of a held root: an assignment, a `push`, a `pop`, and a `mut` write-back. A mutation in the frame of a called function is not a mutation of the root, but the `mut` write-back of the call is. A read that changes its root charges the recursive size of its result, at the index node. This charge comes after all other checks and charges of the read. These include the range check and the zero size of an empty part of a reference. Its result is then a new value. Thus it refers to no local, a binding of it is not a copy, and it holds no local while it waits. A read that does not change its root has no such charge, and its result refers to the root as before. An index of a string keeps its own rule (below), because its result is a new value already. An implementation can count the mutations of each local and compare the count before and after the index. For example, `t[(t.1.push(1), 1).1];` on a local `t` of the type `(UInt[8], List[UInt[8]])` charges the size of `t` at the `push`, because the base `t` waits. Then the read charges the size of its result, the list `t.1` before the `push`. Each read in a nest or in a loop applies the rule by itself.
- **List part of a hardware aggregate.** A `push` or a `pop` can change a static list part of an aggregate root. The change then refreshes the stored size and depth of each aggregate node on the path of the place. Thus the mutation charges the number of parts of each such node, before the change. This charge comes after the charge of the element and immediately before the charge of a held root. A root without a hardware leaf has no such charge. For example, `x.1.push(5);` on an aggregate root `x` of the type `(UInt[8], List[UInt[8]])` charges 2 for the root node. Thus a loop that pushes `n` elements into a list part of a tuple of width `w` charges `n * w` for the refresh. The refresh of a node reads no other part of the node. The element changes the size of the node by its own size. A `push` can only make the node deeper, by the depth of the element. A `pop` can make the list less deep only when its element is deeper than the element type of the list. Only then does the refresh find the depth of each node on the path again from its parts. Thus such a `pop` also charges the recursive size of the root, immediately after the part counts. For example, a `pop` of the type `[[UInt[8]; 1]; 1]` from a list part of the type `List[Type]` charges the size of its root. A `pop` from a list part of the type `List[UInt[8]]` does not.
- **Shared lists.** An implementation can share a list with another binding. It then copies the list at the first change. The earlier copy of that binding paid for this work.
- **Static equality.** Equality of two containers, two strings, or two types reads both operands in full. It charges the sum of the two recursive sizes. The conversion of a static integer to the finite type of its pair charges nothing more. This rule applies to a static pair of a hardware equality too. A leaf pair of a hardware equality keeps the rule of slice 1 (below).
- **Place update.** An assignment to a place with a step charges 1 for each step of the place, as an expression node does. Thus the charge pays for the walk over the path. It also charges the copy of its value, as each assignment does. The update copies only the containers on the path of the place. When the new root has no hardware leaf, the update charges nothing more for the copy of the path. A reference on the path still expands one level, and its parts without a hardware leaf become static values. For each such part, the update charges the zero size of its type, from the type metadata, before the static value exists. This is the rule of an empty part of a reference (above). For example, `x.0 = 5;` on a reference `x` of the type `(UInt[8], [Unit; 3])` charges the zero size 4 of `[Unit; 3]`. A binding that shares a container paid for its copy before. Before the change, the assignment checks the depth of the root, as a `mut` write-back does. The depth is the number of steps of the place plus the depth of the value after its typed use. A depth above the nesting depth is `S015` at the assignment. The check comes after the typed use and the element checks of the value, and before the change. The copy and the conversion of the value charge before it, by the rule of typed uses.
- **Rebind.** A place update with a step can give a new root with a hardware leaf. The update then binds each hardware leaf of the root again, at the next version of the root (section 7.3). The rebind charges the recursive size of the new root. This size is the old size of the root, minus the size of the replaced part, plus the size of the new part. The stored sizes give it with no walk.
- **Place update order.** An assignment to a place with a step runs in this order:
  1. The steps of the place (section 5.2).
  2. The value.
  3. The copy of the value and its typed use, by the rule of typed uses. Then the depth check of the root.
  4. The rebind charge, when the new root has a hardware leaf. It comes before the copy of the path and before a reference in the root expands into references to its parts. When the new root has no hardware leaf, the empty parts of the references on the path charge their zero sizes here instead.
  5. The charge of a held root, immediately before the change.
  6. The change, and one core `let` for each hardware leaf of a rebound root.
- **Typed use of a hardware aggregate.** A typed use checks a reference part in one step, by its type. It never expands the reference. The other leaves check first, in packing order. Thus the first leaf that fails gives the error, `S010` or `S012`:
  1. A hardware leaf needs the exact type of its position (`S010`).
  2. A static leaf checks its sign (`S012`).
  3. Then the conversion charges, by the rule of typed uses.
  4. Then the static leaves convert, and each conversion checks its fit (`S012`).
- **Hardware equality.** `==` and `!=` on a hardware aggregate run in the order below.
  1. The function flag of the two types, then their enum flag (section 5.1, `S010`).
  2. The join of the two types, with the join charge. Two types without a join are `S010`.
  3. The walk of section 7.4 over both operands. It charges 1 for each pair that it visits, before it visits the pair. The root pair of the two containers counts as a pair, and so does a pair of `()`.
  4. A static pair charges as a static equality before it compares, and its result goes into `s` (section 7.4).
  5. A hardware pair runs the rule of slice 1 for a scalar `==`. A static leaf converts to the type of its pair with its conversion charge, and it checks its fit (`S012`). Then the `icmp eq` node charges at the pair, by the rule of hardware operations.
  6. After the walk, the chain of `and` nodes charges in chain order, from `E_0`. `E_0` is `(const 1 s)` when static pairs exist, and this constant has no charge. For `!=`, the `xor` node charges last. A walk without a hardware pair has no chain. Its result is a static `Bool`.
- **Hardware `if`.** A hardware `if` with two arms of a container type runs in the order below. Take an `if` with arms of a type that is not a container, for example a scalar or a function. It has no join charge and no walk. From slice 3 on, an enum counts as a container type for this rule, so two enum arms get the join and the walk. Its arms need a common type (`S010`), and it keeps the rule of slice 1. An `if` with two arms of a list type charges the join of step 1, and the arms are one static pair with no walk unit. Two static arms of a type that is not hardware data follow step 3 (F19). Equal arms give the static value, and different arms are `S011`.
  1. The join of the types of the arms (`S010`). Thus an `Int` arm and a `Bool` arm are `S010`.
  2. The walk of section 7.4 over both arms, with the same charge for each visited pair.
  3. A static pair charges as a static equality. Two identical sides give that value. Other sides compare by the static equality of `==`. Equal sides give the side of the joined type. This is the first side when it has this type, else the second side when it has this type. Equal sides without the joined type are `S011`, as different sides are. No value conversion occurs. The first static pair in the walk order that is `S011` stops the walk, and the error is at the `if`.
  4. A hardware pair makes one `mux` node and charges it as a hardware operation: 1 plus 3. A pair of two static leaves makes constants, as in slice 1.
- **Shared condition.** When the walk of a hardware `if` makes two or more `mux` nodes, elaboration marks the condition `c` once as shared. A core name or a constant gets no mark. Section 7.4 gives the temporary of the mark. From slice 3 on, the hardware operand `b` of `reinterpret(E, b)` gets the same mark when `P` is not 0, because both leaves of the result read it. A hardware `match` has its own marks (**Marks of a hardware `match`**, below).
- **Charge of a shared mark.** Each mark charges the recursive size of its operand once, when elaboration makes the mark. The mark of an `if` charges at the `if`, after the join and before the walk. The mark of `reinterpret(E, b)` charges at the call, after the type check of `b` and before the result exists. In a value that holds the mark, the mark has the size of a finite value of its type. A reference to a core name has this size too, and the operand does not count again. The lowering binds the mark to a temporary (section 7.4), so the mark is a core name in the output. The size of a mark and its charge depend only on its operand and its type, so they are the same in each front end. Without this rule, a value counts the operand once for each use of the mark. Then `k` nested round trips `reinterpret(E, reinterpret(UInt[W + P], ...))` charge about `2^k` times the size of the innermost operand. But their nodes and their work grow only linearly in `k`. With this rule, the charge also grows linearly in `k`.
- **Serialization.** A serialization of a container charges 1 for each container node, for the walk that measures it. It then charges its length in bytes, as in slice 1. A scalar keeps the rule of slice 1, so the costs of slice 1 do not change. From slice 3 on, an enum value is one container node, so it charges 1. An integer in a type, for example a width or the length `N` of `[T; N]`, gets no charge for its decimal form.
- **Serialization parts.** The byte length of the text is the charge. An implementation measures this length first, charges it, and then makes the text. The earlier charges do not bound the work of the text. The text holds the element type of each array value and each list value. The recursive size of the value does not count this type. The Lean reference can make the text first, because only the charge is normative.
- **Calls through a function value.** They charge as a named call: the call node, the copies of the arguments, and the body block. The callee charges as an expression, and no function name charges.
- **`mut` formals.** The copy at the call and the write-back at the return each charge the recursive size of the value. Each step of a `mut` actual charges 1, as a step of an assignment target does (section 5.2). At the return, the write-backs run in the order of the parameters. Each write-back checks the mutation rule of section 9.4 (`S016`), then the depth, then charges, then writes into the live root. The depth check counts the steps of the place, plus the depth of a static value, as the `push` depth does. A depth above the nesting depth is `S015` at the call. The type of a value that is not static is the type of the place, so the root keeps its depth. A hardware result binds its core name `0ret` before the write-backs. Each write-back checks the mutation rule, also when the value did not change. Thus a `mut` actual with a root from before a hardware arm is `S016`. A write-back reports `S016`, `S015`, `S010`, and `S011` at the call.
- **`diagnostic`.** A call charges its node and its function name. Then its arguments evaluate, and their copies charge by the rule of builtins. A handle has the size 1. A reference aggregate charges its zero size, from the type metadata, before any walk of its type. Then the checks of section 6.2 run. The serialization of the record (section 8.2) then charges in this order:
  1. Each static part charges its measure, as Lean `Value.measureCharge` computes it. A container node charges 1. An integer charges the square of its size, for its decimal form.
  2. Each rendered container with a hardware leaf charges 1. A static part of a reference charges 0, because the copy of the reference paid its zero size.
  3. The record charges its length in bytes. An implementation measures the length first and makes the text after the charge.
- **`diagnostic` rendering.** The rendering of a record has no charge, because the charges above pay for it. It never calls the charged normalization. The charge does not depend on the display.
- **Aliases.** A `type` item and a `type` statement copy nothing. The type expression makes the type, and a use of the alias refers to it. A use of a done `type` item charges only its node, as a constant does.
- **Struct specializations.** Each use of a specialization charges the recursive size of each argument right after its typed use, before the next parameter type evaluates. These charges come before the lookup in the table, because the lookup reads the arguments in full. The first use then charges the size of the struct type once. It then evaluates the field types, and each one charges as a type expression. A later use refers to the done entry and charges nothing more (section 5.6).
- **Type metadata.** Each type carries four numbers. They are its bit width as hardware data, its leaf count, the recursive size of its zero value, and its depth. A type constructor computes them from the numbers of its parts when it makes the type. `Nat`, `Int`, `Type`, `String`, and `List[T]` are not hardware data, and their width, leaf count, and zero size are 0. The depth of `String` is 1. The depth of `List[T]` is 1 plus the depth of `T`. `List[T]` reads only the depth of `T`, so its metadata adds no charge to its type constructor. A function type is not hardware data either: its width, leaf count, and zero size are 0. Its depth is 1 plus the largest depth of a parameter type or the result type. A `mut` mark adds no depth. A function type has no metadata charge: its three numbers are 0, and its size charge covers its depth. `[T; N]` multiplies the width, the leaf count, and the zero size of `T` by `N`. Each of the three products charges as a multiplication of static integers: the product of the size of `N` and the size of the number of `T`. These charges come before `[T; N]` exists, at its node. A struct specialization computes them once, when it completes, from the stored numbers of its field types. Its depth also takes the depths of its static arguments. A tuple type and a struct specialization add the numbers of their parts. Before the sums, they charge the sizes of the four numbers of each part, because the sums read them. Then they charge the sizes of the four new numbers. Thus a struct with many fields of a type with a large width pays for each addition. No later operation walks the field types of a struct to get these numbers.
- **Function flag.** Each type also carries a flag: a function type is a part of it, at any depth. A type constructor computes the flag from the flags of its parts, with no charge. A struct specialization computes it from its field types when it completes. `==` and `!=` read this flag (section 5.1).
- **Enum flag (slice 3).** Each type also carries a second flag: an enum type is a part of it, at any depth. An enum type has the flag. A type constructor and a struct specialization compute the flag as they compute the function flag, with no charge. `==` and `!=` read this flag after the function flag (section 5.1).
- **Big metadata.** The four numbers are integers of any size. A chain of structs that doubles at each step thus has an exponential width as a value. The charge-before-work rule then rejects each operation whose charge is too large, for example `T()`.
- **Struct values.** Each operation that reads a struct value in full charges its recursive size, as for each value: a copy, an equality, and a serialization.
- **Lowering.** Each emitted core node charges one unit, so an aggregate pays for each of its leaves. The lowering of a port charges each leaf before it makes that leaf: 1 for the port node, plus the bytes of the leaf name. The lowering makes no list of the leaves before their charges.
- **`mem` statement.** The statement charges 1, and its type expression and its depth expression charge as expressions. Nothing else charges. The statement makes no `[T; N]` type, so the metadata products of `[T; N]` do not charge. The width of the word comes from the type metadata, with no walk. Section 6.2 gives the order of the checks.
- **Memory port calls.** A call of `read_port` or `write_port` charges its node and its function name. Then its arguments evaluate from left to right, the receiver first. Then the copies of the arguments charge, by the rule of builtins. The memory handle has the size 1. When `data` is a handle, it charges as the copy of a handle read (**References**, above). A wide `data` argument charges its full zero size as a copy, by the rule of builtins. Section 6.2 gives the full order of the checks and the charges.
- **Read response.** The use of `ReadResponse[T]` charges as a struct use. The response then charges the zero size of `ReadResponse[T]`, from the type metadata, before it exists. Its `data` part is a reference and its `valid` part refers to a core name (section 7.6), so this is its only charge. A binding of the response is not a copy.
- **Second port call.** A second call of `read_port` or `write_port` on one memory runs all the steps and charges of the first call. Thus its charge is the same as the charge of a first call. The one exception is `ReadResponse[T]`: only the first use pays its specialization. For `UInt[8]`, the first read charges 32 units, and a second read charges 15.
- **Memory block.** The lowering of a memory charges each core node before the node exists, in pre-order: the node first, then its operands. Each field of a core name charges its bytes. The write data charges each leaf and each `concat` node before it makes the node (section 7.6).

Slice 3 adds these charges. Each charge is known before its work, by the principle above:

- **Enum declaration.** The first use of an enum charges as the first use of a struct specialization. It charges the size of the enum type once. Then the checks of section 5.6 run in their order, and each tag type, tag value, and payload type charges as an expression. An enum in progress counts toward the nesting depth, as a struct specialization does. A later use refers to the done entry and charges only its node.
- **Second tag value.** The tag check of each variant (section 5.6) has no charge. It inserts the tag into the tag map of the enum, with `O(log v)` compares for `v` variants. This log factor is a stated exception to the principle above.
- **Enum terms.** An enum type is a node without arguments, so its size is 1. A static enum value has the size of a record with the parts `tag` and `payload` (section 5.1). A hardware enum node has the size of a record node with its two parts. An empty payload part adds nothing.
- **Enum metadata.** The payload types of each variant give the metadata of the tuple of these types. This tuple type is not made, so its size does not charge. Its sums charge as the sums of a tuple type (**Type metadata**, above), after their size-limit check. `P` is the largest width of these tuples. After the check of `P` (section 5.6), the metadata of the enum charges as the sums of the record of `UInt[W]` and `UInt[P]`. When `P` is 0, this record has only the part `UInt[W]`.
- **Enum constructor.** A constructor `Op::Load(x)` is one node, as `Op::Add` is. It runs in this order:
  1. The node charges 1. A use of the enum follows (**Enum declaration**, above).
  2. The payload values evaluate from left to right.
  3. The copies of the payload values charge, by the rule of builtins.
  4. Each payload value gets its typed use at its payload type, in order (`S010`, `S012`).
  5. The depth check of the result (section 5.5). Then the recursive size of the result charges, before the static pack or the hardware pack.
  6. The pack makes the result (section 5.1). The lowering charges each core node of a hardware pack (section 7.4).
- **`reinterpret` of an enum.** An unpack checks the depth of its result after the type check (section 5.5). A static pack or unpack then charges the size of its result, as a conversion does. Each core node of a hardware pack or unpack charges 1 in the lowering.
- **`match`.** The `match` node charges 1. The scrutinee then evaluates, and its type gets its check. Then each arm runs its pattern charge, its checks, and its coverage share, in the order of section 5.6. The pattern charge depends on the kind of the pattern:
  - `_` charges 1.
  - A literal charges 1 and the size of its value. `true` and `false` have the size 1.
  - A variant pattern charges 1 and the size of a finite value of the tag type of the scrutinee. This is the size of its tag value when the pattern has the kind of the scrutinee. When the scrutinee is not an enum, this size is 1. Thus the charge needs no use of the enum of the pattern. Each binder and each `_` in the pattern then charges 1.
- **Coverage share.** Each arm whose pattern is not `_` charges its share of the coverage check: `1 + floor(log2 n) + s`. Here `n` is the number of arms whose pattern is not `_`, counted from the syntax. `s` is the size of the value of the pattern in its pattern charge: the value of a literal, or the tag value of a variant. The share comes after the fit check of its arm and before check 3 (section 5.6). The sum of the shares is `n * (1 + floor(log2 n))` plus the sum of the sizes. A `_` arm has no share, so a `match` with `n` equal to 0 charges no share.
- **Log factor of the coverage.** The share pays for one insert into the ordered map of section 5.6. The insert makes at most `1 + floor(log2 n)` compares, and each compare reads at most `s` words. Thus the work of the insert is up to a factor `log n` above its share. This log factor is a stated exception to the principle above.
- **Coverage check.** After the last arm, the checks of a `_` without values and of an uncovered value have no charge. A `_` without values compares the number of keys with `2^W`, by `W` and the bit length of the number. The smallest uncovered value comes from one pass over the ordered keys. An uncovered tag gets its variant from the tag map of the enum. The count `2^W` is a number, not a loop, so no check walks the values of a type.
- **Binders.** Each binder runs these steps in order:
  1. The check of the size limit of a value that a type makes, at its zero size (`S015`, below).
  2. The charge of the zero size of the binder type, from the type metadata. This holds for a static and for a hardware scrutinee.
  3. When the `payload` leaf is hardware, each `extract` node of the binder charges 2, as a hardware operation with one operand.
- **Depth of a binder.** A binder has no depth check of its own. The node that made the enum value checked its depth (section 5.5). Its depth counts its enum type and thus each payload type. So the depth of the value bounds the depth of each binder value.
- **Binder order.** A static scrutinee runs the binders of the selected arm after the selection and before the arm evaluates. A hardware scrutinee runs the binders of each arm first in the arm, under its guard. A static payload part of a hardware enum gives static binder values, with no `extract` node. Without the zero size charge, a payload `[[(); 4096]; 4096]` builds 2^24 nodes for no charge.
- **Marks of a hardware `match`.** A core name or a constant gets no mark. Each mark charges by the rule **Charge of a shared mark** (above). The marks are these:
  - The scrutinee gets a mark when `n` is 2 or more, because only the selects read it. For an enum, the mark is on its `tag` leaf.
  - The hardware `payload` leaf gets a mark when the binders of all arms have 2 or more leaves together.
  - A select `s_i` has `u = L + 1` uses when an arm `_` exists, and `u = L` uses otherwise. Here `L` is the leaf count of the joined type. A select with `u` of 2 or more gets a mark.
  - The select of `_` gets a mark when `L` is 2 or more.
- **Use count of a select.** The select of `_` reads each select once, so it adds 1 to `u`. Without this 1, `k` nested `match (match (c) { true => p, _ => q }) { true => p, _ => q }` give `2^k` nodes.
- **Hardware `match` order.** After the coverage check, a hardware scrutinee runs in this order:
  1. The mark of the scrutinee, then the mark of the `payload` leaf.
  2. The arms evaluate in source order, each under the guard `arm` in a `data` context. The binders of an arm come first, and each binds its core name as a `let` does.
  3. The join of the arm types, as the elements of an array literal join, with the join charge. Then the conversion of each arm to the joined type, as for an element of an array literal.
  4. The selects `icmp eq` build in arm order. Each select first charges the size of its key constant: the size of a finite value of the type of the scrutinee leaf. This charge comes before the constant exists, and it pays for the work of the constant. Then the select builds with no other charge, and its mark charges. A select pays for its constant also when it gets no mark, and also when no leaf reads it.
  5. The select of `_` is one node `rest` over the `n` selects. It charges `1 + n` as a hardware operation, before the node exists. Then its mark charges.
  6. The walk over the arms (below). The lowering of section 7.4 charges each core node that it emits.
- **Walk of a hardware `match`.** The walk of section 7.4 visits the `m` arms together, by the joined type. It charges `m - 1` for each position, before it visits the position. For `m` equal to 2, this is the charge of a hardware `if`. A root of a scalar type gets no walk charge, as for an `if`. These rules apply at each position:
  - A static position compares each arm `j >= 1` with arm 0, and each compare charges as a static equality. Equal sides give the first side in arm order that has the joined type.
  - Different sides, or equal sides without the joined type, are `S011` at the `match`. The first such position stops the walk.
  - A leaf of hardware data makes one node `onehot`, with the `m` selects and then the `m` values. It charges `1 + 2m` as a hardware operation.
  - A `match` with the single arm `_` gives the value of the arm, under its guard, with no node.
- **Handle types.** `Reg[T]`, `Wire[T]`, and `Input[T]` are nodes with `T`. `Mem[T, N]` is a node with `T` and the integer `N`. `Instance[M, args]` is a node with its arguments as values, as a struct type. A handle type constructor charges the recursive size of the type that it makes. Its type metadata is that of `List[T]`: the width, the leaf count, and the zero size are 0. Its depth is 1 plus the largest depth of a part.
- **`read`.** A call of `read` charges as the other prelude calls. Its node and its function name charge first, then the copy of the handle with the size 1. The read then follows the rule of **References** above.

`Source.Eval` and `Source.Flatten` give the exact charges of these rules, as for each rule of this section. `Proof/Fuel` covers them for `eval_cost`.

A static value has a **size limit** (issue #255). The fuel is a 64-bit number, so a large fuel can pay for a value that no machine can hold. The limit stops such a value before its charge. The **bit length** of an integer `n` is the number of bits of its magnitude `|n|`. The bit length of 0 is 0. These are the limits:

- A static `Int` or `Nat` has a bit length of at most 2^32.
- A string has at most 2^32 bytes in UTF-8. This includes a string literal.
- A list has at most 2^32 elements.
- The width, the leaf count, and the zero size of the type metadata each have a bit length of at most 2^32. Thus `data_bits(T)` always gives a static `Int` in the limit.
- A value that a type makes has a zero size of at most 2^32. There are four such values. The first is the zero `T()`. The second is an empty part of a reference that becomes a static value (**Empty parts of a reference**, above). The third is the parts that a reference on the path of a place update makes when it expands. The fourth is a binder of a `match` (**Binders**, above). The zero size of a type is the recursive size of such a value. Thus the limit also bounds the length of each array in it.
- A `diagnostic` record renders each reference part from its type. Thus the recorded value has a recursive size of at most 2^32.

A finite width is 1 to 65536 (`S012`), so a finite value has no check of its own. Each check reads only numbers that a front end knows in constant time: bit lengths, byte lengths, and list lengths. It comes before the charge of the operation that makes the value, after the type checks of the operation. A value above its limit is `S015` at the node of that charge. For an integer operation, the check uses a bound `B` on the bit length of the result, from the bit lengths `a` and `b` of the operands. A bound above 2^32 is `S015`, also when the result is shorter:

- `x + y`, `x - y`, `x & y`, `x | y`, and `x ^ y` on static integers: `B = max(a, b) + 1`.
- `x * y`: `B = a + b`.
- `x << k`: `B = a + k`, and `B = 0` when `x` is 0. This bound is the bit length of the result. A count `k` above 2^32 with `x` not 0 fails before the addition.
- `~x`: `B = a + 1`.
- `-x`, `x / y`, `x % y`, and `x >> k` make no result longer than an operand. They have no check.
- `[T; N]`: each product of the metadata gets the bound of `*`: the bit length of `N` plus the bit length of the number of `T`. The zero size `1 + N * z` gets 1 more. The check comes after the depth check and before the charges of `[T; N]`.
- A tuple type and a struct specialization: each sum of the metadata gets a bound from the parts before the sum runs. The bound is the largest bit length of that number in a part, plus the bit length of the number of parts. The zero size `1 + z_1 + ... + z_n` gets 1 more. The check comes first, before the depth check and the charges of the new type.
- `s + t` on strings: the sum of the two byte lengths.
- A string literal: its byte length, before the charge of its value.
- `T()`: the zero size of the type, after the depth check and before the charge of the zero size.
- An empty part of a reference: the zero size of its type, before the charge of the zero size.
- A binder of a `match`: the zero size of its type, before the charge of the zero size.
- A place update with a step: the zero size of the type of the first reference on the path, when one exists. The check comes before step 4 of the **Place update order**, so it comes before each charge of the expansion.
- `diagnostic`: the recursive size of the value, after the checks of section 6.2 and before the measure charge. A reference part has the zero size of its type.
- `push`: the length of the list plus 1. The check comes after the depth check of step 5 and before the charge of the element.

The other operations need no check. A number literal is below 2^65536 (`S001`). `str(n)` of an integer in the limit has fewer than 2^31 characters. `s[i]` gives one scalar. Some operations give a finite value or a value that is not longer than an existing value. These are a conversion, `len`, an index, a selection, `data_bits`, and the loop value of a `comptime for`. A literal of an array, a tuple, or a record has one element for each element in the source. An array type has no limit of its own. A type `[T; N]` with a large `N` stays valid, and a reference of that type stays valid while it does not expand. Each array value with more elements than the source gives is a value that a type makes, so the zero limit bounds it. The limits are far above a value that a design uses, so they are not a limit of the language in practice.

This section gives the principles of the cost model. `Source.Eval`, `Source.Elab`, and `Source.Flatten` are its normative definition: the exact charge of each operation, the order of the charges, and the position of each `S015`. The Rust elaborator matches them through `cost` and the corpus, not through this prose. The charge of an operation is known from the sizes of its operands, before the operation runs. When the fuel cannot pay a charge, elaboration fails with `S015` at the node of that charge. The operation then does not run.

When the nesting depth goes above its limit, elaboration fails with `S015` at the call, the `instance` statement, or the constant use that goes above it. From slice 2 on, it can also fail at the use of a struct specialization that goes above it. The typed use of the module arguments nests one level at each `instance` statement and at the top selection. This holds also for a done `InstantiationId` and for a module without parameters. A new instantiation nests one level after the typed use ends, so the two levels do not add. The nesting depth bounds the native stack of the Rust elaborator. Totality does not need it.

A top-level `const` evaluates once, at its first use. A table of constants holds each constant with one of three states: not started, in progress, or done with its value. This table is normative, because the first use fixes the order of the evaluation:

- A use of a constant in the state "in progress" fails with `S019` at that use. This rejects a constant that depends on itself, directly or through other constants.
- A use of a constant in the state "done" gives its value and charges only the use.
- A use of a constant in the state "not started" sets it to "in progress" and evaluates it.

The Lean evaluator `Eval` is total by the fuel alone. Each step charges at least one cost unit, and the fuel never grows. Proofs can thus use `Eval` directly.

### 5.5 Resource bounds

This section lists the paths by which a source could use resources. For each path, it states the bound. `F` is the fuel.

- **Evaluation work and memory.** Each operation charges the recursive size of each value that it makes, copies, or reads in full. An implementation without sharing thus allocates memory in `O(F)`. Sharing only lowers the memory. The work is in `O((F + s) log (F + s))`, where `s` is the size of the source. The reason is that the elaborators look up names and nodes in ordered maps, and a lookup costs the logarithm of the map size. This work bound is a claim about the Rust front end. The Lean reference defines the meaning and the fuel, but it compares types by structure, so its run time can be higher. Issue #196 tracks a type table for Lean. The theorem `eval_cost` is about the result for each fuel, not about the run time. The `eval` command pays for the printing of its result (section 8). The printing of an error message is outside this bound. An error message prints at most 256 bits of an integer, 64 characters of a string, and 1024 bytes of the text of a type. A type shares its parts, so its text can be exponentially longer than its size.
- **Nested aggregates.** A value that holds another value twice has at least twice its recursive size. A chain of such values thus doubles its charge at each step. The nested doubling of section 11.3 shows it: `let a_k = [a_(k-1), a_(k-1)];` charges `2^(k + 2) - 1` for its value. The join of its two element types visits `k` pairs of arrays and charges `k` more. A mark of a shared operand is different (section 5.4). It pays for its operand once, and a value that holds it counts only the size of a finite value of its type. Thus nested round trips through `reinterpret` charge linearly in their number.
- **Nested values and types (slice 2).** A value and a type have a nesting depth. It is 1 for a part that is not a container. For a container, it is 1 plus the largest depth of an element. The depth of an array value and of a list value also counts its element type. It is 1 plus the largest depth of its element type and its elements. Thus the depth bounds each walk over an array or a list, also over an empty one. The depth of a record also counts its struct type in the same way. The depth of an enum value counts its enum type in the same way, and its `tag` and `payload` have the depth 1. A type as a value has the depth of the type. The parts of a type are those of its term in section 5.4. The parts of a struct type are its field types and its static arguments. Thus the depth of a struct type is 1 plus the largest depth of a field type or an argument. The type metadata stores it, so no walk computes it again. The serialization, the equality, and the destruction of a type term thus stay within the depth budget. `()`, `Unit`, and a scalar type have the depth 1. A struct specialization whose depth goes above the budget fails with `S015` at the use that completes it, which is its first use. The depth of a new value or type is known before it exists. A depth above the nesting depth budget fails with `S015` at the node that makes the value or the type. Without this bound, a loop such as `t = [t; 1];` makes a type of any depth. Each recursive walk over it can then overflow the native stack: the size, the serialization, the equality, and the destruction.
- **Destruction (slice 2).** The work to destroy a value is at most the work that made it, because each node paid when it was made or copied. The depth of the value bounds the recursion of a destruction. An arena, as the Rust `elab` uses for hardware values, needs no recursion.
- **Walks over a hardware aggregate (slice 2).** Equality, `if`, a typed use, a binding, and the lowering walk an aggregate. Each walk visits a pair or a leaf only after its charge. The depth of the value bounds the recursion of a Lean walk, which recurses on the structure of the value. A Rust walk uses an explicit stack, so it does not recurse on the depth of the value. A reference part does not expand, so its typed use and its selection have no walk over its leaves. The chain of `and` nodes of `==` is as long as the number of hardware pairs. The lowering builds the left spine of a chain of binary nodes in a loop. Thus this chain does not grow the native stack.
- **Static integer arithmetic.** A product grows the size additively, and its work is in the charge. A shift charges its result, so `1 << k` with a large `k` fails before it runs. The size limit of section 5.4 bounds each static integer, string, and list, also for a fuel near 2^64. Thus `1 << k` with `k` of 2^32 or more is `S015` before its charge, and no front end makes a value above the limit.
- **Collections and strings.** A copy, a concatenation, a comparison, and a serialization charge the recursive sizes. A `push` and a `pop` charge the recursive size of the element. `len` and an index of a string charge the size of the string, and `str(n)` charges as section 5.4 gives.
- **Types.** A struct specialization pays for its size and its field types once (section 5.6). Each use pays for the sizes of its arguments, so the lookup in the table is linear in the charge. A generated record type (slice 4) has the recursive size of its normalized term, so nested `@Struct` calls pay like nested aggregates.
- **Memory (slice 2).** The lowering of a memory emits a fixed number of core nodes, plus one node for each leaf of its word type. The fit rule bounds the depth and the word width (section 7.6). The `data` part of a response is a reference to the word, so a selection of a part of it is one step. The Rust front end stores the bit offsets of the parts of each tuple type and each struct type in its type table. Thus each step costs `O(1)`. The Lean reference adds the widths of the earlier parts from the type metadata. Its run time has no bound, but its charges are the same. The write data builds in a loop after its charges. A Lean walk over a word type recurses on its structure, and the depth bounds it. A Rust walk uses an explicit stack.
- **Instantiations.** A new `InstantiationId` elaborates once and charges its body. A repeat charges only its `instance` statement, its arguments, their parameter types and typed uses, and the serialization. The typed use of a container argument checks the types and the signs of its elements before its charge. The size that the argument paid when it was made bounds this walk, and a charge or an error comes next. A tree of distinct instantiations thus costs at least one unit for each node. A shared hierarchy costs one elaboration for each distinct `InstantiationId`.
- **Output size.** Each emitted core node charges one unit, and each user field of a core name charges its length in bytes. A made field that holds an integer has at most 20 bytes for each unit of its charge. Each `$` separator belongs to a paid field. The output thus has at most `F` nodes and `O(F)` bytes of names. The temporaries of section 7.4 keep it also linear in the source.
- **Constants.** Each constant evaluates once, and a cycle fails with `S019`. A use refers to the value, and a copy of it pays its recursive size.
- **Stack.** The nesting depth bounds it. From slice 2 on, it bounds the depth of each value and each type too.
- **Front-end passes before elaboration.** The lexer and the parser are linear in the source. The resolver and the generic pre-check are linear up to a factor `log n` for name lookups in ordered maps, which keep the result deterministic. `S008` is the exception. A simple check of `S008` is quadratic in the size of one call. A counter for each root makes it linear.
- **After elaboration.** `canonicalize` sorts, in `O(n log n)` for `n` core statements. The Lean core checker is near-linear since issue #23 closed. The Rust parse and check of the core IR are linear in the statement count, except the inference of the port dependencies. That inference costs `O(N + E * min(I, O) + sum of d log d)`. Here `N` is the number of nodes and `E` the number of edges of the combinational graph. `I` is the number of inputs, `O` the number of outputs, and `d` the size of one result. The graph build and the table setup are linear. The work can grow faster than the output: `N` outputs that share a chain of `N` nodes to one input need `N^2` steps for `N` dependencies. The Lean walk of each output has the same order.

The oracle of the cost model is the command `cost` (section 8). Both implementations print the same total and the same units for each instantiation.

### 5.6 Items, types, and calls of slices 2 and 3

Slice 2 adds these items and calls:

- **Structs.** `struct P(comptime W: Nat) { a: UInt[W], b: Bool }` declares a record type with parameters. `P[8]` is a struct specialization, and `P[8](x, y)` constructs a record. A struct without parameters has the use `P` and the constructor `P(x, y)`. Each struct parameter has `comptime`. A struct parameter without `comptime`, also a `mut` parameter, is `S001`. This agrees with v0.1, where a struct declaration takes only static parameters, and with the rule for module parameters. A message names a struct type in its source form, with its arguments as literals, for example `P[8]`. A use of a struct with parameters without its arguments, for example `P` or `P(x, y)`, is `S007`.

- **Specialization table.** A table of struct specializations holds each specialization with one of three states: not started, in progress, or done with its field types. The table is normative, as the table of constants is. The key of a specialization is its struct item and its static arguments, each after its typed use at its declared parameter type. These are the normalized identities of v0.1. Thus `P[8]` and `P[UInt[4](8)]` are one type when the parameter of `P` has the type `UInt[4]`. An `InstantiationId` uses the same typed use of the module arguments (section 5.3). Each parameter type evaluates in order, and the size of each converted argument charges right after its typed use (section 5.4). The first use evaluates the field types. A later use charges only its node and the sizes of its arguments. A use in the state "in progress" fails with `S019`. A recursive hardware type is thus `S019`. A specialization in progress counts toward the nesting depth, because the first use of a chain of distinct structs evaluates their field types recursively. `S015` is then at the use that goes above the depth.

- **Type aliases.** `type A = T;` at the item level is a constant of type `Type` in the table of constants. In a block, it is a local of type `Type` that evaluates at its statement. An alias that depends on itself is `S019`. An index of a `type` item is `S007` in pass 4. An index of a local that holds a type is `S007` in pass 5, at the index node, after the base evaluates.

- **Static types.** A `comptime T: Type` parameter, a local of type `Type`, and a type equality are static. A local can be a type name. Thus `fn f(Bool: Nat, x: Bool)` resolves, and elaboration gives `S010` at the type name `Bool` of `x`, because the local holds no type.

- **Zero and size.** `T()` gives the static recursive zero of a hardware data type `T`: 0 for each integer leaf and `false` for each `Bool` leaf. `data_bits(T)` gives the number of bits of a hardware data type. `Bool` has 1 bit, `UInt[W]` and `SInt[W]` have `W` bits, and `Unit` has 0 bits. An array has `N` times the element size. A tuple and a record have the sum of the element sizes. For a type that is not hardware data, both are `S010`. The argument of `data_bits` is not a static position, so pass 4 does not check it. An argument that is not a type is `S010` in pass 5. `T()` of a struct type is always the zero, never a constructor without arguments. Thus `P()` of a struct with fields that are not hardware data is `S010`, not `S007`. A struct without fields is hardware data with 0 bits and no leaf.

- **Parameter modes.** A parameter has one of three modes: none, `comptime`, or `mut`. A parameter with both marks is `S001` at the second mark. A module parameter has the mode `comptime`, as a struct parameter has, so `mut` there is `S001`. Only a parameter of a `fn` or a `comptime fn` can have the mode `mut`.

- **Receiver calls.** `x.m(args)` calls the function `m`. `m` resolves in the item namespace, then in the prelude namespace, and never to a local. A name `m` that resolves to no function there is `S003` at `m`. `(obj.f)(args)` calls a function value in a field. The resolver makes this choice from the syntax only. A receiver call is its own node, at the position of `x` (section 7.3).

- **Receiver binding.** The receiver binds to the first parameter of `m` that has no written `comptime` mark. The rule counts the written marks, also in a `comptime fn`. If each parameter has the mark, the call is `S007`. The rule holds for each function, also for each prelude function.

- **Receiver order.** The receiver evaluates first, then the explicit arguments from left to right (v0.1, section 2). The binding order thus differs from the evaluation order. For example, `xs.append(T, v)` binds as `append(T, xs, v)`, but `xs` evaluates before `T`.

- **Prelude signatures.** The prelude functions of slice 2 have these parameter modes. The receiver column follows the receiver binding rule.

  | Function                        | Modes             | Receiver binds to |
  | ------------------------------- | ----------------- | ----------------- |
  | `resize(T, x)`                  | `T` is `comptime` | `x`               |
  | `reinterpret(T, x)`             | `T` is `comptime` | `x`               |
  | `list(T)`                       | `T` is `comptime` | None: `S007`      |
  | `data_bits(T)`                  | None              | `T`               |
  | `push(xs, x)`                   | `xs` is `mut`     | `xs`              |
  | `pop(xs)`                       | `xs` is `mut`     | `xs`              |
  | `len(x)`, `str(n)`              | None              | `x`, `n`          |
  | `static_assert(c, message)`     | None              | `c`               |
  | `error(message)`                | None              | `message`         |
  | `read_port(m, addr, en)`        | None              | `m`               |
  | `write_port(m, addr, data, en)` | None              | `m`               |

  `diagnostic` has no `comptime` and no `mut` parameter. Thus `m.read_port(a, e)` is `read_port(m, a, e)`. A static position of a prelude call is an argument at a `comptime` parameter, and each argument of `static_assert` and `error`. Thus the argument of `list(T)` is a static position, and the arguments of `data_bits(T)` and `str(n)` are not. `T.data_bits()` thus binds its receiver to `T`.

- **Prelude struct.** `ReadResponse` is a struct of the prelude. It acts as the declaration `struct ReadResponse(comptime T: Type) { data: T, valid: Bool }`. The resolver appends it as one struct item after the user items, with a prelude flag. The resolver builds this item already resolved. Its field type `Bool` is the builtin type, and `T` is a local of the item. The item never resolves in the scope of the user items. Thus a user `struct Bool` or a user `type Type` does not change it. The struct rules apply to it unchanged: the number of arguments, the specialization table, the constructor, the zero, `data_bits`, the field selection, and the leaf names. The passes that order their errors by position skip this item.

- **Prelude identity.** By the rule of `S002`, a user item can shadow a prelude name. A user `struct ReadResponse` thus shadows the prelude struct, but both types can exist in one design, as section 7.1 shows. A message names the prelude type in its source form, for example `ReadResponse[UInt[8]]`. A user function `read_port` or `write_port` shadows the prelude function, and its calls get no memory rule. The checks `S006` and `S007` of a memory port call use the resolved prelude reference, never the text of the name. From slice 5 on, the prelude items move to the package `std::prelude`, after the model of the Rust standard library (#208).

- **`mut` formals.** A `mut` formal and a `mut` receiver follow section 9.1. A `mut` actual is a place with a mutable root (section 9.1). The type of the place equals the type of the formal, because a `mut` actual gets no typed use. Another type is `S010`. The type of a place is its declared type: the annotation of the root, through the steps of the place. A root without an annotation gives the type of the value. Thus a place of a `let mut` local of type `Nat` at an `Int` formal is `S010`.

- **Calls through a function value.** A call whose callee is not the name of a function item or of a prelude function evaluates its callee once, before the arguments. The value of the callee then selects the call:

  - A type gives a constructor call: `T()`, `T(x)`, or a record constructor. A function type `T` is not hardware data, so `T()` and `T(x)` are `S010` at the call. This holds for each number of arguments. The error comes after the callee and before the arguments.
  - A function value gives a call of its function item, as below.
  - Another value is `S010` at the call.

  A call of a function value compares the number of arguments with its function type before the arguments evaluate. A difference is `S007` at the call, in pass 5. The arguments then evaluate in their order. The `mut` marks of the function type select the `mut` actuals. The lookup of the function item of the value has no charge, because the factor `log n` of the work bound covers it. The call then runs as a named call of the function item. This includes the copies, the call frame of section 7.3, the body, the result, and the write-backs. A `comptime fn` thus runs in the mode `static` (section 9.4), and a hardware argument is `S011`, as at a named call.

- **Diagnostic records.** A call of `diagnostic` appends one observation record (section 8.2).

Slice 3a adds these items and expressions ([ADR 0021](../adr/0021-enums-and-a-pure-match.md)):

- **Enums.** `enum Op: UInt[2] { Add = 0, Load(UInt[8]) = 1, Pair(Bool, UInt[4]) = 2 }` declares an enum. The tag type follows the `:`. Each variant has a name, zero or more payload types in parentheses, and an explicit static tag value after `=`. The payload of `Pair(Bool, UInt[4])` packs as the tuple `(Bool, UInt[4])`. An enum has no parameters in slice 3 (F23). Thus `enum E(` is `S004` at the `(`, with the text of section 6.2.
- **Enum checks.** A second variant with the name of an earlier variant of the same enum is `S002`. The first use of an enum runs these checks of pass 5. Each error is at the node that fails it, and the payload width is at the `enum` keyword:
  1. The tag type evaluates as a type expression. It is `UInt[W]` (`S010`).
  2. For each variant in declaration order, its tag value evaluates first. It gets its typed use at `UInt[W]`, so a value of another type is `S010`, and a value that does not fit is `S012`. Right after the typed use, the tag goes into the tag map of the enum, with no charge (section 5.4). A tag value of an earlier variant is `S021` at the tag value. Then each payload type evaluates as a type expression, from left to right. It is hardware data (`S010`). Then the payload metadata of the variant charges (section 5.4). This order is not the source order, where the payload types come before the tag value. A handle type is not hardware data, so a payload never holds a handle. The enum keeps its tag map for the coverage check of a `match`.
  3. After all variants, the payload width `P` is at most 65536, as for a memory word (`S012`). The check compares the metadata numbers, and it has no charge. Then the metadata of the enum charges (section 5.4).
- **Enum cycles.** The tag type, the tag values, and the payload types are structural contexts (section 9.4). An enum whose payload names the enum itself, directly or through other types, is `S019`, as a struct is.
- **Variant paths.** `Op::Add` is a value, and `Op::Load(x)` constructs one (F23). The parser accepts a path of two identifiers in an expression and in a pattern. A third part, a `::` in a type, and a `::` after the module name of an `instance` statement are `S004` at that `::`. They share one text in section 6.2, because each one is a package path of slice 5.
- **Path resolution.** The first part `X` of `X::Y` resolves by the ordinary scoping of a name. Thus a local or a parameter named `X` shadows an enum item `X`. When `X` resolves to an enum item, the path resolves to a variant of it. Else the path is `S003` at its start, with the text of section 6.2.
- **Paths without an enum.** The `S003` of a path holds for a local, a parameter, a struct, a function, a module, and a name with no declaration, for example `std` in `std::x`. A `type` alias of an enum is not an enum item, so `type A = Op;` makes `A::Add` `S003`. A second part that names no variant of the enum is `S003` at the second part. The checks are in pass 3.
- **Constructors.** The number of payload values equals the number of payload types of the variant, else `S007` in pass 4. A path without a call gives zero payload values. The values evaluate from left to right. Each one gets its typed use at its payload type (`S010`, `S012`). The constructor then packs them (section 5.1). Section 5.4 gives the order of the charges.
- **Call of an enum type.** `E()` gives the zero of `E`, as `T()` does. A call of an enum type with one or more arguments, for example `Op(x)`, is `S010` at the call, with the text of section 6.2. The check comes after the callee and before the arguments evaluate, as for a function type.
- **`reinterpret` of an enum.** `reinterpret(UInt[data_bits(E)], e)` gives the bits of `e`: the tag in the low `W` bits, then the payload. `reinterpret(E, b)` takes the tag from the low `W` bits of `b` and the payload from the next `P` bits. The result can have a tag that no variant declares (F26). The other side of the conversion has exactly the type `UInt[W + P]`. Another type is `S010`, also `SInt[W + P]`, `Bool`, and a static `Int`.
- **`match` syntax.** `match (x) { Op::Add => a, Op::Load(v) => v, _ => 0 }` is an expression at the level of the conditional. An operand of an operator thus needs parentheses around a `match`. An arm holds one expression, and a trailing `,` is valid. Block arms and tail expressions stay out (#193). A `match` with zero arms parses, and its coverage check gives `S021`.
- **Patterns.** A pattern is an integer literal, also with `-`, `true`, `false`, a variant path, or `_` (F25). A variant path has one binder or `_` for each payload value, for example `Op::Pair(b, _)`. `Op::Add()` is the same pattern as `Op::Add`. The `-` takes only a number token. In a pattern, `_` never binds. Two binders with one name in one pattern are `S002`. A variant pattern with a number of binders and `_` other than the number of payload values is `S007` in pass 4.
- **Pattern syntax errors.** A bare name, a nested pattern, an expression, a range, and `|` are `S001` at the first token that is not valid. Section 6.2 gives the text. A third part of a path keeps the `S004` of a package path. A path in a pattern resolves as a path in an expression.
- **`match` checks.** A `match` runs in this order, and each check is in pass 5:
  1. The `match` node charges 1. The scrutinee evaluates in a `data` context (section 9.2).
  2. The scrutinee type is `Bool`, `UInt[W]`, `SInt[W]`, `Int`, `Nat`, or an enum. Another type is `S010` at the scrutinee. A `Nat` is an `Int` at run time, because each static integer has the type `Int` (section 5.1). Thus a scrutinee of a `Nat` value has the type `Int`.
  3. Each arm runs the arm checks (below), in arm order.
  4. After the last arm, a `_` that matches no value is `S021`. Then a value that no arm matches is `S021`.
- **Arm checks.** Each arm runs these steps, in order:
  1. The pattern charge (section 5.4).
  2. The pattern has the kind of the scrutinee type, else `S010`. An integer type takes an integer literal, and `Bool` takes `true` or `false`. An enum takes a variant of the same enum.
  3. The literal fits the scrutinee type (`S012`).
  4. The coverage share of the arm (section 5.4), when its pattern is not `_`.
  5. The pattern matches no value of an earlier arm (`S021`). An arm after `_`, also a second `_`, is `S021` with the text of an arm after `_`. This case comes before the case of a second match.
- **Kind of a variant pattern.** The kind check compares the resolved enum items. It is no use of the enum of the pattern: it starts no first use, charges nothing, and gives no error of that enum. Thus a pattern of another enum with an error in its declaration is `S010`.
- **Ordered map.** The checks keep one ordered map from each value of a pattern to the first arm that matches it. A key is an integer in the order of the type. It is 0 for `false` and 1 for `true`, the signed value for `SInt`, and the tag for an enum. Step 5 of the arm checks and the coverage share use one insert into this map.
- **Coverage.** The check counts each value of the scrutinee type, not only the declared tags (ADR 0021). A `match` on `Int` thus needs `_`. A message names the smallest value in the order of the type: the signed order for `SInt`, `false` before `true`, and the tag order for an enum.
- **Coverage without enumeration.** A `_` without values occurs when the number of keys equals `2^W`. The check compares the two numbers by `W` and the bit length of the number of keys. The smallest uncovered value comes from one pass over the ordered keys. The tag map of the enum gives the variant of an uncovered tag. No check makes a list of the values of a type.
- **Check order.** The pattern checks, the coverage shares, and the coverage check all run before an arm expression evaluates. This holds for a static and for a hardware scrutinee.
- **Static scrutinee.** A scrutinee without a hardware leaf is static. Only the selected arm evaluates, as in a static `if`. The selection finds the value of the scrutinee in the ordered map. A value that is not in the map selects the arm `_`. The coverage check runs before the selection, so an error does not depend on the value. A binder gets a static unpack of the payload bits, at the leaf offsets of the pack (section 7.4).
- **Hardware scrutinee.** All arms evaluate in source order, each under the guard `arm` (section 9.4), in a `data` context. The arm types join by the operand rule of slice 1, as the elements of an array literal do. Thus in `A => x, _ => 0`, the `0` converts to the type of `x`. Arms without a common type are `S010`. The arms then follow the walk of a hardware `match` (section 5.4). A leaf of hardware data lowers by section 7.4, also when it is static in each arm. Only a static part of a type that is not hardware data must be equal in all arms, else `S011` (F19).
- **Static tag of a hardware enum.** A hardware enum with a static `tag` leaf is a hardware scrutinee. Its selects do not fold to constants. They lower to compares of two constants (section 7.4).
- **Binders.** A binder of a hardware scrutinee binds its payload bits, unpacked to the leaves of its type (section 7.4). It gets a core name as a `let` does (section 7.3). Two arms with the binder `v` thus give `v` and `v$1v`. A static payload part of a hardware enum gives a static binder value.

Slice 3b adds these items and calls ([ADR 0026](../adr/0026-handles-copy-as-identities.md)):

- **Prelude handle types.** `Reg[T]`, `Wire[T]`, `Mem[T, N]`, `Input[T]`, and `Instance[M, args]` are prelude type families. Their uses give the handle types of section 5.1. `Domain` waits for #11. The `S003` of slices 1 and 2 for these names goes away.
- **`Instance`.** The first argument of `Instance` is a module item. The resolver accepts a module name there and nowhere else (`S003`). The other arguments get the typed use of section 5.3 at the parameter types of the module.
- **`Mem`.** `T` and `N` of `Mem[T, N]` have the checks of `T` and `N` of a `mem` statement (section 6.2).
- **`read(h)`.** `read` is a prelude function with one parameter and no mode, so `h.read()` binds its receiver to `h`. `read` checks its argument before the read. An input handle is `S017` with the text of section 6.2. A memory, an instance, or a value that is not a handle is `S010`. Then the `data` context of section 9.2 reads the register or the wire.
- **Resource-typed formals and results.** A parameter or a result of a `fn` with a handle type keeps the handle: its context is `raw` (section 9.2). A `mut` formal with a handle type follows section 9.1. An argument of a `comptime fn` is a static position, so a handle there is `S011`.
- **Helpers that declare resources.** A `fn` without `comptime` can declare a `reg`, a `wire`, a `mem`, and an `instance`. The resource belongs to the owner of the caller. Its path has the call frame (section 7.3), for example `f$0c$r`. A helper can return a handle that it declares.
- **Ports in helpers.** A port in a `fn` stays `S004` until slice 4 (F29). The message of section 6.2 tells the user to declare the port in the module body. A declaration in a `comptime fn` stays `S006`.
- **Effects of helpers.** A helper call that declares a resource in a hardware arm or in a structural context is `S016`, by the rule of section 9.4.
- **Memory ports on a formal.** `read_port` and `write_port` take a `Mem` handle from a formal, a container, or a result too. Each memory still has exactly one call of each (`S018`), through each alias.
- **Bindings.** `S018` counts each resource through each alias and each helper (F28). Its message names the declaration and both bindings (section 6.2).

### 6.2 Report order

Both front ends apply the passes in order. They stop at the first pass with an error.

| Pass | Codes                                                                                                                                                                     | Order in the pass                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 1    | `S001`, `S004`                                                                                                                                                            | Position                                       |
| 2    | `S002`                                                                                                                                                                    | Position                                       |
| 3    | `S003`                                                                                                                                                                    | Position                                       |
| 4    | `S005` to `S008`                                                                                                                                                          | Position                                       |
| 5    | `S007` at a call through a function value or at an index of a type in a local (section 5.6). `S008` at run time (section 9.1). `S010` to `S019`. From slice 3 on, `S021`. | Evaluation order (section 5.2 and section 5.3) |
| 6    | `S020`                                                                                                                                                                    | Position                                       |

Position order is the lowest line, then the lowest column. In pass 5, the first error in the evaluation order wins. `S018` comes at the end of the body of its instantiation. In one instantiation, the `S018` errors compete by position.

The position of an error is:

- `S001`: the first token that does not match, or the end of the file.

- `S001` for a number literal above its limit: the literal.

- `S001` for the brackets: the first `(`, `[`, or `{` at the depth N + 1. The lexer marks this bracket as an error token. The depth counts all three kinds of brackets together.

- `S001` for the height: the first token of the first outermost expression or type, in position order, whose height is above N. This check runs only after pass 1 finds no other error. An outermost expression or type is not part of another expression or type. The height of a leaf is 1, and each node of the AST adds 1. Parentheses make no node.

- `S002`: the name in the second declaration.

- `S004`: the reserved token, or the first token of the construct.

- `S008`: the second mutation of the root. This is the `mut` actual with the root `R` in the window of `R`, thus the second of two `mut` actuals with one root. For a `mut` actual that is not a place or whose root is not mutable: the start of the actual.

- Pass 4 at one position: a receiver call starts at its receiver, so its `S007` can share the position of an `S005` or an `S008` at the receiver. The first error is `S007`, then `S008`, then `S005`.

- At one memory port call, `S006` comes before `S007`.

- `S015`: the node of the charge, or the node that goes above the budget.

- The messages of the budgets are normative, as the `S018` message below is. The harnesses compare them with `expected-message`. Each message ends with its fix: the flag of the budget to raise. When the message knows a value that the run needs, the fix also names it: `raise --F to at least V`. Here `F` is the flag and `V` is the value.

  - `S001` for the brackets: `brackets nest deeper than N levels; raise --syntax-depth`. Here `N` is the syntax depth.
  - `S001` for a height: `an expression or a type is higher than N levels; raise --syntax-depth`. Here `N` is the syntax depth.
  - `S015` for a charge: `the fuel cannot pay K unit(s); N remain; raise --fuel`. Here `K` is the charge and `N` is the fuel that remains. The fuel that the run needs after the charge is not known, so the fix names no value.
  - `S015` for a charge of the lowering: `the fuel cannot pay K unit(s) of the lowering; N remain; raise --fuel`.
  - `S015` for the result of `eval` (section 8): `the fuel cannot pay K unit(s) of the result; N remain; raise --fuel to at least V`. Here `V` is the fuel that the evaluation used plus `K`. The result is the last charge, so this fuel is sufficient.
  - `S015` for the joins of types: `the fuel cannot pay the joins of the types; N remain; raise --fuel`. Here `N` is the fuel that remains. The joins give the common type of array elements, of the operands of `==` and `!=` on containers, and of the arms of a hardware `if`. The message has no count of units. The Rust front end stops its walk when the fuel cannot pay it, so it does not know the whole count.
  - `S015` for the scan of a string by `s[i]` or `len(s)`: `the fuel cannot pay the scan of the string; N remain; raise --fuel`. Here `N` is the fuel that remains. The message has no count of units. The Rust front end does not count the scalars of a string that the fuel cannot pay.
  - `S015` for the nesting depth: `the nesting depth goes above L; raise --depth`. Here `L` is the nesting depth.
  - `S015` for the depth of a value or a type: `the depth D goes above the nesting depth L; raise --depth to at least D`. Here `D` is the depth of the new value or type, and `L` is the nesting depth.

- The messages of the size limit (section 5.4) are normative too. No flag changes the limit, so each fix tells how to make the value smaller:

  - `S015` for a static integer: `the result can have more than 2^32 bits, the limit of a static Int; use smaller operands`.
  - `S015` for the metadata of a type: `the metadata of the type can have more than 2^32 bits, the limit of a static Int; use a smaller type`.
  - `S015` for a string: `the string has more than 2^32 bytes, the limit of a string; use shorter strings`.
  - `S015` for a list: `the list has more than 2^32 elements, the limit of a list; use a shorter list`.
  - `S015` for a value that a type makes: `the value of the type has a size above 2^32, the limit of a value from a type; use a smaller type or keep it a reference`.
  - `S015` for a `diagnostic` record: `the recorded value has a size above 2^32, the limit of a record; record a smaller part`.

- Two more messages are normative:

  - `S001` after an element of a list that closes with `)` or `]`: `` expected `,` or `)` `` or `` expected `,` or `]` ``. The lists are the arguments of a call, the elements of an array literal, and an index.
  - `S011` for a hardware `if` with different static arms: `` the arms of a hardware `if` differ in a static part: X and Y ``. Here `X` and `Y` are the texts of the two arms.

- `S010` to `S014`, `S016`, and `S017`: the start of the node whose evaluation fails.

- `S018`: the second binding. If there is none, the declaration of the resource. For a child input, the `instance` statement.

- The `S018` message for a child input is `` the input `p` of the instance `c` has no binding; bind it with `c.p := ...;` ``. Here `c` is the name of the instance. The input `p` is the first input of the child with no binding. It is the input with the first source position in the child module, also when a comptime loop declares the ports in a different order. The position is the `instance` statement. This text is normative.

- `S019`: the `instance` statement, the use of the constant in progress, or the second declaration with the same core name.

- `S020`: the source position of the core node with the lowest source position on the cycle.

- Slice 2 adds these positions:

  - `S003` for a receiver call: the name of the function.
  - `S006`: the `mem` statement or the memory port call.
  - `S007` for a receiver call: the start of the call, which is the start of the receiver.
  - `S011`: the index expression, or the element. For two different static leaves in the arms of a hardware `if`: the start of the `if`.
  - The checks of the `mem` order and of the memory port order (below): the `mem` statement or the memory port call.
  - `S010` for an index with two or more arguments: the start of the index node. For an order operator or an equality on containers: the start of the operator node.
  - `S013`: the index expression, the number literal of a `.N` selector, or the call of `pop`.
  - `S015` for the depth of a value or a type: the node that makes it. For a `push` and a `mut` write-back: the call.
  - `S015` for the size limit (section 5.4): the node of the operation that makes the value. For a `push` and a `diagnostic`: the call. For a place update: the assignment. For an empty part of a reference: the node that selects or reads it.
  - `S016`: the node of the effect, in an arm and in a structural context. For a `push`, a `pop`, and a `mut` write-back: the call.
  - `S017`: the node of the target, or the statement. A `:=` target with a step (section 5.2) gives `S017` at the start of the target, before its indices evaluate.

  - `S011` for a hardware `match` with different static arms: the `match` keyword.
  - `S015` for the size limit of a binder: the binder.

  - A value of `UInt` is a decimal integer, for example `3`. The tag of the cases "Uncovered tag without variant" and "Second tag value" has this form too.
  - A value of `SInt` or `Int` is a decimal integer with a `-` when it is negative, for example `-8`.

  - A variant without payload is its path, for example `Op::Add`. A variant with payload has one `_` for each payload value, for example `Op::Load(_)` and `Op::Pair(_, _)`.

| `S003` | Unknown variant                | `{E}` has no variant `{v}`; use a variant that `{E}` declares                                                                                   |
| `S007` | Arity of a variant constructor | the variant `{E}::{v}` has {n} payload value(s), but the constructor has {m}; pass one value for each payload type                              |
| `S003` | Path without an enum           | `{x}` is not an enum, so `{x}::{y}` names no variant; use the name of an enum                                                                   |
| `S004` | Port in a `fn`                 | a helper cannot declare a port; declare the port in the module body and pass its value to the helper                                            |
| `S004` | Package path                   | a package path is not supported yet; in this slice, a path is a variant `E::V` of an enum `E`, in an expression or a pattern                    |
| `S004` | Enum with parameters           | an enum with parameters is not supported yet; remove the parameters, and give each payload a fixed type                                         |
| `S010` | Field of an enum               | `{T}` is an enum and has no field `{f}`; read a payload with `match`, or the bits with `reinterpret(UInt[{n}], e)`                              |
| `S010` | Call of an enum type           | `{T}` is an enum, so `{T}(...)` takes no arguments; construct a variant such as `{T}::V(...)`, or write `{T}()` for the zero                    |
| `S018` | Second binding                 | `{r}` has a second binding; the first binding is at {b}, and the declaration is at {d}; remove one of the two bindings                          |

- In these messages, `{x}` is a source name, for example the name of a variant. `{y}` is the second part of a path. `{n}` and `{m}` are decimal counts. Two texts use `{E}` and `{v}`: the `S003` text of an unknown variant and the `S007` text of a variant constructor. There, `{E}` is the name of the enum, and `{v}` is the name of the variant. The `S003` text reports at the second part of the path, and the `S007` text at the start of the path. `{p}` is the name of an input port, and `{u}` is the name of the instance. `{r}` is the source name of a resource. `{k}` is the kind of the handle: `register`, `wire`, `memory`, `instance`, or `input`. `{s}` is the static position: `a module argument`, `a comptime parameter`, `an argument of a comptime fn`, or `a const`. The `S018` text applies to each second binding of a wire, a register, an output, and a child input.

- The case "Uncovered tag without variant" replaces "Uncovered value" when the uncovered value is a tag of an enum that no variant declares. The case "Second tag value" is the `S021` of an `enum` item (section 5.6). The case "Arm after `_`" replaces "Second match of a value" for each arm after `_`.

- In the `S010` text of a pattern kind, `{k}` and `{p}` have their own meanings. `{T}` is the scrutinee type, and `{p}` is the pattern in source syntax. `{k}` is the kind that the scrutinee type takes:

  - `an integer` for `UInt`, `SInt`, `Int`, and `Nat`.
  - `` `true` or `false` `` for `Bool`.
  - `` a variant of `{T}` `` for an enum.

- In the `S010` text of a pattern kind, `{p}` writes a literal as `{v}` does. It writes a variant pattern as its path with its binders and `_`, separated by `, `, for example `Op::Pair(b, _)`.

- In the `S011` text of a `match`, `X` and `Y` are the texts of two sides of the first static position that fails. This is the rule of the `S011` text of a hardware `if`. `X` is the side of arm 0. `Y` is the side of the first arm that differs from arm 0. When all sides are equal and none has the joined type, `Y` is the side of arm 1.

- All other errors: the start of the form that breaks the rule.

**Prelude struct (slice 2).** An error in the work of the prelude struct `ReadResponse` reports at the position of its use: the memory port call or the type use. This holds for its specialization, its field types, its parameter types, and an `S015` in this work. The prelude struct has no source position of its own, so no error reports at its hidden item.

**`instance` order.** An `instance u = M(args);` statement runs in this order. The top selection runs steps 2, 3, and 5 to 7 in the same order. Its errors are at its position (section 5.4). An error in a parameter type is the exception: it reports at the node of the type, as in an `instance` statement.

1. The statement charges 1. The arguments evaluate from left to right, and each argument is static (`S011`).
2. The typed use nests one level. A depth above the nesting depth is `S015` at the statement.
3. Each parameter in order: its type evaluates as a type expression, and an error in it is at its own node. Then the argument gets its typed use. A wrong type is `S010`, and a value that does not fit is `S012`, both at the statement. Then the recursive size of the converted argument charges (`S015` at the statement). Thus an `S015` of this charge comes before an error of a later parameter type.
4. A clocked child in a combinational module is `S017` at the statement.
5. The serialization charges. An instantiation in progress is `S019` at the statement. A done one gives its interface.
6. A new instantiation nests one level (`S015` at the statement). Its emitted name charges its length in bytes, and it must be new (`S019` at the statement).
7. The new instantiation goes in progress, runs its body, checks its bindings, and is done.

Thus an error of a typed use comes before `S017`. For example, `instance u = Clocked(300);` in a combinational module is `S012` when the parameter has the type `UInt[8]`.

**`mem` order (slice 2).** A `mem m: [T; N];` statement runs in this order. Each error is at the statement.

1. The statement charges 1.
2. A combinational module is `S017`, before the type, as for a `reg`.
3. `T` evaluates as a type expression. A type that is not hardware data or that is empty is `S010`. Thus `Int`, `()`, `[Unit; 4]`, and `[fn () -> Bool; 0]` are `S010`.
4. A word above 65536 bits is `S012`. The width comes from the type metadata.
5. `N` evaluates. It is static (`S011`), an `Int` (`S010`), and 1 to 16777216 (`S012`). A static `UInt` or `SInt` depth is `S010`, as for the length of `[T; N]`. An empty list `[]` is not an `Int`, so it is `S010` at the statement.
6. The path of the memory comes from its frame, as for a register (section 7.3). This includes the version field, the loop frame, and `S019`.
7. The declaration goes into the body, and the name binds a memory handle.

**Memory port order (slice 2).** A call `read_port(m, addr, en)` or `write_port(m, addr, data, en)` runs in this order, as the other prelude calls do. Each error is at the call.

1. The node and the function name charge.
2. The arguments evaluate from left to right, the receiver first.
3. The copies of the arguments charge (section 5.4).
4. The first argument is a memory, else `S010`.
5. The effect rule of section 9.4 (`S016`), under a guard of either kind.
6. The typed uses, in the order of the arguments. `addr` has the type `UInt[A]`: another hardware type is `S010`, and a static value that does not fit is `S012`. `en` has the type `Bool`. `data` has the type `T`, by the typed use of a hardware aggregate (section 5.4).
7. The memory counts the call for `S018` (below).
8. `read_port` charges the use of `ReadResponse[T]` as a struct use. Then the depth of the response gets its check (`S015`), and the response charges its zero size (section 5.4). The response is the result. `write_port` gives `()` with no charge.

A static address that fits `UInt[A]` but is not below `N` is valid. It is not `S013`. The read gives `data` 0 and `valid` false, and the write has no effect (section 7.6).

**Memory bindings (slice 2).** Each memory counts its `read_port` calls and its `write_port` calls. A second call keeps the request of the first call: its address, its data, and its enable. Its `S018` waits for the end of the body. A memory without a read or without a write gives `S018` at its `mem` statement. All `S018` errors of one instantiation compete by position. A `let` alias of a memory handle counts for the same memory.

**`diagnostic` order (slice 2).** `diagnostic` has two parameters, without `comptime` and without `mut`. A call with another number of arguments is `S007` in pass 4. No argument is a static position. A call `diagnostic(message, value)` runs in this order, as the other prelude calls do. Each error is at the call.

1. The node and the function name charge.
2. The arguments evaluate from left to right, the receiver first. `value` is in the `raw` context (section 9.2), so a register stays a handle.
3. The copies of the arguments charge, by the rule of builtins (section 5.4).
4. The effect rule of section 9.4 (`S016`), as for a memory port call.
5. `message` takes the `data` context (section 9.2). A register, a wire, or an output reads as hardware, so it is `S011`. This holds also when its type is empty, because the handle check comes before the data read. An own input is hardware, so it is `S011` too. A child input is `S017`. A memory, an instance, or a domain is `S010`. Then a hardware value is `S011`, and a static value that is not a `String` is `S010`. A `message` that is a literal and waits for its type, for example `[]`, is `S010` at the call.
6. A `value` that is a literal and waits for its type is `S010` at the call, for example `[]` or `[1, []]`.
7. The serialization of the record charges (section 5.4).
8. The rendering makes the text of the record (section 8.2). The record goes into the list of records. The result is `()`.

The error line has the form of the core IR: `error[S010]: 12:5: <message>`. The message names the instantiation path, as v0.1 section 9 requires. The harnesses compare the code, the line, and the column, but not the message. A file with an `expected-message` directive also compares the message (section 11.3).

### 6.3 Diagnostics

A diagnostic is the report of one error. Section 6.1 and section 6.2 make its code and its line normative. The other parts of a diagnostic help a human or an agent fix the error. Lean does not model these parts. [ADR 0014](../adr/0014-structured-diagnostics.md) records the decision.

The records of the v0.1 builtin `diagnostic` are observation records, not diagnostics. This section does not change them.

**Structure.** The crate `diagnostics` defines the diagnostic type. Each stage returns diagnostics as values and prints nothing. A diagnostic has these parts:

| Part            | Content                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------- |
| Code            | `S001` to `S021`                                                                          |
| Primary span    | The position of section 6.2, with a label                                                 |
| Secondary spans | Related positions, each with a label. Example: the first declaration of an `S002` name.   |
| Notes           | Facts about the error: the actual and the expected values (v0.1 section 9), the backtrace |
| Help            | One sentence that tells how to fix the error                                              |
| Suggested edits | Text replacements, each with an applicability                                             |

An applicability has one of two values:

- **Machine-applicable.** The edit is correct. A tool can apply it without a human.
- **Maybe-incorrect.** The edit can be wrong. A human or an agent must look at it.

**Instantiation backtrace.** An error of pass 5 occurs in one instantiation. A note lists the chain of `instance` statements from the top selection to that instantiation, with a span for each statement. This is the form of the "required by" notes of rustc. It gives the instantiation path that v0.1 section 9 requires.

**Renderers.** The `driver` renders the diagnostics. The flag `--error-format` selects the form:

| Value   | Form                                                                                  | User                     |
| ------- | ------------------------------------------------------------------------------------- | ------------------------ |
| `human` | The form of rustc: source snippets with labelled spans, made with `annotate-snippets` | A human on a terminal    |
| `short` | One line for each diagnostic: `error[S010]: 12:5: <message>` (section 6.2)            | The harnesses, and Lean  |
| `json`  | One JSON object for each diagnostic, with all parts, on one line                      | An LLM agent and the LSP |

`human` is the default. The fields of `json` are a contract: a change of a field is a breaking change of the command-line interface.

**`silicon explain`.** `silicon explain S010` prints the long text of a code: the rule, a failing example, and a fixed example. Each code has one text in the crate `diagnostics`. A test elaborates both examples of each text. The failing example must give its code, and the fixed example must give no error.

**Recovery.** The front end reports more than one error. Each stage continues after an error where it can, and reports all errors of the first pass that has errors. It does not start a later pass (section 6.2). Only the first error is normative: Lean defines it, and the harnesses compare it. The later errors have no oracle.

**Trust.** A diagnostic does not change the result. The result is the accept or reject decision, and for a reject the first code, line, and column. A wrong help or a wrong edit can thus mislead a user, but it cannot make a wrong design pass.

**Quality loop.** These checks keep the diagnostics useful:

1. **Snapshots.** Each file of `tests/source/check/` has an `insta` snapshot of its `human` and `json` output. A snapshot is a review aid (section 10.2).
2. **Machine-applicable edits.** For each file of `tests/source/check/` and `tests/source/llm/`, a test applies all machine-applicable edits. The edited file must not give the same diagnostic again.
3. **Corpus of LLM mistakes.** `tests/source/llm/` holds the mistakes that LLM agents typically make in Silicon, for example Verilog syntax or a missing width. Each file has its expected first error and a fixed version.
4. **One-turn-fix metric.** A harness gives an LLM a file of `tests/source/llm/` and its `json` diagnostics, for one turn. The metric is the fraction of answers that elaborate and pass the source vectors of the fixed version. The project pins the model and its settings. A CI gate fails when the metric falls below the recorded baseline.

## 7. Lowering to core IR

### 7.1 InstantiationId and emitted module names

An `InstantiationId` is a `ModuleId` and the canonical serialization of the module arguments after their typed use at the parameter types (section 5.3). Thus `C(1)` and `C(UInt[8](1))` give one identity, `(instantiation root C ((uint 8 1)))`, when the parameter of `C` has the type `UInt[8]`. Up to slice 5, the `PackageId` of each `ModuleId` is the root package, `root`. `Source.Value` defines the serialization. Slice 1 has these forms:

```text
(int -5)  (bool true)  (string "a\"b")
(instantiation root Counter ((int 8)))
```

Slice 2 adds the forms of the containers, the types, and the functions. Each container form records its type where its elements cannot give it, so the serialization stays injective for each type:

```text
(unit)
(array (uint 8) ((uint 8 1) (uint 8 2)))     (array bool ())
(tuple ((int 1) (bool true)))
(record (struct root Packet ((int 8))) ((uint 8 3) (bool false)))
(list int ((int 1) (int 2)))
(function root inc)
(type (array (uint 8) 4))   (type (tuple (bool (uint 8))))   (type (list int))
(type (fn ((mut (uint 8)) bool) unit))   (type string)   (type type)   (type unit)
```

A struct type serializes its declaration and its static arguments, because its identity is nominal. A function serializes its package and its name.

The prelude struct `ReadResponse` (section 5.6) has the token `prelude` in the place of the package. Thus `ReadResponse[UInt[8]]` serializes as `(struct prelude ReadResponse ((type (uint 8))))`. A user struct `ReadResponse` serializes as `(struct root ReadResponse ...)`, so the two types never share an identity.

Slice 3 adds the forms of enums and handle types:

```text
(type (enum root Op ()))
(enum (enum root Op ()) 1 (uint 8 3))
(type (reg (uint 8)))   (type (wire bool))   (type (mem (uint 8) 16))
(type (input (uint 8)))   (type (instance root Counter ((int 8))))
```

An enum type serializes its declaration and an empty list, because its identity is nominal. The list holds the arguments that a later slice can add, so that slice keeps this form. An enum value serializes its type, its tag as an integer, and its payload bits as a value of type `UInt[P]`. An enum without payload bits has no payload part: `(enum (enum root Op ()) 0)`. A handle type serializes its kind and its parts. `Instance[M, args]` serializes the module and the converted arguments, as an `InstantiationId` does. A handle value never serializes, because a static position rejects it (`S011`).

The emitted module name of an instantiation is one of two forms:

- **Readable.** The module name, then `$` and one token for each argument. An integer token is its decimal value, with the suffix `n` for a negative value: `-5` gives `5n`. A finite value of type `UInt[w]` or `SInt[w]` gives the token of its integer value. Thus `C(1)` and `C(UInt[8](1))` both give `C$1`. A Boolean token is `1b` or `0b`. Examples: `Counter$8`, `Fifo$16$1b`. A module without arguments keeps its name.
- **Digest.** The module name, then `$0h` and the first 16 hexadecimal digits of the SHA-256 of the serialization. Example: `Fifo$0h3f2a9c0b1d4e5f60`.

The readable form applies when each argument is an integer, a finite integer, or a Boolean, and the name has at most 64 bytes. The magnitude of each integer argument must be below `2^256`. The readable form is injective for one module. Each parameter type follows from the module and the earlier arguments. Thus a token and its parameter type give one value. The limit applies also to a module without arguments. Otherwise, the digest form applies. A container, a string, a type, or a function as an argument thus gives the digest form (slice 2). Only a truncated digest can make two identities share an emitted name. Elaboration then fails with `S019`. It never merges two modules.

Slice 5 adds the package prefix of [ADR 0007](../adr/0007-mandatory-uniquification.md). It closes the open grammar of that ADR. Issue #53 tracks the gap until then. The plan for slice 5:

1. **Identity propagation.** The `PackageId` from the Lattice lock is part of each `ModuleId`, and thus of each `InstantiationId`. The core module name is the only carrier of the identity after elaboration. `backend-circt` keeps the core module name unchanged, so uniquification happens in one place: the elaborator.
2. **Uniquification.** The emitted name gets a prefix from the full `PackageId`: the package name, the version, and a digest of the `PackageId`. The name and the version alone are not sufficient, because two sources can give the same name and version. The prefix uses the field kinds of section 7.2, so `decode` stays injective. A prefix longer than the limit of the readable form takes the digest form. The slice 5 spec update gives the exact grammar.
3. **Name map.** Elaboration writes a map from each emitted module name to its `PackageId`, `ModuleId`, and arguments. RTL, formal artifacts, and debug tools read this map.
4. **Collision tests.** A corpus design uses two versions of one package with the same module name. A second corpus design uses one version of one package from two sources. Each design must give two emitted modules, and LEC checks each against its source. `names_injective` covers the prefixed names. A unit test in each front end makes two identities share a digest through a test digest function, and expects `S019`.

### 7.2 Names without collisions

The language reserves no name. A user can name a port `clk`, `add`, or `silicon_reg_x`. Elaboration keeps user names and made names apart by construction, not by a rule for the user.

The core IR spec (#39) defines the form of a core name: a list of fields, joined by one `$`. Its pattern is `[A-Za-z_][A-Za-z0-9_]*(\$[A-Za-z0-9_]+)*`. A core name thus never contains `$$`. Each field has one of two kinds:

- **User field.** It starts with a letter or `_`. It is a source name unchanged. A source name has no `$`, so it needs no escape.
- **Made field.** It starts with a digit. Only elaboration makes it. The table below lists its forms.

| Made field                                                    | Meaning                                                                             |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `5`, `5n`                                                     | A loop value or an integer argument, also a finite one. `n` marks a negative value. |
| `3c`                                                          | The call site `3` of a call frame                                                   |
| `2v`                                                          | The version `2` of a binding (section 7.3)                                          |
| `1b`, `0b`                                                    | A Boolean argument                                                                  |
| `0h<hex>`                                                     | A digest                                                                            |
| `0k`                                                          | The escape of a core keyword                                                        |
| `4t`                                                          | The temporary `4` of a statement (section 7.4)                                      |
| `2e`                                                          | The element `2` of an array or a tuple (slice 2, section 7.3)                       |
| `0clk`, `0rst`, `0ret`, `0rdata`, `0rvalid`, `0ren`, `0raddr` | A role: clock, reset, call result, memory response, memory request                  |

The decoder splits a name at each `$`. No field contains `$`, so this split is unique. The first character of a field then gives its kind. The first field of each name is a user field.

The core IR still rejects a keyword as a name (core IR spec, section 3). A user name alone that equals a core keyword thus gets the field `0k`: a port `add` becomes `add$0k`. No other name gets `0k`. A name with a separator is never a keyword.

The proof obligation is injectivity. A name structure is valid when each user field is a source identifier and each digest is non-empty lowercase hex. `Source.Names` defines a function `decode` with `decode (encode p) = some p` for each valid name structure `p`. An invalid structure can collide: `a$b` alone and `a` with the user field `b` both give `a$b`. The theorem `names_injective` follows from it (section 10.3). The function `encode` also gives only names that match the core name pattern and are not keywords. These are the oracles:

- A Lean unit test and a Rust `proptest` test of the round trip on random name structures.
- A file of `tests/source/corpus/` with user names equal to each core keyword and to each made field form. It also uses backend kinds, for example `reg` and `mem`, and `silicon_reg_r`. From slice 2 on, its record fields use the same names, so the leaf names cover them too.
- The generator (section 11.4) takes user names from the same list.

Issue #39 removes the reserved prefix `silicon_` from the core IR. The backend and the oracles then make names that contain `$$`, for example `reg$$<n>`. A core name never contains `$$`, so no name of the front end can collide with a backend name.

### 7.3 Structural paths

Each declaration and each binding of a hardware value gets a core name. The name is its structural path: the frames that enclose it, then its source name. `$` separates the fields. The frames, from the outside in:

- **Loop frame.** A `comptime for` iteration gives the field pair `<binder>$<value>`, for example `i$2`. A negative value has the suffix `n`.
- **Call frame.** A call of an ordinary function gives the field pair `<fn>$<k>c`. `k` counts from 0 over the distinct start positions of the call nodes of the enclosing body, in source order. It is the index of the start position of the call. Two call nodes with one start position, such as `uint(8)(x)`, share `k`.

Examples: a register `r` in the loop body at `i = 2` is `i$2$r`. A `let t` in the helper `f`, at the first call site, is `f$0c$t`.

**Call sites from slice 2 on.** A receiver call `x.m(a)` starts at the position of `x` (section 5.6), and a call inside `x` can start there too. Positions thus no longer tell two call nodes apart. From slice 2 on, this rule replaces the rule of the call frame above:

- `k` counts from 0 over the call nodes of the enclosing body, in pre-order of the resolved AST. A call node comes before its callee and its arguments.
- The children of a node come in source order: the order of their first tokens in the written source. Two children never share a first token. The rule thus does not depend on the field order of a constructor in `Source.Syntax` or in the Rust AST.
- Each call node gets its own `k`. Both front ends key a call site by its node, not by its position.
- The receiver-call node has the receiver as its first child, before the explicit arguments. When `m` has no leading `comptime` formal, `x.m(a)` and `m(x, a)` thus give the same `k`. The metamorphic pair of section 11.3 covers this case only.
- For the syntax of slice 1, the new order differs only where two call nodes share a start position, for example the constructor call `uint(8)(x)`. The outer call then gets the lower `k`, and the inner call gets its own `k`.
- Thus one case of slice 1 gets new core names: a body with such a constructor call before a function call. Each later call frame `<f>$<k>c` of that body moves up by one. Decision F18 records this change.
- Lean `Source.Resolve` and the Rust `resolve` give each call node its call site. They changed together, in the phase that brings receiver calls (section 14.2). The changed expectations of the slice-1 `elab` files land in a commit that changes only tests.

A call through a function value (slice 2) gives the call frame `<f>$<k>c`, where `f` is the name of the called function, not of the callee expression. The frame thus names the code that runs.

These bindings get a core name:

- A port, a register, a wire, a memory, and an instance.
- A `let` or an assignment `=` that binds a hardware value.
- A hardware argument of an ordinary function call. Its source name is the formal parameter.
- The hardware result of an ordinary function call. It gets the role field `0ret` after its call frame, in the place of the name of the binding.

One frame can bind one source name more than once, for example in an assignment to a `let mut` binding. The first binding keeps the path. The binding with index `n ≥ 1` gets the made field `<n>v`. The count includes the ports and covers all bindings of the frame that get a core name, in evaluation order.

A `mut` write-back (section 9.1) binds a new version of the caller root in the caller frame, as an assignment to the place does. When the new value of the root has a hardware leaf, the write-back counts. For example, take a call `f(x)` with a `mut` formal of a hardware type. It gives the root `x` its next version, `x$1v` after the first binding.

From slice 2 on, an aggregate binding counts once, as one binding of its source name. All its leaves share its version, for example `q$1v$a` and `q$1v$b`. A binding counts only when at least one of its leaves gets a core name. A binding whose leaves are all static, and an empty binding, thus do not count. Each hardware leaf of a counted binding gets one core `let`. This rule also applies to a hardware argument, to a call result, and to a `mut` write-back. A place update with a step can give a new root with a hardware leaf. It then binds each hardware leaf of the root again, at the next version of the root (section 5.4). A root that held no hardware leaf before has no counted binding, so this binding is its first and gets no version field. A `push` or a `pop` into a list part of an aggregate root changes no hardware leaf, so it binds nothing and takes no version.

A call result never gets a version. One call frame has one result, and a call node runs at most once for each frame path. A loop and a recursion each add a frame.

A static value gets no core name. A handle alias, for example `let a = q`, gets no core name. A port keeps its source name, because the port names are the interface. Two ports with one name, for example from a loop, fail with `S019`.

The paths are injective by section 7.2. A frame is a user field and a made field. The name of the binding is a user field. A version or a role is a made field at the end.

**Leaves (slice 2).** Each leaf of an aggregate binding gets a core name. The leaf part follows the name of the binding and its version:

```text
path  ::= frame* head leaf* (role | temp)?
frame ::= USER <value>  |  USER <k>c
head  ::= NAME version?
        | 0ret          ; a call result, with no version
leaf  ::= USER          ; a record field
        | <k>e          ; an array index or a tuple element
```

Examples: the field `a` of the port `p` is `p$a`. The element 2 of the register `r` is `r$2e`. The element 0 of the field `xs` of the second version of `q` is `q$1v$xs$0e`. The field `a` of the result of the first call of `f` is `f$0c$0ret$a`, and its element 0 is `f$0c$0ret$0e`. A temporary follows the full leaf name: `<leaf name>$<k>t`. The temporary 0 of the leaf `a` of the child input `p` of the instance `u` is `u$p$a$0t`.

The made field `<k>e` is new in slice 2. The integer field `5` cannot serve: the leaf `p.0.x` would give `p$0$x`, which equals the register `x` in the loop frame `p$0`. A static leaf and an empty leaf get no core name. `names_injective` covers the field `<k>e`.

**Slice 3.** These rules add to the rules above:

- The two leaves of an enum get the user fields `tag` and `payload`, as record fields do. Examples are `op$tag` and `op$payload`. One binding has one type, so no record field of a second path can give `op$tag`. `names_injective` does not change.
- A binder of a hardware `match` gets a core name as a `let` does. It is a binding of its source name in the current frame, and it counts for the version field. Two arms with the binder `v` thus give `v` and `v$1v`. A binder with an empty or a static value gets no core name.
- A resource that a helper declares gets the call frame of the helper, as a `let` in the helper does. Examples are the register `f$0c$r` and the instance `f$0c$u`. The rules above already give these paths, so no new field exists.
- A handle in a container, a parameter, or a result gets no core name, as a handle alias does.

A path contains no byte offset, because with byte offsets each edit, even one blank line, would rename each later declaration. This is a change from v0.1 section 4.

### 7.4 Expressions

Each core name gets one core statement. An expression without a name stays inline in the statement of its binding. The lowering keeps each inline expression at most 64 nodes high. It computes an effective height bottom-up. A leaf, a reference to a named binding, and an operand that binds to a temporary have the effective height 1. A node whose effective height reaches 64 binds to a temporary, as an operand that is used twice does. The value of the statement itself never binds. Each row of the table below adds at most 4 core levels. A core expression thus nests at most 256 levels, the limit of the core IR. A binding with a name breaks the nesting, so a call chain cannot go above the limit.

In this table, `w` is the width of the left operand, and `c` has the width `wc`.

| Source                                    | Core                                                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `Bool`, `UInt[W]`, `SInt[W]`              | `(bits 1)`, `(bits W)`, `(bits W)`                                                           |
| Literal or static finite value `v`        | `(const w v mod 2^w)`. `true` is `(const 1 1)`.                                              |
| `a +% b`, `a -% b`, `a *% b`              | `(add a b)`, `(sub a b)`, `(mul a b)`                                                        |
| `-a` on a finite integer                  | `(sub (const w 0) a)`                                                                        |
| `~a`, `a & b`, `a \| b`, `a ^ b`          | `(not a)`, `(and a b)`, `(or a b)`, `(xor a b)`                                              |
| `!a`, `a && b`, `a \|\| b` on hardware    | `(xor a (const 1 1))`, `(and a b)`, `(or a b)`                                               |
| `==`, `!=`                                | `(icmp eq a b)`, `(icmp ne a b)`                                                             |
| `<`, `<=`, `>`, `>=`                      | `icmp` with `ult`, `ule`, `ugt`, `uge` for `UInt`, and `slt`, `sle`, `sgt`, `sge` for `SInt` |
| `a << c`, `a >> c`, equal widths          | `(shl a c)`; `(shru a c)` for `UInt`, `(shrs a c)` for `SInt`                                |
| Shift, `wc < w`                           | The count is `(concat (const (w - wc) 0) c)`                                                 |
| Shift, `wc > w`                           | `(mux (icmp uge c (const wc w)) F (op a (extract c 0 w)))`. `F` is the fill.                 |
| Shift by a static count `k`               | The count is `(const w (min k w))`                                                           |
| `if (c) { a } else { b }` on hardware     | `(mux c a b)`                                                                                |
| `resize` to a smaller width `n`           | `(extract a 0 n)`                                                                            |
| `resize` of `UInt` to a larger width      | `(concat (const (n - w) 0) a)`                                                               |
| `resize` of `SInt` to a larger width      | `(concat (replicate (extract a (w - 1) 1) (n - w)) a)`                                       |
| `reinterpret`, `resize` to an equal width | `a`                                                                                          |

The fill `F` is `(const w 0)` for `<<` and for `>>` on `UInt`. For `>>` on `SInt`, it is `(shrs a (const w (w - 1)))`.

A width `w` fits in `wc > w` bits, and `w - 1 < 2^w`. The constants of the table thus always pass `E005`.

Two rows use an operand more than once: the shift with `wc > w` uses `c` twice, and for `SInt` also `a`. The `resize` of `SInt` to a larger width uses `a` twice. Inline copies would make the output grow exponentially with nested operations. The lowering thus obeys this rule:

- A rule can use an operand more than once. If that operand is not a core name or a constant, the lowering first binds it to a core `let`.
- The name of this temporary is the core name of the target of the statement, then the made field `<k>t`. For a child input `u.a`, the target is the instance path, then the user field `a`.
- `k` counts the temporaries of the statement from 0, in evaluation order.
- From slice 2 on, an aggregate statement gives one core statement for each leaf. Each leaf statement has the leaf name as its target and its own count `k`.
- A temporary that several leaf statements share belongs to the statement that lowers first among the statements that use it. That statement binds it at its first use. Its number is the next number of that statement after the temporaries of the shared operand itself. Each later use refers to it.
- The `write` statement of a memory `m` has the target `m` (section 7.6). Its temporaries are thus `m$<k>t`, for example for a long `concat` chain of the write data.
- The temporaries of the `write` statement count in this order. First come the temporaries of the write address. Then come the temporaries of the write data in packing order. Each leaf adds its own temporaries. The spine of the chain adds a temporary when it reaches the height 64. The temporaries of the write enable come last.
- The temporaries of the request `let` values of a memory `m` are `m$0ren$<k>t` and `m$0raddr$<k>t`.

Each source node thus gives a bounded number of core nodes, and the output size stays linear in the source. The rule needs no budget for the output size.

Slice 2 lowers a hardware aggregate to its leaves ([ADR 0019](../adr/0019-aggregates-lower-to-leaves.md)). The core IR has only `(bits N)`, so each leaf becomes one core value of its scalar type. In this table, `T` is the type of a hardware aggregate. `a_i` and `b_i` are the leaves `i` of `a` and `b` in packing order (section 7.5):

| Source                                     | Core                                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `a == b` of type `T`                       | `E_0` is `(icmp eq a_0 b_0)`, or `(const 1 s)` when static pairs exist. `E_i` is `(and E_(i-1) (icmp eq a_i b_i))`. The last `E_i` is the result. |
| `a != b` of type `T`                       | `(xor E (const 1 1))`, where `E` is the core of `a == b`                                                                                          |
| `if (c) { a } else { b }` of type `T`      | `(mux c a_i b_i)` for each hardware pair `i`. A static pair gives its one static value.                                                           |
| `x.f`, `x.0`, and `x[i]` with a static `i` | The selected leaf or subtree. No core node.                                                                                                       |

The lowering walks the two operands of `==`, `!=`, or a hardware `if` together, by their one type. At each pair of corresponding parts, the first rule that applies holds:

1. An array, a tuple, or a record: the walk descends into the pairs of its elements, in packing order. This rule also holds for a container type that is not hardware data, for example `[Int; 2]`. From slice 3 on, an enum is a container pair too. The walk descends into its `tag` pair, then its `payload` pair. A static enum opens into its two static parts of types `UInt[W]` and `UInt[P]`. When `P` is 0, the walk visits only the root pair and the `tag` pair.
2. `()`: the pair adds no core node, but its visit charges 1 as each pair does. `Unit` is hardware data (section 5.1). An `if` with two arms of type `()` gives `()`.
3. A part of a type that is not hardware data, for example a list, a string, a type, an `Int`, or a function: a **static pair**. Such a part never holds a hardware leaf, so both sides are static. Its value includes its shape, for example the length of a list.
4. A scalar part of a hardware data type: a leaf pair. In `==` and `!=`, a leaf pair with two static leaves joins the static pairs. Each other leaf pair is a hardware pair.

A static leaf in a hardware pair lowers to a constant by the row "Literal or static finite value". The table then reads `i` over the hardware pairs only, in the order of the walk. The walk charges 1 for each pair of parts that it visits, before it visits the pair. Section 5.4 gives the order of the charges. The walk starts only at a root of a container type. A root of a scalar type thus gets no charge for the walk. These rules apply to the static pairs:

- `==` and `!=` compare the static pairs at elaboration time, by the static equality of section 5.4. This equality is structural, so it compares the length of each list. `s` is `1` when all static pairs are equal, and `0` otherwise. `E_0` is then `(const 1 s)`, and each hardware pair joins with `and`.
- An equality of two aggregates without a hardware leaf is a static equality. It makes no core node.
- A hardware `if` needs equal static pairs. A static pair whose two sides differ is `S011`, because a static part cannot depend on the hardware condition. A static pair of equal sides that do not have the joined type is also `S011` (section 5.4). The error is at the start of the `if`. The first such pair in the walk order stops the walk.
- The scalar case follows the same rule. Take two static arms of a type that is not hardware data, for example `Int`, `String`, or `Type`. Thus `if (h) { 3 } else { 3 }` with a hardware `h` gives the static value 3, and `if (h) { 3 } else { 4 }` is `S011` at the start of the `if`. Two function arms follow the same rule: one function gives the static value, and two different functions are `S011`.
- Slice 1 gives `S010` for each such scalar `if`, because the Lean `mux` lowers each static arm to a hardware constant. Decision F19 records the change. Lean and Rust change together in phase 6 of section 14.2. The changed expectations of slice 1 land in a commit that changes only tests.
- `==` and `!=` with a type that holds a function type are `S010` before the walk (section 5.1). A hardware `if` compares two functions in a static pair by their function items, and charges this as a static equality.
- In a hardware `if`, a leaf pair with two static leaves is a hardware pair. It lowers to constants, as in slice 1.

The condition `c` of an aggregate `if` is an operand that the leaves use more than once. When the walk makes two or more `mux` nodes, `c` thus binds to a temporary, unless it is a core name or a constant. Each leaf statement uses this temporary. It belongs to the statement that lowers first, as the rules above give. That statement gives it the next number after the temporaries of `c` itself. Section 5.4 gives the charge of the mark of `c`. The chain of `and` nodes obeys the height rule of this section. A hardware index of an array is `S011`.

Slice 3 adds the rows of enums and `match`. An enum `E` has the tag width `W` and the payload width `P` (section 5.1). A variant `V` has the tag `c` and a payload of `p` bits, with the leaves `l_0` to `l_(n-1)` in packing order. `o_i` is the sum of the widths of the leaves before `l_i`, and `w_i` is the width of `l_i`.

| Source                                     | Core                                                                                                                         |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `E::V(a, b)`, the leaf `tag`               | `(const W c)`                                                                                                                |
| `E::V(a, b)`, the leaf `payload`           | `(concat (const (P - p) 0) (concat l_(n-1) ... l_0))`. Without high bits, the `concat` chain alone. One leaf is that leaf.   |
| `E::V` without payload, the leaf `payload` | `(const P 0)`, when `P` is not 0                                                                                             |
| `reinterpret(UInt[W + P], e)`              | `(concat e$payload e$tag)`, or `e$tag` when `P` is 0                                                                         |
| `reinterpret(E, b)`                        | `tag` is `(extract b 0 W)`, and `payload` is `(extract b W P)` when `P` is not 0. When `P` is 0, `tag` is `b`.               |
| The leaf `l_i` of a binder                 | `(extract x$payload o_i w_i)`                                                                                                |
| The select `s_i` of arm `i`                | `(icmp eq x c_i)` for a literal. For a variant, `x$tag` takes the place of `x`.                                              |
| The select of the arm `_`                  | `(xor (or s_0 ... s_(n-1)) (const 1 1))` over the arms before `_`                                                            |
| A result leaf of width `w`                 | `(or (and (replicate s_0 w) v_0) ... (and (replicate s_(m-1) w) v_(m-1)))` over the `m` arms, with `v_j` the leaf of arm `j` |

These rules apply to the rows of `match`:

- A hardware `match` lowers to a parallel AND-OR mux. The arms match disjoint sets of values, so at most one select is 1. Coverage makes exactly one select 1.
- A static leaf of an arm lowers to a constant, by the row "Literal or static finite value". A binder leaf of a static payload part is a static value.
- A static `tag` leaf of a hardware scrutinee does not fold. Its selects lower to compares of two constants, by the row of the select (section 5.6).
- Each mark of a hardware `match` binds to a temporary: the scrutinee or its `tag` leaf, the `payload` leaf, a select, and the select of `_`. Section 5.4 gives the use counts that make a mark.
- Each mark belongs to the statement that lowers it first, by the rule of shared temporaries above. That statement binds it at its first use. Its number is the next number of that statement after the temporaries of its operand.
- The lowering of one result leaf of `m` arms runs in this order. First the operands lower: all selects `s_0` to `s_(m-1)`, then all values `v_0` to `v_(m-1)`. Thus the temporary numbers of the selects do not depend on the temporaries of the values. Then a loop runs over the arms. Arm `j` charges and builds its `replicate` node, then its `and` node. The result is `(or (or a_0 a_1) ... a_(m-1))` with `a_j = (and (replicate s_j w) v_j)`. The lowering charges each node before the node exists, as for each core node.
- The height rule of this section applies to the `or` chain and to the `concat` chain of a pack. A `replicate` node or an `and` node binds to a temporary right after it is built, when its height reaches 64. From arm 1 on, the chain so far binds, by the same rule, before the `or` node that joins it with `a_j`. Thus the `and` node of an arm binds before the chain that it joins. The lowering builds the left spine of each chain in a loop.
- The select of `_` over the `n` selects before `_` is `(xor (or s_0 ... s_(n-1)) (const 1 1))`. The `xor` node and its constant charge 2 first. Then the `or` chain builds from `s_0`: each step binds the chain so far by the height rule, charges its `or` node, then lowers its select. At the end, the chain binds by the height rule before the `xor` node. The `or` of one select `(or s_0)` is `s_0`.
- A `match` with the single arm `_ => a` gives `a` and makes no core node.
- `reinterpret` between an enum and its bits uses the leaves of section 7.5, so a port of an enum type keeps its two leaves.
- `reinterpret(E, b)` with `P` not 0 uses `b` in two leaf statements. Thus `b` binds to a temporary unless it is a core name or a constant, as the condition of an aggregate `if` does. Without the temporary, `k` nested conversions would give `2^k` nodes. The mark of `b` charges the size of `b` once (section 5.4), so the charge of `k` nested conversions also stays linear. The temporary belongs to the leaf statement that lowers first, by the rule of shared temporaries above. Its number comes after the temporaries of `b` itself.

### 7.5 Statements, ports, and the domain

Slice 1 has one domain or none. A module has the clause `domains(d)` with one name, or `domains()`. Without a clause, the domain is `clock`. A clause with more than one name is `S004` in the parser.

| Source                         | Core                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| The domain `d`                 | The inputs `d$0clk` of type `clock` and `d$0rst` of type `(bits 1)`    |
| `input x: T;`                  | `(input x <type of T>)`                                                |
| `output y: T;` and `y := e;`   | `(output y <type of T>)` and `(assign y e)`                            |
| `reg r: T = v;` and `r := e;`  | `(reg r <type> d$0clk (reset sync d$0rst C))` and `(next r e)`         |
| `wire x: T;` and `x := e;`     | `(let x <type> e)`                                                     |
| A hardware binding with a name | `(let <path> <type> e)`                                                |
| `instance u = M(args);`        | `(inst u <emitted name> (c$0clk d$0clk) (c$0rst d$0rst) (<input> e)*)` |
| `u.a := e;`                    | The connection `(a e)` of `u`                                          |
| `u.q` in an expression         | `u.q`                                                                  |

In this table, `x`, `r`, and `u` stand for their structural paths, and `c` is the domain of the child. `C` is the constant of `v` by the row "Literal or static finite value" of section 7.4.

The **port layout** is the order of the core ports of a module:

- The domain ports come first: `d$0clk`, then `d$0rst`.
- Then the inputs come, sorted by source name, and then the outputs, sorted by source name. Names sort by byte order.
- From slice 2 on, the leaves of one port follow in packing order. Array index 0, tuple element 0, and the first record field come first, recursively (v0.1, section 2). A `Bool` is one leaf of 1 bit.

`Source.Layout` in Lean and `elab::layout` in Rust define the port layout. `Flatten` and `Vectors` both read it. The layout also owns the expansion of a port into its leaves in packing order. No other module expands a port. An empty leaf or an empty port gives no core port and no schema entry. The layout order is not the byte order of the core names, because the leaves of a port follow in packing order.

The lowering makes the core ports in declaration order, and the leaves of each port in packing order. It charges each leaf before it makes the leaf (section 5.4). It thus makes no list of the leaves before their charges. The core design then lists the ports in the layout order.

From slice 2 on, the memories lower after the registers and before the named `let` values, in declaration order (section 7.6). A memory adds no port, so the port layout, the schema, and the source vectors do not change.

Slice 2 adds the aggregate rows. In this table, `T` is an aggregate type, and each row applies to each leaf of `T`:

| Source                               | Core                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------- |
| `input p: T;` or `output p: T;`      | One core port for each leaf, with the leaf name of section 7.3                            |
| `reg r: T = v;` and `r := e;`        | One `reg` and one `next` for each leaf. The reset constant of a leaf is that leaf of `v`. |
| `wire w: T;` and `w := e;`           | One `let` for each leaf                                                                   |
| A named hardware binding of type `T` | One `let` for each hardware leaf                                                          |
| `u.p := e;` for a child input `p`    | One connection for each leaf of `p`                                                       |
| `u.q` for a child output `q`         | A reference to `q` (section 5.4). Each hardware leaf of it lowers to `u.<leaf name>`.     |

These rules apply to the aggregate rows:

- A binding of a whole resource stays one binding. `S018` counts the resource, not its leaves. A `:=` to a part of a resource, for example `r.a := e;`, is `S017` at the start of the target.
- A port, a `reg`, and a `wire` can have an empty type. An empty port, register, or wire lowers to no core node. An empty register and an empty wire still need exactly one `:=` (`S018`). An empty output needs it too. A register in a combinational module is `S017` first, also with an empty type.
- A static leaf of a bound value lowers to a constant, by the row "Literal or static finite value" of section 7.4.
- A leaf of a reference in a bound value refers to its core name or to its child output. It takes the position of its statement.
- Each kind of statement keeps its order of slice 1. The leaf statements of one binding follow in packing order.
- The reference to a child output names the port by its core name, with its leaf fields. It is not a text.
- A cycle through one leaf is a cycle (`S020`). A dependency between two different leaves of one wire is not a cycle.
- `canonicalize` keeps the order of the ports, so the port layout survives the comparison of `validate`.

Slice 3 adds enum ports. An enum is hardware data with the two leaves `tag` and `payload` (section 5.1). The aggregate rows above apply to it unchanged:

- A port of an enum type has the core ports `op$tag` and `op$payload`, in this order. An empty payload gives no core port.
- A register of an enum type resets each leaf to that leaf of its reset value. A wire and a named binding of an enum type give one `let` for each hardware leaf.
- An enum in an aggregate, for example a record field `f` of an enum type, adds its two leaves at its place in packing order: `p$f$tag`, then `p$f$payload`.
- A memory word of an enum type packs the tag in the low bits and the payload above it (section 7.6).
- A port, a `reg`, and a `wire` of a handle type are `S010`, because a handle type is not hardware data.

A combinational module (`domains()`) has no clock and no reset. A register in it is `S017`. An instance of a clocked child in a combinational parent is `S017`.

After the top instantiation, elaboration runs `Core.check` on the lowered design. Each core node carries the source position of the node that made it. A core `E008` becomes `S020` at that position. Each other core error is a defect of the reference elaborator. The theorem `elab_wellFormed` (section 10.3) excludes it.

The core design is `(design <emitted name of the top> <items>)`. It holds each instantiation that the top reaches, once.

### 7.6 The memory (slice 2)

v0.1 section 5 defines a memory with a synchronous read and one write port. The core memory has a combinational read (core IR spec, decision D4).

These rules define the source memory:

- `mem m: [T; N];` is the syntax of the v0.1 grammar. The brackets belong to the statement, so `[T; N]` is not an array type. `T` is a type expression, and `N` is an expression. The AST dump of the statement is `(mem <name> <type> <expr>)`.
- `mem m: [T; N];` needs a nonempty hardware data type `T` (`S010`) and a depth `1 ≤ N ≤ 16777216` (`S012`). Section 6.2 gives the order of its checks.
- A `mem` in a `fn` without `comptime` is `S004`, because a helper that declares resources is in slice 3. From slice 3 on, a helper can declare a `mem` in the owner of its caller (section 9.4). A `mem` in a `comptime fn` is `S006`. The annotation `in d` is `S004`.
- The word width is `w = data_bits(T)`. It is 1 to 65536 (`S012`).
- The address type is `UInt[A]` with `A = max(1, ⌈log₂ N⌉)`.
- `read_port(m, addr, en)` and `write_port(m, addr, data, en)` are prelude builtins. `addr` has the type `UInt[A]`, `en` has the type `Bool`, and `data` has the type `T` (`S010`). The receiver form `m.read_port(addr, en)` binds the receiver to `m` (section 5.6). Section 6.2 gives the order of the checks and the charges.
- The name `m` binds a memory handle. A memory is never read, so a memory in a `data` context is `S010`, as an instance is. An index or a field of a memory is `S010`. A `let` alias keeps the handle and counts for the same memory. A memory name at a static position is `S005`.
- Each memory has exactly one call of each (`S018`). Each call is a graph effect, so a call in an arm of a hardware conditional or in a structural context is `S016`. A second call gives the same response as the first call. The memory keeps the request of the first call.
- `write_port` returns `()`. `read_port` returns the response: a record of the prelude type `ReadResponse[T]` with the fields `data` of type `T` and `valid` of type `Bool` (section 5.6). A user can shadow this name, because the language reserves no name.
- The memory belongs to the owner that declares it. A memory port call on a memory of another owner is `S017`. This case cannot occur in slice 2 (section 9.5).
- A static address that fits `UInt[A]` but is not below `N` is valid, not `S013`. The rows below give its meaning.

Elaboration lowers `mem m: [T; N]` onto the core memory and two registers. The memories lower after the registers and before the named `let` values, in declaration order. Each memory lowers as one block, in the order of the list below:

- `(mem m (bits w) N d$0clk)`.
- The response registers `m$0rdata` of width `w` and `m$0rvalid` of width 1. Both reset to 0.
- The read enable and the read address are each used twice. The lowering binds them to `(let m$0ren (bits 1) en)` and `(let m$0raddr (bits A) addr)`, as in section 7.4. These request `let` values always exist, also for a constant request. They are not named `let` values of the module.
- `(next m$0rdata (mux m$0ren (read m m$0raddr) m$0rdata))`. A core read out of range gives 0, as v0.1 requires.
- `(next m$0rvalid (and m$0ren C))`. `C` is `(const 1 1)` when `N = 2^A`, else `(icmp ult m$0raddr (const A N))`.
- `(write m 0 waddr wdata (and wen (xor d$0rst (const 1 1))))`. A reset cancels the write.

The block charges each core node before the node exists, in pre-order: the node first, then its operands. Each field of a core name charges its bytes (section 5.4).

The depth `N` is 1 to 16777216, the limit of the core checker (`E005`). The fit rule `S012` rejects a depth outside this range before the lowering, at the start of the `mem` declaration. `tests/source/check/` has a file with `N = 16777216`, which passes, and a file with `N = 16777217`, which gives `S012`.

The registers read the old memory state, so a read and a write of the same word give the old word. This is the read-first behavior of v0.1. Issue #12 changes only the mapping to macros, not this meaning.

A word packs the leaves of `T` in packing order (section 7.5), with the first leaf in the least significant bits. For the leaves `l_0` to `l_(n-1)`, the write data `wdata` is `(concat l_(n-1) (concat ... l_0))`. A word with one leaf is that leaf. The response unpacks the leaf `i` as `(extract m$0rdata o_i w_i)`. Here `w_i` is the width of the leaf, and `o_i` is the sum of the widths of the earlier leaves. `valid` is `m$0rvalid`. A word is one core memory, so its leaves get no core names.

The lowering builds the write data in a loop over the leaves in packing order, from `l_0`. It charges each leaf and each `concat` node before it makes the node. It makes no list of the leaves before their charges. The height rule of section 7.4 binds the temporaries `m$<k>t`. A static leaf is a constant, and an empty leaf adds nothing.

The response is a record node of `ReadResponse[T]` with two parts:

- `data` refers to the word of `m` at the bit offset 0, with the type `T`. When `T` is a scalar, it is a leaf that refers to the word.
- `valid` is a leaf that refers to `m$0rvalid`.

A selection of a part of `data` adds the offset of the part to the offset of the word. For an array, this offset is `k * w_e`, where `w_e` is the width of the element. For a tuple or a record, it is the sum of the widths of the earlier parts. A scalar leaf at the offset `o` with the width `w_l` lowers to `(extract m$0rdata o w_l)`. This rule also holds for a word with one leaf. The rules of section 5.4 for references, typed uses, and bindings handle the rest. A binding of the response binds its hardware leaves as other bindings do, for example `r$data$a` and `r$valid`.

The memory, its two registers, and the two request `let` values keep the names of section 7.2. The nodes and the temporaries of the memory block take the position of the `mem` statement.

A user name alone that equals a core keyword gets the field `0k`. Thus a memory `add` is `add$0k`, and a memory `read` is `read$0k`. A memory cannot have the name `mem`, because `mem` is a source keyword. A role name of such a memory gets no `0k`, for example `add$0rdata`.

The lowering has an oracle at the source level that does not come from either front end (#160). Hand-written source vectors in `tests/source/run/` cover these cases:

- The read latency of one cycle, and the `valid` pulse.
- A disabled read that holds its data.
- A read and a write of one word in one cycle, which reads the old word.
- A read out of range, with `data` 0 and `valid` false, and a write out of range, with no change.
- A reset: the response is `(zero, false)`, the write has no effect, and the words hold.
- A depth that is not a power of 2, and a depth of 1.
- A word type with a record leaf, a `Bool` leaf, and an `SInt` leaf.

LEC (`just lec`) and the differential tests add a second oracle.

## 8. Commands

`silicon-check` gets these commands. The Rust `silicon` gets the same commands with the same output. Only the message text of an error line can differ (section 6.2). The exit codes are those of the core IR spec, section 6.4.2.

| Command                         | Output on success                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| `parse F.si`                    | The AST dump (section 11.1)                                                                    |
| `elab F.si --top T`             | The canonical `.sil` text of the design                                                        |
| `validate F.si --top T OUT.sil` | `ok`. For a mismatch, the first line that differs, and exit code 1.                            |
| `run F.si --top T`              | One output source vector for each input source vector                                          |
| `eval F.si EXPR`                | The canonical serialization of a static expression in the file scope                           |
| `cost F.si --top T`             | `total <units>`, then one line `<emitted name> <units>` for each instantiation, sorted by name |
| `observe F.si --top T`          | One line for each observation record, in evaluation order (slice 2, section 8.2)               |

Each command takes the budget flags that section 5.4 lists. `T` is a top selection in source syntax: a module name, then the static arguments in parentheses. Each argument is a literal. A top selection that does not parse is a usage error with exit code 2. A wrong number of arguments is `S007`. `eval` charges the length in bytes of the serialization of its result, without the final line feed. The charge comes after the evaluation and before the text exists, so an implementation measures the length first. When the fuel that remains cannot pay it, `eval` fails with `S015` at `1:1`, as the design node does for the top selection (section 5.4). Thus the output of `eval` is in `O(F)`. A core error other than `E008` in the output of the reference elaborator is a defect, not a design error. `silicon-check elab` then prints the core error on stderr and exits with code 3. Until phase 5 (#69), `cost` covers only the top selection: its arguments and its parameter types. Phase 5 adds the module bodies, the instantiations with their serialization and digests, the lowering, and the line for each instantiation.

`observe` elaborates like `elab` and prints the observation records instead of the design. It runs the same stages as `elab`: the parse, the checks, the elaboration, the lowering, and the core check of pass 6. The lowering and pass 6 make no records. On success, it prints the record lines and exits with code 0. An empty output is valid. For a rejected design at any stage, it prints the records before the first error, then the error line, and exits with code 1. Thus a record that comes before an error stays visible. A usage error has the exit code 2, and a defect has the exit code 3, as for `elab`. An `S015` of the lowering reports at `1:1`, the top selection, as for `elab`. The usage text of both front ends lists `observe FILE --top T` after `elab`. `elab`, `build`, and `cost` print no records. [ADR 0020](../adr/0020-observation-records-once-per-instantiation.md) gives the reasons.

`validate` reads `OUT.sil` first, so a missing file is a usage error with exit code 2. It then works in these steps:

1. Elaborate `F.si` with the reference elaborator.
2. Parse and check `OUT.sil` with the core checker.
3. Compare `print (canonicalize ...)` of the two designs byte for byte.

`validate` thus also does the work of `silicon-check check` on the compiler output (issue #27). The comparison is in Lean, so no Rust code is on the trusted path of the comparison.

When the reference elaborator rejects the source, `validate` prints that error and exits with code 1. `validate` thus covers an accepted design. For a rejected design, the build produces no artifact. The shared corpus and the generator check that both front ends reject with the same first code, line, and column.

### 8.1 Validation in a build

`silicon build F.si --top T` elaborates in Rust, writes the `.sil` file, runs `silicon-check validate`, and then runs the backend. Validation is on by default. The flag `--no-validate` turns it off for an interactive build. The build prints `validated` or `not validated`. An artifact without validation has the status Trusted (section 13). The LSP never validates.

The Lean core checker is near-linear in the size of the design (issue #23, closed). The time of the Lean elaboration depends on the comptime work of the source, which the fuel bounds (section 5.4).

### 8.2 Observation records (slice 2)

`diagnostic(message, value)` returns `()` and appends one observation record. A record is not a diagnostic of section 6.3. Section 6.2 gives the order of its checks and its charges. Section 9.4 gives the contexts that allow a call of `diagnostic`.

`observe` prints one line for each record, in evaluation order:

```text
(record <line> <col> <emitted> (<frames>) <message> <value>)
(record 12 5 Fifo$16 ((call f 30 9) (call g 41 3)) (string "depth") (int 16))
```

These rules define the fields:

- `<line>` and `<col>` are the position of the call. A receiver call starts at its receiver.
- `<emitted>` is the emitted module name of the current instantiation.
- `<frames>` are the call frames from the module body to the call, outermost first. A frame is `(call <name> <line> <col>)`, with the position of the call. `<name>` is the item name of the called function, also for a call through a function value and for a receiver call. A prelude call, a constant, and a struct use add no frame.
- `<message>` is the canonical serialization of the `String` of section 7.1, for example `(string "depth")`.
- `<value>` is the rendering of the value, by the rules below.

The rendering of a value:

- A static value renders as its canonical serialization of section 7.1.
- A hardware scalar or a hardware leaf renders as `(hw <type>)`.
- An aggregate renders in its container form of section 7.1, with each part rendered.
- A part of a reference renders as the value that it stands for. A part without a hardware leaf renders as its static zero value, and each hardware leaf renders as `(hw <type>)`. The type metadata gives this rendering, with no charge.
- An enum with a hardware leaf renders as `(enum <type> <tag> <payload>)`. This is the form of a static enum value of section 7.1. A static tag renders as an integer, and a static payload as `(uint P n)`. A hardware leaf renders as `(hw (uint W))` or `(hw (uint P))`. When `P` is 0, the payload part is absent. A reference of an enum type renders each of its leaves as a hardware leaf, by the rule above. For example, `(enum (enum root Op ()) 1 (hw (uint 8)))`.
- A handle renders by its kind, as the list below shows. A rendering holds no sampled bits.

| Handle      | Rendering                                                      |
| ----------- | -------------------------------------------------------------- |
| Register    | `(reg <type> <core name>)`, for example `(reg (uint 8) i$2$r)` |
| Wire        | `(wire <type> <core name>)`                                    |
| Output      | `(output <type> <core name>)`                                  |
| Memory      | `(mem (array <word> <depth>) <core name>)`                     |
| Instance    | `(instance <emitted module name> <core name>)`                 |
| Child input | `(input <type> <instance core name> <port name>)`              |
| Domain      | `(domain <name>)`                                              |

In `(input ...)`, the `<port name>` is the source name of the port, not its encoded core name.

Each `InstantiationId` gives its records once, when it elaborates. A done instantiation does not replay its records. A record thus names the emitted module name, not an instance path. This deviates from v0.1 section 9 (decision F15). A structural context makes no record (section 9.4), so a cached constant, alias, specialization, or signature has no record to replay.

A record has no length limit and no truncation, because its charge pays for it (section 5.4). The limits of an error message (section 5.5) do not apply to it.

An error keeps the records before it. Each front end returns the records with both outcomes: Lean through `Elab.observe`, and Rust through `elab::observe`. `elaborate` is a projection of `observe` in each front end.

`eval` prints no records. Its expression belongs to no instantiation. A call of `diagnostic` under `eval` still charges as above, and its `<emitted>` field is `-` for the byte charge. The frames are part of the line that the byte charge measures.

The source suites compare the records (section 11.3):

- The suites `elab`, `run`, `check`, and `budget` compare the `observe` output of both front ends for each file whose text holds `diagnostic`. A `budget` file runs at its limit, with its budget flags. The record lines must be equal byte for byte. For a final error line, the suites compare only the code, the line, and the column, because the message text can differ (section 6.2).
- The `OBSERVE` lines of a file give an oracle outside the two front ends. A human or an agent writes them by hand from this section, and LLVM `FileCheck` checks the `observe` output of each front end.

## 9. Lean definitions of the difficult features

v0.1 has features that are hard to define. This section gives the Lean definition of each. The slices of section 12 bring them in.

### 9.1 `mut` formals and the aliasing rule

The aliasing rule of v0.1 section 2 is static. A mutable root is a `let mut` binding or a `mut` formal. A program has no global variable, no closure, and no reference value. A callee can thus reach a place of the caller only through a `mut` formal. Each mutation of a root is thus visible in the syntax: an assignment with that root, or a `mut` actual with that root.

A `mut` actual that is not a place, or whose root is not a mutable root, is `S008`. A place is a name, or a static index, a `.N` selector, or a field of a place.

The **window** of a pending root:

- For a `mut` actual: its own index expressions and each argument of the same call that evaluates later. For a receiver call, the receiver evaluates first (section 5.6). The window of a `mut` receiver thus holds all explicit arguments, also those that bind to leading `comptime` formals.
- For an assignment `place = e`: the index expressions of the place and `e`.

`S008`: in the window of a pending root `R`, no assignment and no `mut` actual has the root `R`. The check follows the evaluation order, not the binding order. Two `mut` actuals of one call have different roots. `Source.Check` decides this rule on the resolved AST, in pass 4. The `mut` marks of a call through a function value are known only at run time. Pass 5 thus checks the rule again, at run time:

- Each active call frame has a counter for each root. The counters have no charge.
- An assignment and each `mut` actual open the window of their root, after they resolve the root. Each call has `mut` actuals: a named call, a call through a function value, a receiver call, `push`, and `pop`.
- A counter above 0 at the open is `S008` at the `mut` actual or the assignment. Else the open adds 1 to the counter.
- The window of a `mut` actual closes after the last argument of its call evaluates. The window of an assignment closes after its right side evaluates. The close subtracts 1 from the counter.
- A call runs in a new frame, so a window of the caller never holds a mutation of the callee.

Pass 4 reports each conflict that the syntax shows. Pass 5 thus reports `S008` only for a window or a `mut` actual of a call through a function value. A `mut` actual of such a call that is not a place is also `S008` in pass 5. The check of pass 4 cannot see the `mut` marks of a value. The window of a place opens after its root resolves and before its steps, so the indices of the place are inside its window. The open of an assignment target never fails, because an assignment is a statement and no window holds one.

Slice 2 brings the `mut` formals, so it reports `S008` for the first time. `push(l, x)` and `pop(l)` take their list as a `mut` actual, and a receiver call `l.push(x)` has the receiver as its first `mut` actual. The window rule applies to each of these calls. For example, take `fn helper(comptime n: Int, mut xs: List[Int])`. The call `xs.helper(xs.pop())` is `S008`: `xs` is pending when `xs.pop()` evaluates. The plain call `helper(xs.pop(), xs)` is not `S008`.

The evaluator then passes a `mut` actual by value and result. It copies the value of the place into the formal at the call. At the return, it writes the final value of the formal into the live root. The write uses the indices that the place got before the call. `S008` excludes each alias, so this definition gives the same result as an alias. It needs no memory model and no borrow check. The builtins `push` and `pop` are the exception to this rule: they change the place directly (section 5.4).

An error ends the elaboration, so a partial write-back is never visible.

From slice 3 on, a `mut` formal can have a handle type. The copy and the write-back pass the handle, which is an identity ([ADR 0026](../adr/0026-handles-copy-as-identities.md)). A write-back thus changes the resource that the root names, not the resource itself.

### 9.2 Implicit reads

An implicit read is a total function of the context, the expected type, and the value:

```lean
coerce : Context → Option Ty → Value → Except Error Value
```

`Context` has two values: `data` and `raw`. `Source.Elab` gives each position one context. The table is normative and follows v0.1 section 2:

| Position                                                                                                | Context |
| ------------------------------------------------------------------------------------------------------- | ------- |
| An operand of an operator, a condition, a data field selection, and a data index selection              | `data`  |
| A `let` with a data type annotation, an assignment of a data place, and a data return                   | `data`  |
| A data parameter of an ordinary function, a constructor argument at a data field, and the value of `:=` | `data`  |
| An explicit `read(h)`                                                                                   | `data`  |
| The message of `diagnostic` (slice 2)                                                                   | `data`  |
| A `let` without an annotation, and a `let` with a handle type                                           | `raw`   |
| An element of an array literal or of a tuple literal                                                    | `raw`   |
| A `mut` actual, a `:=` target, and the operand of `@TypeOf`                                             | `raw`   |
| A resource-typed formal and a resource-typed result (slice 3)                                           | `raw`   |
| An arm of a hardware `if` or of a hardware `match` (slice 3)                                            | `data`  |
| The scrutinee of a `match` (slice 3)                                                                    | `data`  |
| The value of `diagnostic`                                                                               | `raw`   |
| The first argument of `read_port` and `write_port` (slice 2)                                            | `raw`   |

In a `data` context, `coerce` maps a register handle or a wire handle to a hardware read of its core name. It recurses through arrays and tuples. In slice 2, no array or tuple holds a handle (section 5.1), so this recursion has no effect before slice 3. It does not convert a nominal record. A memory, a domain, and an instance are never read. An input handle in a `data` context is `S017`. In a `raw` context, `coerce` returns the value unchanged.

Slice 2 tests the rows "a data field selection" and "a data index selection". Take a register or a wire of an aggregate type. A read of it gives a reference to the whole resource, with no charge (section 5.4). A field or a static index of it gives a reference to the selected part. A `mut` actual and the value of `diagnostic` stay `raw`. An element of a literal stays `raw` too, so `[r]` for a register `r` holds a handle, and it is `S010` until slice 3. A constructor argument is `data`, so `P(r)` reads `r`.

Slice 1 has handles only as names and as unannotated `let` aliases. Slice 1 has no handle types. Its prelude has no `Reg` and no other handle type, so a use of such a name fails with `S003`. The message names the slice of the feature.

Slice 3 adds these rules:

- The prelude has the handle types of section 5.6, so a `let` with a handle type and a resource-typed formal exist. Their rows are `raw`.
- In a `data` context, the recursion of `coerce` reads each register leaf and each wire leaf of an array or a tuple of handles. A memory leaf or an instance leaf is `S010`, and an input leaf is `S017`, as for a scalar handle.
- A record of handles in a `data` context is `S010`. The text of section 6.2 tells the user to construct the data record from the fields.
- A position with a handle type is `raw`, also in a row that this table gives as `data`. Examples are a constructor argument at a field of a handle type and an element of `push` into a list of handles. An argument at a resource-typed formal and a return at a handle type are `raw` too. Each typed use there keeps the handle (section 5.1). A literal element is `raw` already.
- An arm of a hardware `if` or of a hardware `match` is `data`. A register or a wire there is read, a memory or an instance is `S010`, and an input is `S017`, as in slice 2.
- An arm of a static `if` and of a `match` on a static scrutinee passes its value on. A handle there stays a handle.
- The `@TypeOf` part of the row of `mut` actuals comes with `@TypeOf` in slice 4.

### 9.3 The `@` builtins

Each builtin is a Lean function. None of them makes hardware.

| Builtin        | Lean definition                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| `@TypeOf(x)`   | The type of the resolved place `x`, in the `raw` context. It evaluates only the static keys and indices of `x`. |
| `@typeInfo(T)` | A total function from a normalized type to a `TypeInfo` record, with the kind tags of v0.1                      |
| `@Struct(fs)`  | A structural record type. Its identity is the list of names and normalized field types.                         |
| `@field(x, k)` | The selection of the field or the index `k`, with the rules of an ordinary selection                            |
| `@ports(h)`    | The public ports of the instance `h` as a list of `PortInfo`, in schema order                                   |

`@TypeOf` and `@ports` accept only the operand forms of v0.1 section 2. The pre-check rejects each other form with `S003`. `@typeInfo` and `@Struct` run in a structural context: a graph effect or a diagnostic in their arguments is `S016`.

### 9.4 Effects

The evaluator has a mode and a guard. In a `comptime fn`, the mode is `static`. A hardware operation in the mode `static` is `S011`.

The **guard** has a kind and a nesting depth. The kind is `arm` or `structural`. The arms of a hardware conditional set a guard of the kind `arm`. Each structural context sets a guard of the kind `structural`. Each start of such a context sets the guard to its kind and to the current nesting depth, so the innermost context wins. The start of a guard is O(1).

The mode and the guard follow the calls, so the rules apply through each helper, as v0.1 requires. They also follow a call through a function value. The checks thus find each effect behind a function value at run time, as v0.1 section 2 requires. A function type holds no effect.

These operations are graph effects:

- The declaration of a port, a resource, or an instance.
- A `:=` binding.
- A call of `diagnostic`.
- From slice 2 on, a call of `read_port` or `write_port`.

A graph effect under a guard of either kind is `S016`. A call of `diagnostic` is thus allowed in a module body and in a `comptime fn`, but not in a structural context or in a hardware arm.

In slice 2, only `diagnostic`, `read_port`, and `write_port` can reach a guard. An arm and a structural context are each one expression. A declaration or a `:=` can thus occur there only in a called function. The evaluator rejects a declaration and a `:=` in each function body with `S011`. The earlier passes find most of these first:

- A declaration in a `fn` without `comptime` is `S004` (pass 1).
- A declaration or a `:=` in a `comptime fn` is `S006` (pass 4).
- A `:=` in a `fn` without `comptime` is `S011` (pass 5).

**Helpers (slice 3).** A `fn` without `comptime` can declare a `reg`, a `wire`, a `mem`, and an `instance`, and it can bind with `:=`. These are no longer `S004` and `S011`. A port in a `fn` stays `S004` (F29), and a `comptime fn` keeps `S006`. A helper call that runs a declaration or a `:=` under a guard is `S016` at that declaration or `:=`, by the rule above.

**`:=` targets (slice 3).** A `:=` target is a place whose steps select a whole resource. The static type of the base of each step decides:

- A step on a container of handles selects an element, for example `rs[i] := e;` for an array `rs` of registers. The target is the resource of that handle. The index is static, by the rule of section 5.2.
- A field of an `Instance` handle selects a child port, for example `u.p := e;`, as in slice 1. The target is the child input `p` of `u`.
- A step on another handle selects a part of the stored value, for example `r.a := e;` for `r: Reg[P]`. This is a projection below a handle, so it stays `S017` at the start of the target.
- `S018` counts the resource of the target, through each alias (section 5.6).

**Structural contexts.** In slice 2, the structural contexts are exactly these:

1. Each type expression that the evaluator evaluates. These are the annotations of a `let`, a port, a `reg`, and a `wire`, and the parameter types and the result types. The signature of a function value is one too.
2. The expression forms that make a type: an index of a prelude type or of a struct item, for example `UInt[e]` or `P[e]`, `[T; N]`, and `fn (...) -> R`.
3. A `const` item and a `type` item at their first use, and a `type` statement.
4. A struct use: its arguments, its parameter types, and its field types.
5. The word type and the depth of a `mem` statement.
6. From slice 3 on, the tag type, the tag values, and the payload types of an `enum` item at its first use.

These are not structural contexts:

- `T(x)` and `T()`.
- The argument of `list(T)` and of `data_bits(T)`.
- `static_assert`, `comptime if`, and `comptime for`.
- The arguments of an instance.
- The body of a `comptime fn` that a module body calls.

Each cached result thus has no record: a constant, an alias, a struct specialization, and a signature. A done result needs no replay of records (decision F15).

**Mutations.** These operations are mutations: an assignment to a place, a `push`, a `pop`, and a `mut` write-back. A mutation of a binding from before the guard is `S016`, for both kinds. Each call, each constant, and each struct use nests one level deeper, with a new frame of locals. A binding is thus from before the guard when the mutation runs at the nesting depth of the guard. A function that the arm or the structural context calls can change its own locals. A `mut` write-back runs at the call, so a `mut` actual with a root from before the guard is `S016`.

Thus `let x: [Bool; xs.pop()] = ...` is `S016` at the call `xs.pop()`. Take `fn f(mut n: Int) -> Int`. Then `UInt[f(n)]` is `S016` at the call, by the write-back. The fix is to do the change before the context, to keep the result in a `let`, and to use that name in the context. Phase 4 of slice 2 reports this `S016` in an arm (section 14.2), and phase 8 reports it in a structural context.

**Messages.** Each message of `S016` names the kind of the guard. These texts are normative. Both front ends print them exactly, and a file with an `expected-message` directive pins them (section 11.3). `{x}` is the name of the changed binding, and `{g}` is the name of the called function. For a declaration or a `:=` in a helper (slice 3), `{g}` is the helper that the guarded call names.

| Kind         | Effect       | Message                                                                                                              |
| ------------ | ------------ | -------------------------------------------------------------------------------------------------------------------- |
| `arm`        | Mutation     | a hardware arm changes a binding from before the arm                                                                 |
| `arm`        | Graph effect | a hardware arm has no graph effect such as `{g}`                                                                     |

### 9.5 Resources and owners

A handle carries the structural path of its owner instantiation. A handle that reaches a different owner is `S017`. Ports and module arguments are the only paths between owners. Ports carry data, and module arguments are recursively static. A handle can thus never cross an owner. The check exists only as a guard. In slice 2, no handle is a container element, so a memory handle cannot reach another owner. The rule of `S017` for a memory port of another owner thus has no check and no check file in slice 2.

From slice 3 on, a handle can be an element of a container, a parameter, and a result. It still cannot cross an owner. A static position rejects a handle (`S011`), so no module argument carries one. A helper runs in the owner of its caller, so its resources and its handles stay in that owner. The `S017` check of an owner thus stays a guard, with no check file.

### 9.6 Later features

- **Domains.** After #11, a domain becomes a static value with a clock, a reset, and a policy. The core IR then has more than one clock. The tag inference of v0.1 section 4 becomes a fixed point in `Elab`, with a fuel bound.
- **Packages.** The `ModuleId` gets the real `PackageId`. `Resolve` reads the locked dependency map that Lattice gives (ADR 0006).
- **Contracts.** The actual machine of v0.1 section 7 is the core `step` of the elaborated design and the port schema. It is not a second generated model.

| Output                      | The existing chain: LEC, the differential tests, and `arcilator`                                                                                                        | `just lec`, `just diff` |

### 10.2 Rules for the oracle loop

- **No expected `.sil` by hand.** The reference elaborator gives the expected output. A test author writes only behavior (source vectors) and intent (`FileCheck`).
- **Snapshots are review aids.** An `insta` snapshot is not an oracle for elaboration. Nobody can update the Lean comparison by hand, because Lean computes its expectation.
- **Fast feedback.** `cargo nextest run -p driver --test suites` with a filter on the path runs only the files that an agent touches, against a built `silicon-check`.
- **Localization.** A failed comparison prints the first line that differs: in the AST dump, then in the `.sil` text. The stage of the defect is thus visible.
- **Task shape.** A feature has three commits: the Lean modules with their unit tests, the corpus with its expectations, and the Rust code. The corpus commit comes before the Rust commit, so the Rust task starts with a failing test.

### 10.3 Theorems

These theorems are proven in `lean/Silicon/Source/Proof/`. `doc/trust.md` names the module of each one. A theorem of this kind does not block a slice:

| Theorem            | Statement                                                                                                                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `elab_wellFormed`  | `Cli.elabChecked o src top g = .ok c → ∃ t, Core.check c.design = .ok t ∧ Core.WellFormed c.design`                                                                                                 |
| `static_op_agrees` | A static operation gives `v`. From each state with enough fuel, `Flatten.lower` emits a core row for it on literal operands. That row evaluates to `v`                                              |
| `parse_print`      | `Parse.parseSource N (print a) = .ok a'` with `a'` equal to `a` after position erasure, for the syntax depth `N` at least the length of `print a`, and for an AST that meets the precondition below |
| `names_injective`  | `p.valid → q.valid → encode p = encode q → p = q`, from `decode (encode p) = some p` (section 7.2)                                                                                                  |
| `eval_cost`        | If the elaboration with fuel `f` uses `u` units, then each fuel `f' ≥ u` gives the same result, and each fuel below `u` gives `S015`                                                                |
| `observe_cost`     | `Cli.observeRun` with fuel `f` gives the records `rs` and a result that uses `u` units. Then each fuel `f' ≥ u` gives the same records and the same result, and each fuel below `u` gives `S015`    |
| `leaf_ne_loop`     | For a valid name, `encode ⟨h, pre ++ .elem k :: post⟩ ≠ encode ⟨h, pre ++ .int k :: post⟩`: the leaf name and the loop-frame name with the same `k` differ (section 7.3), from `names_injective`    |

The precondition of `parse_print` has these parts:

- Each name, field, and binder is a source identifier that is not a keyword. This includes the name of a struct, of a struct field, and of a type alias.
- No index is empty.
- No tuple is empty. The printer writes an empty tuple as `()`, which is the unit value or the unit type.
- Each module parameter and each struct parameter has the mode `comptime` (section 5.6).
- A `domains` declaration has at most one name.
- Each assignment and connection target is a place.
- No resource statement is in a `fn` without `comptime`. From slice 3 on, this clause is: no port is in a `fn` without `comptime`.
- Each body has only the statement kinds that the parser accepts in that body.
- No string has a control character other than LF, CR, and tab.
- Each number is below 2^65536.

Position erasure sets each source position to line 0 and column 0. The proof task defines the erasure function and the precondition as a predicate.

The precondition follows the grammar of each slice. Slice 2 adds syntax forms, for example `mut` parameters of a `fn`, indexed places, and `.N` places. The proof of `parse_print` works constructor by constructor, and it names the token sets of the parser. Each new form thus needs edits in `Print`, in the precondition, and in the proof (`Parse/Runs.lean`, `Parse/Expr.lean`, and `Parse/Stmt.lean`). A place is a name, or a field, an index, or a `.N` selector of a place. The clause "each target is a place" uses this definition, and the lemma `Runs.stmt_place` covers each such target. `lake build` checks the proof, so the feature phase that adds a form also updates the proof. The proof covers the `mut` parameters of a `fn` and the receiver calls. The first clause of the precondition covers the function name of a receiver call. A receiver call is not a place, so it is never a target.

`elab_wellFormed` holds by construction, because `Cli.elabChecked` returns a design only with the proof of the core checker. `Cli.elabRun` does not run the core checker, so the theorem does not apply to it. `static_op_agrees` covers each row family of the scalar table of section 7.4 (slice 1). These are the wrapping operations, the comparisons, `==` and `!=` on `Bool`, `&&`, `\|\|`, `~`, unary `-`, and `!`. They also include the shifts by a static `Int` or `UInt` count, `resize`, and `reinterpret`. The proof runs `Flatten.lower` itself, so a change of `lower` breaks it. The claim about `lower` holds for each state with enough fuel. The evaluator runs `&&` and `\|\|` by a short circuit in `Eval.eval`. For these two, the theorem takes `v` as the Boolean operation. The theorem also covers the rows of slice 2 that walk an aggregate by leaf: `==`, `!=`, and a hardware `if`. For these rows, the operands are hardware pairs with constant leaves, and the condition of an `if` is a constant. The static result of `==` is the conjunction of the result `s` of the static pairs and the static `==` of each hardware pair. `Eval.mux` makes the same `mux` node for two scalar arms, so the `mux` row also holds for a scalar `if`. For `==` and `!=`, the claim about `lower` holds for at most 60 pairs. Then the `and` chain stays below the height 64, so no temporary binds. The theorem takes the pairs and `s` as given. It does not prove that the walk of section 7.4 makes them. Issue #286 tracks the walk, the chains above 60 pairs, and the shared condition. The stronger theorem, that the lowering never returns a defect, is issue #147.

Slice 3 adds syntax forms: the `enum` item, variant paths, the `match` expression, and its patterns with binders. Each needs edits in `Print`, in the precondition, and in the proof, as above. Phase 1 of section 14.3 adds the keywords `enum` and `match` and the tokens `=>` and `::` to the token sets of the proof. Each feature phase then adds only its case. The clause "each name, field, and binder" covers the variant names and the binders of a pattern. `static_op_agrees` gets the rows of `match` in phase 9a, after #223 covers the rows of slice 2 by leaf.

A declarative type relation with `check_sound` and `check_complete` for the pre-check comes later. It follows the model of the core checker.

### 10.4 Oracles against a shared misreading

Both front ends come from the same prose. They can agree and both be wrong. These oracles do not come from either front end:

- **Source vectors by hand.** The test author writes the expected outputs.
- **Lean models as references.** A small corpus has designs with an independent Lean model, for example the counter of the v0.1 README. A differential test compares the model with the core interpreter of the elaborated design on random inputs.
- **Metamorphic tests.** A change that keeps the meaning keeps the canonical `.sil` text, up to an explicit name correspondence. Section 11.3 lists the changes and their oracles.
- **The human gate.** The Lean `Source` modules define the language. A change to them needs the approval of the user, as [ADR 0009](../adr/0009-cross-vendor-review-before-merge.md) gives for language design.

## 11. Formats, tests, and the generator

### 11.1 The AST dump

The AST dump is one S-expression for each item. Each node prints as `(<constructor> <fields>)`, with the constructor names of `Source.Syntax` in lowercase. The dump has no source positions and no comments. Each item starts a new line. A string prints in double quotes with the escapes of the grammar. Each item ends with one LF, so a file without items gives an empty dump. The module doc of `lean/Silicon/Source/Print.lean` gives the full byte format.

### 11.2 Source vectors

A source vector has the form of a core vector (core IR spec, section 6.4.3), with source names and source values:

- An input line lists the reset of the domain as `d$0rst`, then each input in schema order. The reset is a `Bool`. A combinational top has no reset entry, and a clock port has no entry.
- The schema order is the port layout of section 7.5 without the clock. It equals the order of the core ports. A vector uses the source name of a port, also when its core name has the field `0k`.
- A `Bool` value is `true` or `false`. A `UInt` value is decimal. An `SInt` value is decimal with `-` for a negative value.
- An empty port has no entry.

Slice 2 adds the leaves:

- The schema has one entry for each leaf of each port, in the port layout. The reset entry `d$0rst` comes first.
- The name of an entry is the source name of the port, then one selector for each level. A selector is `.field` for a record field, or `.index` for an array index or a tuple element. Examples are `pkt.data`, `pkt.hdr.0`, and `v.3`. An entry never has the field `0k`.
- A port with the field `0k` keeps its source name. Thus `add.x` is the leaf `x` of the port `add`.
- Each leaf value has the form of its scalar type, as in slice 1.
- An empty leaf has no entry.
- `Source.Vectors` maps each leaf entry to its core port through the port layout. The line format stays the core format, and a leaf name is one token of it.

Slice 3 adds enum ports. An enum port has the two entries `<port>.tag` and `<port>.payload`, for example `op.tag` and `op.payload`. Each value is a `UInt` in decimal. A vector can thus give a tag that no variant declares. An empty payload has no entry.

`Source.Vectors` maps a source vector to a core vector through the port schema, and back. `run` uses the core interpreter. The start state is all zero, as in section 6.4.3 of the core IR spec. This start state is a test convention, not semantics.

The initial state of a source design is free, as in section 5.2 of the core IR spec. A real register has no defined value before its first reset. A design that needs a defined start applies its reset. This replaces v0.1 section 4 on purpose, which starts the native registers at their reset values. The meaning of a source design is the core IR `step` of its elaboration, so the source cannot promise more than the core IR. A file of `tests/source/run/` has a register with a nonzero reset value. Its vectors show the register before the first reset edge, with the value 0 of the test convention, and its reset value after that edge. A second register of type `SInt[8]` has the reset value `-1`. Its vectors show `-1` after the first reset edge.

The metamorphic tests compare two programs that differ by one change. The oracle depends on the effect of the change on the structural paths (section 7.3).

These changes keep each structural path. The canonical `.sil` text must stay equal byte for byte:

- The order of the items.
- The order of two adjacent `:=` statements without calls. A `:=` binds no name, so the versions stay equal.
- Redundant parentheses.
- A receiver call against its plain call, when the function has no leading `comptime` formal (slice 2, #117). Then both forms evaluate in the same order.
- A `type` alias against the type that it names (slice 2, #117).
- A struct without parameters against a struct with one fixed parameter (slice 2, #117).

These changes rename structural paths. Byte equality thus does not apply directly:

- The name of a local or a loop binder.
- A `comptime for` against its body written out by hand.
- A call of a helper against its body written out by hand.

For these changes, the test gives an explicit name correspondence from the core names of the first program to those of the second. The harness renames the first core design with it, then compares the canonical `.sil` text byte for byte. A correspondence must be a bijection on the core names, and the ports must map to themselves. When a test has no complete correspondence, LEC compares the two designs instead. The current LEC matches registers by name, so the correspondence must at least cover the registers.

### 11.4 The program generator

The crate `srcgen` makes source programs. `cargo xtask diff-si` runs it. [ADR 0018](../adr/0018-source-generator-crate.md) gives the limits of its static evaluator. It has four modes:

1. **Lift.** It renders each core design of `core-ir` `gen` as a source program. A port can be a tuple, an array, or a record of a generated struct. A memory with one registered read and one write that the reset disables becomes the memory of section 7.6. The oracle: the elaborated program and the original design give the same outputs on random source vectors. The vector map follows the port layout of section 7.5.
2. **Typed.** It makes well-typed programs of the current slice directly from types. These programs have comptime parameters, comptime functions with structural recursion, loops, branches, helpers, registers, and instance trees with arguments. Each wire reads only earlier values, so no cycle occurs. The oracle: `validate` passes, and `eval` and `cost` agree. The `observe` output of both front ends is equal. The `diagnostic` records of the output equal the records that the generator predicts.
3. **Mutation.** It applies one mutation to a typed program, for example the deletion of a binding or a change of a width. The oracle: both front ends report the same first code, line, and column. Some kinds reach `S008`, for example a mutable root that a `pop` argument changes in the window of a receiver call. Other kinds reach `S016`, for example a `diagnostic` call in a hardware arm or in a width. The generator predicts a code only where the pass order makes it certain.
4. **Budget.** It reads the cost of a typed program from `cost`. The oracle: the fuel equal to the cost succeeds, and one unit less gives `S015`.

A typed program also comes with a twin: the same program with each comptime construct written out. The oracle: the two programs give the same outputs on random source vectors.

Slice 3 extends the generator in its typed mode only, in the scope of [ADR 0018](../adr/0018-source-generator-crate.md) and [ADR 0024](../adr/0024-generator-converts-finite-module-arguments.md):

- The typed mode makes enums, constructors, `match` on integers, Booleans, and enums, and helpers that declare resources and take handles.
- No enum is a module argument. An enum argument has the digest form of the emitted name, which ADR 0024 does not give the generator.
- No `diagnostic` has a handle leaf in its value. Its rendering holds the core path with call-site numbers, which ADR 0023 does not give the generator.
- The mutation mode gets kinds that reach `S021`, for example a deleted arm or a deleted `_`.
- The budget mode reads the cost of programs with a `match`.
- The lift mode does not change, because `core-ir gen` makes no enums.

The generator has a fixed set of seeds for `just ci`. A failure prints the shrunk program and its seed.

## 12. Slices

A slice is a set of features with its own closed oracle loop. A slice is done when each item of its list holds and `just ci` passes. Its milestone review (section 14, phase 12) must have no open blocker. The grammar grows with each slice. The keywords are those of the v0.1 grammar from slice 1 on, and no slice adds a reserved identifier. Slice 3 is the exception: it adds the keywords `enum` and `match` and the token `=>` (ADR 0021). The parser of a slice rejects the syntax of a later slice, for example `import` or `struct`, with `S004`. The prelude of a slice has only its own names. A use of a prelude name of a later slice, for example `List`, thus fails with `S003` in the resolver.

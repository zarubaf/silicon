# Front end

- Status: proposed
- Date: 2026-10-09

## 1. Purpose and scope

This spec defines the front end of Silicon: the stages from a `.si` file to core IR. It covers build step 4 of [the architecture](../architecture.md), the source language and the elaborator.

The goal: a source design has one meaning, which a Lean reference elaborator defines. The Rust front end agrees with that meaning on each run. A mechanical oracle checks each stage.

The language is the v0.1 proposal in [`doc/reference/`](../reference/SILICON_SPEC.md). This spec keeps all its features. It orders them into slices (section 12). Each feature gets a Lean definition in the reference elaborator. Section 9 shows how the features with the highest risk get one.

These items are out of scope. Each item has a follow-up issue (section 15):

- More than one clock domain, domain maps, and asynchronous reset. Issue #11 blocks them.
- Synchronous read ports in the core IR. Issue #12 adds them. Section 7.6 lowers the source memory onto the current core memory.
- The design of contracts (`conforms`, `using`) and certificates. They come after packages. The parser reserves their syntax now.
- The LSP and `salsa`. They come in build step 5.

## 3. The meaning of a source design

A build has a `.si` file and a top selection. A top selection names a module and its static arguments, for example `Counter(8)`. The Lean function `elaborate` maps them to a core design or to an error:

```lean
elaborate : Source → TopSelection → Budgets → Except Error Core.Design
```

The meaning of a source design is the semantics of the core IR (core IR spec, section 5) of `canonicalize (elaborate src top budgets)`. The front end adds no second semantics. Elaboration exists only to produce core IR. The core IR then has its proven semantics, its interpreter, its reference lowering, and LEC.

These consequences follow:

- The Lean `Source` modules are the normative definition of the language. The prose of v0.1 is input for them, not a second authority. A disagreement between them is a bug in the Lean modules or a language decision for the human gate.
- A port schema maps each source port to its core port. Source vectors (section 11.2) and, later, contracts use it.
- Elaboration does no optimization. An optimization is a core-to-core pass, and LEC checks it.

## 4. Pipeline

```text
.si text
  │ syntax: lexer, rowan tree types                 Lean: Source.Lex
  │ parse: lossless tree with recovery, typed AST   Lean: Source.Parse, Source.Print
  │ resolve: item table, scopes, names               Lean: Source.Resolve
  │ typeck: generic pre-check                       Lean: Source.Check
  │ elab: static evaluator, instantiations,         Lean: Source.Value, Source.Eval,
  │       checks for each instantiation                   Source.Elab
  │ elab: lowering to core IR, names                Lean: Source.Flatten, Source.Names
  ▼
core IR (.sil) → existing chain: check, run, backend-circt, reference lowering, LEC
```

### 4.1 Stage interfaces

Each stage is a pure function of its inputs. Each stage reports the first error of its pass in the order of section 6.

| Stage     | Input                                | Output                                                                               |
| --------- | ------------------------------------ | ------------------------------------------------------------------------------------ |
| `syntax`  | Bytes                                | Tokens                                                                               |
| `parse`   | Tokens                               | A lossless syntax tree with errors, and an AST with source spans. Or `S001`, `S004`. |
| `resolve` | AST                                  | A resolved AST: each name points to its declaration. Or `S002`, `S003`.              |
| `typeck`  | Resolved AST                         | The same AST, or `S005` to `S008`                                                    |
| `elab`    | Resolved AST, top selection, budgets | A core design, or `S008` (section 9.1) or `S010` to `S020`                           |

The resolved AST is the boundary between the stages that work on all code and the stages that work on instantiations. `elab` holds no syntax tree. It reads the resolved AST only.

### 4.2 The generic pre-check and the checks for each instantiation

A width such as `UInt[W + 1]` has no value before `W` has a value. A type check before elaboration thus cannot check widths. The work splits into two parts:

- **Generic pre-check (`typeck`).** These checks need no static values: the syntactic stage rule, placement, arity, and the aliasing rule of `mut` places. They run on each item, also on an item that no instantiation uses. An agent thus gets these errors without a top selection.
- **Checks for each instantiation (`elab`).** These checks need static values: types and widths, fit, the dynamic stage rule, effects, resources, and bindings. They run on the code that an instantiation executes. A `comptime if` checks only its selected branch, as v0.1 section 1 requires.

Lean has the same split: `Source.Check` and `Source.Elab`.

### 4.4 Rust crates

| Crate           | Layer | Content                                                                                |
| --------------- | ----- | -------------------------------------------------------------------------------------- |
| `core-ir`       | 1     | Unchanged                                                                              |
| `syntax`        | 2     | Lexer, `rowan` syntax tree, typed AST wrappers, source printer, the generator `gen`    |
| `parse`         | 3     | The parser with recovery, the AST, and the AST dump                                    |
| `resolve`       | 4     | Item table, scopes, and the resolved AST                                               |

| `backend-circt` | 7     | Unchanged                                                                              |
| `driver`        | 8     | The `silicon` CLI                                                                      |

The module `gen` is behind the cargo feature `gen`. Only `xtask` and the tests use this feature, as in `core-ir`.

These rules apply to the Rust front end:

- **Query shape.** Each stage is a pure function. Its key is a file and an item, or an `InstantiationId`. No stage has global mutable state. `salsa` replaces the plain calls when the LSP starts.
- **Determinism.** The crates `resolve`, `typeck`, and `elab` use no `std::collections::HashMap` and no `HashSet`. A clippy `disallowed-types` rule enforces this. An output order comes from the evaluation order or from a sort, never from an address or a hash.
- **Recovery.** The parser and the resolver continue after an error, for the LSP. The first error in the order of section 6 must equal the error of Lean. Later errors have no oracle.
- **Interfaces.** Each crate exports a small interface. `elab` exports `elaborate`, `eval`, `cost`, and the schema.

### 4.5 Preparation for an Aeneas proof

The end goal is a proof of the Rust front end against the Lean reference elaborator. Aeneas translates Rust code to Lean, and a proof then relates the translation to the reference. Issue #10 plans the same proof for the core IR checker and interpreter. Until that proof exists, `silicon-check validate` on each run is the oracle.

Aeneas reads the MIR of the compiler through Charon. It supports a subset of safe Rust. These limits of Aeneas matter for the front end:

- No `unsafe` code, no interior mutability (`Cell`, `RefCell`), and no shared ownership with mutation (`Rc`, `Arc`).
- No trait objects (`dyn`). Support for closures, iterator adapters, and complex trait code is partial.
- Only a part of the standard library has a Lean model. `Vec` and `Box` have one. `HashMap`, external crates, and most iterator adapters do not.
- A loop becomes a recursive Lean function. A panic and an arithmetic overflow become an error result.
- Borrows inside data structures and nested mutable borrows have limited support.

The Rust front end thus follows these rules where they cost little:

- The **elaborator core** is the code of `elab` from the resolved AST to the core design: `Value`, `Eval`, `Elab`, `Flatten`, and `Names`. It uses plain `enum` data, `match`, `Vec`, `Box`, and indices into a `Vec` for arenas. It has no trait object, no closure that captures a mutable value, no iterator adapter chain, and no external crate.
- The elaborator core returns `Result` for each error and does not panic. It passes the fuel as an explicit argument, so its loops have a visible bound.
- The resolved AST is a plain owned tree. It holds no `rowan` node and no `salsa` handle.
- `salsa`, the LSP, the diagnostics, and the `driver` stay outside the elaborator core. They call it as a pure function.

These parts cost a lot to adapt. They stay outside the first proof, and validation keeps them covered:

- **The syntax tree and the parser.** `rowan` uses `Rc` and `unsafe` code. A parser for Aeneas needs a second, plain tree. The proof of the parser comes after the proof of the elaborator core, or the parser keeps validation as its oracle.
- **Static integers of any size.** The elaborator core uses an integer type of its own with a small interface. The proof can take a Lean model of this interface as an assumption, and `doc/trust.md` lists it.
- **The SHA-256 digest.** The proof takes it as an opaque function with the Lean `Sha256` as its model.

## 5. Elaboration

### 5.1 Values

A value of the evaluator has one of these forms:

- **Static value.** An integer (`Int`, and `Nat` as a checked `Int`), a Boolean, a string, a type, a named function, or a finite static integer of type `UInt[W]` or `SInt[W]`. Containers of static values come in slice 2.
- **Hardware value.** A typed tree of core operations over core names. Its source type is `Bool`, `UInt[W]`, or `SInt[W]`. Aggregates come in slice 2.
- **Handle.** A reference to a register, a wire, a memory, an instance, or a child input. Its identity is its structural path (section 7.3).

A finite static value uses the same `BitVec` function as the core operation. The Lean definitions share the function, so `static_op_agrees` (section 10.3) is nearly definitional.

### 5.2 Evaluation order

Elaboration executes statements in source order. The order of the operands, the arguments, and the branches is the order of v0.1, section 1. This order is normative. It fixes the first error, the cost, and the core names.

### 5.3 Instantiations

An `instance u = M(args);` statement elaborates as follows:

1. Evaluate the arguments from left to right. Each argument is a recursively static value.
2. Make the `InstantiationId`: the `ModuleId` of `M` and the canonical serialization of the arguments (section 7.1).
3. If the `InstantiationId` is in progress, report `S019` at the statement.
4. If the `InstantiationId` is done, use its result. Nothing more charges.
5. Otherwise, mark it in progress, elaborate `M` with the arguments now, and mark it done.
6. Bind `u` to an instance handle in the parent.

The table of instantiations is normative, as the table of constants is. The evaluation order fixes which use of an `InstantiationId` comes first. Both front ends thus elaborate and charge the same instantiations, and no implementation cache can change a result. A child elaborates before its parent continues. The first error is the first error in this depth-first order.

An instantiation elaborates in two steps:

1. It executes the module body.
2. It checks the bindings (`S018`) of its resources.

After the top instantiation, the elaborator lowers the design and runs the core checker on it (section 7.5).

### 5.4 Budgets and the cost model

One elaboration has two budgets. All parts of the elaboration share them, in the normative evaluation order: the top selection, each instantiation, and each constant. An `eval` command is its own elaboration. The defaults are normative. The budget values are build inputs, and the build record names them.

| Budget        | Unit                                                                | Default   | Flag      |
| ------------- | ------------------------------------------------------------------- | --------- | --------- |
| Fuel          | Cost units                                                          | 100000000 | `--fuel`  |
| Nesting depth | Active calls, instantiations in progress, and constants in progress | 1000      | `--depth` |

The parse stage has one budget of its own: the **syntax depth** N. It bounds the depth of brackets and the height of an expression or a type (section 6.2). Its default is 4096, and the flag `--syntax-depth` sets it to a value from 1 to 65536. Another value is a usage error with exit code 2. Like the other budgets, it is a build input, and the build record names it. Compilation and validation use the same value. The default is far above the depth of written or generated code, so it is not a limit of the language.

The syntax depth bounds the native stack of each front end:

- The lexer rejects a bracket above the depth N, so the recursion of a parser stays bounded for any input.
- A parser builds a chain of binary operators, unary operators, fields, calls, or `else if` branches in a loop.
- After the parse, each recursive pass over the AST goes at most about 2N deep: N for the blocks and N for an expression.
- The Rust front end runs on a thread with a stack for the depth N. When the machine cannot give this stack, the command fails with exit code 2 before it parses.
- Each front end has a test at the default limit, a test at the depth 65536, and a test with 1,000,000 open brackets. Each gives the expected result and no stack overflow.

The cost model:

- Elaboration charges one cost unit before it evaluates an expression node.
- It charges one cost unit before it executes a statement. A block is a statement.
- A `comptime for` charges its statement once, and the sum of the sizes of its two bounds for the range. Each iteration then charges the size of its loop value before it binds it, and its body block charges once.
- A call charges its expression node. The body block of the callee charges as a statement.
- A type expression charges as an expression.
- An operation that makes a value charges a bound on the recursive size of that value, known before the operation runs. The bound holds up to a constant factor: `2^32 * 2^32` charges one word and makes two. A unary operation charges the size of its operand. An addition, a subtraction, and a bitwise operation charge the sum of the operand sizes. A conversion charges the operand size plus the result size. An operation that reads a value in full, for example a comparison or a serialization, charges its recursive size.
- An operation that only refers to a value charges no size: a name, a field selection, an index, and `len`.
- A static condition, a static `&&` or `||`, and a static `if` that selects a value charge only their node. An `if` or a name that selects an existing value passes the reference on, so a later binding of it is a copy.
- A typed use converts a static integer to a finite value. These are typed uses: an annotation, an assignment, an argument, a return, a constant, `T(n)`, and an operand next to a finite operand. The copy comes first, then the conversion charge. A use of the same type charges no conversion.
- A call of a builtin (`resize`, `reinterpret`, `static_assert`, `error`) or of a constructor `T(x)` charges the sizes of its arguments as copies, before the type check and the conversion.
- An explicit block `{ ... }` is one statement and charges once. The body of a call, each `comptime if` branch, and each loop iteration charge once each. An assignment target charges nothing.
- A copy charges the recursive size of the value. These are copies: a binding of an existing value, an argument, a return, a `mut` write-back, a `push`, and a `pop`. A binding of a value that its expression just made is not a copy.
- A serialization charges its length in bytes, and the decimal form of an integer charges the square of its size. The emitted name of an instantiation charges its length in bytes too.
- A multiplication, a division, and a remainder of static integers charge the product of the operand sizes. A left shift charges the size of its result. A right shift charges the size of its operand, because it reads the operand in full.
- An `instance` statement charges the recursive size of its arguments, also when the `InstantiationId` is done.
- A hardware operation makes one node and charges 1 plus the number of its operands. Its operand trees are shared, not copied. `&&`, `||`, and `if` on hardware values are hardware operations.
- The `cost` command attributes each charge to one instantiation. The parent pays for an `instance` statement, its serialization, and the emitted name of a new child. The units of an instantiation do not include those of its children. The charges of the top selection belong to no instantiation, so `total` can exceed the sum of the lines.

The recursive size of a value counts each node and each payload, over all nested values:

- An integer has the size 1 for each 64-bit word of its magnitude, and at least 1. A finite value of type `UInt[w]` or `SInt[w]` has the size 1 for each 64-bit word of its width `w`, and at least 1. A Boolean, a handle, and a named function have the size 1.
- A string has the size 1 plus its number of characters.
- An array, a list, a tuple, and a record have the size 1 plus the recursive sizes of their elements.
- A type has the number of nodes of its normalized term, plus the size of each integer in it: `UInt[8]` has the size 2. A hardware value has the number of nodes of its tree without names.

An implementation can share immutable parts of a value. The charge is the recursive size all the same, so acceptance does not depend on the sharing.

- The lowering charges one cost unit for each core node that it emits. A core node is a design, a module, a port, a statement, a reset, a connection, or an expression node.
- The lowering runs in this order, which fixes the position of an `S015`: the instantiations in the order in which they finish. In a module: the module, the domain ports, the ports, the registers, the named `let` values, each `:=` binding with its connections, then the instances.
- The lowering units of a module count toward its instantiation. The design node and the name of the top count toward no instantiation.
- The lowering charges one cost unit for each core node that it emits. Each field of a core name charges its length in bytes, at least 1. A made field that holds an integer charges the square of the size of the integer, at least 1.

This section gives the principles of the cost model. `Source.Eval`, `Source.Elab`, and `Source.Flatten` are its normative definition: the exact charge of each operation, the order of the charges, and the position of each `S015`. The Rust elaborator matches them through `cost` and the corpus, not through this prose. The charge of an operation is known from the sizes of its operands, before the operation runs. When the fuel cannot pay a charge, elaboration fails with `S015` at the node of that charge. The operation then does not run.

When the nesting depth goes above its limit, elaboration fails with `S015` at the call, the `instance` statement, or the constant use that goes above it. The nesting depth bounds the native stack of the Rust elaborator. Totality does not need it.

A top-level `const` evaluates once, at its first use. A table of constants holds each constant with one of three states: not started, in progress, or done with its value. This table is normative, because the first use fixes the order of the evaluation:

- A use of a constant in the state "in progress" fails with `S019` at that use. This rejects a constant that depends on itself, directly or through other constants.
- A use of a constant in the state "done" gives its value and charges only the use.
- A use of a constant in the state "not started" sets it to "in progress" and evaluates it.

The Lean evaluator `Eval` is total by the fuel alone. Each step charges at least one cost unit, and the fuel never grows. Proofs can thus use `Eval` directly.

### 5.5 Resource bounds

This section lists the paths by which a source could use resources. For each path, it states the bound. `F` is the fuel.

- **Evaluation work and memory.** Each operation charges the recursive size of each value that it makes, copies, or reads in full. An implementation without sharing thus does work and allocates memory in `O(F)`. Sharing only lowers the memory. The printing of the result of `eval` and of an error message is outside this bound. An error message prints at most 256 bits of an integer and 64 characters of a string.
- **Nested aggregates.** A value that holds another value twice has at least twice its recursive size. A chain of such values thus doubles its charge at each step.
- **Static integer arithmetic.** A product grows the size additively, and its work is in the charge. A shift charges its result, so `1 << k` with a large `k` fails before it runs.
- **Collections and strings.** A copy, a concatenation, a comparison, and a serialization charge the recursive sizes. A `push` and a `pop` charge the recursive size of the element.
- **Types.** A generated record type (slice 4) has the recursive size of its normalized term, so nested `@Struct` calls pay like nested aggregates.
- **Instantiations.** A new `InstantiationId` elaborates once and charges its body. A repeat charges only its `instance` statement and its arguments. A tree of distinct instantiations thus costs at least one unit for each node. A shared hierarchy costs one elaboration for each distinct `InstantiationId`.
- **Output size.** Each emitted core node charges one unit, and each user field of a core name charges its length in bytes. A made field that holds an integer has at most 20 bytes for each unit of its charge. Each `$` separator belongs to a paid field. The output thus has at most `F` nodes and `O(F)` bytes of names. The temporaries of section 7.4 keep it also linear in the source.
- **Constants.** Each constant evaluates once, and a cycle fails with `S019`. A use refers to the value, and a copy of it pays its recursive size.
- **Stack.** The nesting depth bounds it.
- **Front-end passes before elaboration.** The lexer and the parser are linear in the source. The resolver and the generic pre-check are linear up to a factor `log n` for name lookups in ordered maps, which keep the result deterministic. `S008` is the exception. A simple check of `S008` is quadratic in the size of one call. A counter for each root makes it linear.
- **After elaboration.** `canonicalize` sorts, in `O(n log n)` for `n` core statements. The Lean core checker is not yet near-linear. Issue #23 tracks this. It is the one path whose work grows faster than the output.

The oracle of the cost model is the command `cost` (section 8). Both implementations print the same total and the same units for each instantiation.

## 6. Errors

### 6.1 Codes

Rust and Lean use the same codes. A test fails when the two front ends report different first codes or different lines for one file.

| Code   | Pass | Rule                                                                                                                                                                                                                                                                 |
| ------ | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `S001` | 1    | The file is valid tokens, and it matches the grammar. Brackets nest at most the syntax depth N (section 5.4). An expression or a type has a height of at most N. The value of a number literal is below 2^65536. A computed static `Int` or `Nat` has no such bound. |
| `S002` | 2    | A name is unique in its scope. A declaration can shadow a prelude name, because the language reserves no name.                                                                                                                                                       |
| `S003` | 3    | Each name resolves to a declaration. A position that needs a fixed kind gets a name of that kind.                                                                                                                                                                    |
| `S004` | 1    | The syntax belongs to the current slice. The keywords are those of the v0.1 grammar (section 12).                                                                                                                                                                    |
| `S005` | 4    | A static position does not name a port, a register, a wire, a memory, or an instance.                                                                                                                                                                                |
| `S006` | 4    | Placement: a module body has no `return`. A `comptime fn` declares no port, resource, or instance, and has no `:=`.                                                                                                                                                  |
| `S007` | 4    | A call, an instance, a type family, and a constructor have the number of arguments of their declaration.                                                                                                                                                             |
| `S008` | 4, 5 | A `mut` actual is a mutable place. No mutation of a pending root occurs in its window (section 9.1).                                                                                                                                                                 |
| `S010` | 5    | Type rule: operands, conditions, assignments, arguments, returns, and bindings have the required types.                                                                                                                                                              |
| `S011` | 5    | Stage rule: a static position gets a static value. A `comptime fn` makes no hardware.                                                                                                                                                                                |
| `S012` | 5    | Fit rule: a value fits its finite type. A `Nat` is not negative. A width is 1 to 65536. A memory depth is 1 to 16777216.                                                                                                                                             |
| `S013` | 5    | Static fault: no division by zero, no negative shift count, no static index out of range, no `pop` of an empty list.                                                                                                                                                 |
| `S014` | 5    | A `static_assert` condition is true. No `error` call executes.                                                                                                                                                                                                       |
| `S015` | 5    | Elaboration stays in its fuel and its nesting depth.                                                                                                                                                                                                                 |
| `S016` | 5    | Effect rule: an arm of a hardware conditional has no graph effect (section 9.4).                                                                                                                                                                                     |
| `S017` | 5    | Resource rule: a `:=` target is a wire, a register, an own output, or a child input. An input handle is never read.                                                                                                                                                  |
| `S018` | 5    | Binding rule: each wire, register, output, and child input has exactly one binding.                                                                                                                                                                                  |
| `S019` | 5    | Identity rule: an instantiation and a constant do not depend on themselves. Two identities do not share a core name.                                                                                                                                                 |
| `S020` | 6    | The lowered design has no combinational cycle.                                                                                                                                                                                                                       |

A file that is not valid UTF-8 is a usage error with exit code 2. The core IR spec has the same rule (section 6.4.2).

### 6.2 Report order

Both front ends apply the passes in order. They stop at the first pass with an error.

| Pass | Codes                                                                     | Order in the pass                              |
| ---- | ------------------------------------------------------------------------- | ---------------------------------------------- |
| 1    | `S001`, `S004`                                                            | Position                                       |
| 2    | `S002`                                                                    | Position                                       |
| 3    | `S003`                                                                    | Position                                       |
| 4    | `S005` to `S008`                                                          | Position                                       |
| 5    | `S008` at a call through a function value (section 9.1), `S010` to `S019` | Evaluation order (section 5.2 and section 5.3) |
| 6    | `S020`                                                                    | Position                                       |

Position order is the lowest line, then the lowest column. In pass 5, the first error in the evaluation order wins. `S018` comes at the end of the body of its instantiation. In one instantiation, the `S018` errors compete by position.

The position of an error is:

- `S001`: the first token that does not match, or the end of the file.

- `S001` for a number literal above its limit: the literal.

- `S001` for the brackets: the first `(`, `[`, or `{` at the depth N + 1. The lexer marks this bracket as an error token. The depth counts all three kinds of brackets together.

- `S001` for the height: the first token of the first outermost expression or type, in position order, whose height is above N. This check runs only after pass 1 finds no other error. An outermost expression or type is not part of another expression or type. The height of a leaf is 1, and each node of the AST adds 1. Parentheses make no node.

- `S002`: the name in the second declaration.

- `S004`: the reserved token, or the first token of the construct.

- `S008`: the second mutation of the root.

- `S015`: the node of the charge, or the node that goes above the budget.

- `S010` to `S014`, `S016`, and `S017`: the start of the node whose evaluation fails.

- `S018`: the second binding. If there is none, the declaration of the resource. For a child input, the `instance` statement.

- `S019`: the `instance` statement, the use of the constant in progress, or the second declaration with the same core name.

- `S020`: the source position of the core node with the lowest source position on the cycle.

- All other errors: the start of the form that breaks the rule.

The error line has the form of the core IR: `error[S010]: 12:5: <message>`. The message names the instantiation path, as v0.1 section 9 requires. The harnesses compare the code, the line, and the column, but not the message.

### 6.3 Diagnostics

A diagnostic is the report of one error. Section 6.1 and section 6.2 make its code and its line normative. The other parts of a diagnostic help a human or an agent fix the error. Lean does not model these parts. [ADR 0014](../adr/0014-structured-diagnostics.md) records the decision.

The records of the v0.1 builtin `diagnostic` are observation records, not diagnostics. This section does not change them.

**Structure.** The crate `diagnostics` defines the diagnostic type. Each stage returns diagnostics as values and prints nothing. A diagnostic has these parts:

| Part            | Content                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------- |
| Code            | `S001` to `S020`                                                                          |
| Primary span    | The position of section 6.2, with a label                                                 |
| Secondary spans | Related positions, each with a label. Example: the first declaration of an `S002` name.   |
| Notes           | Facts about the error: the actual and the expected values (v0.1 section 9), the backtrace |
| Help            | One sentence that tells how to fix the error                                              |
| Suggested edits | Text replacements, each with an applicability                                             |

An applicability has one of two values:

- **Machine-applicable.** The edit is correct. A tool can apply it without a human.
- **Maybe-incorrect.** The edit can be wrong. A human or an agent must look at it.

**Instantiation backtrace.** An error of pass 5 occurs in one instantiation. A note lists the chain of `instance` statements from the top selection to that instantiation, with a span for each statement. This is the form of the "required by" notes of rustc. It gives the instantiation path that v0.1 section 9 requires.

**Renderers.** The `driver` renders the diagnostics. The flag `--error-format` selects the form:

| Value   | Form                                                                                  | User                     |
| ------- | ------------------------------------------------------------------------------------- | ------------------------ |
| `human` | The form of rustc: source snippets with labelled spans, made with `annotate-snippets` | A human on a terminal    |
| `short` | One line for each diagnostic: `error[S010]: 12:5: <message>` (section 6.2)            | The harnesses, and Lean  |
| `json`  | One JSON object for each diagnostic, with all parts, on one line                      | An LLM agent and the LSP |

`human` is the default. The fields of `json` are a contract: a change of a field is a breaking change of the command-line interface.

**`silicon explain`.** `silicon explain S010` prints the long text of a code: the rule, a failing example, and a fixed example. Each code has one text in the crate `diagnostics`. A test elaborates both examples of each text. The failing example must give its code, and the fixed example must give no error.

**Recovery.** The front end reports more than one error. Each stage continues after an error where it can, and reports all errors of the first pass that has errors. It does not start a later pass (section 6.2). Only the first error is normative: Lean defines it, and the harnesses compare it. The later errors have no oracle.

**Trust.** A diagnostic does not change the result. The result is the accept or reject decision, and for a reject the first code, line, and column. A wrong help or a wrong edit can thus mislead a user, but it cannot make a wrong design pass.

**Quality loop.** These checks keep the diagnostics useful:

1. **Snapshots.** Each file of `tests/si/check/` has an `insta` snapshot of its `human` and `json` output. A snapshot is a review aid (section 10.2).
2. **Machine-applicable edits.** For each file of `tests/si/check/` and `tests/si/llm/`, a test applies all machine-applicable edits. The edited file must not give the same diagnostic again.
3. **Corpus of LLM mistakes.** `tests/si/llm/` holds the mistakes that LLM agents typically make in Silicon, for example Verilog syntax or a missing width. Each file has its expected first error and a fixed version.
4. **One-turn-fix metric.** A harness gives an LLM a file of `tests/si/llm/` and its `json` diagnostics, for one turn. The metric is the fraction of answers that elaborate and pass the source vectors of the fixed version. The project pins the model and its settings. A CI gate fails when the metric falls below the recorded baseline.

## 7. Lowering to core IR

### 7.1 InstantiationId and emitted module names

An `InstantiationId` is a `ModuleId` and the canonical serialization of the static arguments. Up to slice 5, the `PackageId` of each `ModuleId` is the root package, `root`. `Source.Value` defines the serialization. Slice 1 has these forms:

```text
(int -5)  (bool true)  (string "a\"b")
(instantiation root Counter ((int 8)))
```

The emitted module name of an instantiation is one of two forms:

- **Readable.** The module name, then `$` and one token for each argument. An integer token is its decimal value, with the suffix `n` for a negative value: `-5` gives `5n`. A Boolean token is `1b` or `0b`. Examples: `Counter$8`, `Fifo$16$1b`. A module without arguments keeps its name.
- **Digest.** The module name, then `$0h` and the first 16 hexadecimal digits of the SHA-256 of the serialization. Example: `Fifo$0h3f2a9c0b1d4e5f60`.

The readable form applies when each argument is an integer or a Boolean and the name has at most 64 bytes. The limit applies also to a module without arguments. Otherwise, the digest form applies. Only a truncated digest can make two identities share an emitted name. Elaboration then fails with `S019`. It never merges two modules.

Slice 5 adds the package prefix of [ADR 0007](../adr/0007-mandatory-uniquification.md). It closes the open grammar of that ADR. Issue #53 tracks the gap until then. The plan for slice 5:

1. **Identity propagation.** The `PackageId` from the Lattice lock is part of each `ModuleId`, and thus of each `InstantiationId`. The core module name is the only carrier of the identity after elaboration. `backend-circt` keeps the core module name unchanged, so uniquification happens in one place: the elaborator.
2. **Uniquification.** The emitted name gets a prefix from the full `PackageId`: the package name, the version, and a digest of the `PackageId`. The name and the version alone are not sufficient, because two sources can give the same name and version. The prefix uses the field kinds of section 7.2, so `decode` stays injective. A prefix longer than the limit of the readable form takes the digest form. The slice 5 spec update gives the exact grammar.
3. **Name map.** Elaboration writes a map from each emitted module name to its `PackageId`, `ModuleId`, and arguments. RTL, formal artifacts, and debug tools read this map.
4. **Collision tests.** A corpus design uses two versions of one package with the same module name. A second corpus design uses one version of one package from two sources. Each design must give two emitted modules, and LEC checks each against its source. `names_injective` covers the prefixed names. A unit test in each front end makes two identities share a digest through a test digest function, and expects `S019`.

### 7.2 Names without collisions

The language reserves no name. A user can name a port `clk`, `add`, or `silicon_reg_x`. Elaboration keeps user names and made names apart by construction, not by a rule for the user.

The core IR spec (#39) defines the form of a core name: a list of fields, joined by one `$`. Its pattern is `[A-Za-z_][A-Za-z0-9_]*(\$[A-Za-z0-9_]+)*`. A core name thus never contains `$$`. Each field has one of two kinds:

- **User field.** It starts with a letter or `_`. It is a source name unchanged. A source name has no `$`, so it needs no escape.
- **Made field.** It starts with a digit. Only elaboration makes it. The table below lists its forms.

| Made field                                                    | Meaning                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------ |
| `5`, `5n`                                                     | A loop value or an integer argument. `n` marks a negative value.   |
| `3c`                                                          | The call site `3` of a call frame                                  |
| `2v`                                                          | The version `2` of a binding (section 7.3)                         |
| `1b`, `0b`                                                    | A Boolean argument                                                 |
| `0h<hex>`                                                     | A digest                                                           |
| `0k`                                                          | The escape of a core keyword                                       |
| `4t`                                                          | The temporary `4` of a statement (section 7.4)                     |
| `0clk`, `0rst`, `0ret`, `0rdata`, `0rvalid`, `0ren`, `0raddr` | A role: clock, reset, call result, memory response, memory request |

The decoder splits a name at each `$`. No field contains `$`, so this split is unique. The first character of a field then gives its kind. The first field of each name is a user field.

The core IR still rejects a keyword as a name (core IR spec, section 3). A user name alone that equals a core keyword thus gets the field `0k`: a port `add` becomes `add$0k`. No other name gets `0k`. A name with a separator is never a keyword.

The proof obligation is injectivity. `Source.Names` defines a function `decode` with `decode (encode p) = some p` for each name structure `p`. The theorem `names_injective` follows from it (section 10.3). The function `encode` also gives only names that match the core name pattern and are not keywords. These are the oracles:

- A Lean unit test and a Rust `proptest` test of the round trip on random name structures.
- A file of `tests/si/corpus/` with user names equal to each core keyword and to each made field form. It also uses backend kinds, for example `reg` and `mem`, and `silicon_reg_r`.
- The generator (section 11.4) takes user names from the same list.

Issue #39 removes the reserved prefix `silicon_` from the core IR. The backend and the oracles then make names that contain `$$`, for example `reg$$<n>`. A core name never contains `$$`, so no name of the front end can collide with a backend name.

### 7.3 Structural paths

Each declaration and each binding of a hardware value gets a core name. The name is its structural path: the frames that enclose it, then its source name. `$` separates the fields. The frames, from the outside in:

- **Loop frame.** A `comptime for` iteration gives the field pair `<binder>$<value>`, for example `i$2`. A negative value has the suffix `n`.
- **Call frame.** A call of an ordinary function gives the field pair `<fn>$<k>c`. `k` is the index of the call node among the call nodes of the enclosing body, in source order, from 0.

Examples: a register `r` in the loop body at `i = 2` is `i$2$r`. A `let t` in the helper `f`, at the first call site, is `f$0c$t`.

These bindings get a core name:

- A port, a register, a wire, a memory, and an instance.
- A `let` or an assignment `=` that binds a hardware value.
- A hardware argument of an ordinary function call. Its source name is the formal parameter.
- The hardware result of an ordinary function call. It gets the role field `0ret` after its call frame.

One frame can bind one source name more than once, for example in an assignment to a `let mut` binding. The first binding keeps the path. The binding with index `n ≥ 1` gets the made field `<n>v`. The count includes the ports and covers all bindings of the frame that get a core name, in evaluation order.

A static value gets no core name. A handle alias, for example `let a = q`, gets no core name. A port keeps its source name, because the port names are the interface. Two ports with one name, for example from a loop, fail with `S019`.

The paths are injective by section 7.2. A frame is a user field and a made field. The name of the binding is a user field. A version or a role is a made field at the end.

A path contains no byte offset, because with byte offsets each edit, even one blank line, would rename each later declaration. This is a change from v0.1 section 4.

### 7.4 Expressions

Each core name gets one core statement. An expression without a name stays inline in the statement of its binding. The lowering keeps each inline expression at most 64 nodes high. It computes an effective height bottom-up. A leaf, a reference to a named binding, and an operand that binds to a temporary have the effective height 1. A node whose effective height reaches 64 binds to a temporary, as an operand that is used twice does. The value of the statement itself never binds. Each row of the table below adds at most 4 core levels. A core expression thus nests at most 256 levels, the limit of the core IR. A binding with a name breaks the nesting, so a call chain cannot go above the limit.

In this table, `w` is the width of the left operand, and `c` has the width `wc`.

| Source                                    | Core                                                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `Bool`, `UInt[W]`, `SInt[W]`              | `(bits 1)`, `(bits W)`, `(bits W)`                                                           |
| Literal or static finite value `v`        | `(const w v mod 2^w)`. `true` is `(const 1 1)`.                                              |
| `a +% b`, `a -% b`, `a *% b`              | `(add a b)`, `(sub a b)`, `(mul a b)`                                                        |
| `-a` on a finite integer                  | `(sub (const w 0) a)`                                                                        |
| `~a`, `a & b`, `a \| b`, `a ^ b`          | `(not a)`, `(and a b)`, `(or a b)`, `(xor a b)`                                              |
| `!a`, `a && b`, `a \|\| b` on hardware    | `(xor a (const 1 1))`, `(and a b)`, `(or a b)`                                               |
| `==`, `!=`                                | `(icmp eq a b)`, `(icmp ne a b)`                                                             |
| `<`, `<=`, `>`, `>=`                      | `icmp` with `ult`, `ule`, `ugt`, `uge` for `UInt`, and `slt`, `sle`, `sgt`, `sge` for `SInt` |
| `a << c`, `a >> c`, equal widths          | `(shl a c)`; `(shru a c)` for `UInt`, `(shrs a c)` for `SInt`                                |
| Shift, `wc < w`                           | The count is `(concat (const (w - wc) 0) c)`                                                 |
| Shift, `wc > w`                           | `(mux (icmp uge c (const wc w)) F (op a (extract c 0 w)))`. `F` is the fill.                 |
| Shift by a static count `k`               | The count is `(const w (min k w))`                                                           |
| `if (c) { a } else { b }` on hardware     | `(mux c a b)`                                                                                |
| `resize` to a smaller width `n`           | `(extract a 0 n)`                                                                            |
| `resize` of `UInt` to a larger width      | `(concat (const (n - w) 0) a)`                                                               |
| `resize` of `SInt` to a larger width      | `(concat (replicate (extract a (w - 1) 1) (n - w)) a)`                                       |
| `reinterpret`, `resize` to an equal width | `a`                                                                                          |

The fill `F` is `(const w 0)` for `<<` and for `>>` on `UInt`. For `>>` on `SInt`, it is `(shrs a (const w (w - 1)))`.

A width `w` fits in `wc > w` bits, and `w - 1 < 2^w`. The constants of the table thus always pass `E005`.

Two rows use an operand more than once: the shift with `wc > w` uses `c` twice, and for `SInt` also `a`. The `resize` of `SInt` to a larger width uses `a` twice. Inline copies would make the output grow exponentially with nested operations. The lowering thus obeys this rule:

- A rule can use an operand more than once. If that operand is not a core name or a constant, the lowering first binds it to a core `let`.
- The name of this temporary is the core name of the target of the statement, then the made field `<k>t`. For a child input `u.a`, the target is the instance path, then the user field `a`.
- `k` counts the temporaries of the statement from 0, in evaluation order.

Each source node thus gives a bounded number of core nodes, and the output size stays linear in the source. The rule needs no budget for the output size.

### 7.5 Statements, ports, and the domain

Slice 1 has one domain or none. A module has the clause `domains(d)` with one name, or `domains()`. Without a clause, the domain is `clock`. A clause with more than one name is `S004` in the parser.

| Source                         | Core                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| The domain `d`                 | The inputs `d$0clk` of type `clock` and `d$0rst` of type `(bits 1)`    |
| `input x: T;`                  | `(input x <type of T>)`                                                |
| `output y: T;` and `y := e;`   | `(output y <type of T>)` and `(assign y e)`                            |
| `reg r: T = v;` and `r := e;`  | `(reg r <type> d$0clk (reset sync d$0rst C))` and `(next r e)`         |
| `wire x: T;` and `x := e;`     | `(let x <type> e)`                                                     |
| A hardware binding with a name | `(let <path> <type> e)`                                                |
| `instance u = M(args);`        | `(inst u <emitted name> (c$0clk d$0clk) (c$0rst d$0rst) (<input> e)*)` |
| `u.a := e;`                    | The connection `(a e)` of `u`                                          |
| `u.q` in an expression         | `u.q`                                                                  |

In this table, `x`, `r`, and `u` stand for their structural paths, and `c` is the domain of the child. `C` is the constant of `v` by the row "Literal or static finite value" of section 7.4. The ports of a core module come in this order: `d$0clk`, `d$0rst`, the inputs sorted by name, then the outputs sorted by name. Names sort by byte order.

A combinational module (`domains()`) has no clock and no reset. A register in it is `S017`. An instance of a clocked child in a combinational parent is `S017`.

After the top instantiation, elaboration runs `Core.check` on the lowered design. Each core node carries the source position of the node that made it. A core `E008` becomes `S020` at that position. Each other core error is a defect of the reference elaborator. The theorem `elab_wellFormed` (section 10.3) excludes it.

The core design is `(design <emitted name of the top> <items>)`. It holds each instantiation that the top reaches, once.

### 7.6 The memory (slice 2)

v0.1 section 5 defines a memory with a synchronous read and one write port. The core memory has a combinational read (core IR spec, decision D4). Elaboration lowers `mem m: [T; N]` with `A = max(1, ⌈log₂ N⌉)` onto the core memory and two registers:

- `(mem m (bits w) N d$0clk)`.
- The response registers `m$0rdata` of width `w` and `m$0rvalid` of width 1. Both reset to 0.
- The read enable and the read address are each used twice. The lowering binds them to `(let m$0ren (bits 1) en)` and `(let m$0raddr (bits A) addr)`, as in section 7.4.
- `(next m$0rdata (mux m$0ren (read m m$0raddr) m$0rdata))`. A core read out of range gives 0, as v0.1 requires.
- `(next m$0rvalid (and m$0ren (icmp ult m$0raddr (const A N))))`. When `N = 2^A`, the compare is `(const 1 1)`.
- `(write m 0 waddr wdata (and wen (xor d$0rst (const 1 1))))`. A reset cancels the write.

The depth `N` is 1 to 16777216, the limit of the core checker (`E005`). The fit rule `S012` rejects a depth outside this range before the lowering, at the start of the `mem` declaration. `tests/si/check/` has a file with `N = 16777216`, which passes, and a file with `N = 16777217`, which gives `S012`.

The registers read the old memory state, so a read and a write of the same word give the old word. This is the read-first behavior of v0.1. Issue #12 changes only the mapping to macros, not this meaning.

## 8. Commands

`silicon-check` gets these commands. The Rust `silicon` gets the same commands with the same output. Only the message text of an error line can differ (section 6.2). The exit codes are those of the core IR spec, section 6.4.2.

| Command                         | Output on success                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| `parse F.si`                    | The AST dump (section 11.1)                                                                    |
| `elab F.si --top T`             | The canonical `.sil` text of the design                                                        |
| `validate F.si --top T OUT.sil` | `ok`. For a mismatch, the first line that differs, and exit code 1.                            |
| `run F.si --top T`              | One output source vector for each input source vector                                          |
| `eval F.si EXPR`                | The canonical serialization of a static expression in the file scope                           |
| `cost F.si --top T`             | `total <units>`, then one line `<emitted name> <units>` for each instantiation, sorted by name |

Each command takes the budget flags that section 5.4 lists. `T` is a top selection in source syntax: a module name, then the static arguments in parentheses. Each argument is a literal. A top selection that does not parse is a usage error with exit code 2. A wrong number of arguments is `S007`. `eval` charges no cost for the printing of its result. A core error other than `E008` in the output of the reference elaborator is a defect, not a design error. `silicon-check elab` then prints the core error on stderr and exits with code 3. Until phase 5 (#69), `cost` covers only the top selection: its arguments and its parameter types. Phase 5 adds the module bodies, the instantiations with their serialization and digests, the lowering, and the line for each instantiation.

`validate` works in these steps:

1. Elaborate `F.si` with the reference elaborator.
2. Parse and check `OUT.sil` with the core checker.
3. Compare `print (canonicalize ...)` of the two designs byte for byte.

`validate` thus also does the work of `silicon-check check` on the compiler output (issue #27). The comparison is in Lean, so no Rust code is on the trusted path of the comparison.

When the reference elaborator rejects the source, `validate` prints that error and exits with code 1. `validate` thus covers an accepted design. For a rejected design, the build produces no artifact. The shared corpus and the generator check that both front ends reject with the same first code, line, and column.

### 8.1 Validation in a build

`silicon build F.si --top T` elaborates in Rust, writes the `.sil` file, runs `silicon-check validate`, and then runs the backend. Validation is on by default. The flag `--no-validate` turns it off for an interactive build. The build prints `validated` or `not validated`. An artifact without validation has the status Trusted (section 13). The LSP never validates.

A large design makes validation slow, because the Lean checker is not yet near-linear. Issue #23 tracks this.

## 9. Lean definitions of the difficult features

v0.1 has features that are hard to define. This section gives the Lean definition of each. The slices of section 12 bring them in.

### 9.1 `mut` formals and the aliasing rule

The aliasing rule of v0.1 section 2 is static. A mutable root is a `let mut` binding or a `mut` formal. A program has no global variable, no closure, and no reference value. A callee can thus reach a place of the caller only through a `mut` formal. Each mutation of a root is thus visible in the syntax: an assignment with that root, or a `mut` actual with that root.

The **window** of a pending root:

- For a `mut` actual: its own index expressions and each later argument of the same call. For a receiver call, the receiver is first, so the window holds all arguments.
- For an assignment `place = e`: the index expressions of the place and `e`.

`S008`: in the window of a pending root `R`, no assignment and no `mut` actual has the root `R`. Two `mut` actuals of one call have different roots. `Source.Check` decides this rule on the resolved AST. A call through a function value has the `mut` marks of its function type, so `Elab` applies the same rule at the call, with the same code.

The evaluator then passes a `mut` actual by value and result. It copies the value of the place into the formal at the call. At the return, it writes the final value of the formal back to the place. The place and its static indices have their values from before the call. `S008` excludes each alias, so this definition gives the same result as an alias. It needs no memory model and no borrow check.

An error ends the elaboration, so a partial write-back is never visible.

### 9.2 Implicit reads

An implicit read is a total function of the context, the expected type, and the value:

```lean
coerce : Context → Option Ty → Value → Except Error Value
```

`Context` has two values: `data` and `raw`. `Source.Elab` gives each position one context. The table is normative and follows v0.1 section 2:

| Position                                                                                   | Context |
| ------------------------------------------------------------------------------------------ | ------- |
| An operand of an operator, a condition, a data field selection, and a data index selection | `data`  |
| A `let` with a data type annotation, an assignment of a data place, and a data return      | `data`  |
| A data parameter of an ordinary function, a constructor argument, and the value of `:=`    | `data`  |
| An explicit `read(h)`                                                                      | `data`  |
| A `let` without an annotation, and a `let` with a handle type                              | `raw`   |
| A `mut` actual, a resource-typed formal, a `:=` target, and the operand of `@TypeOf`       | `raw`   |
| The value of `diagnostic`                                                                  | `raw`   |

In a `data` context, `coerce` maps a register handle or a wire handle to a hardware read of its core name. It recurses through arrays and tuples. It does not convert a nominal record. A memory, a domain, and an instance are never read. An input handle in a `data` context is `S017`. In a `raw` context, `coerce` returns the value unchanged.

Slice 1 has handles only as names and as unannotated `let` aliases. Slice 1 has no handle types. Its prelude has no `Reg` and no other handle type, so a use of such a name fails with `S003`. The message names the slice of the feature.

### 9.3 The `@` builtins

Each builtin is a Lean function. None of them makes hardware.

| Builtin        | Lean definition                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| `@TypeOf(x)`   | The type of the resolved place `x`, in the `raw` context. It evaluates only the static keys and indices of `x`. |
| `@typeInfo(T)` | A total function from a normalized type to a `TypeInfo` record, with the kind tags of v0.1                      |
| `@Struct(fs)`  | A structural record type. Its identity is the list of names and normalized field types.                         |
| `@field(x, k)` | The selection of the field or the index `k`, with the rules of an ordinary selection                            |
| `@ports(h)`    | The public ports of the instance `h` as a list of `PortInfo`, in schema order                                   |

`@TypeOf` and `@ports` accept only the operand forms of v0.1 section 2. The pre-check rejects each other form with `S003`. `@typeInfo` and `@Struct` run in a structural context: a graph effect or a diagnostic in their arguments is `S016`.

### 9.4 Effects

The evaluator has a mode. In the arms of a hardware conditional, the mode is `pure`. In a `comptime fn`, the mode is `static`. These operations are graph effects:

- The declaration of a port, a resource, or an instance.
- A `:=` binding.
- A call of `diagnostic`.
- A mutation of a binding that existed before the arm started.

A graph effect in the mode `pure` is `S016`. A hardware operation in the mode `static` is `S011`. The mode follows the calls, so the rule applies through each helper, as v0.1 requires.

### 9.5 Resources and owners

A handle carries the structural path of its owner instantiation. A handle that reaches a different owner is `S017`. Ports and module arguments are the only paths between owners. Ports carry data, and module arguments are recursively static. A handle can thus never cross an owner. The check exists only as a guard.

### 9.6 Later features

- **Domains.** After #11, a domain becomes a static value with a clock, a reset, and a policy. The core IR then has more than one clock. The tag inference of v0.1 section 4 becomes a fixed point in `Elab`, with a fuel bound.
- **Packages.** The `ModuleId` gets the real `PackageId`. `Resolve` reads the locked dependency map that Lattice gives (ADR 0006).
- **Contracts.** The actual machine of v0.1 section 7 is the core `step` of the elaborated design and the port schema. It is not a second generated model.

## 10. Oracles

### 10.1 Oracle of each stage

| Stage               | Oracle                                                                                                             | Command                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------- |
| Lossless tree       | The text of the syntax tree equals the input for arbitrary strings. No panic on arbitrary bytes.                   | `just test`             |
| Source printer      | `parse (print a) = a` for generated ASTs, which tests the precedence and the parentheses                           | `just test`             |
| `parse`             | The Rust AST dump equals the Lean AST dump byte for byte. A rejection gives the same first code, line, and column. | `just lean-check`       |
| `resolve`, `typeck` | The same first code, line, and column as Lean, on the corpus and on generated programs                             | `just lean-check`       |
| `elab`: evaluator   | `eval` and `cost` give the same output as Lean                                                                     | `just diff-si`          |
| `elab`: elaboration | `validate`: byte equality with Lean. Budget boundary tests.                                                        | `just lean-check`       |
| `elab`: lowering    | `validate`, the core checker, and the proven `elab_wellFormed`                                                     | `just lean-check`       |
| Whole front end     | Source vectors through both front ends and both interpreters                                                       | `just lean-check`       |
| Output              | The existing chain: LEC, the differential tests, and `arcilator`                                                   | `just lec`, `just diff` |

### 10.2 Rules for the oracle loop

- **No expected `.sil` by hand.** The reference elaborator gives the expected output. A test author writes only behavior (source vectors) and intent (`FileCheck`).
- **Snapshots are review aids.** An `insta` snapshot is not an oracle for elaboration. Nobody can update the Lean comparison by hand, because Lean computes its expectation.
- **Fast feedback.** `cargo xtask lean-check --suite si --filter PATH` runs only the files that an agent touches, against a built `silicon-check`.
- **Localization.** A failed comparison prints the first line that differs: in the AST dump, then in the `.sil` text. The stage of the defect is thus visible.
- **Task shape.** A feature has three commits: the Lean modules with their unit tests, the corpus with its expectations, and the Rust code. The corpus commit comes before the Rust commit, so the Rust task starts with a failing test.

### 10.3 Theorems

The project plans these theorems. They do not block a slice. A fresh Opus agent proves each one as its own task:

| Theorem            | Statement                                                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------- |
| `elab_wellFormed`  | `elaborate src top b = .ok d → ∃ t, Core.check d = .ok t`                                       |
| `static_op_agrees` | Each finite static operation equals the core operation on the lifted constants                  |
| `parse_print`      | `parse (print a) = .ok a` up to source positions, for an AST with valid names within the limits |
| `names_injective`  | `encode p = encode q → p = q`, from `decode (encode p) = some p` (section 7.2)                  |
| `eval_cost`        | The fuel that an elaboration uses equals the output of `cost`                                   |

A declarative type relation with `check_sound` and `check_complete` for the pre-check comes later. It follows the model of the core checker.

### 10.4 Oracles against a shared misreading

Both front ends come from the same prose. They can agree and both be wrong. These oracles do not come from either front end:

- **Source vectors by hand.** The test author writes the expected outputs.
- **Lean models as references.** A small corpus has designs with an independent Lean model, for example the counter of the v0.1 README. A differential test compares the model with the core interpreter of the elaborated design on random inputs.
- **Metamorphic tests.** A change that keeps the meaning keeps the canonical `.sil` text, up to an explicit name correspondence. Section 11.3 lists the changes and their oracles.
- **The human gate.** The Lean `Source` modules define the language. A change to them needs the approval of the user, as [ADR 0009](../adr/0009-cross-vendor-review-before-merge.md) gives for language design.

## 11. Formats, tests, and the generator

### 11.1 The AST dump

The AST dump is one S-expression for each item. Each node prints as `(<constructor> <fields>)`, with the constructor names of `Source.Syntax` in lowercase. The dump has no source positions and no comments. Each item starts a new line. A string prints in double quotes with the escapes of the grammar. Each item ends with one LF, so a file without items gives an empty dump. The module doc of `lean/Silicon/Source/Print.lean` gives the full byte format.

### 11.2 Source vectors

A source vector has the form of a core vector (core IR spec, section 6.4.3), with source names and source values:

- An input line lists the reset of the domain as `d$0rst`, then each input in schema order.
- A `Bool` value is `true` or `false`. A `UInt` value is decimal. An `SInt` value is decimal with `-` for a negative value.
- An aggregate port has one entry for each leaf. The leaf name is the port name with `.field` or `.index` for each level, in packing order (slice 2).
- An empty port has no entry.

`Source.Vectors` maps a source vector to a core vector through the port schema, and back. `run` uses the core interpreter. The start state is all zero, as in section 6.4.3 of the core IR spec. This start state is a test convention, not semantics.

The initial state of a source design is free, as in section 5.2 of the core IR spec. A real register has no defined value before its first reset. A design that needs a defined start applies its reset. This replaces v0.1 section 4 on purpose, which starts the native registers at their reset values. The meaning of a source design is the core IR `step` of its elaboration, so the source cannot promise more than the core IR. A file of `tests/si/run/` has a register with a nonzero reset value. Its vectors show the register before the first reset edge, with the value 0 of the test convention, and its reset value after that edge. A second register of type `SInt[8]` has the reset value `-1`. Its vectors show `-1` after the first reset edge.

### 11.3 Test directories

[The testing guide](../guide/testing.md) gives the suites, their commands, their oracles, and their directives, for example `// TOP Counter(8)` for the top selection. This section gives only what is special to the source suites. The guide names the tree `tests/source/`. This spec calls it `tests/si/` until phase 9 renames it.

These budget and identity cases each get a file:

- A branching hierarchy: `M(d, id)` instantiates `M(d - 1, 2 * id)` and `M(d - 1, 2 * id + 1)`, with `d = 10`. The fuel equal to the output of `cost` succeeds, and one unit less gives `S015`.
- A shared hierarchy: `M(d)` instantiates `M(d - 1)` twice, with `d = 30`. `cost` lists exactly 31 instantiations, and the total stays linear in `d`.
- A top that instantiates a deep child first and a shallow child later, and the same design in the reverse order. Each order runs at the exact nesting depth and one level below it. Both front ends give the same result for each order.
- A constant that uses itself, and two constants that use each other. Both give `S019`.
- A chain of 300 acyclic constants. A nesting depth of 301 succeeds, and 300 gives `S015`.
- A static `1 << k` with a large `k`, and a loop that copies a large list. Both give `S015` before the operation runs.
- A nested doubling: `let a0 = [0, 0];`, then `let a1 = [a0, a0];` and so on up to `a20`, with `--fuel 1000000`. Making `a_k` charges `2^(k + 2) - 1`. The sum first goes above the fuel at the `let` of `a17`, which gives `S015`.

A file of `tests/si/elab/` nests 30 `>>` operations on `SInt[1]` with a `UInt[2]` count. Its `CHECK-COUNT` lines require exactly 2 `shrs` operations for each source shift. The output thus stays linear in the source. The negative cases of v0.1 section 9 each get a file in `tests/si/check/`.

The metamorphic tests compare two programs that differ by one change. The oracle depends on the effect of the change on the structural paths (section 7.3).

These changes keep each structural path. The canonical `.sil` text must stay equal byte for byte:

- The order of the items.
- The order of two adjacent `:=` statements without calls. A `:=` binds no name, so the versions stay equal.
- Redundant parentheses.

These changes rename structural paths. Byte equality thus does not apply directly:

- The name of a local or a loop binder.
- A `comptime for` against its body written out by hand.
- A call of a helper against its body written out by hand.

For these changes, the test gives an explicit name correspondence from the core names of the first program to those of the second. The harness renames the first core design with it, then compares the canonical `.sil` text byte for byte. A correspondence must be a bijection on the core names, and the ports must map to themselves. When a test has no complete correspondence, LEC compares the two designs instead. The current LEC matches registers by name, so the correspondence must at least cover the registers.

### 11.4 The program generator

The module `gen` of the crate `syntax` makes source programs. `cargo xtask diff-si` runs it. It has four modes:

1. **Lift.** It renders each core design of `core-ir` `gen` as a source program of slice 1. The oracle: the elaborated program and the original design give the same outputs on random source vectors.
2. **Typed.** It makes well-typed programs of the current slice directly from types. These programs have comptime parameters, comptime functions with structural recursion, loops, branches, helpers, registers, and instance trees with arguments. Each wire reads only earlier values, so no cycle occurs. The oracle: `validate` passes, and `eval` and `cost` agree.
3. **Mutation.** It applies one mutation to a typed program, for example the deletion of a binding or a change of a width. The oracle: both front ends report the same first code, line, and column.
4. **Budget.** It reads the cost of a typed program from `cost`. The oracle: the fuel equal to the cost succeeds, and one unit less gives `S015`.

A typed program also comes with a twin: the same program with each comptime construct written out. The oracle: the two programs give the same outputs on random source vectors.

The generator has a fixed set of seeds for `just ci`. A failure prints the shrunk program and its seed.

### 11.5 Recipes

| Recipe            | Command                  | Oracle                                       |
| ----------------- | ------------------------ | -------------------------------------------- |
| `just lean-check` | `cargo xtask lean-check` | Extended with the suite `si` of section 11.3 |
| `just diff-si`    | `cargo xtask diff-si`    | The generator of section 11.4                |

`just ci` runs both recipes from slice 1 on.

## 12. Slices

A slice is a set of features with its own closed oracle loop. A slice is done when each item of its list holds and `just ci` passes. Its milestone review (section 14, phase 12) must have no open blocker. The grammar grows with each slice. The keywords are those of the v0.1 grammar from slice 1 on, and no slice adds a reserved identifier. The parser of a slice rejects the syntax of a later slice, for example `import` or `struct`, with `S004`. The prelude of a slice has only its own names. A use of a prelude name of a later slice, for example `List`, thus fails with `S003` in the resolver.

### 12.1 Slice 1: comptime core

Features:

- One file, no imports. The top selection on the command line.
- Modules with `comptime` parameters of type `Nat`, `Int`, and `Bool`. One domain or none.
- Ports, `reg`, `wire`, `:=`, `let`, `let mut`, and assignment of a local.
- The types `Bool`, `UInt[e]`, and `SInt[e]` with static widths. Top-level `const`.
- The operators of v0.1 section 3, static and on hardware. `resize`, `reinterpret`, `T(n)`, and both kinds of `if`.
- `fn` helpers over data, `comptime fn` with recursion, `comptime if`, `comptime for`, and `return`.
- `static_assert` and `error` with string literals.
- `instance` with static arguments, `InstantiationId`, and emitted module names with digests.
- Implicit reads of registers and wires, and unannotated `let` aliases of handles.

Done criteria:

1. The Lean modules of section 4.3 exist for these features. `lake build` passes.
2. The Rust crates `syntax`, `parse`, `resolve`, `typeck`, and `elab` exist. The `driver` has the commands of section 8.
3. `tests/si/` has each directory of section 11.3. Each code from `S001` to `S007` and from `S010` to `S015` and `S017` to `S020` has at least one file in `tests/si/check/`.
4. `just lean-check` passes on `tests/si/`. `just diff-si` passes on the fixed seeds with all four modes.
5. Each file of `tests/si/corpus/` passes `validate`, `just lec`, and `just diff`.
6. `silicon build` validates by default.
7. `doc/trust.md` shows the new rows of section 13 with their status.

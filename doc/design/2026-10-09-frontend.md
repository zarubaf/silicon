# Front end

- Status: accepted
- Date: 2026-10-09

## 1. Purpose and scope

This spec defines the front end of Silicon: the stages from a `.si` file to core IR. It covers build step 4 of [the architecture](../architecture.md), the source language and the elaborator.

The goal: a source design has one meaning, which a Lean reference elaborator defines. The Rust front end agrees with that meaning on each run. A mechanical oracle checks each stage.

The language is the v0.1 proposal in [`doc/reference/`](../reference/SILICON_SPEC.md). This spec keeps all its features. It orders them into slices (section 12). Each feature gets a Lean definition in the reference elaborator. Section 9 shows how the features with the highest risk get one.

These items are out of scope. Each item has a follow-up issue (section 15):

- More than one clock domain, domain maps, and asynchronous reset. Issue #11 blocks them.
- Synchronous read ports in the core IR. Issue #12 adds them. Section 7.6 lowers the source memory onto the current core memory.
- The design of contracts (`conforms`, `using`) and certificates. They come after packages. The parser reserves their syntax now.
- The LSP and `salsa`. They come in build step 5.

## 3. The meaning of a source design

A build has a `.si` file and a top selection. A top selection names a module and its static arguments, for example `Counter(8)`. The Lean function `elaborate` maps them to a core design or to an error:

```lean
elaborate : Source → TopSelection → Budgets → Except Error Core.Design
```

The meaning of a source design is the semantics of the core IR (core IR spec, section 5) of `canonicalize (elaborate src top budgets)`. The front end adds no second semantics. Elaboration exists only to produce core IR. The core IR then has its proven semantics, its interpreter, its reference lowering, and LEC.

These consequences follow:

- The Lean `Source` modules are the normative definition of the language. The prose of v0.1 is input for them, not a second authority. A disagreement between them is a bug in the Lean modules or a language decision for the human gate.
- A port schema maps each source port to its core port. Source vectors (section 11.2) and, later, contracts use it.
- Elaboration does no optimization. An optimization is a core-to-core pass, and LEC checks it.

## 4. Pipeline

```text
.si text
  │ syntax: lexer, rowan tree types                 Lean: Source.Lex
  │ parse: lossless tree with recovery, typed AST   Lean: Source.Parse, Source.Print
  │ resolve: item table, scopes, names               Lean: Source.Resolve
  │ typeck: generic pre-check                       Lean: Source.Check
  │ elab: static evaluator, instantiations,         Lean: Source.Value, Source.Eval,
  │       checks for each instantiation                   Source.Elab
  │ elab: lowering to core IR, names                Lean: Source.Flatten, Source.Layout,
  │                                                       Source.Names
  ▼
core IR (.sil) → existing chain: check, run, backend-circt, reference lowering, LEC
```

### 4.1 Stage interfaces

Each stage is a pure function of its inputs. Each stage reports the first error of its pass in the order of section 6.

| Stage     | Input                                | Output                                                                               |
| --------- | ------------------------------------ | ------------------------------------------------------------------------------------ |
| `syntax`  | Bytes                                | Tokens                                                                               |
| `parse`   | Tokens                               | A lossless syntax tree with errors, and an AST with source spans. Or `S001`, `S004`. |
| `resolve` | AST                                  | A resolved AST: each name points to its declaration. Or `S002`, `S003`.              |
| `typeck`  | Resolved AST                         | The same AST, or `S005` to `S008`                                                    |
| `elab`    | Resolved AST, top selection, budgets | A core design, or `S008` (section 9.1) or `S010` to `S020`                           |

The resolved AST is the boundary between the stages that work on all code and the stages that work on instantiations. `elab` holds no syntax tree. It reads the resolved AST only.

### 4.2 The generic pre-check and the checks for each instantiation

A width such as `UInt[W + 1]` has no value before `W` has a value. A type check before elaboration thus cannot check widths. The work splits into two parts:

- **Generic pre-check (`typeck`).** These checks need no static values: the syntactic stage rule, placement, arity, and the aliasing rule of `mut` places. They run on each item, also on an item that no instantiation uses. An agent thus gets these errors without a top selection.
- **Checks for each instantiation (`elab`).** These checks need static values: types and widths, fit, the dynamic stage rule, effects, resources, and bindings. They run on the code that an instantiation executes. A `comptime if` checks only its selected branch, as v0.1 section 1 requires.

Lean has the same split: `Source.Check` and `Source.Elab`.

### 4.3 Lean modules

The modules are under `lean/Silicon/Source/`, in dependency order:

| Crate           | Layer    | Content                                                                                                 |
| --------------- | -------- | ------------------------------------------------------------------------------------------------------- |
| `core-ir`       | 1        | Unchanged                                                                                               |
| `syntax`        | 2        | Lexer, `rowan` syntax tree, typed AST wrappers                                                          |
| `srcgen`        | Dev-only | The source generator of section 11.4                                                                    |
| `parse`         | 3        | The parser with recovery, the AST, and the AST dump                                                     |
| `resolve`       | 4        | Item table, scopes, and the resolved AST                                                                |
| `typeck`        | 5        | The generic pre-check                                                                                   |
| `elab`          | 6        | Static values, the evaluator, instantiations, the lowering, names, the port layout, vectors, the schema |
| `backend-circt` | 7        | Unchanged                                                                                               |
| `driver`        | 8        | The `silicon` CLI                                                                                       |

The crate `srcgen` is dev-only, as `testkit` is. Only `xtask` and `[dev-dependencies]` name it. It comes before `parse` in the layer order, so it cannot use the code of the stages that it tests. See [ADR 0018](../adr/0018-source-generator-crate.md).

These rules apply to the Rust front end:

- **Query shape.** Each stage is a pure function. Its key is a file and an item, or an `InstantiationId`. No stage has global mutable state. `salsa` replaces the plain calls when the LSP starts.
- **Determinism.** The crates `resolve`, `typeck`, and `elab` use no `std::collections::HashMap` and no `HashSet`. A clippy `disallowed-types` rule enforces this. An output order comes from the evaluation order or from a sort, never from an address or a hash.
- **Recovery.** The parser and the resolver continue after an error, for the LSP. The first error in the order of section 6 must equal the error of Lean. Later errors have no oracle.
- **Interfaces.** Each crate exports a small interface. `elab` exports `elaborate`, `eval`, `cost`, and the schema. Slice 2 adds `observe`.

### 4.5 Preparation for an Aeneas proof

The end goal is a proof of the Rust front end against the Lean reference elaborator. Aeneas translates Rust code to Lean, and a proof then relates the translation to the reference. Issue #10 plans the same proof for the core IR checker and interpreter. Until that proof exists, `silicon-check validate` on each run is the oracle.

Aeneas reads the MIR of the compiler through Charon. It supports a subset of safe Rust. These limits of Aeneas matter for the front end:

- No `unsafe` code, no interior mutability (`Cell`, `RefCell`), and no shared ownership with mutation (`Rc`, `Arc`).
- No trait objects (`dyn`). Support for closures, iterator adapters, and complex trait code is partial.
- Only a part of the standard library has a Lean model. `Vec` and `Box` have one. `HashMap`, external crates, and most iterator adapters do not.
- A loop becomes a recursive Lean function. A panic and an arithmetic overflow become an error result.
- Borrows inside data structures and nested mutable borrows have limited support.

The Rust front end thus follows these rules where they cost little:

- The **elaborator core** is the code of `elab` from the resolved AST to the core design: `Value`, `Eval`, `Elab`, `Flatten`, and `Names`. It uses plain `enum` data, `match`, `Vec`, `Box`, and indices into a `Vec` for arenas. It has no trait object, no closure that captures a mutable value, no iterator adapter chain, and no external crate.
- The elaborator core returns `Result` for each error and does not panic. It passes the fuel as an explicit argument, so its loops have a visible bound.
- The resolved AST is a plain owned tree. It holds no `rowan` node and no `salsa` handle.
- `salsa`, the LSP, the diagnostics, and the `driver` stay outside the elaborator core. They call it as a pure function.

These parts cost a lot to adapt. They stay outside the first proof, and validation keeps them covered:

- **The syntax tree and the parser.** `rowan` uses `Rc` and `unsafe` code. A parser for Aeneas needs a second, plain tree. The proof of the parser comes after the proof of the elaborator core, or the parser keeps validation as its oracle.
- **Static integers of any size.** The elaborator core uses an integer type of its own with a small interface. The proof can take a Lean model of this interface as an assumption, and `doc/trust.md` lists it.
- **The SHA-256 digest.** The proof takes it as an opaque function with the Lean `Sha256` as its model.
- **The ordered maps.** The elaborator core keeps its tables in `BTreeMap` and `BTreeSet`: the frames of locals, the core names, the versions, the instantiations, and the results of the scan. Aeneas has no Lean model of these types. A `Vec` costs more. A search takes a linear step at each look-up. A `Vec` with an index for each declaration takes a step for each declaration at each call. Thus the work of the elaboration grows with the square of the size of the program. Some keys are strings or tuples, so they are not dense indices. Thus the maps stay. The proof takes the few map operations that the core calls as an assumption, as for the integers. Their model is the Lean `Std.TreeMap`. `doc/trust.md` lists this assumption.

## 5. Elaboration

### 5.1 Values

A value of the evaluator has one of these forms:

- **Static value.** An integer (`Int`, and `Nat` as a checked `Int`), a Boolean, a string, a type, a named function, or a finite static integer of type `UInt[W]` or `SInt[W]`. Slice 2 adds the unit value `()`.
- **Container (slice 2).** An array, a tuple, a record, or a list. It holds a sequence of values, its elements.
- **Hardware value.** A typed tree of core operations over core names. Its source type is `Bool`, `UInt[W]`, or `SInt[W]`.
- **Handle.** A reference to a register, a wire, a memory, an instance, or a child input. Its identity is its structural path (section 7.3).

A finite static value uses the same `BitVec` function as the core operation. The Lean definitions share the function, so `static_op_agrees` (section 10.3) is nearly definitional.

Slice 2 adds these rules. The parser of slice 1 rejects their syntax with `S004`, so they do not change slice 1.

- **Shape.** The shape of a container is static: its length, its indices, and its field names. Each element keeps its own stage, so one container can hold static and hardware elements.
- **Leaf.** A leaf of a value is a part, at any depth, that is not a container and not `()`. A leaf is a static value or a hardware value. A **hardware leaf** is a leaf that is a hardware value. In slice 2, a leaf is never a handle: a handle as an element is `S010`, and the message names slice 3.
- **Array.** The type `[T; N]` has the fixed length `N` and one element type `T`. `[a, b]` makes an array. The element type is the common type of the elements, by the operand rule of slice 1. Thus a static integer converts to the finite type of another element. Elements with no common type give `S010`. The length `N` of `[T; N]` is a static position (`S005`). In an expression, `[T; N]` is a type, as in the v0.1 grammar. Its element `T` is a type expression, and its length `N` is an expression. The two syntax categories are thus mutually recursive. The parser decides at the `[`: a `;` at the depth of this bracket makes it `[T; N]`, and the `;` is a separator at this depth. The parser does not try again, so the parse stays linear. Thus the `0` of `[0; 4]` is not a type, and it gives `S001` at its first token.
- **Empty array.** `[]` gets its type `[T; 0]` only at a typed use: an annotation, an assignment, an argument, a return, a constant, or a module argument. As a module argument, `[]` takes the type of its parameter. That parameter type then evaluates in the scope of the module, with each earlier parameter bound to its argument. The parent pays for this work. A struct argument does the same in the scope of the struct, before the key of the specialization exists. Thus `P[[]]` is valid when the parameter of `P` has the type `[Bool; 0]`. The type of a typed use also goes into each element of a nested literal. Thus `let a: [[Int; 0]; 1] = [[]];` is valid. A literal that holds `[]` without a typed use, for example `[[]]`, is `S010` at the first `[]`.
- **Index.** An index of a container is a static position. Its value is a static `Int` or `UInt`. An `SInt` index is `S010`. An index that names a port, a register, a wire, or an instance is `S005` in pass 4. Another hardware index is `S011` in pass 5.
- **Container equality.** `==` and `!=` on containers compare each pair of elements by the operand rule. A static integer thus converts to the finite type of its pair, and the conversion checks its fit (`S012`). This conversion has no charge of its own (section 5.4). The length of a list is a value, not a part of its type. Two lists of different lengths are thus unequal, not `S010`.
- **Tuple.** The type `(T, U)` and the value `(a, b)`. A tuple with one element is `(a,)`. The selectors `.0`, `.1`, and so on select an element. The selector after `.` can be any number literal, and its value selects the element. Thus `t.0x1` and `t.0b1` select the element 1, as `t.1` does. This differs from the v0.1 grammar, which allows only a decimal selector.
- **Record.** A value of a `struct` type (section 5.6). Its type is nominal: its identity is the declaration and the static arguments. `P[8](a, b)` makes a record with the fields in declaration order.
- **List.** `List[T]` is a static type only. `list(T)` makes an empty list. `push`, `pop`, and `len` change and read it. A hardware value in a list is `S011`.
- **String.** A static sequence of Unicode scalar values. `+` joins two strings. `s[i]` gives a string with the scalar `i` of `s`. `str(n)` gives the decimal form of an `Int` or a `Nat`. `len(s)` counts the scalars. `str` of a finite integer is `S010` by the type rule, also for a hardware `UInt`. An order operator on two strings is `S010`. A string is not a container, so an assignment to an index of a string is `S010` at the index.
- **Type.** A static value of type `Type`. Its forms are `Bool`, `Nat`, `Int`, `UInt[W]`, `SInt[W]`, `Unit`, `String`, `Type`, `[T; N]`, `(T, U)`, `List[T]`, a struct specialization, and `fn (T, mut U) -> V`. A `type` alias is transparent: it names the normalized type. Two types are equal when their normalized terms are equal.
- **Function type.** `fn (T, mut U) -> V` is a type expression. In an expression, it is a unary operand, as in the v0.1 grammar, so a postfix after it belongs to its result type. A parameter type can have the mark `mut`. A `comptime` mark there is `S001` at the mark. An index of a function type, for example `(fn () -> UInt)[8]`, is `S007` in pass 4.
- **Function value.** A named function that is not generic, also a `comptime fn`. A function is generic when it has a `comptime` parameter, or when a parameter type or its result type names one of its parameters, for example `fn d(T: Type, x: T) -> T`. The resolver knows this, so the check needs no evaluation. Its type is its signature, with the `mut` mark of each parameter. A named wrapper gives a function value for one specialization (v0.1, section 2).
- **Function name as a value.** A name of a function item gives a function value, except as the callee of a call (section 5.6). The name charges its node. A generic function or a builtin is then `S010` at the name. Then the signature evaluates in the scope of the function: each parameter type, then the result type, as type expressions. The function type then charges its recursive size, as a type constructor does. This evaluation is not a call, so it adds no call frame. It is a nested evaluation, so it adds one nesting level. A signature can name its own function, for example as an argument of a call in a parameter type. The nesting depth then ends this cycle with `S015` at the name. A value or a type of this evaluation above the nesting depth is `S015` at the name, as the function type is. A call, a constant, or a struct use in the signature nests, so its own checks keep their positions. The name makes the value, so a binding of it is not a copy.
- **Typed use of a function value.** A typed use of a function value needs its exact function type: equal parameter types, equal `mut` marks, and an equal result type. It converts nothing and charges no conversion, as a record at its struct type does. Another type is `S010`.
- **Function equality.** `==` and `!=` are `S010` at the operator when the type of an operand holds a function type at any depth. Examples are a function, a value of type `[fn () -> Bool; 0]`, and a value of type `List[fn () -> Bool]`. The check comes after both operands evaluate, before each join and each charge of the operator. It reads the type metadata (section 5.4), so it walks no value.
- **Hardware data.** `Bool`, `UInt[W]`, `SInt[W]`, and `Unit` are hardware data. An array, a tuple, or a record is hardware data when each element type is hardware data. `Int`, `Nat`, `String`, `Type`, `List[T]`, and a function type are not.
- **Leaf of a type.** A leaf of a hardware data type is a part of type `Bool`, `UInt[W]`, or `SInt[W]`. A type without a leaf, for example `Unit` or `[T; 0]`, is empty.
- **Hardware aggregate.** A container with at least one hardware leaf. Section 7.4 lowers it leaf by leaf ([ADR 0019](../adr/0019-aggregates-lower-to-leaves.md)).

Lean defines `Value` and `Ty` as nested inductive types. A Lean container uses `Array`, so an index and `len` of an array or a list take constant work. The Rust containers use `Vec` and `Box`, inside the subset of section 4.5.

### 5.2 Evaluation order

Elaboration executes statements in source order. The order of the operands, the arguments, and the branches is the order of v0.1, section 1. This order is normative. It fixes the first error, the cost, and the core names.

Slice 2 adds the order of an assignment `place = e` whose place has a step. A step of a place is an index, a `.N` selector, or a field `.f`. The steps of the place come first, from the root outward. Each step charges 1 before it applies, as an expression node does. Then the index expression of an index step evaluates, and the index gets its static check (`S011` and `S013`). Then `e` evaluates. The assignment then replaces the selected part of the root.

Each step reads the live value of the root after its index evaluates, and its range check uses that value. The assignment writes into the live value of the root after `e` evaluates. A `mut` actual resolves its place by the same steps (section 9.1). `S008` keeps the root unchanged in the window of the place, so each read gives the value of the root when it became pending.

An index, in a place or in an expression, does its checks in this order after it evaluates:

1. The index is static (`S011`).
2. The indexed value can take an index, for example an array or a tuple (`S010`).
3. The index is a static `Int` or `UInt` (`S010`). Thus an `SInt` index is `S010`.
4. The index is in range (`S013`).

### 5.3 Instantiations

An `instance u = M(args);` statement elaborates as follows:

1. Evaluate the arguments from left to right. Each argument is a recursively static value.
2. Make the `InstantiationId`: the `ModuleId` of `M` and the canonical serialization of the arguments (section 7.1).
3. If the `InstantiationId` is in progress, report `S019` at the statement.
4. If the `InstantiationId` is done, use its result. Nothing more charges.
5. Otherwise, mark it in progress, elaborate `M` with the arguments now, and mark it done.
6. Bind `u` to an instance handle in the parent.

The table of instantiations is normative, as the table of constants is. The evaluation order fixes which use of an `InstantiationId` comes first. Both front ends thus elaborate and charge the same instantiations, and no implementation cache can change a result. A child elaborates before its parent continues. The first error is the first error in this depth-first order.

An instantiation elaborates in two steps:

1. It executes the module body.
2. It checks the bindings (`S018`) of its resources.

After the top instantiation, the elaborator lowers the design and runs the core checker on it (section 7.5).

### 5.4 Budgets and the cost model

One elaboration has two budgets. All parts of the elaboration share them, in the normative evaluation order: the top selection, each instantiation, and each constant. An `eval` command is its own elaboration. The defaults are normative. The budget values are build inputs, and the build record names them.

| Budget        | Unit                                                                | Default   | Flag      |
| ------------- | ------------------------------------------------------------------- | --------- | --------- |
| Fuel          | Cost units                                                          | 100000000 | `--fuel`  |
| Nesting depth | Active calls, instantiations in progress, and constants in progress | 1000      | `--depth` |

From slice 2 on, the nesting depth also counts the struct specializations in progress (section 5.6). It also bounds the depth of each value and each type (section 5.5). It needs no budget of its own.

The parse stage has one budget of its own: the **syntax depth** N. It bounds the depth of brackets and the height of an expression or a type (section 6.2). Its default is 4096, and the flag `--syntax-depth` sets it to a value from 1 to 65536. Another value is a usage error with exit code 2. Like the other budgets, it is a build input, and the build record names it. Compilation and validation use the same value. The default is far above the depth of written or generated code, so it is not a limit of the language.

The syntax depth bounds the native stack of each front end:

- The lexer rejects a bracket above the depth N, so the recursion of a parser stays bounded for any input.
- A parser builds a chain of binary operators, unary operators, fields, calls, or `else if` branches in a loop.
- After the parse, each recursive pass over the AST goes at most about 2N deep: N for the blocks and N for an expression.
- The Rust front end runs on a thread with a stack for the depth N. When the machine cannot give this stack, the command fails with exit code 2 before it parses.
- Each front end has a test at the default limit, a test at the depth 65536, and a test with 1,000,000 open brackets. Each gives the expected result and no stack overflow.

The cost model:

- Elaboration charges one cost unit before it evaluates an expression node.
- It charges one cost unit before it executes a statement. A block is a statement.
- A `comptime for` charges its statement once, and the sum of the sizes of its two bounds for the range. Each iteration then charges the size of its loop value before it binds it, and its body block charges once.
- A call charges its expression node. The body block of the callee charges as a statement.
- A type expression charges as an expression.
- An operation that makes a value charges a bound on the recursive size of that value, known before the operation runs. The bound holds up to a constant factor: `2^32 * 2^32` charges one word and makes two. A unary operation charges the size of its operand. An addition, a subtraction, and a bitwise operation charge the sum of the operand sizes. A conversion charges the operand size plus the result size. An operation that reads a value in full, for example a comparison or a serialization, charges its recursive size.
- An operation that only refers to a value charges no size: a name, a field selection, a static index, and `len`. A string is the exception (slice 2, below).
- A static condition, a static `&&` or `||`, and a static `if` that selects a value charge only their node. An `if` or a name that selects an existing value passes the reference on, so a later binding of it is a copy.
- A typed use converts a static integer to a finite value. These are typed uses: an annotation, an assignment, an argument, a return, a constant, `T(n)`, and an operand next to a finite operand. The copy comes first, then the conversion charge. A use of the same type charges no conversion.
- A typed use at `Nat` checks the sign before its charge. A typed use at a finite type checks the fit after its charge. Thus a negative integer at `Nat` is `S012` before the conversion charges. A typed use of a container checks the types and signs of all its elements before its charge. Thus a negative `Nat` element is `S012` before the charge, also after an earlier element that does not fit its finite type.
- A call of a builtin or of a constructor `T(x)` charges the sizes of its arguments as copies, before the type check and the conversion. The builtins are `resize`, `reinterpret`, `static_assert`, and `error`, and from slice 2 on `str` and `list`. `len` only refers to its argument, so it charges no copy.
- An explicit block `{ ... }` is one statement and charges once. The body of a call, each `comptime if` branch, and each loop iteration charge once each. The root name of an assignment target charges nothing. Each step of the target charges 1 (section 5.2).
- A copy charges the recursive size of the value. These are copies: a binding of an existing value, an argument, a return, a `mut` write-back, a `push`, and a `pop`. A binding of a value that its expression just made is not a copy.
- A serialization charges its length in bytes, and the decimal form of an integer charges the square of its size. The emitted name of an instantiation charges its length in bytes too.
- A multiplication, a division, and a remainder of static integers charge the product of the operand sizes. A left shift charges the size of its result. A right shift charges the size of its operand, because it reads the operand in full.
- An `instance` statement charges the recursive size of its arguments, also when the `InstantiationId` is done.
- A hardware operation makes one node and charges 1 plus the number of its operands. Its operand trees are shared, not copied. `&&`, `||`, and `if` on hardware values are hardware operations.
- The `cost` command attributes each charge to one instantiation. The parent pays for an `instance` statement, its serialization, and the emitted name of a new child. It also pays for each parameter type that gives a `[]` argument its type (section 5.1). The units of an instantiation do not include those of its children. The charges of the top selection belong to no instantiation, so `total` can exceed the sum of the lines.

The recursive size of a value counts each node and each payload, over all nested values:

- An integer has the size 1 for each 64-bit word of its magnitude, and at least 1. A finite value of type `UInt[w]` or `SInt[w]` has the size 1 for each 64-bit word of its width `w`, and at least 1. A Boolean, a handle, and a named function have the size 1.
- A string has the size 1 plus its number of characters.
- An array, a list, a tuple, and a record have the size 1 plus the recursive sizes of their elements.
- A type has the number of nodes of its normalized term, plus the size of each integer in it: `UInt[8]` has the size 2. A hardware value has the number of nodes of its tree without names.
- Slice 2 gives the terms of the new types. The unit value `()` and the types `Unit`, `String`, and `Type` have the size 1. `[T; N]` is a node with `T` and the integer `N`. `List[T]` is a node with `T`.
- A tuple type is a node with each element type. A function type is a node with each parameter type and the result type, and each `mut` mark is one more node.
- A struct type is a node with its static arguments as values. Its field types do not count, because its identity is nominal. Thus `P[8]` has the size 2.

An implementation can share immutable parts of a value. The charge is the recursive size all the same, so acceptance does not depend on the sharing.

- The lowering charges one cost unit for each core node that it emits. A core node is a design, a module, a port, a statement, a reset, a connection, or an expression node.
- The lowering runs in this order, which fixes the position of an `S015`: the instantiations in the order in which they finish. In a module: the module, the domain ports, the ports, the registers, the named `let` values, each `:=` binding with its connections, then the instances.
- The lowering units of a module count toward its instantiation. The design node and the name of the top count toward no instantiation.
- The design node and the name of the top charge last, at the position of the top selection. The top selection is a text of its own, so this position is line 1, column 1. Thus a fuel one unit below the total of `cost` gives `S015` at `1:1`.
- The lowering charges one cost unit for each core node that it emits. Each field of a core name charges its length in bytes, at least 1. A made field that holds an integer charges the square of the size of the integer, at least 1.

Slice 2 adds these charges. Each charge is known before its work, by the principle above:

- **Construction.** An array literal, a tuple literal, and a record constructor charge the recursive size of the result. The charge comes after the elements evaluate and before the construction. An element that refers to an existing value thus pays its copy here and nowhere else. `T(x)` of a scalar type keeps the rule of slice 1.
- **Zero.** `T()` charges its node and the recursive size of the result, before it builds the result. The type metadata below gives this size, so no walk measures it. Thus `[[UInt[8]; 1048576]; 1048576]()` fails with `S015` before any work.
- **`data_bits`.** `data_bits(T)` charges its node and the size of the width that it gives, because it copies the width. The type metadata below gives the width, so the size of `T` does not count.
- **Types.** A type constructor charges the recursive size of the type that it makes: `[T; N]`, a tuple type, `List[T]`, and a function type. A struct specialization has its own rule below. A type equality charges the sum of the two sizes.
- **Join.** The join of two types is their common type by the operand rule (section 5.1). An array literal joins the type of each element after the first with the join of the earlier elements, from left to right. `==` and `!=` on two arrays join their element types. A join walks both types together. It charges 1 for each pair of container types that it visits, before it visits the pair. A pair that is not two container types charges nothing. Thus `[1, 2]` charges no join, and `[[1], [2]]` charges 1. A join of two tuple types thus charges 1 for each pair of container types and nothing for its scalar pairs. The work stays bounded, because each tuple type paid for its parts, and a front end keeps the join of each pair of types. A pair of two struct types charges as a type equality, the sum of the two sizes, instead of 1, and compares the identities. A pair of two function types charges in the same way, and it needs two equal types, also in their `mut` marks. A pair of two container types of different kinds, for example an array and a tuple, charges 1 and then fails. A failed pair stops the walk. A pair of two list types charges 1 and joins the element types, as a pair of two array types does. `String` is not a container type, so a pair of two `String` types charges nothing.
- **Selection.** A static index, a field selection, and `len` of an array or a list only refer to a value. They charge no size.
- **Strings.** `len(s)` and `s[i]` charge the size of `s` before the scan, because a UTF-8 string needs a scan. `s[i]` charges it after the checks 1 to 3 of section 5.2 and before the range check. `+` charges the sum of the two sizes before it joins the strings. `str(n)` charges the copy of `n`, then the square of the size of `n` before the conversion, then the size of the result before the string value exists. A string that an operation just made binds without a copy, so a step `s = s + t` charges only its nodes and the sum.
- **Lists.** `list(T)` charges the copy of `T`, plus 1 for the empty list. `push` and `pop` charge the recursive size of the element. They change the live list place directly: they do not copy the list in, and they have no write-back. `S008` excludes an alias of the place, so the result equals the rule of section 9.1 for a `mut` actual. A loop that pushes `n` elements thus charges in proportion to the sum of the element sizes.
- **`push` and `pop` order.** Both charge their node and their function name, then resolve the steps of the place (section 5.2). `push` then runs in this order:
  1. The element evaluates.
  2. The place holds a list, else `S010`.
  3. The mutation rule of section 9.4 (`S016`).
  4. The element is not a hardware value, else `S011` at the element. Then the typed use of the element at the element type of the list.
  5. The depth check. Then the charge of the element, and the change of the list.
  6. The result is `()`, with no charge.
- **`pop` order.** After the steps of the place, the place holds a list, else `S010`. Then `pop` checks for an empty list (`S013`), then the mutation rule (`S016`). Then it charges the element and changes the list. Its result is a new value, so a binding of it is not another copy.
- **`push` depth.** `push` reads only the depth of the element. The root of the place is in the nesting depth, so only the path to the new element can go above it. The check thus counts the steps of the place, plus 1, plus the depth of the element. A depth above the nesting depth is `S015` at the call, before the list changes.
- **Receiver calls.** A receiver call charges as the call that it binds to. Its node charges first. Its function name then charges 1, as the callee name of a call does. The receiver and the explicit arguments then evaluate in their order (section 5.6). After all arguments run, the copies charge in the binding order of the parameters. Thus `x.m(a)` and `m(x, a)` charge the same units when the receiver binds to the first parameter.
- **Waiting results.** A node evaluates its operands in order. The result of an earlier operand waits while the later operands evaluate. The left operand of a binary operator other than `&&` and `||` waits, and so does the first arm of a hardware `if`. Each argument of a call, of an instance, of a type family, and of a struct use waits. The callee of a call that evaluates its callee waits too (section 5.6). Each element of a literal, the base of an index, and the lower bound of a `comptime for` wait too. The place of a `mut` actual or of an assignment target does not wait, because `S008` keeps its root unchanged in its window.
- **Held roots.** A waiting result **holds** a local when it refers to a static value in that local. Such a result is a name of the local, or an index, a selector, a field, or a static `if` that selects a part of it. A local is a **held root** while at least one waiting result holds it. A call runs in a new frame, so a waiting result of the caller holds no local of the callee.
- **Mutation of a held root.** The mutations are an assignment, a `push`, a `pop`, and a `mut` write-back. A mutation of a held root charges the recursive size of the root before the change. This charge comes after all other checks and charges of the mutation, immediately before the change. A mutation charges it once, also when more than one waiting result holds the root. A mutation of a root that is not held has no such charge. The charge pays for a copy of each waiting result that refers to the root. Thus an implementation can keep the value that each waiting result read. For example, `let y = xs[xs.pop()];` charges the size of `xs` at the `pop`, because the base `xs` waits while the index evaluates.
- **Shared lists.** An implementation can share a list with another binding. It then copies the list at the first change. The earlier copy of that binding paid for this work.
- **Static equality.** Equality of two containers, two strings, or two types reads both operands in full. It charges the sum of the two recursive sizes. The conversion of a static integer to the finite type of its pair charges nothing more.
- **Place update.** An assignment to a place with a step charges 1 for each step of the place, as an expression node does. Thus the charge pays for the walk over the path. It also charges the copy of its value, as each assignment does. The update copies only the containers on the path of the place, and it charges nothing more. A binding that shares a container paid for its copy before. Before the change, the assignment checks the depth of the root, as a `mut` write-back does. The depth is the number of steps of the place plus the depth of the value after its typed use. A depth above the nesting depth is `S015` at the assignment. The check comes after the typed use and the element checks of the value, and before the change. The copy and the conversion of the value charge before it, by the rule of typed uses.
- **Hardware equality.** Equality of a hardware aggregate walks both operands together (section 7.4). The walk charges 1 for each pair of parts before it visits the pair. Each static pair charges as a static equality. Each `icmp eq` node and each `and` node charges by the rule of hardware operations.
- **Hardware `if`.** A hardware `if` on an aggregate walks both arms together, with the same charge for each visited pair. It makes one `mux` node for each hardware pair and charges these nodes as hardware operations. Its static pairs charge as a static equality.
- **Serialization.** A serialization of a container charges 1 for each container node, for the walk that measures it. It then charges its length in bytes, as in slice 1. A scalar keeps the rule of slice 1, so the costs of slice 1 do not change. An integer in a type, for example a width or the length `N` of `[T; N]`, gets no charge for its decimal form.
- **Serialization parts.** The byte length of the text is the charge. An implementation measures this length first, charges it, and then makes the text. The earlier charges do not bound the work of the text. The text holds the element type of each array value and each list value. The recursive size of the value does not count this type. The Lean reference can make the text first, because only the charge is normative.
- **Calls through a function value.** They charge as a named call: the call node, the copies of the arguments, and the body block. The callee charges as an expression, and no function name charges.
- **`mut` formals.** The copy at the call and the write-back at the return each charge the recursive size of the value. Each step of a `mut` actual charges 1, as a step of an assignment target does (section 5.2). At the return, the write-backs run in the order of the parameters. Each write-back checks the mutation rule of section 9.4 (`S016`), then the depth, then charges, then writes into the live root. The depth check counts the steps of the place, plus the depth of a static value, as the `push` depth does. A depth above the nesting depth is `S015` at the call. The type of a value that is not static is the type of the place, so the root keeps its depth. A hardware result binds its core name `0ret` before the write-backs. Each write-back checks the mutation rule, also when the value did not change. Thus a `mut` actual with a root from before a hardware arm is `S016`. A write-back reports `S016`, `S015`, `S010`, and `S011` at the call.
- **`diagnostic`.** A call charges its node, then the serialization of its record (section 8.2). The charge does not depend on the display.
- **Aliases.** A `type` item and a `type` statement copy nothing. The type expression makes the type, and a use of the alias refers to it. A use of a done `type` item charges only its node, as a constant does.
- **Struct specializations.** Each use of a specialization charges the sum of the sizes of its arguments after their typed use. This charge comes before the lookup in the table, because the lookup reads the arguments in full. The first use then charges the size of the struct type once. It then evaluates the field types, and each one charges as a type expression. A later use refers to the done entry and charges nothing more (section 5.6).
- **Type metadata.** Each type carries four numbers. They are its bit width as hardware data, its leaf count, the recursive size of its zero value, and its depth. A type constructor computes them from the numbers of its parts when it makes the type. `Nat`, `Int`, `Type`, `String`, and `List[T]` are not hardware data, and their width, leaf count, and zero size are 0. The depth of `String` is 1. The depth of `List[T]` is 1 plus the depth of `T`. `List[T]` reads only the depth of `T`, so its metadata adds no charge to its type constructor. A function type is not hardware data either: its width, leaf count, and zero size are 0. Its depth is 1 plus the largest depth of a parameter type or the result type. A `mut` mark adds no depth. A function type has no metadata charge: its three numbers are 0, and its size charge covers its depth. `[T; N]` multiplies the width, the leaf count, and the zero size of `T` by `N`. Each of the three products charges as a multiplication of static integers: the product of the size of `N` and the size of the number of `T`. These charges come before `[T; N]` exists, at its node. A struct specialization computes them once, when it completes, from the stored numbers of its field types. Its depth also takes the depths of its static arguments. A tuple type and a struct specialization add the numbers of their parts. Before the sums, they charge the sizes of the four numbers of each part, because the sums read them. Then they charge the sizes of the four new numbers. Thus a struct with many fields of a type with a large width pays for each addition. No later operation walks the field types of a struct to get these numbers.
- **Function flag.** Each type also carries a flag: a function type is a part of it, at any depth. A type constructor computes the flag from the flags of its parts, with no charge. A struct specialization computes it from its field types when it completes. `==` and `!=` read this flag (section 5.1).
- **Big metadata.** The four numbers are integers of any size. A chain of structs that doubles at each step thus has an exponential width as a value. The charge-before-work rule then rejects each operation whose charge is too large, for example `T()`.
- **Struct values.** Each operation that reads a struct value in full charges its recursive size, as for each value: a copy, an equality, and a serialization.
- **Lowering.** No new rule. Each emitted core node charges one unit, so an aggregate pays for each of its leaves.

This section gives the principles of the cost model. `Source.Eval`, `Source.Elab`, and `Source.Flatten` are its normative definition: the exact charge of each operation, the order of the charges, and the position of each `S015`. The Rust elaborator matches them through `cost` and the corpus, not through this prose. The charge of an operation is known from the sizes of its operands, before the operation runs. When the fuel cannot pay a charge, elaboration fails with `S015` at the node of that charge. The operation then does not run.

When the nesting depth goes above its limit, elaboration fails with `S015` at the call, the `instance` statement, or the constant use that goes above it. From slice 2 on, it can also fail at the use of a struct specialization that goes above it. The nesting depth bounds the native stack of the Rust elaborator. Totality does not need it.

A top-level `const` evaluates once, at its first use. A table of constants holds each constant with one of three states: not started, in progress, or done with its value. This table is normative, because the first use fixes the order of the evaluation:

- A use of a constant in the state "in progress" fails with `S019` at that use. This rejects a constant that depends on itself, directly or through other constants.
- A use of a constant in the state "done" gives its value and charges only the use.
- A use of a constant in the state "not started" sets it to "in progress" and evaluates it.

The Lean evaluator `Eval` is total by the fuel alone. Each step charges at least one cost unit, and the fuel never grows. Proofs can thus use `Eval` directly.

### 5.5 Resource bounds

This section lists the paths by which a source could use resources. For each path, it states the bound. `F` is the fuel.

- **Evaluation work and memory.** Each operation charges the recursive size of each value that it makes, copies, or reads in full. An implementation without sharing thus allocates memory in `O(F)`. Sharing only lowers the memory. The work is in `O((F + s) log (F + s))`, where `s` is the size of the source. The reason is that the elaborators look up names and nodes in ordered maps, and a lookup costs the logarithm of the map size. This work bound is a claim about the Rust front end. The Lean reference defines the meaning and the fuel, but it compares types by structure, so its run time can be higher. Issue #196 tracks a type table for Lean. The theorem `eval_cost` is about the result for each fuel, not about the run time. The `eval` command pays for the printing of its result (section 8). The printing of an error message is outside this bound. An error message prints at most 256 bits of an integer, 64 characters of a string, and 1024 bytes of the text of a type. A type shares its parts, so its text can be exponentially longer than its size.
- **Nested aggregates.** A value that holds another value twice has at least twice its recursive size. A chain of such values thus doubles its charge at each step. The nested doubling of section 11.3 shows it: `let a_k = [a_(k-1), a_(k-1)];` charges `2^(k + 2) - 1` for its value. The join of its two element types visits `k` pairs of arrays and charges `k` more.
- **Nested values and types (slice 2).** A value and a type have a nesting depth. It is 1 for a part that is not a container. For a container, it is 1 plus the largest depth of an element. The depth of an array value and of a list value also counts its element type. It is 1 plus the largest depth of its element type and its elements. Thus the depth bounds each walk over an array or a list, also over an empty one. The depth of a record also counts its struct type in the same way. A type as a value has the depth of the type. The parts of a type are those of its term in section 5.4. The parts of a struct type are its field types and its static arguments. Thus the depth of a struct type is 1 plus the largest depth of a field type or an argument. The type metadata stores it, so no walk computes it again. The serialization, the equality, and the destruction of a type term thus stay within the depth budget. `()`, `Unit`, and a scalar type have the depth 1. A struct specialization whose depth goes above the budget fails with `S015` at the use that completes it, which is its first use. The depth of a new value or type is known before it exists. A depth above the nesting depth budget fails with `S015` at the node that makes the value or the type. Without this bound, a loop such as `t = [t; 1];` makes a type of any depth. Each recursive walk over it can then overflow the native stack: the size, the serialization, the equality, and the destruction.
- **Destruction (slice 2).** The work to destroy a value is at most the work that made it, because each node paid when it was made or copied. The depth of the value bounds the recursion of a destruction. An arena, as the Rust `elab` uses for hardware values, needs no recursion.
- **Static integer arithmetic.** A product grows the size additively, and its work is in the charge. A shift charges its result, so `1 << k` with a large `k` fails before it runs.
- **Collections and strings.** A copy, a concatenation, a comparison, and a serialization charge the recursive sizes. A `push` and a `pop` charge the recursive size of the element. `len` and an index of a string charge the size of the string, and `str(n)` charges as section 5.4 gives.
- **Types.** A struct specialization pays for its size and its field types once (section 5.6). Each use pays for the sizes of its arguments, so the lookup in the table is linear in the charge. A generated record type (slice 4) has the recursive size of its normalized term, so nested `@Struct` calls pay like nested aggregates.
- **Memory (slice 2).** The lowering of a memory emits a fixed number of core nodes, plus one node for each leaf of its word type. The fit rule bounds the depth and the word width (section 7.6).
- **Instantiations.** A new `InstantiationId` elaborates once and charges its body. A repeat charges only its `instance` statement and its arguments. A tree of distinct instantiations thus costs at least one unit for each node. A shared hierarchy costs one elaboration for each distinct `InstantiationId`.
- **Output size.** Each emitted core node charges one unit, and each user field of a core name charges its length in bytes. A made field that holds an integer has at most 20 bytes for each unit of its charge. Each `$` separator belongs to a paid field. The output thus has at most `F` nodes and `O(F)` bytes of names. The temporaries of section 7.4 keep it also linear in the source.
- **Constants.** Each constant evaluates once, and a cycle fails with `S019`. A use refers to the value, and a copy of it pays its recursive size.
- **Stack.** The nesting depth bounds it. From slice 2 on, it bounds the depth of each value and each type too.
- **Front-end passes before elaboration.** The lexer and the parser are linear in the source. The resolver and the generic pre-check are linear up to a factor `log n` for name lookups in ordered maps, which keep the result deterministic. `S008` is the exception. A simple check of `S008` is quadratic in the size of one call. A counter for each root makes it linear.
- **After elaboration.** `canonicalize` sorts, in `O(n log n)` for `n` core statements. The Lean core checker is near-linear since issue #23 closed. `canonicalize` is the one path whose work grows faster than the output.

The oracle of the cost model is the command `cost` (section 8). Both implementations print the same total and the same units for each instantiation.

### 5.6 Items, types, and calls of slice 2

Slice 2 adds these items and calls:

- **Structs.** `struct P(comptime W: Nat) { a: UInt[W], b: Bool }` declares a record type with parameters. `P[8]` is a struct specialization, and `P[8](x, y)` constructs a record. A struct without parameters has the use `P` and the constructor `P(x, y)`. Each struct parameter has `comptime`. A struct parameter without `comptime`, also a `mut` parameter, is `S001`. This agrees with v0.1, where a struct declaration takes only static parameters, and with the rule for module parameters. A message names a struct type in its source form, with its arguments as literals, for example `P[8]`. A use of a struct with parameters without its arguments, for example `P` or `P(x, y)`, is `S007`.

- **Specialization table.** A table of struct specializations holds each specialization with one of three states: not started, in progress, or done with its field types. The table is normative, as the table of constants is. The key of a specialization is its struct item and its static arguments, each after its typed use at its declared parameter type. These are the normalized identities of v0.1. Thus `P[8]` and `P[UInt[4](8)]` are one type when the parameter of `P` has the type `UInt[4]`. The first use evaluates the field types. A later use charges only its node and the sizes of its arguments (section 5.4). A use in the state "in progress" fails with `S019`. A recursive hardware type is thus `S019`. A specialization in progress counts toward the nesting depth, because the first use of a chain of distinct structs evaluates their field types recursively. `S015` is then at the use that goes above the depth.

- **Type aliases.** `type A = T;` at the item level is a constant of type `Type` in the table of constants. In a block, it is a local of type `Type` that evaluates at its statement. An alias that depends on itself is `S019`. An index of a `type` item is `S007` in pass 4. An index of a local that holds a type is `S007` in pass 5, at the index node, after the base evaluates.

- **Static types.** A `comptime T: Type` parameter, a local of type `Type`, and a type equality are static. A local can be a type name. Thus `fn f(Bool: Nat, x: Bool)` resolves, and elaboration gives `S010` at the type name `Bool` of `x`, because the local holds no type.

- **Zero and size.** `T()` gives the static recursive zero of a hardware data type `T`: 0 for each integer leaf and `false` for each `Bool` leaf. `data_bits(T)` gives the number of bits of a hardware data type. `Bool` has 1 bit, `UInt[W]` and `SInt[W]` have `W` bits, and `Unit` has 0 bits. An array has `N` times the element size. A tuple and a record have the sum of the element sizes. For a type that is not hardware data, both are `S010`. The argument of `data_bits` is not a static position, so pass 4 does not check it. An argument that is not a type is `S010` in pass 5. `T()` of a struct type is always the zero, never a constructor without arguments. Thus `P()` of a struct with fields that are not hardware data is `S010`, not `S007`. A struct without fields is hardware data with 0 bits and no leaf.

- **Parameter modes.** A parameter has one of three modes: none, `comptime`, or `mut`. A parameter with both marks is `S001` at the second mark. A module parameter has the mode `comptime`, as a struct parameter has, so `mut` there is `S001`. Only a parameter of a `fn` or a `comptime fn` can have the mode `mut`.

- **Receiver calls.** `x.m(args)` calls the function `m`. `m` resolves in the item namespace, then in the prelude namespace, and never to a local. A name `m` that resolves to no function there is `S003` at `m`. `(obj.f)(args)` calls a function value in a field. The resolver makes this choice from the syntax only. A receiver call is its own node, at the position of `x` (section 7.3).

- **Receiver binding.** The receiver binds to the first parameter of `m` that has no written `comptime` mark. The rule counts the written marks, also in a `comptime fn`. If each parameter has the mark, the call is `S007`. The rule holds for each function, also for each prelude function.

- **Receiver order.** The receiver evaluates first, then the explicit arguments from left to right (v0.1, section 2). The binding order thus differs from the evaluation order. For example, `xs.append(T, v)` binds as `append(T, xs, v)`, but `xs` evaluates before `T`.

- **Prelude signatures.** The prelude functions of slice 2 have these parameter modes. The receiver column follows the receiver binding rule.

  | Function                    | Modes             | Receiver binds to |
  | --------------------------- | ----------------- | ----------------- |
  | `resize(T, x)`              | `T` is `comptime` | `x`               |
  | `reinterpret(T, x)`         | `T` is `comptime` | `x`               |
  | `list(T)`                   | `T` is `comptime` | None: `S007`      |
  | `data_bits(T)`              | None              | `T`               |
  | `push(xs, x)`               | `xs` is `mut`     | `xs`              |
  | `pop(xs)`                   | `xs` is `mut`     | `xs`              |
  | `len(x)`, `str(n)`          | None              | `x`, `n`          |
  | `static_assert(c, message)` | None              | `c`               |
  | `error(message)`            | None              | `message`         |

  `diagnostic`, `read_port`, and `write_port` have no `comptime` and no `mut` parameter. A static position of a prelude call is an argument at a `comptime` parameter, and each argument of `static_assert` and `error`. Thus the argument of `list(T)` is a static position, and the arguments of `data_bits(T)` and `str(n)` are not. `T.data_bits()` thus binds its receiver to `T`.

- **`mut` formals.** A `mut` formal and a `mut` receiver follow section 9.1. A `mut` actual is a place with a mutable root (section 9.1). The type of the place equals the type of the formal, because a `mut` actual gets no typed use. Another type is `S010`. The type of a place is its declared type: the annotation of the root, through the steps of the place. A root without an annotation gives the type of the value. Thus a place of a `let mut` local of type `Nat` at an `Int` formal is `S010`.

- **Calls through a function value.** A call whose callee is not the name of a function item or of a prelude function evaluates its callee once, before the arguments. The value of the callee then selects the call:

  - A type gives a constructor call: `T()`, `T(x)`, or a record constructor. A function type `T` is not hardware data, so `T()` and `T(x)` are `S010` at the call. This holds for each number of arguments. The error comes after the callee and before the arguments.
  - A function value gives a call of its function item, as below.
  - Another value is `S010` at the call.

  A call of a function value compares the number of arguments with its function type before the arguments evaluate. A difference is `S007` at the call, in pass 5. The arguments then evaluate in their order. The `mut` marks of the function type select the `mut` actuals. The lookup of the function item of the value has no charge, because the factor `log n` of the work bound covers it. The call then runs as a named call of the function item. This includes the copies, the call frame of section 7.3, the body, the result, and the write-backs. A `comptime fn` thus runs in the mode `static` (section 9.4), and a hardware argument is `S011`, as at a named call.

- **Diagnostic records.** A call of `diagnostic` appends one observation record (section 8.2).

### 6.2 Report order

Both front ends apply the passes in order. They stop at the first pass with an error.

| Pass | Codes                                                                                                                                            | Order in the pass                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| 1    | `S001`, `S004`                                                                                                                                   | Position                                       |
| 2    | `S002`                                                                                                                                           | Position                                       |
| 3    | `S003`                                                                                                                                           | Position                                       |
| 4    | `S005` to `S008`                                                                                                                                 | Position                                       |
| 5    | `S007` at a call through a function value or at an index of a type in a local (section 5.6). `S008` at run time (section 9.1). `S010` to `S019`. | Evaluation order (section 5.2 and section 5.3) |
| 6    | `S020`                                                                                                                                           | Position                                       |

Position order is the lowest line, then the lowest column. In pass 5, the first error in the evaluation order wins. `S018` comes at the end of the body of its instantiation. In one instantiation, the `S018` errors compete by position.

The position of an error is:

- `S001`: the first token that does not match, or the end of the file.

- `S001` for a number literal above its limit: the literal.

- `S001` for the brackets: the first `(`, `[`, or `{` at the depth N + 1. The lexer marks this bracket as an error token. The depth counts all three kinds of brackets together.

- `S001` for the height: the first token of the first outermost expression or type, in position order, whose height is above N. This check runs only after pass 1 finds no other error. An outermost expression or type is not part of another expression or type. The height of a leaf is 1, and each node of the AST adds 1. Parentheses make no node.

- `S002`: the name in the second declaration.

- `S004`: the reserved token, or the first token of the construct.

- `S008`: the second mutation of the root. This is the `mut` actual with the root `R` in the window of `R`, thus the second of two `mut` actuals with one root. For a `mut` actual that is not a place or whose root is not mutable: the start of the actual.

- Pass 4 at one position: a receiver call starts at its receiver, so its `S007` can share the position of an `S005` or an `S008` at the receiver. The first error is `S007`, then `S008`, then `S005`.

- `S015`: the node of the charge, or the node that goes above the budget.

- `S010` to `S014`, `S016`, and `S017`: the start of the node whose evaluation fails.

- `S018`: the second binding. If there is none, the declaration of the resource. For a child input, the `instance` statement.

- `S019`: the `instance` statement, the use of the constant in progress, or the second declaration with the same core name.

- `S020`: the source position of the core node with the lowest source position on the cycle.

- Slice 2 adds these positions:

  - `S003` for a receiver call: the name of the function.
  - `S006`: the `mem` statement or the memory port call.
  - `S007` for a receiver call: the start of the call, which is the start of the receiver.
  - `S011`: the index expression, or the element. For two different static leaves in the arms of a hardware `if`: the start of the `if`.
  - `S012`: the `mem` statement.
  - `S010` for an index with two or more arguments: the start of the index node. For an order operator or an equality on containers: the start of the operator node.
  - `S013`: the index expression, the number literal of a `.N` selector, or the call of `pop`.
  - `S015` for the depth of a value or a type: the node that makes it. For a `push` and a `mut` write-back: the call.
  - `S016`: the node of the effect. For a `push`, a `pop`, and a `mut` write-back: the call.
  - `S017`: the node of the target, or the statement. A `:=` target with a step (section 5.2) gives `S017` at the start of the target, before its indices evaluate.
  - `S018` for a memory: the second `read_port` or `write_port` call. If there is none, the `mem` statement.
  - `S019`: the use of the specialization or the alias that is in progress.

- All other errors: the start of the form that breaks the rule.

The error line has the form of the core IR: `error[S010]: 12:5: <message>`. The message names the instantiation path, as v0.1 section 9 requires. The harnesses compare the code, the line, and the column, but not the message.

### 6.3 Diagnostics

A diagnostic is the report of one error. Section 6.1 and section 6.2 make its code and its line normative. The other parts of a diagnostic help a human or an agent fix the error. Lean does not model these parts. [ADR 0014](../adr/0014-structured-diagnostics.md) records the decision.

The records of the v0.1 builtin `diagnostic` are observation records, not diagnostics. This section does not change them.

**Structure.** The crate `diagnostics` defines the diagnostic type. Each stage returns diagnostics as values and prints nothing. A diagnostic has these parts:

| Part            | Content                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------- |
| Code            | `S001` to `S020`                                                                          |
| Primary span    | The position of section 6.2, with a label                                                 |
| Secondary spans | Related positions, each with a label. Example: the first declaration of an `S002` name.   |
| Notes           | Facts about the error: the actual and the expected values (v0.1 section 9), the backtrace |
| Help            | One sentence that tells how to fix the error                                              |
| Suggested edits | Text replacements, each with an applicability                                             |

An applicability has one of two values:

- **Machine-applicable.** The edit is correct. A tool can apply it without a human.
- **Maybe-incorrect.** The edit can be wrong. A human or an agent must look at it.

**Instantiation backtrace.** An error of pass 5 occurs in one instantiation. A note lists the chain of `instance` statements from the top selection to that instantiation, with a span for each statement. This is the form of the "required by" notes of rustc. It gives the instantiation path that v0.1 section 9 requires.

**Renderers.** The `driver` renders the diagnostics. The flag `--error-format` selects the form:

| Value   | Form                                                                                  | User                     |
| ------- | ------------------------------------------------------------------------------------- | ------------------------ |
| `human` | The form of rustc: source snippets with labelled spans, made with `annotate-snippets` | A human on a terminal    |
| `short` | One line for each diagnostic: `error[S010]: 12:5: <message>` (section 6.2)            | The harnesses, and Lean  |
| `json`  | One JSON object for each diagnostic, with all parts, on one line                      | An LLM agent and the LSP |

`human` is the default. The fields of `json` are a contract: a change of a field is a breaking change of the command-line interface.

**`silicon explain`.** `silicon explain S010` prints the long text of a code: the rule, a failing example, and a fixed example. Each code has one text in the crate `diagnostics`. A test elaborates both examples of each text. The failing example must give its code, and the fixed example must give no error.

**Recovery.** The front end reports more than one error. Each stage continues after an error where it can, and reports all errors of the first pass that has errors. It does not start a later pass (section 6.2). Only the first error is normative: Lean defines it, and the harnesses compare it. The later errors have no oracle.

**Trust.** A diagnostic does not change the result. The result is the accept or reject decision, and for a reject the first code, line, and column. A wrong help or a wrong edit can thus mislead a user, but it cannot make a wrong design pass.

**Quality loop.** These checks keep the diagnostics useful:

1. **Snapshots.** Each file of `tests/source/check/` has an `insta` snapshot of its `human` and `json` output. A snapshot is a review aid (section 10.2).
2. **Machine-applicable edits.** For each file of `tests/source/check/` and `tests/source/llm/`, a test applies all machine-applicable edits. The edited file must not give the same diagnostic again.
3. **Corpus of LLM mistakes.** `tests/source/llm/` holds the mistakes that LLM agents typically make in Silicon, for example Verilog syntax or a missing width. Each file has its expected first error and a fixed version.
4. **One-turn-fix metric.** A harness gives an LLM a file of `tests/source/llm/` and its `json` diagnostics, for one turn. The metric is the fraction of answers that elaborate and pass the source vectors of the fixed version. The project pins the model and its settings. A CI gate fails when the metric falls below the recorded baseline.

## 7. Lowering to core IR

### 7.1 InstantiationId and emitted module names

An `InstantiationId` is a `ModuleId` and the canonical serialization of the static arguments. Up to slice 5, the `PackageId` of each `ModuleId` is the root package, `root`. `Source.Value` defines the serialization. Slice 1 has these forms:

```text
(int -5)  (bool true)  (string "a\"b")
(instantiation root Counter ((int 8)))
```

Slice 2 adds the forms of the containers, the types, and the functions. Each container form records its type where its elements cannot give it, so the serialization stays injective for each type:

```text
(unit)
(array (uint 8) ((uint 8 1) (uint 8 2)))     (array bool ())
(tuple ((int 1) (bool true)))
(record (struct root Packet ((int 8))) ((uint 8 3) (bool false)))
(list int ((int 1) (int 2)))
(function root inc)
(type (array (uint 8) 4))   (type (tuple (bool (uint 8))))   (type (list int))
(type (fn ((mut (uint 8)) bool) unit))   (type string)   (type type)   (type unit)
```

A struct type serializes its declaration and its static arguments, because its identity is nominal. A function serializes its package and its name.

The emitted module name of an instantiation is one of two forms:

- **Readable.** The module name, then `$` and one token for each argument. An integer token is its decimal value, with the suffix `n` for a negative value: `-5` gives `5n`. A Boolean token is `1b` or `0b`. Examples: `Counter$8`, `Fifo$16$1b`. A module without arguments keeps its name.
- **Digest.** The module name, then `$0h` and the first 16 hexadecimal digits of the SHA-256 of the serialization. Example: `Fifo$0h3f2a9c0b1d4e5f60`.

The readable form applies when each argument is an integer or a Boolean and the name has at most 64 bytes. The limit applies also to a module without arguments. Otherwise, the digest form applies. A container, a string, a type, or a function as an argument thus gives the digest form (slice 2). Only a truncated digest can make two identities share an emitted name. Elaboration then fails with `S019`. It never merges two modules.

Slice 5 adds the package prefix of [ADR 0007](../adr/0007-mandatory-uniquification.md). It closes the open grammar of that ADR. Issue #53 tracks the gap until then. The plan for slice 5:

1. **Identity propagation.** The `PackageId` from the Lattice lock is part of each `ModuleId`, and thus of each `InstantiationId`. The core module name is the only carrier of the identity after elaboration. `backend-circt` keeps the core module name unchanged, so uniquification happens in one place: the elaborator.
2. **Uniquification.** The emitted name gets a prefix from the full `PackageId`: the package name, the version, and a digest of the `PackageId`. The name and the version alone are not sufficient, because two sources can give the same name and version. The prefix uses the field kinds of section 7.2, so `decode` stays injective. A prefix longer than the limit of the readable form takes the digest form. The slice 5 spec update gives the exact grammar.
3. **Name map.** Elaboration writes a map from each emitted module name to its `PackageId`, `ModuleId`, and arguments. RTL, formal artifacts, and debug tools read this map.
4. **Collision tests.** A corpus design uses two versions of one package with the same module name. A second corpus design uses one version of one package from two sources. Each design must give two emitted modules, and LEC checks each against its source. `names_injective` covers the prefixed names. A unit test in each front end makes two identities share a digest through a test digest function, and expects `S019`.

### 7.2 Names without collisions

The language reserves no name. A user can name a port `clk`, `add`, or `silicon_reg_x`. Elaboration keeps user names and made names apart by construction, not by a rule for the user.

The core IR spec (#39) defines the form of a core name: a list of fields, joined by one `$`. Its pattern is `[A-Za-z_][A-Za-z0-9_]*(\$[A-Za-z0-9_]+)*`. A core name thus never contains `$$`. Each field has one of two kinds:

- **User field.** It starts with a letter or `_`. It is a source name unchanged. A source name has no `$`, so it needs no escape.
- **Made field.** It starts with a digit. Only elaboration makes it. The table below lists its forms.

| Made field                                                    | Meaning                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------ |
| `5`, `5n`                                                     | A loop value or an integer argument. `n` marks a negative value.   |
| `3c`                                                          | The call site `3` of a call frame                                  |
| `2v`                                                          | The version `2` of a binding (section 7.3)                         |
| `1b`, `0b`                                                    | A Boolean argument                                                 |
| `0h<hex>`                                                     | A digest                                                           |
| `0k`                                                          | The escape of a core keyword                                       |
| `4t`                                                          | The temporary `4` of a statement (section 7.4)                     |
| `2e`                                                          | The element `2` of an array or a tuple (slice 2, section 7.3)      |
| `0clk`, `0rst`, `0ret`, `0rdata`, `0rvalid`, `0ren`, `0raddr` | A role: clock, reset, call result, memory response, memory request |

The decoder splits a name at each `$`. No field contains `$`, so this split is unique. The first character of a field then gives its kind. The first field of each name is a user field.

The core IR still rejects a keyword as a name (core IR spec, section 3). A user name alone that equals a core keyword thus gets the field `0k`: a port `add` becomes `add$0k`. No other name gets `0k`. A name with a separator is never a keyword.

The proof obligation is injectivity. A name structure is valid when each user field is a source identifier and each digest is non-empty lowercase hex. `Source.Names` defines a function `decode` with `decode (encode p) = some p` for each valid name structure `p`. An invalid structure can collide: `a$b` alone and `a` with the user field `b` both give `a$b`. The theorem `names_injective` follows from it (section 10.3). The function `encode` also gives only names that match the core name pattern and are not keywords. These are the oracles:

- A Lean unit test and a Rust `proptest` test of the round trip on random name structures.
- A file of `tests/source/corpus/` with user names equal to each core keyword and to each made field form. It also uses backend kinds, for example `reg` and `mem`, and `silicon_reg_r`. From slice 2 on, its record fields use the same names, so the leaf names cover them too.
- The generator (section 11.4) takes user names from the same list.

Issue #39 removes the reserved prefix `silicon_` from the core IR. The backend and the oracles then make names that contain `$$`, for example `reg$$<n>`. A core name never contains `$$`, so no name of the front end can collide with a backend name.

### 7.3 Structural paths

Each declaration and each binding of a hardware value gets a core name. The name is its structural path: the frames that enclose it, then its source name. `$` separates the fields. The frames, from the outside in:

- **Loop frame.** A `comptime for` iteration gives the field pair `<binder>$<value>`, for example `i$2`. A negative value has the suffix `n`.
- **Call frame.** A call of an ordinary function gives the field pair `<fn>$<k>c`. `k` counts from 0 over the distinct start positions of the call nodes of the enclosing body, in source order. It is the index of the start position of the call. Two call nodes with one start position, such as `uint(8)(x)`, share `k`.

Examples: a register `r` in the loop body at `i = 2` is `i$2$r`. A `let t` in the helper `f`, at the first call site, is `f$0c$t`.

**Call sites from slice 2 on.** A receiver call `x.m(a)` starts at the position of `x` (section 5.6), and a call inside `x` can start there too. Positions thus no longer tell two call nodes apart. From slice 2 on, this rule replaces the rule of the call frame above:

- `k` counts from 0 over the call nodes of the enclosing body, in pre-order of the resolved AST. A call node comes before its callee and its arguments.
- The children of a node come in source order: the order of their first tokens in the written source. Two children never share a first token. The rule thus does not depend on the field order of a constructor in `Source.Syntax` or in the Rust AST.
- Each call node gets its own `k`. Both front ends key a call site by its node, not by its position.
- The receiver-call node has the receiver as its first child, before the explicit arguments. When `m` has no leading `comptime` formal, `x.m(a)` and `m(x, a)` thus give the same `k`. The metamorphic pair of section 11.3 covers this case only.
- For the syntax of slice 1, the new order differs only where two call nodes share a start position, for example the constructor call `uint(8)(x)`. The outer call then gets the lower `k`, and the inner call gets its own `k`.
- Thus one case of slice 1 gets new core names: a body with such a constructor call before a function call. Each later call frame `<f>$<k>c` of that body moves up by one. Decision F18 records this change.
- Lean `Source.Resolve` and the Rust `resolve` give each call node its call site. They changed together, in the phase that brings receiver calls (section 14.2). The changed expectations of the slice-1 `elab` files land in a commit that changes only tests.

A call through a function value (slice 2) gives the call frame `<f>$<k>c`, where `f` is the name of the called function, not of the callee expression. The frame thus names the code that runs.

These bindings get a core name:

- A port, a register, a wire, a memory, and an instance.
- A `let` or an assignment `=` that binds a hardware value.
- A hardware argument of an ordinary function call. Its source name is the formal parameter.
- The hardware result of an ordinary function call. It gets the role field `0ret` after its call frame.

One frame can bind one source name more than once, for example in an assignment to a `let mut` binding. The first binding keeps the path. The binding with index `n ≥ 1` gets the made field `<n>v`. The count includes the ports and covers all bindings of the frame that get a core name, in evaluation order.

A `mut` write-back (section 9.1) binds a new version of the caller root in the caller frame, as an assignment to the place does. When the new value of the root has a hardware leaf, the write-back counts. For example, a call `f(x)` with a `mut` formal of a hardware type gives the root `x` its next version, `x$1v` after the first binding.

From slice 2 on, an aggregate binding counts once, as one binding of its source name. All its leaves share its version, for example `q$1v$a` and `q$1v$b`. A binding counts only when at least one of its leaves gets a core name. A binding whose leaves are all static, and an empty binding, thus do not count.

A static value gets no core name. A handle alias, for example `let a = q`, gets no core name. A port keeps its source name, because the port names are the interface. Two ports with one name, for example from a loop, fail with `S019`.

The paths are injective by section 7.2. A frame is a user field and a made field. The name of the binding is a user field. A version or a role is a made field at the end.

**Leaves (slice 2).** Each leaf of an aggregate binding gets a core name. The leaf part follows the name of the binding and its version:

```text
path  ::= frame* NAME version? leaf* (role | temp)?
frame ::= USER <value>  |  USER <k>c
leaf  ::= USER          ; a record field
        | <k>e          ; an array index or a tuple element
```

Examples: the field `a` of the port `p` is `p$a`. The element 2 of the register `r` is `r$2e`. The element 0 of the field `xs` of the second version of `q` is `q$1v$xs$0e`.

The made field `<k>e` is new in slice 2. The integer field `5` cannot serve: the leaf `p.0.x` would give `p$0$x`, which equals the register `x` in the loop frame `p$0`. A static leaf and an empty leaf get no core name. `names_injective` covers the field `<k>e`.

A path contains no byte offset, because with byte offsets each edit, even one blank line, would rename each later declaration. This is a change from v0.1 section 4.

### 7.4 Expressions

Each core name gets one core statement. An expression without a name stays inline in the statement of its binding. The lowering keeps each inline expression at most 64 nodes high. It computes an effective height bottom-up. A leaf, a reference to a named binding, and an operand that binds to a temporary have the effective height 1. A node whose effective height reaches 64 binds to a temporary, as an operand that is used twice does. The value of the statement itself never binds. Each row of the table below adds at most 4 core levels. A core expression thus nests at most 256 levels, the limit of the core IR. A binding with a name breaks the nesting, so a call chain cannot go above the limit.

In this table, `w` is the width of the left operand, and `c` has the width `wc`.

| Source                                    | Core                                                                                         |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `Bool`, `UInt[W]`, `SInt[W]`              | `(bits 1)`, `(bits W)`, `(bits W)`                                                           |
| Literal or static finite value `v`        | `(const w v mod 2^w)`. `true` is `(const 1 1)`.                                              |
| `a +% b`, `a -% b`, `a *% b`              | `(add a b)`, `(sub a b)`, `(mul a b)`                                                        |
| `-a` on a finite integer                  | `(sub (const w 0) a)`                                                                        |
| `~a`, `a & b`, `a \| b`, `a ^ b`          | `(not a)`, `(and a b)`, `(or a b)`, `(xor a b)`                                              |
| `!a`, `a && b`, `a \|\| b` on hardware    | `(xor a (const 1 1))`, `(and a b)`, `(or a b)`                                               |
| `==`, `!=`                                | `(icmp eq a b)`, `(icmp ne a b)`                                                             |
| `<`, `<=`, `>`, `>=`                      | `icmp` with `ult`, `ule`, `ugt`, `uge` for `UInt`, and `slt`, `sle`, `sgt`, `sge` for `SInt` |
| `a << c`, `a >> c`, equal widths          | `(shl a c)`; `(shru a c)` for `UInt`, `(shrs a c)` for `SInt`                                |
| Shift, `wc < w`                           | The count is `(concat (const (w - wc) 0) c)`                                                 |
| Shift, `wc > w`                           | `(mux (icmp uge c (const wc w)) F (op a (extract c 0 w)))`. `F` is the fill.                 |
| Shift by a static count `k`               | The count is `(const w (min k w))`                                                           |
| `if (c) { a } else { b }` on hardware     | `(mux c a b)`                                                                                |
| `resize` to a smaller width `n`           | `(extract a 0 n)`                                                                            |
| `resize` of `UInt` to a larger width      | `(concat (const (n - w) 0) a)`                                                               |
| `resize` of `SInt` to a larger width      | `(concat (replicate (extract a (w - 1) 1) (n - w)) a)`                                       |
| `reinterpret`, `resize` to an equal width | `a`                                                                                          |

The fill `F` is `(const w 0)` for `<<` and for `>>` on `UInt`. For `>>` on `SInt`, it is `(shrs a (const w (w - 1)))`.

A width `w` fits in `wc > w` bits, and `w - 1 < 2^w`. The constants of the table thus always pass `E005`.

Two rows use an operand more than once: the shift with `wc > w` uses `c` twice, and for `SInt` also `a`. The `resize` of `SInt` to a larger width uses `a` twice. Inline copies would make the output grow exponentially with nested operations. The lowering thus obeys this rule:

- A rule can use an operand more than once. If that operand is not a core name or a constant, the lowering first binds it to a core `let`.
- The name of this temporary is the core name of the target of the statement, then the made field `<k>t`. For a child input `u.a`, the target is the instance path, then the user field `a`.
- `k` counts the temporaries of the statement from 0, in evaluation order.
- From slice 2 on, an aggregate statement gives one core statement for each leaf. Each leaf statement has the leaf name as its target and its own count `k`.
- A temporary that several leaf statements share belongs to the first leaf statement that gets a core name. It counts there before the own temporaries of that statement.
- The `write` statement of a memory `m` has the target `m` (section 7.6). Its temporaries are thus `m$<k>t`, for example for a long `concat` chain of the write data.

Each source node thus gives a bounded number of core nodes, and the output size stays linear in the source. The rule needs no budget for the output size.

Slice 2 lowers a hardware aggregate to its leaves ([ADR 0019](../adr/0019-aggregates-lower-to-leaves.md)). The core IR has only `(bits N)`, so each leaf becomes one core value of its scalar type. In this table, `T` is the type of a hardware aggregate. `a_i` and `b_i` are the leaves `i` of `a` and `b` in packing order (section 7.5):

| Source                                     | Core                                                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `a == b` of type `T`                       | `E_0` is `(icmp eq a_0 b_0)`, or `(const 1 s)` when static pairs exist. `E_i` is `(and E_(i-1) (icmp eq a_i b_i))`. The last `E_i` is the result. |
| `a != b` of type `T`                       | `(xor E (const 1 1))`, where `E` is the core of `a == b`                                                                                          |
| `if (c) { a } else { b }` of type `T`      | `(mux c a_i b_i)` for each hardware pair `i`. A static pair gives its one static value.                                                           |
| `x.f`, `x.0`, and `x[i]` with a static `i` | The selected leaf or subtree. No core node.                                                                                                       |

The lowering walks the two operands of `==`, `!=`, or a hardware `if` together, by their one type. At each pair of corresponding parts, the first rule that applies holds:

1. An array, a tuple, or a record: the walk descends into the pairs of its elements, in packing order.
2. `()`: the pair adds nothing.
3. A part of a type that is not hardware data, for example a list, a string, a type, an `Int`, or a function: a **static pair**. Such a part never holds a hardware leaf, so both sides are static. Its value includes its shape, for example the length of a list.
4. A scalar part of a hardware data type: a leaf pair. In `==` and `!=`, a leaf pair with two static leaves joins the static pairs. Each other leaf pair is a hardware pair.

A static leaf in a hardware pair lowers to a constant by the row "Literal or static finite value". The table then reads `i` over the hardware pairs only, in the order of the walk. The walk charges 1 for each pair of parts that it visits, before it visits the pair. These rules apply to the static pairs:

- `==` and `!=` compare the static pairs at elaboration time, by the static equality of section 5.4. This equality is structural, so it compares the length of each list. `s` is `1` when all static pairs are equal, and `0` otherwise. `E_0` is then `(const 1 s)`, and each hardware pair joins with `and`.
- An equality of two aggregates without a hardware leaf is a static equality. It makes no core node.
- A hardware `if` needs equal static pairs. A static pair whose two sides differ is `S011`, because a static part cannot depend on the hardware condition. The error is at the start of the `if`.
- The scalar case follows the same rule. Take two static arms of a type that is not hardware data, for example `Int`, `String`, or `Type`. Thus `if (h) { 3 } else { 3 }` with a hardware `h` gives the static value 3, and `if (h) { 3 } else { 4 }` is `S011` at the start of the `if`. Two function arms follow the same rule: one function gives the static value, and two different functions are `S011`.
- Slice 1 gives `S010` for each such scalar `if`, because the Lean `mux` lowers each static arm to a hardware constant. Decision F19 records the change. Lean and Rust change together in phase 6 of section 14.2. The changed expectations of slice 1 land in a commit that changes only tests.
- `==` and `!=` with a type that holds a function type are `S010` before the walk (section 5.1). A hardware `if` compares two functions in a static pair by their function items, and charges this as a static equality.
- In a hardware `if`, a leaf pair with two static leaves is a hardware pair. It lowers to constants, as in slice 1.

The condition `c` of an aggregate `if` is an operand that the leaves use more than once. When `T` has two or more leaves, `c` thus binds to a temporary, unless it is a core name or a constant. Each leaf statement uses this temporary, so it belongs to the first leaf statement, as the rules above give. The chain of `and` nodes obeys the height rule of this section. A hardware index of an array is `S011`.

### 7.5 Statements, ports, and the domain

Slice 1 has one domain or none. A module has the clause `domains(d)` with one name, or `domains()`. Without a clause, the domain is `clock`. A clause with more than one name is `S004` in the parser.

| Source                         | Core                                                                   |
| ------------------------------ | ---------------------------------------------------------------------- |
| The domain `d`                 | The inputs `d$0clk` of type `clock` and `d$0rst` of type `(bits 1)`    |
| `input x: T;`                  | `(input x <type of T>)`                                                |
| `output y: T;` and `y := e;`   | `(output y <type of T>)` and `(assign y e)`                            |
| `reg r: T = v;` and `r := e;`  | `(reg r <type> d$0clk (reset sync d$0rst C))` and `(next r e)`         |
| `wire x: T;` and `x := e;`     | `(let x <type> e)`                                                     |
| A hardware binding with a name | `(let <path> <type> e)`                                                |
| `instance u = M(args);`        | `(inst u <emitted name> (c$0clk d$0clk) (c$0rst d$0rst) (<input> e)*)` |
| `u.a := e;`                    | The connection `(a e)` of `u`                                          |
| `u.q` in an expression         | `u.q`                                                                  |

In this table, `x`, `r`, and `u` stand for their structural paths, and `c` is the domain of the child. `C` is the constant of `v` by the row "Literal or static finite value" of section 7.4.

The **port layout** is the order of the core ports of a module:

- The domain ports come first: `d$0clk`, then `d$0rst`.
- Then the inputs come, sorted by source name, and then the outputs, sorted by source name. Names sort by byte order.
- From slice 2 on, the leaves of one port follow in packing order. Array index 0, tuple element 0, and the first record field come first, recursively (v0.1, section 2). A `Bool` is one leaf of 1 bit.

`Source.Layout` in Lean and `elab::layout` in Rust define the port layout. `Flatten` and `Vectors` both read it. From slice 2 on, the layout also owns the expansion of a port into its leaves in packing order. No other module expands a port. In slice 1, each port has one leaf, so `Flatten` and `Vectors` each build the one entry of a port. The phase of slice 2 that brings aggregate ports moves this expansion into the layout first (section 14.2).

Slice 2 adds the aggregate rows. In this table, `T` is an aggregate type, and each row applies to each leaf of `T`:

| Source                               | Core                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------- |
| `input p: T;` or `output p: T;`      | One core port for each leaf, with the leaf name of section 7.3                            |
| `reg r: T = v;` and `r := e;`        | One `reg` and one `next` for each leaf. The reset constant of a leaf is that leaf of `v`. |
| `wire w: T;` and `w := e;`           | One `let` for each leaf                                                                   |
| A named hardware binding of type `T` | One `let` for each hardware leaf                                                          |
| `u.p := e;` for a child input `p`    | One connection for each leaf of `p`                                                       |
| `u.q` for a child output `q`         | An aggregate of the references `u.<leaf name>`                                            |

These rules apply to the aggregate rows:

- A binding of a whole resource stays one binding. `S018` counts the resource, not its leaves. A `:=` to a part of a resource, for example `r.a := e;`, is `S017`.
- A cycle through one leaf is a cycle. A dependency between two different leaves of one wire is not a cycle.
- `canonicalize` keeps the order of the ports, so the port layout survives the comparison of `validate`.

A combinational module (`domains()`) has no clock and no reset. A register in it is `S017`. An instance of a clocked child in a combinational parent is `S017`.

After the top instantiation, elaboration runs `Core.check` on the lowered design. Each core node carries the source position of the node that made it. A core `E008` becomes `S020` at that position. Each other core error is a defect of the reference elaborator. The theorem `elab_wellFormed` (section 10.3) excludes it.

The core design is `(design <emitted name of the top> <items>)`. It holds each instantiation that the top reaches, once.

### 7.6 The memory (slice 2)

v0.1 section 5 defines a memory with a synchronous read and one write port. The core memory has a combinational read (core IR spec, decision D4).

These rules define the source memory:

- `mem m: [T; N];` needs a nonempty hardware data type `T` (`S010`) and a depth `1 ≤ N ≤ 16777216` (`S012`).
- The word width is `w = data_bits(T)`. It is 1 to 65536 (`S012`).
- The address type is `UInt[A]` with `A = max(1, ⌈log₂ N⌉)`.
- `read_port(m, addr, en)` and `write_port(m, addr, data, en)` are prelude builtins. `addr` has the type `UInt[A]`, `en` has the type `Bool`, and `data` has the type `T` (`S010`).
- Each memory has exactly one call of each (`S018`). Each call is a graph effect, so a call in an arm of a hardware conditional is `S016`.
- `write_port` returns `()`. `read_port` returns the response: a record of the prelude type `ReadResponse[T]` with the fields `data` of type `T` and `valid` of type `Bool`. A user can shadow this name, because the language reserves no name.
- The memory belongs to the owner that declares it. A memory port call on a memory of another owner is `S017`.

Elaboration lowers `mem m: [T; N]` onto the core memory and two registers:

- `(mem m (bits w) N d$0clk)`.
- The response registers `m$0rdata` of width `w` and `m$0rvalid` of width 1. Both reset to 0.
- The read enable and the read address are each used twice. The lowering binds them to `(let m$0ren (bits 1) en)` and `(let m$0raddr (bits A) addr)`, as in section 7.4.
- `(next m$0rdata (mux m$0ren (read m m$0raddr) m$0rdata))`. A core read out of range gives 0, as v0.1 requires.
- `(next m$0rvalid (and m$0ren (icmp ult m$0raddr (const A N))))`. When `N = 2^A`, the compare is `(const 1 1)`.
- `(write m 0 waddr wdata (and wen (xor d$0rst (const 1 1))))`. A reset cancels the write.

The depth `N` is 1 to 16777216, the limit of the core checker (`E005`). The fit rule `S012` rejects a depth outside this range before the lowering, at the start of the `mem` declaration. `tests/source/check/` has a file with `N = 16777216`, which passes, and a file with `N = 16777217`, which gives `S012`.

The registers read the old memory state, so a read and a write of the same word give the old word. This is the read-first behavior of v0.1. Issue #12 changes only the mapping to macros, not this meaning.

A word packs the leaves of `T` in packing order (section 7.5), with the first leaf in the least significant bits. For the leaves `l_0` to `l_(n-1)`, the write data `wdata` is `(concat l_(n-1) (concat ... l_0))`. A word with one leaf is that leaf. The response unpacks the leaf `i` as `(extract m$0rdata o_i w_i)`. Here `w_i` is the width of the leaf, and `o_i` is the sum of the widths of the earlier leaves. `valid` is `m$0rvalid`. A word is one core memory, so its leaves get no core names.

The memory, its two registers, and the two request `let` values keep the names of section 7.2.

The lowering has an oracle at the source level that does not come from either front end (#160). Hand-written source vectors in `tests/source/run/` cover these cases:

- The read latency of one cycle, and the `valid` pulse.
- A disabled read that holds its data.
- A read and a write of one word in one cycle, which reads the old word.
- A read out of range, with `data` 0 and `valid` false, and a write out of range, with no change.
- A reset: the response is `(zero, false)`, the write has no effect, and the words hold.
- A depth that is not a power of 2, and a depth of 1.
- A word type with a record leaf, a `Bool` leaf, and an `SInt` leaf.

LEC (`just lec`) and the differential tests add a second oracle.

## 8. Commands

`silicon-check` gets these commands. The Rust `silicon` gets the same commands with the same output. Only the message text of an error line can differ (section 6.2). The exit codes are those of the core IR spec, section 6.4.2.

| Command                         | Output on success                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| `parse F.si`                    | The AST dump (section 11.1)                                                                    |
| `elab F.si --top T`             | The canonical `.sil` text of the design                                                        |
| `validate F.si --top T OUT.sil` | `ok`. For a mismatch, the first line that differs, and exit code 1.                            |
| `run F.si --top T`              | One output source vector for each input source vector                                          |
| `eval F.si EXPR`                | The canonical serialization of a static expression in the file scope                           |
| `cost F.si --top T`             | `total <units>`, then one line `<emitted name> <units>` for each instantiation, sorted by name |
| `observe F.si --top T`          | One line for each observation record, in evaluation order (slice 2, section 8.2)               |

Each command takes the budget flags that section 5.4 lists. `T` is a top selection in source syntax: a module name, then the static arguments in parentheses. Each argument is a literal. A top selection that does not parse is a usage error with exit code 2. A wrong number of arguments is `S007`. `eval` charges the length in bytes of the serialization of its result, without the final line feed. The charge comes after the evaluation and before the text exists, so an implementation measures the length first. When the fuel that remains cannot pay it, `eval` fails with `S015` at `1:1`, as the design node does for the top selection (section 5.4). Thus the output of `eval` is in `O(F)`. A core error other than `E008` in the output of the reference elaborator is a defect, not a design error. `silicon-check elab` then prints the core error on stderr and exits with code 3. Until phase 5 (#69), `cost` covers only the top selection: its arguments and its parameter types. Phase 5 adds the module bodies, the instantiations with their serialization and digests, the lowering, and the line for each instantiation.

`observe` elaborates like `elab` and prints the observation records instead of the design. For a rejected design, it prints the records before the first error, then the error line, and exits with code 1. Thus a record that comes before an error stays visible. [ADR 0020](../adr/0020-observation-records-once-per-instantiation.md) gives the reasons.

`validate` reads `OUT.sil` first, so a missing file is a usage error with exit code 2. It then works in these steps:

1. Elaborate `F.si` with the reference elaborator.
2. Parse and check `OUT.sil` with the core checker.
3. Compare `print (canonicalize ...)` of the two designs byte for byte.

`validate` thus also does the work of `silicon-check check` on the compiler output (issue #27). The comparison is in Lean, so no Rust code is on the trusted path of the comparison.

When the reference elaborator rejects the source, `validate` prints that error and exits with code 1. `validate` thus covers an accepted design. For a rejected design, the build produces no artifact. The shared corpus and the generator check that both front ends reject with the same first code, line, and column.

### 8.1 Validation in a build

`silicon build F.si --top T` elaborates in Rust, writes the `.sil` file, runs `silicon-check validate`, and then runs the backend. Validation is on by default. The flag `--no-validate` turns it off for an interactive build. The build prints `validated` or `not validated`. An artifact without validation has the status Trusted (section 13). The LSP never validates.

The Lean core checker is near-linear in the size of the design (issue #23, closed). The time of the Lean elaboration depends on the comptime work of the source, which the fuel bounds (section 5.4).

### 8.2 Observation records (slice 2)

`diagnostic(message, value)` returns `()` and appends one observation record. A record is not a diagnostic of section 6.3. These rules define it:

- `message` is a static `String`. A hardware message is `S011`, and a static message of another type is `S010`. `value` is any value, in the `raw` context of section 9.2.
- A record holds the position of the call and the emitted name of its instantiation. It also holds the call frames from the module body to the call, the message, and the rendering of the value.
- A static leaf renders as its canonical serialization of section 7.1. A hardware leaf renders as `(hw <type>)`. A container renders in its form of section 7.1, with each leaf rendered.
- A handle renders as `(<kind> <type> <core name>)`, for example `(reg (uint 8) i$2$r)`. `Source.Elab` defines the kind and the type of each handle. A rendering holds no sampled bits.
- A call frame renders as `(call <function> <line> <column>)`, with the position of the call.
- Section 9.4 gives the contexts that allow a call of `diagnostic`.

`observe` prints one line for each record, in evaluation order:

```text
(record 12 5 Fifo$16 ((call f 30 9) (call g 41 3)) (string "depth") (int 16))
```

Each `InstantiationId` gives its records once, when it elaborates. A done instantiation does not replay its records. A record thus names the emitted module name, not an instance path. This deviates from v0.1 section 9 (decision F15).

A record has no length limit and no truncation, because its charge pays for it (section 5.4). The limits of an error message (section 5.5) do not apply to it.

The source suites `elab` and `run` compare the `observe` output of both front ends, for each file that calls `diagnostic`. The record lines must be equal byte for byte. For a final error line, they compare only the code, the line, and the column, because the message text can differ (section 6.2).

`eval` prints no records. Its expression belongs to no instantiation, so a record of it has no emitted module name. A call of `diagnostic` under `eval` still charges its node and the serialization of its record.

## 9. Lean definitions of the difficult features

v0.1 has features that are hard to define. This section gives the Lean definition of each. The slices of section 12 bring them in.

### 9.1 `mut` formals and the aliasing rule

The aliasing rule of v0.1 section 2 is static. A mutable root is a `let mut` binding or a `mut` formal. A program has no global variable, no closure, and no reference value. A callee can thus reach a place of the caller only through a `mut` formal. Each mutation of a root is thus visible in the syntax: an assignment with that root, or a `mut` actual with that root.

A `mut` actual that is not a place, or whose root is not a mutable root, is `S008`. A place is a name, or a static index, a `.N` selector, or a field of a place.

The **window** of a pending root:

- For a `mut` actual: its own index expressions and each argument of the same call that evaluates later. For a receiver call, the receiver evaluates first (section 5.6). The window of a `mut` receiver thus holds all explicit arguments, also those that bind to leading `comptime` formals.
- For an assignment `place = e`: the index expressions of the place and `e`.

`S008`: in the window of a pending root `R`, no assignment and no `mut` actual has the root `R`. The check follows the evaluation order, not the binding order. Two `mut` actuals of one call have different roots. `Source.Check` decides this rule on the resolved AST, in pass 4. The `mut` marks of a call through a function value are known only at run time. Pass 5 thus checks the rule again, at run time:

- Each active call frame has a counter for each root. The counters have no charge.
- An assignment and each `mut` actual open the window of their root, after they resolve the root. Each call has `mut` actuals: a named call, a call through a function value, a receiver call, `push`, and `pop`.
- A counter above 0 at the open is `S008` at the `mut` actual or the assignment. Else the open adds 1 to the counter.
- The window of a `mut` actual closes after the last argument of its call evaluates. The window of an assignment closes after its right side evaluates. The close subtracts 1 from the counter.
- A call runs in a new frame, so a window of the caller never holds a mutation of the callee.

Pass 4 reports each conflict that the syntax shows. Pass 5 thus reports `S008` only for a window or a `mut` actual of a call through a function value. A `mut` actual of such a call that is not a place is also `S008` in pass 5. The check of pass 4 cannot see the `mut` marks of a value. The window of a place opens after its root resolves and before its steps, so the indices of the place are inside its window. The open of an assignment target never fails, because an assignment is a statement and no window holds one.

Slice 2 brings the `mut` formals, so it reports `S008` for the first time. `push(l, x)` and `pop(l)` take their list as a `mut` actual, and a receiver call `l.push(x)` has the receiver as its first `mut` actual. The window rule applies to each of these calls. For example, take `fn helper(comptime n: Int, mut xs: List[Int])`. The call `xs.helper(xs.pop())` is `S008`: `xs` is pending when `xs.pop()` evaluates. The plain call `helper(xs.pop(), xs)` is not `S008`.

The evaluator then passes a `mut` actual by value and result. It copies the value of the place into the formal at the call. At the return, it writes the final value of the formal into the live root. The write uses the indices that the place got before the call. `S008` excludes each alias, so this definition gives the same result as an alias. It needs no memory model and no borrow check. The builtins `push` and `pop` are the exception to this rule: they change the place directly (section 5.4).

An error ends the elaboration, so a partial write-back is never visible.

### 9.2 Implicit reads

An implicit read is a total function of the context, the expected type, and the value:

```lean
coerce : Context → Option Ty → Value → Except Error Value
```

`Context` has two values: `data` and `raw`. `Source.Elab` gives each position one context. The table is normative and follows v0.1 section 2:

| Position                                                                                   | Context |
| ------------------------------------------------------------------------------------------ | ------- |
| An operand of an operator, a condition, a data field selection, and a data index selection | `data`  |
| A `let` with a data type annotation, an assignment of a data place, and a data return      | `data`  |
| A data parameter of an ordinary function, a constructor argument, and the value of `:=`    | `data`  |
| An explicit `read(h)`                                                                      | `data`  |
| A `let` without an annotation, and a `let` with a handle type                              | `raw`   |
| A `mut` actual, a resource-typed formal, a `:=` target, and the operand of `@TypeOf`       | `raw`   |
| The value of `diagnostic`                                                                  | `raw`   |

In a `data` context, `coerce` maps a register handle or a wire handle to a hardware read of its core name. It recurses through arrays and tuples. It does not convert a nominal record. A memory, a domain, and an instance are never read. An input handle in a `data` context is `S017`. In a `raw` context, `coerce` returns the value unchanged.

Slice 2 tests the rows "a data field selection" and "a data index selection". Take a register or a wire of an aggregate type. A field or a static index of it reads the resource, then selects the leaf. A `mut` actual and the value of `diagnostic` stay `raw`. The rows for resource-typed formals wait for slice 3.

Slice 1 has handles only as names and as unannotated `let` aliases. Slice 1 has no handle types. Its prelude has no `Reg` and no other handle type, so a use of such a name fails with `S003`. The message names the slice of the feature.

### 9.3 The `@` builtins

Each builtin is a Lean function. None of them makes hardware.

| Builtin        | Lean definition                                                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| `@TypeOf(x)`   | The type of the resolved place `x`, in the `raw` context. It evaluates only the static keys and indices of `x`. |
| `@typeInfo(T)` | A total function from a normalized type to a `TypeInfo` record, with the kind tags of v0.1                      |
| `@Struct(fs)`  | A structural record type. Its identity is the list of names and normalized field types.                         |
| `@field(x, k)` | The selection of the field or the index `k`, with the rules of an ordinary selection                            |
| `@ports(h)`    | The public ports of the instance `h` as a list of `PortInfo`, in schema order                                   |

`@TypeOf` and `@ports` accept only the operand forms of v0.1 section 2. The pre-check rejects each other form with `S003`. `@typeInfo` and `@Struct` run in a structural context: a graph effect or a diagnostic in their arguments is `S016`.

### 9.4 Effects

The evaluator has a mode. In the arms of a hardware conditional, the mode is `pure`. In a `comptime fn`, the mode is `static`. These operations are graph effects:

- The declaration of a port, a resource, or an instance.
- A `:=` binding.
- A call of `diagnostic`.
- A mutation of a binding that existed before the arm started.
- From slice 2 on, a call of `read_port` or `write_port`.

A graph effect in the mode `pure` is `S016`. A hardware operation in the mode `static` is `S011`. The mode follows the calls, so the rule applies through each helper, as v0.1 requires. The mode also follows a call through a function value. The checks thus find each effect behind a function value at run time, as v0.1 section 2 requires. A function type holds no effect.

Slice 2 adds the mode `structural`. It holds in a `const`, a type expression, and a struct field type. A graph effect in the mode `structural` is `S016`, also through a call. A call of `diagnostic` is thus allowed in a `comptime fn`, but not in a structural context or in a hardware arm.

These operations are mutations: an assignment to a place, a `push`, a `pop`, and a `mut` write-back. A mutation of a binding from before the arm is `S016`. A binding is from before the arm when it exists at the start of the innermost hardware arm that encloses the mutation, also through calls. A binding of a function that the arm calls is thus newer, and the arm can change it. Phase 4 of slice 2 reports this `S016` for a `push`, a `pop`, and a `mut` write-back (section 14.2).

### 9.5 Resources and owners

A handle carries the structural path of its owner instantiation. A handle that reaches a different owner is `S017`. Ports and module arguments are the only paths between owners. Ports carry data, and module arguments are recursively static. A handle can thus never cross an owner. The check exists only as a guard.

### 9.6 Later features

- **Domains.** After #11, a domain becomes a static value with a clock, a reset, and a policy. The core IR then has more than one clock. The tag inference of v0.1 section 4 becomes a fixed point in `Elab`, with a fuel bound.
- **Packages.** The `ModuleId` gets the real `PackageId`. `Resolve` reads the locked dependency map that Lattice gives (ADR 0006).
- **Contracts.** The actual machine of v0.1 section 7 is the core `step` of the elaborated design and the port schema. It is not a second generated model.

### 10.2 Rules for the oracle loop

- **No expected `.sil` by hand.** The reference elaborator gives the expected output. A test author writes only behavior (source vectors) and intent (`FileCheck`).
- **Snapshots are review aids.** An `insta` snapshot is not an oracle for elaboration. Nobody can update the Lean comparison by hand, because Lean computes its expectation.
- **Fast feedback.** `cargo nextest run -p driver --test suites` with a filter on the path runs only the files that an agent touches, against a built `silicon-check`.
- **Localization.** A failed comparison prints the first line that differs: in the AST dump, then in the `.sil` text. The stage of the defect is thus visible.
- **Task shape.** A feature has three commits: the Lean modules with their unit tests, the corpus with its expectations, and the Rust code. The corpus commit comes before the Rust commit, so the Rust task starts with a failing test.

### 10.3 Theorems

These theorems are proven in `lean/Silicon/Source/Proof/`. `doc/trust.md` names the module of each one. A theorem of this kind does not block a slice:

| Theorem            | Statement                                                                                                                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `elab_wellFormed`  | `Cli.elabChecked o src top g = .ok c → ∃ t, Core.check c.design = .ok t ∧ Core.WellFormed c.design`                                                                                                 |
| `static_op_agrees` | A static operation gives `v`. From each state with enough fuel, `Flatten.lower` emits a core row for it on literal operands. That row evaluates to `v`                                              |
| `parse_print`      | `Parse.parseSource N (print a) = .ok a'` with `a'` equal to `a` after position erasure, for the syntax depth `N` at least the length of `print a`, and for an AST that meets the precondition below |
| `names_injective`  | `p.valid → q.valid → encode p = encode q → p = q`, from `decode (encode p) = some p` (section 7.2)                                                                                                  |
| `eval_cost`        | If the elaboration with fuel `f` uses `u` units, then each fuel `f' ≥ u` gives the same result, and each fuel below `u` gives `S015`                                                                |

The precondition of `parse_print` has these parts:

- Each name, field, and binder is a source identifier that is not a keyword. This includes the name of a struct, of a struct field, and of a type alias.
- No index is empty.
- No tuple is empty. The printer writes an empty tuple as `()`, which is the unit value or the unit type.
- Each module parameter and each struct parameter has the mode `comptime` (section 5.6).
- A `domains` declaration has at most one name.
- Each assignment and connection target is a place.
- No resource statement is in a `fn` without `comptime`.
- Each body has only the statement kinds that the parser accepts in that body.
- No string has a control character other than LF, CR, and tab.
- Each number is below 2^65536.

Position erasure sets each source position to line 0 and column 0. The proof task defines the erasure function and the precondition as a predicate.

The precondition follows the grammar of each slice. Slice 2 adds syntax forms, for example `mut` parameters of a `fn`, indexed places, and `.N` places. The proof of `parse_print` works constructor by constructor, and it names the token sets of the parser. Each new form thus needs edits in `Print`, in the precondition, and in the proof (`Parse/Runs.lean`, `Parse/Expr.lean`, and `Parse/Stmt.lean`). A place is a name, or a field, an index, or a `.N` selector of a place. The clause "each target is a place" uses this definition, and the lemma `Runs.stmt_place` covers each such target. `lake build` checks the proof, so the feature phase that adds a form also updates the proof. The proof covers the `mut` parameters of a `fn` and the receiver calls. The first clause of the precondition covers the function name of a receiver call. A receiver call is not a place, so it is never a target.

`elab_wellFormed` holds by construction, because `Cli.elabChecked` returns a design only with the proof of the core checker. `Cli.elabRun` does not run the core checker, so the theorem does not apply to it. `static_op_agrees` covers each row family of section 7.4. These are the wrapping operations, the comparisons, `==` and `!=` on `Bool`, `&&`, `\|\|`, `~`, unary `-`, and `!`. They also include the shifts by a static `Int` or `UInt` count, `resize`, and `reinterpret`. The proof runs `Flatten.lower` itself, so a change of `lower` breaks it. The claim about `lower` holds for each state with enough fuel. The evaluator runs `&&` and `\|\|` by a short circuit in `Eval.eval`. For these two, the theorem takes `v` as the Boolean operation. The stronger theorem, that the lowering never returns a defect, is issue #147.

A declarative type relation with `check_sound` and `check_complete` for the pre-check comes later. It follows the model of the core checker.

### 10.4 Oracles against a shared misreading

Both front ends come from the same prose. They can agree and both be wrong. These oracles do not come from either front end:

- **Source vectors by hand.** The test author writes the expected outputs.
- **Lean models as references.** A small corpus has designs with an independent Lean model, for example the counter of the v0.1 README. A differential test compares the model with the core interpreter of the elaborated design on random inputs.
- **Metamorphic tests.** A change that keeps the meaning keeps the canonical `.sil` text, up to an explicit name correspondence. Section 11.3 lists the changes and their oracles.
- **The human gate.** The Lean `Source` modules define the language. A change to them needs the approval of the user, as [ADR 0009](../adr/0009-cross-vendor-review-before-merge.md) gives for language design.

## 11. Formats, tests, and the generator

### 11.1 The AST dump

The AST dump is one S-expression for each item. Each node prints as `(<constructor> <fields>)`, with the constructor names of `Source.Syntax` in lowercase. The dump has no source positions and no comments. Each item starts a new line. A string prints in double quotes with the escapes of the grammar. Each item ends with one LF, so a file without items gives an empty dump. The module doc of `lean/Silicon/Source/Print.lean` gives the full byte format.

### 11.2 Source vectors

A source vector has the form of a core vector (core IR spec, section 6.4.3), with source names and source values:

- An input line lists the reset of the domain as `d$0rst`, then each input in schema order. The reset is a `Bool`. A combinational top has no reset entry, and a clock port has no entry.
- The schema order is the port layout of section 7.5 without the clock. It equals the order of the core ports. A vector uses the source name of a port, also when its core name has the field `0k`.
- A `Bool` value is `true` or `false`. A `UInt` value is decimal. An `SInt` value is decimal with `-` for a negative value.
- An empty port has no entry.

Slice 2 adds the leaves:

- The schema has one entry for each leaf of each port, in the port layout. The reset entry `d$0rst` comes first.
- The name of an entry is the source name of the port, then `.field` or `.index` for each level, for example `pkt.data`, `pkt.hdr.0`, and `v.3`.
- A port with the field `0k` keeps its source name. Thus `add.x` is the leaf `x` of the port `add`.
- Each leaf value has the form of its scalar type, as in slice 1.
- An empty leaf has no entry.
- `Source.Vectors` maps each leaf entry to its core port through the port layout. The line format stays the core format, and a leaf name is one token of it.

`Source.Vectors` maps a source vector to a core vector through the port schema, and back. `run` uses the core interpreter. The start state is all zero, as in section 6.4.3 of the core IR spec. This start state is a test convention, not semantics.

The initial state of a source design is free, as in section 5.2 of the core IR spec. A real register has no defined value before its first reset. A design that needs a defined start applies its reset. This replaces v0.1 section 4 on purpose, which starts the native registers at their reset values. The meaning of a source design is the core IR `step` of its elaboration, so the source cannot promise more than the core IR. A file of `tests/source/run/` has a register with a nonzero reset value. Its vectors show the register before the first reset edge, with the value 0 of the test convention, and its reset value after that edge. A second register of type `SInt[8]` has the reset value `-1`. Its vectors show `-1` after the first reset edge.

### 11.3 Test directories

[The testing guide](../guide/testing.md) gives the suites, their commands, their oracles, and their directives, for example `// TOP Counter(8)` for the top selection. This section gives only what is special to the source suites. Each source runner runs both front ends in one test, so `just test` compares them. Three parts have their own issues: `tests/source/llm/` (#116), the metamorphic tests (#117), and LEC with the differential tests on the source corpus (#118).

These budget and identity cases each get a file:

- A branching hierarchy: `M(d, id)` instantiates `M(d - 1, 2 * id)` and `M(d - 1, 2 * id + 1)`, with `d = 10`. The fuel equal to the output of `cost` succeeds, and one unit less gives `S015`.
- A shared hierarchy: `M(d)` instantiates `M(d - 1)` twice, with `d = 30`. `cost` lists exactly 31 instantiations, and the total stays linear in `d`.
- A top that instantiates a deep child first and a shallow child later, and the same design in the reverse order. Each order runs at the exact nesting depth and one level below it. Both front ends give the same result for each order.
- A constant that uses itself, and two constants that use each other. Both give `S019`.
- A chain of 300 acyclic constants. A nesting depth of 301 succeeds, and 300 gives `S015`.
- Slice 2: a chain of structs that the test specializes one at a time, from the innermost struct outward. Each `S_k` has one field of `S_(k-1)`. Then `data_bits` and `T()` of the outer struct run at the exact value depth, and one level above it gives `S015`.
- Slice 2: `xs` is an empty `List[Unit]`, `ys` is `[()]` as a `List[Unit]`, and `h` is a hardware `Bool`. `(h, xs) == (h, ys)` gives `(const 1 0)` joined with the compare of `h`, and `!=` gives its inverse. `if (c) { (h, xs) } else { (h, ys) }` gives `S011`.
- Slice 2: `struct P(comptime T: Type) { x: Bool }` and a loop that repeats `t = P[t];`. The type `t` nests its arguments, and its field depth stays 2. The loop runs at the exact nesting depth, and one more step gives `S015` at the node `P[t]`.
- Slice 2: asymmetric stages in nested tuples. `h` and `x` are hardware, `h` is a `Bool`, `x` is a `UInt[8]`, and `z` is a static `UInt[8]`. `(h, (3, z)) == (h, (3, x))` compares `3` with `3` statically and `z` with `x` in hardware. The same pair with `!=` and as the arms of a hardware `if` gets a file each. A variant with `4` in one arm gives `S011` in the `if`.
- Slice 2: a doubling chain of structs, specialized the same way. Each `S_k` has two fields of `S_(k-1)`. `data_bits` of the outer struct gives its exponential width. It charges its node and the size of the width, not the size of the type. `T()` of it fails with `S015` before it builds the value.
- Slice 2: a chain of 300 acyclic structs without parameters, where each struct has one field of the next struct. One file makes the first use in a `let` annotation. A second file makes it through a port type, from phase 6 on (section 14.2). Each runs at the exact nesting depth and one level below it.
- A static `1 << k` with a large `k`, and a loop that copies a large list. Both give `S015` before the operation runs. Slice 1 has no `List`, so `s015_loop_copy.si` copies a large integer. Slice 2 changes it to copy a large list, in a commit of its own.
- A nested doubling: `let a0 = [0, 0];`, then `let a1 = [a0, a0];` and so on up to `a20`, with `--fuel 1000000`. Making `a_k` charges `2^(k + 2) - 1` for its value and `k` for the join of its element types. The sum first goes above the fuel at the `let` of `a17`, which gives `S015`. Slice 1 has no arrays and gives `S004`. The phase of slice 2 that brings arrays adds this file to `tests/source/budget/` with `FUEL` (#161).

Slice 2 adds these files:

- A `check` file with `xs.helper(xs.pop())` for `fn helper(comptime n: Int, mut xs: List[Int])`. It gives `S008`, because the receiver evaluates first.
- A `check` file for each new case of section 6.1. `S008` and `S016` get their first files, and they leave `LATER` in `xtask/src/arch.rs`.
- A `run` file for each memory case of section 7.6 (#160).
- A `budget` file for each cost rule of the containers in section 5.4 (#161).
- New designs in `tests/source/corpus/`. They have aggregate ports, a register of a record type, and a memory with a record word. One has a table of constants that a list builds. Each passes `validate`, `just lec`, and `just diff`.
- For each file that calls `diagnostic`, the comparison of the `observe` output (section 8.2).

A file of `tests/source/elab/` nests 30 `>>` operations on `SInt[1]` with a `UInt[2]` count. Its `CHECK-COUNT` lines require exactly 2 `shrs` operations for each source shift. The output thus stays linear in the source. The negative cases of v0.1 section 9 each get a file in `tests/source/check/`.

The metamorphic tests compare two programs that differ by one change. The oracle depends on the effect of the change on the structural paths (section 7.3).

These changes keep each structural path. The canonical `.sil` text must stay equal byte for byte:

- The order of the items.
- The order of two adjacent `:=` statements without calls. A `:=` binds no name, so the versions stay equal.
- Redundant parentheses.
- A receiver call against its plain call, when the function has no leading `comptime` formal (slice 2, #117). Then both forms evaluate in the same order.
- A `type` alias against the type that it names (slice 2, #117).
- A struct without parameters against a struct with one fixed parameter (slice 2, #117).

These changes rename structural paths. Byte equality thus does not apply directly:

- The name of a local or a loop binder.
- A `comptime for` against its body written out by hand.
- A call of a helper against its body written out by hand.

For these changes, the test gives an explicit name correspondence from the core names of the first program to those of the second. The harness renames the first core design with it, then compares the canonical `.sil` text byte for byte. A correspondence must be a bijection on the core names, and the ports must map to themselves. When a test has no complete correspondence, LEC compares the two designs instead. The current LEC matches registers by name, so the correspondence must at least cover the registers.

### 11.4 The program generator

The crate `srcgen` makes source programs. `cargo xtask diff-si` runs it. [ADR 0018](../adr/0018-source-generator-crate.md) gives the limits of its static evaluator. It has four modes:

1. **Lift.** It renders each core design of `core-ir` `gen` as a source program of slice 1. The oracle: the elaborated program and the original design give the same outputs on random source vectors.
2. **Typed.** It makes well-typed programs of the current slice directly from types. These programs have comptime parameters, comptime functions with structural recursion, loops, branches, helpers, registers, and instance trees with arguments. Each wire reads only earlier values, so no cycle occurs. The oracle: `validate` passes, and `eval` and `cost` agree.
3. **Mutation.** It applies one mutation to a typed program, for example the deletion of a binding or a change of a width. The oracle: both front ends report the same first code, line, and column.
4. **Budget.** It reads the cost of a typed program from `cost`. The oracle: the fuel equal to the cost succeeds, and one unit less gives `S015`.

A typed program also comes with a twin: the same program with each comptime construct written out. The oracle: the two programs give the same outputs on random source vectors.

The generator has a fixed set of seeds for `just ci`. A failure prints the shrunk program and its seed.

## 12. Slices

A slice is a set of features with its own closed oracle loop. A slice is done when each item of its list holds and `just ci` passes. Its milestone review (section 14, phase 12) must have no open blocker. The grammar grows with each slice. The keywords are those of the v0.1 grammar from slice 1 on, and no slice adds a reserved identifier. Slice 3 is the exception: it adds the keywords `enum` and `match` (ADR 0021). The parser of a slice rejects the syntax of a later slice, for example `import` or `struct`, with `S004`. The prelude of a slice has only its own names. A use of a prelude name of a later slice, for example `List`, thus fails with `S003` in the resolver.

### 12.1 Slice 1: comptime core

Features:

- One file, no imports. The top selection on the command line.
- Modules with `comptime` parameters of type `Nat`, `Int`, and `Bool`. One domain or none.
- Ports, `reg`, `wire`, `:=`, `let`, `let mut`, and assignment of a local.
- The types `Bool`, `UInt[e]`, and `SInt[e]` with static widths. Top-level `const`.

- `fn` helpers over data, `comptime fn` with recursion, `comptime if`, `comptime for`, and `return`.

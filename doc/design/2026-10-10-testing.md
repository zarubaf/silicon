# Testing

- Status: accepted
- Date: 2026-10-10

## 1. Purpose and scope

This spec defines one test approach for the core IR and for the source language. It gives one layout, one set of directives, one runner, and three measures of completeness. [ADR 0015](../adr/0015-unified-exhaustive-testing.md) records the decision. Issue #87 tracks it.

The goal: each test has the same form in both languages, and a mechanical check finds each missing test.

Today the core IR suites and the planned source suites differ in their directories, their runners, and their documentation. Nothing checks that each error code, construct, command, or budget has a test. This spec closes both gaps.

These items stay unchanged:

- The oracles: the comparison with `silicon-check`, `FileCheck`, LEC, the differential tests, and the inventories.
- The unit tests and the `proptest` tests in the crates.
- The rules for the oracle loop of the front-end spec, section 10.2.

## 2. Decisions

| #   | Question                         | Decision                                                                                                   |
| --- | -------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| T1  | Layout                           | One tree for each language: `tests/core/` and `tests/source/`. The inventories go to `tests/inventory/`.   |
| T2  | Directives                       | The same names in both languages. Only the comment marker differs.                                         |
| T3  | Runner                           | One dev-only crate `testkit` with one suite table, one directive parser, and one harness.                  |
| T4  | Is each item of the spec tested? | `cargo xtask coverage` checks each error code, construct, command, and budget against the suites.          |
| T5  | Is each line of Rust tested?     | `cargo-llvm-cov` measures the line coverage of each crate. A floor for each crate stops a decrease.        |
| T6  | Does each test find a defect?    | `cargo-mutants` changes the code. A mutant that no test kills fails, unless the inventory lists it.        |
| T7  | Lean                             | No coverage or mutation tool. The shared files cover Lean, because each file runs through both front ends. |
| T8  | Documentation                    | `doc/guide/testing.md` is the single map. Each spec keeps only what is special to its language.            |

## 3. Layout

Each language has one tree. The name of a directory below the tree is the name of its suite.

| Tree               | Suites                                                               | Language        |
| ------------------ | -------------------------------------------------------------------- | --------------- |
| `tests/core/`      | `check`, `run`, `lower`, `corpus`                                    | Core IR, `.sil` |
| `tests/source/`    | `parse`, `check`, `run`, `elab`, `budget`, `corpus`, `llm`           | Source, `.si`   |
| `tests/inventory/` | `lec.txt`, `diff.txt`, `coverage.txt`, `llvm-cov.txt`, `mutants.txt` | None            |

The layout changes these paths:

- `tests/check/`, `tests/run/`, `tests/lower/`, and `tests/corpus/` move to `tests/core/`.
- `tests/si/` of the front-end spec becomes `tests/source/`.
- `tests/lec-checks.txt` becomes `tests/inventory/lec.txt`, and `tests/diff-checks.txt` becomes `tests/inventory/diff.txt`.

`commit-check` treats each file under `tests/core/`, `tests/source/`, and `tests/inventory/` as a test expectation. The rule `commit-expectations-code` thus applies to these files.

## 4. Directives

A directive is a comment line that gives the expectation of a test file. Both languages use the same directive names. Only the comment marker differs: `;` in a `.sil` file, `//` in a `.si` file.

| Directive                                                                             | Suites                | Meaning                                                                                   |
| ------------------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------- |
| `expected-error CODE @+N`                                                             | `check`, `run`, `llm` | The first error has the code `CODE` at N lines below the directive.                       |
| `STEP in=(...) out=(...)`                                                             | `run`                 | One clock cycle: the inputs and the expected outputs.                                     |
| All `FileCheck` directives, for example `CHECK:`, `CHECK-NEXT:`, and `CHECK-COUNT-2:` | `lower`, `elab`       | LLVM `FileCheck` reads these lines and checks the output.                                 |
| `TOP M(args)`                                                                         | The source suites     | The top selection of the file.                                                            |
| `FUEL N`                                                                              | `budget`              | The file elaborates with the fuel N. With the fuel N - 1, it fails with `S015`.           |
| `DEPTH N`                                                                             | `budget`              | The file elaborates with the nesting depth N. With the depth N - 1, it fails with `S015`. |
| `SYNTAX-DEPTH N`                                                                      | `budget`              | The file parses with the syntax depth N. With the depth N - 1, it fails with `S001`.      |

A budget file passes only when both front ends meet both conditions. At N, the file gives its expected result. At N - 1, each front end gives the exact code with the error exit code 1: `S015` for `FUEL` and `DEPTH`, `S001` for `SYNTAX-DEPTH`. A crash, a signal, a timeout, or a usage error with exit code 2 fails the test and covers nothing.

Examples: `; expected-error E004 @+1` in a `.sil` file, and `// expected-error S010 @+1` in a `.si` file.

## 5. Runner

The dev-only crate `testkit` runs all suites. It holds three parts:

1. **The suite table.** One table maps each suite to its command and its oracle. A suite is a directory, for example `tests/core/run`.
2. **The directive parser.** One parser reads the directives of section 4 for both comment markers.
3. **The harness.** One `datatest-stable` harness finds the files of each suite and runs the command of the table.

The suites find their files on their own. A new file thus needs no change to `Cargo.toml`.

The oracles stay the same. `testkit` only gives them one entry point.

### 5.1 Place in the workspace

- `testkit` is a library. It depends on `core-ir` and `parse`, because it reads each file with the real parser.
- In the layer order, `testkit` comes after `backend-circt` and before `driver`.
- `driver` names `testkit` in its `[dev-dependencies]`. Only `xtask` names it in its `[dependencies]`. `xtask` is a tool outside the layer order, and `diff-si` uses the agreement rule of `testkit`.
- Rule `workspace-layers` reads all dependency kinds from `cargo metadata`, so it also checks the dev-dependencies.
- `testkit` owns the harness code. `driver` owns the one test target that calls it, because only a test of `driver` gets `CARGO_BIN_EXE_silicon`.
- The harness finds `silicon-check` as the driver tests do today: the variable `SILICON_CHECK`, else the Lake build output in `lean/.lake/build/bin/`.
- As each crate does, `testkit` joins the workspace members and gets a row in `doc/trust.md`.

### 5.2 Corpus smoke checks

The smoke checks of the `corpus` suites stay. For each file, `silicon check` accepts it, `circt-opt` parses the output of `silicon lower`, and `silicon verilog` succeeds with and without `--models`.

## 6. Spec coverage

Spec coverage is the check that each item of the spec has a test. `cargo xtask coverage` runs it, and `just ci` runs `cargo xtask coverage`.

### 6.1 Required items

| Item       | Source of the items                                                                                     | Requirement                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Error code | The code tables of the core IR spec and the front-end spec. The reader of rule `arch-codes` reads them. | At least 2 different files in the suite whose command reports the code: `check`, or `run` for `E014`.                           |
| Construct  | The AST enums of each language, section 6.2                                                             | At least 1 file in each behavior suite. Core: `run` and `lower`. Source: `run` and `elab`.                                      |
| Command    | The commands of `silicon` and `silicon-check`, read as rule `arch-trust` reads them                     | At least 1 suite or CLI test, section 6.3                                                                                       |
| Budget     | The budgets of the front-end spec, section 5.4                                                          | A file at the limit that passes, and one unit above the limit that fails. A `FUEL`, `DEPTH`, or `SYNTAX-DEPTH` line gives both. |

The rule for an error code is two different files. The intent is a minimal case and a case in another context. No mechanical rule tells these two apart, so the review of the test checks the intent.

### 6.2 Construct IDs

A construct ID is `LANG:Enum::Variant`, for each variant of each AST enum of the list. `LANG` is `core` or `source`.

| Language | Crate     | Enums                                                                       |
| -------- | --------- | --------------------------------------------------------------------------- |
| Core IR  | `core-ir` | `Item`, `Stmt`, `Expr`, `UnOp`, `BinOp`, and `Pred` (the `icmp` predicates) |
| Source   | `parse`   | `Item`, `Stmt`, `Expr`, `TypeExpr`, `UnOp`, and `BinOp`                     |

Examples: `core:Stmt::Reg`, `core:BinOp::Shrs`, `core:Pred::Slt`, and `source:Item::Fn`. Each operator variant is a separate construct. `testkit` makes the list from the enums, so a new variant is a new item. Each enum mirrors Lean.

### 6.3 How a test covers an item

`testkit` writes a record for each check that ran and passed. `cargo xtask coverage` runs the suites and the CLI tests, then reads the records. A check that failed, or that printed SKIP, writes no record.

- **Construct.** `testkit` reads the file with the real parser of its language. Only a file that reaches the behavior counts: a passed file without `expected-error`. A `run` file needs at least one `STEP`. The file covers only the construct IDs in the code that its top reaches, section 6.4.
- **Error code.** An `expected-error` line covers its code in its suite. The file needs no AST. A file that does not parse, for example with `E001` or `S001`, thus covers only its code.
- **Command.** A suite covers the command of its row in the suite table. A CLI test of `driver` starts its command through one `testkit` function that names the command. Thus each CLI test registers its command.
- **Budget.** A passed `FUEL`, `DEPTH`, or `SYNTAX-DEPTH` file covers its budget. Section 4 gives the conditions of a pass.

No file carries hand-written coverage tags.

A file with `expected-error` covers no construct. Example: a `run` file that expects `E014` for an extern covers `E014`, but not the extern.

### 6.4 Reachable code

A behavior file covers only the constructs in the code that its top reaches:

- **Core IR.** The top module of the design, and each module that it instantiates, transitively along the instance graph.
- **Source.** The items that the `TOP` selection reaches through instances, calls, and constant uses, transitively. `testkit` follows these edges on the resolved AST.

This reachability is syntactic. It does not prove that a construct runs. Both branches of a `comptime if` count when the item that holds them is reached.

A regression test of `testkit` keeps this rule: an operator that occurs only in a module that no instance reaches stays uncovered.

### 6.5 Exceptions

`tests/inventory/coverage.txt` lists the items that have no test yet. The format of a line is `ITEM SUITE SKIP TAG`:

- `ITEM` is an error code, a construct ID, a command, or a budget.
- `SUITE` is the suite that has no test, for example `run`. It is `-` for an error code, a command, and a budget.
- Examples: `core:Item::Extern run SKIP E014` and `S016 - SKIP #11`.

An exception covers one item in one suite only. The interpreters reject an extern with `E014`, so `core:Item::Extern` can never pass in `run`. Its exception does not hide a missing test in `lower`. A regression test of `testkit` keeps this rule: with the exception above, `core:Item::Extern` stays required in `lower`.

The rules of the LEC inventory apply:

- `TAG` names a gap in `doc/trust.md` (rule `arch-skips`).
- A stale exception fails. The check runs for each pair of item and suite. When the item gets its test in that suite, the line must go.
- A new feature removes its exception in the same pull request.

A failure prints the item and the suite that has no test for it.

## 7. Code coverage

`cargo-llvm-cov` measures the line coverage of the Rust code. The Nix flake pins it.

- `just coverage` runs all Rust tests with instrumentation. This includes the tests that start `silicon` as a process.
- The measure is the line coverage of each crate. `tests/inventory/llvm-cov.txt` holds a floor for each crate. `xtask` is exempt.
- CI fails when a crate goes below its floor. `just ci` runs `just coverage`.
- The first floors are the values of today, rounded down. The target is 90 % for each compiler crate.
- A floor can rise in any commit. A commit that lowers a floor changes nothing else. `commit-check` enforces this.
- The run is deterministic. `just coverage` sets a fixed seed and a fixed case count for `proptest`. The random designs of the tests also use fixed seeds.

## 8. Mutation testing

`cargo-mutants` changes the code, for example it replaces a condition with `true`. Each changed program is a mutant. A test kills a mutant when the test fails on it. The Nix flake pins `cargo-mutants`.

- On each pull request, `cargo mutants --in-diff` makes mutants on the changed lines.
- A weekly scheduled CI job makes mutants on all compiler crates.
- A surviving mutant fails, unless `tests/inventory/mutants.txt` lists it.
- A listed mutant has one of two tags. `#ISSUE` names the issue for the missing test. `EQUIV` marks a mutant that has the same behavior as the original, with one line of reason.
- A stale entry fails. A pull request run checks only the entries of the mutants that it made. The weekly run checks the full inventory.
- Each mutant has a timeout, and the pull request job has a runtime limit. The CI configuration sets both values. A mutant that runs into its timeout does not survive.
- The pull request job becomes a required check only after rollout step 5 shows that it stays below its runtime limit.

## 9. Lean

Lean gets no coverage tool and no mutation tool. The shared files cover Lean, because each file runs through both front ends: the Rust front end and `silicon-check`.

The unit tests and the `proptest` tests of the crates stay. They count toward code coverage only, not toward spec coverage. The CLI tests of `driver` are the exception: a CLI test that runs a command covers that command (section 6.3).

## 10. Documentation

Each fact has one place:

- `doc/guide/testing.md` is the single map. It gives the suite table with the directory, the command, the oracle, and the directives. It also gives the three measures, and the inventories with their formats.
- The core IR spec, section 9, and the front-end spec, section 11.3, keep only what is special to their language. They point to the guide.
- This spec and ADR 0015 record the decision.

## 11. Rollout

Each step is one pull request. The refactor comes first.

1. This spec, ADR 0015, and the guide.
2. `testkit` runs the core suites, with no change to their results. The files then move in three commits:
   1. The runner accepts the old path and the new path.
   2. A commit with only tests moves the files.
   3. A commit removes the old path.
3. `cargo xtask coverage` with `tests/inventory/coverage.txt`. The first exceptions are the gaps of today, each with an issue.
4. The floors of `cargo-llvm-cov`.
5. `cargo-mutants` on each pull request and in the weekly job.

Then phase 9 of the front end (#73) builds `tests/source/` directly. The front-end spec then changes `tests/si/` to `tests/source/`, and `commit-check` follows.

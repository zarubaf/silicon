# Core IR

- Status: accepted
- Date: 2026-10-08

## 1. Purpose and scope

This spec defines the core IR of Silicon and the tools around it. It covers build steps 1 to 3 of [the architecture](../architecture.md):

1. The core IR semantics and a reference interpreter in Lean.
2. The core IR in Rust, the text format, the translation validator, and differential tests.
3. The CIRCT backend with LEC.

The goal: a design in the core IR has one meaning, which the Lean spec defines. Each tool that reads or writes the core IR agrees with that meaning. A mechanical oracle checks each agreement.

These items are out of scope for this iteration. Each item has a follow-up issue (section 12):

- A proof of the Rust implementation against the Lean spec, for example through Aeneas.
- Asynchronous reset, more than one clock domain, and CDC primitives.
- Synchronous memory read ports and write masks.

The source language, elaboration, and the `.si` frontend come after this iteration.

## 3. The text format

The core IR has one text format. A core IR file has the extension `.sil`. A Silicon source file has the extension `.si`.

The format uses S-expressions. A comment starts with `;` and ends at the end of the line. A name matches `[A-Za-z_][A-Za-z0-9_$]*`. A number is a decimal natural number. A number can have leading zeros, and its value is decimal: `007` is 7.

A token is a maximal run of characters that are not ASCII whitespace, not a parenthesis, and not `;`. The ASCII whitespace is space, tab, CR, and LF. A token that is not a name, a `NAME.PORT`, or a number is an `E001` error:

- If the token contains a character outside `[A-Za-z0-9_$.]`, the error is at the first such character. For example, `(design\x0cm)` with a form feed gives `E001` at 1:8. In `aé`, the error is at `é`.
- Otherwise, the error is at the start of the token. Examples are `12abc`, `a.1`, and `a.`.

The keywords are exactly these words: `design module extern input output clock bits deps let reg next mem write inst assign reset sync const not add sub mul and or xor shl shru shrs concat icmp eq ne ult ule ugt uge slt sle sgt sge mux extract replicate read`. The nonterminal names and the comment words of the grammar are not keywords.

The keyword rule applies to each name, also to both parts of a `NAME.PORT`. A keyword in the position of a name is an `E001` error at that name or at that part.

A file is UTF-8. A file that is not valid UTF-8 is a usage error with exit code 2 (section 6.4.2). LF ends a line. Each other character counts as one column, also CR and tab.

The parser has these limits. A violation is an `E001` error:

- Whitespace is the ASCII space, tab, carriage return (CR), and line feed (LF) only. Each other character outside a comment is part of a token, and the token rules above apply.
- A number is at most 4294967295, except the value of a `const`. A larger number is an `E001` error at the number. The value of a `const` has no limit.
- Expressions nest at most 256 levels deep. A compound expression directly inside a statement is level 1. Each nested compound expression adds one level. Level 257 is an `E001` error at its opening parenthesis.
- A name, a number, a `reset` form, and an instance connection `(PORT expr)` are not levels. A compound expression directly inside a `reset` form or a connection is thus level 1.

### 3.1 Example

```lisp
(design counter
  (module counter
    (input clk clock)
    (input rst (bits 1))
    (input en (bits 1))
    (output q (bits 8))
    (reg r (bits 8) clk (reset sync rst (const 8 0)))
    (let inc (bits 8) (add r (const 8 1)))
    (next r (mux en inc r))
    (assign q r)))
```

### 3.2 Grammar

```text
design ::= (design TOP item*)
item   ::= module | extern
module ::= (module NAME port* stmt*)
extern ::= (extern NAME port* dep*)
port   ::= (input NAME type) | (output NAME type)
type   ::= clock | (bits N)
dep    ::= (deps OUT (IN*))

stmt   ::= (let NAME (bits N) expr)
         | (reg NAME (bits N) CLK reset?)
         | (next REG expr)
         | (mem NAME (bits N) DEPTH CLK)
         | (write MEM PORT expr expr expr)      ; address, data, enable
         | (inst NAME MODULE (PORT expr)*)
         | (assign OUT expr)
reset  ::= (reset sync expr expr)              ; signal, value

expr   ::= NAME | NAME.PORT
         | (const N VALUE)
         | (UNOP expr) | (BINOP expr expr)
         | (icmp PRED expr expr)
         | (mux expr expr expr)                 ; condition, then, else
         | (extract expr LO N)
         | (replicate expr K)
         | (read MEM expr)

UNOP   ::= not
BINOP  ::= add | sub | mul | and | or | xor | shl | shru | shrs | concat
PRED   ::= eq | ne | ult | ule | ugt | uge | slt | sle | sgt | sge
```

Notes:

- The reset field `sync` is the only reset kind now. The parser rejects each other kind with `E001`. Asynchronous reset adds a second kind later, and the format stays compatible.
- A `write` has an explicit port index `PORT`. The order of the statements in a body thus has no meaning.
- An instance input of type `clock` connects to a clock name. `NAME.PORT` reads an output of an instance.
- Each definition states its type: a port, a `let`, a `reg`, and a `mem`. An expression has no annotation, because its operands and section 4.1 fix its type. The declared type is redundant on purpose: a compiler bug then shows at the definition, not at a later use.
- The order of the ports is part of the interface. The order of the statements and the items is not.

### 3.3 Canonical form

The function `canonicalize` sorts a design that passes the checker into a total order. Names compare by byte order:

- The items sort by name.
- The statements of a module sort by kind, in the order `reg`, `mem`, `inst`, `let`, `next`, `write`, `assign`.
- In one kind, the statements sort by the name that they define or that they name first. A `next` sorts by its register, and an `assign` by its output.
- The `write` statements sort by memory name, then by port index.
- The `deps` entries of an extern sort by the port order of their output.
- The connections `(PORT expr)` of an `inst` sort by the port order of the child.
- The ports keep their order.

The printer `print` keeps the order of its input. The formatter prints `print (canonicalize d)`. For a design that does not pass the checker, the formatter reports the checker error and prints no design. Two designs that differ only in statement order thus print to the same bytes. The digest of a semantic artifact needs this property.

The printer writes the canonical layout:

- The design header, each item header, each port, each `deps` entry, and each statement start a new line.
- An expression stays on the line of its statement. For example, `(reset sync rst (const 8 0))` stays on one line.
- One space separates two elements of a list on a line. No space follows an opening parenthesis, and no space comes before a closing parenthesis.
- The closing parentheses of a form end the last line of that form.
- The indent is two spaces for each list level. The design header has no indent. An item header has 2 spaces. A port, a `deps` entry, or a statement has 4 spaces.
- The file ends with one LF.
- An empty list prints as `()`.
- The printer drops comments.

The example in section 3.1 has this layout.

## 4. Typing and well-formedness

### 4.1 Operation types

The core IR is fully typed. Each value has a type that the checker knows before a run. The core IR has no implicit conversion: no extension, no truncation, and no signed type. An operation states its signedness, as in `comb`. `clock` is a separate type, and logic cannot read it.

In this table, `w` is the width of the first operand.

| Operation                 | Operand rule                                    | Result width | Meaning                                                                                                            |
| ------------------------- | ----------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------ |
| `const N V`               | None. Rule `E005` checks `N` and `V`.           | `N`          | The constant `V`                                                                                                   |
| `add`, `sub`, `mul`       | Equal widths                                    | `w`          | Modulo `2^w`                                                                                                       |
| `and`, `or`, `xor`, `not` | Equal widths                                    | `w`          | Bitwise                                                                                                            |
| `shl`, `shru`, `shrs`     | Equal widths                                    | `w`          | A shift reads its amount as an unsigned number. A shift amount of `w` or more gives 0, or the sign fill for `shrs` |
| `icmp P a b`              | Equal widths                                    | `1`          | Unsigned or signed comparison                                                                                      |
| `mux c t e`               | `c` has width 1. `t` and `e` have equal widths. | width of `t` | `t` if `c = 1`, else `e`                                                                                           |
| `concat a b`              | The result width is at most 65536.              | `wa + wb`    | `a` gives the high bits                                                                                            |
| `extract x LO N`          | `LO + N ≤ w`                                    | `N`          | The bits `LO` to `LO + N - 1`                                                                                      |
| `replicate x K`           | The result width is at most 65536.              | `w × K`      | `K` copies of `x`                                                                                                  |
| `read m a`                | `a` has the address width of `m`                | data width   | The current state, or 0 out of range                                                                               |

A memory with depth `D` has the address width `max(1, ⌈log₂ D⌉)`.

These numbers in a form are the declared numbers: a width, a depth, `N` of `const`, `N` of `extract`, and `K` of `replicate`. Rule `E005` checks the declared numbers:

- Each declared number is at least 1. Zero is an `E005` error.
- A declared width is at most 65536. This covers the width of a port, a `let`, a `reg`, a `mem`, and a `const`.
- A memory depth is at most 16777216.
- A `const` value `V` is less than `2^N`.

Rule `E004` checks only the operand rules of the table:

- Equal widths.
- `LO + N ≤ w`.
- Width 1 where the table requires it.
- The address width.
- The result width limit of 65536.

### 4.2 Rules and error codes

The checker accepts a design, or it reports the first error with its code and its source line. It checks each item, also an item that `TOP` does not reach. Rust and Lean use the same codes. A test fails when the two checkers report different codes for one file. Section 6.4.1 gives the order in which the checkers apply the rules.

| Code   | Rule                                                                                                                                                                                                                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `E001` | The file is valid S-expression syntax, and it matches the grammar.                                                                                                                                                                                                                                            |
| `E002` | A name is unique in its scope. Modules and externs share one scope. The ports and the statements of a module share its body scope. The ports of an extern form one scope. No name starts with `silicon_` or contains `.`.                                                                                     |
| `E003` | Each name and each `NAME.PORT` resolves to a definition of the kind that its position requires. `TOP` names a module. The cases of `E009`, `E011`, and `E013` below are not `E003` errors.                                                                                                                    |
| `E004` | The operand rules of section 4.1 hold. Each `let`, `next`, `assign`, and instance input has the width of its target. A reset signal has width 1. A reset value has the width of its register. A write address has the address width of its memory. Write data has the data width. A write enable has width 1. |
| `E005` | The declared numbers obey section 4.1.                                                                                                                                                                                                                                                                        |
| `E006` | Each register has exactly one `next`.                                                                                                                                                                                                                                                                         |
| `E007` | Each output has exactly one `assign`.                                                                                                                                                                                                                                                                         |
| `E008` | The combinational graph has no cycle (section 5.3).                                                                                                                                                                                                                                                           |
| `E009` | A module or an extern has at most one input of type `clock`. An output port does not have type `clock`. A value expression does not read a clock. A `bits` input of an instance does not connect to a clock name.                                                                                             |
| `E010` | The instance graph has no cycle.                                                                                                                                                                                                                                                                              |
| `E011` | An instance connects each input of its module exactly once. A `clock` input connects to a single name of a `clock` input of the parent.                                                                                                                                                                       |
| `E012` | The write ports of a memory have the indices `0` to `k-1`, each exactly once.                                                                                                                                                                                                                                 |
| `E013` | A `deps` entry names an output and inputs of its extern. Each output of an extern has exactly one entry. A `deps` list names each input at most once and names no `clock` input.                                                                                                                              |

A name of the wrong kind is an `E003` error. These are examples:

- A `mem` or an `inst` as a value.
- A `read` or a `write` of a name that is not a memory.
- A `next` of a name that is not a register.
- An `assign` of a name that is not an output.
- A `reg` or a `mem` that names a clock that is not a `clock` input.
- An instance connection `(PORT expr)` where `PORT` is not an input of the child.
- A `NAME.PORT` where `PORT` is not an output of the child.

These cases have another code. `E003` does not cover them:

- A clock name in a value position is an `E009` error (pass 5). This includes a read of a `clock` output port of the same module, and `u.P` where `P` is a `clock` output of the child.
- A `clock` input of an instance that connects to something other than a single name of a `clock` input of the parent is an `E011` error (pass 6). The list below gives the conditions.
- A `deps` entry that names something other than an output or an input of its extern is an `E013` error (pass 6).
- An `assign` to an output port of type `clock` is an `E009` error (pass 5), not an `E003` error. Its position is the port.

The lowering reserves the prefix `silicon_` and the character `.` for the names that it generates. Memory modules and registers start with `silicon_`. An instance result has the name `<inst>.<port>`. No name of any kind starts with this prefix or contains this character: a module, an extern, a port, a `let`, a `reg`, a `mem`, or an `inst`. A violation is an `E002` error at the name. The parser rejects a `.` in a name, so only a hand-built AST reaches this rule.

The checker checks the names inside the expression of an instance connection like the names of each value expression:

- An unresolved name or a name of the wrong kind is an `E003` error (pass 3).
- A clock name that the expression reads as a value is an `E009` error (pass 5) at the name. A single name of a `clock` input of the parent, connected to a `clock` input, is not a read as a value.
- `E011` for a `clock` input applies only when two conditions hold. The connected expression is not a single name of a `clock` input of the parent. No name in it has an `E003` or `E009` error.

A value expression can read an output port of its own module. The value of that read is the expression of the `assign` of the port. A read of a `clock` output port stays an `E009` error.

Rule `E009` gives decision D2. Each module has at most one clock input, so a design has at most one clock.

## 5. Semantics

### 5.1 Values and state

A value of width `n` is a Lean `BitVec n`. The state of a module has these parts:

- A value for each register.
- A function from `Fin D` to values for each memory of depth `D`.
- A state for each instance.

An input has a value for each input port that is not a clock. An output has a value for each output port.

### 5.2 One clock cycle

The step function has the form `step : State → Input → State × Output`. It has two parts:

1. **Solution.** The equations of the module give a value to each `let`, each output, and each instance output. A solution is an assignment that satisfies all equations for the given state and input.
2. **Update.** The next state comes from the solution:
   - A register with a reset takes the reset value if the reset signal is 1. Otherwise, it takes its `next` value.
   - A memory applies its write ports in index order. A higher port thus overwrites a lower port at the same address. A write with enable 0 or with an address out of range does nothing.
   - An instance takes the next state of its module, with its inputs from the solution.

The initial state is free. A property of a design holds for each start state, or the property states its own reset assumption.

### 5.3 Port dependencies and the combinational graph

The **port dependencies** of a module map each output to the set of inputs that the output can read in the same cycle. The checker infers them from the module body. An extern declares them with `deps`.

The combinational graph of a module has one node for each `let`, each output, and each instance output. It has an edge from `x` to `y` when the expression of `y` reads `x`. These reads make no edge:

- A read of a register.
- The stored contents of a memory in a `read`, because the read gets the old state. The address expression of a `read` still makes edges. Thus `(let a (bits 1) (read m a))` is an `E008` error.
- A connection to an input of instance `u` that is not in the dependencies of the output `u.q`. This read makes no edge to `u.q`.

The inference is syntactic reachability with no simplification. Thus `(and x (const 1 0))` depends on `x`. A `read m a` gives each dependency of `a`. The contents of `m` give none.

Rule `E008` requires an acyclic graph. The theorem `solution_unique` shows that such a graph has exactly one solution.

### 5.4 Black boxes

An extern has an assumed contract. The semantics takes an environment. The environment gives each extern a state type, an output function, and a next-state function. The output function must respect the declared `deps`.

Black boxes are on the trusted side of the trust boundary. The interpreters reject a design with an extern, because this iteration has no environment for them. They report the code `E014`. `E014` is not a checker code: only `run` reports it, and `check` accepts a design with an extern. Section 6.4.3 gives the output.

## 6. The Lean spec

### 6.1 Form

The normative modules are literate Lean. Prose blocks `/-! -/` alternate with definitions, and the Lean kernel checks each definition next to its prose. `cargo xtask prose` checks these prose blocks with vale. A Verso book that renders the modules stays in build step 5.

### 6.2 Modules

The modules are under `lean/Silicon/Core/`, in dependency order:

| Module      | Content                                                                                  |
| ----------- | ---------------------------------------------------------------------------------------- |
| `Syntax`    | The AST: types, expressions, statements, modules, designs, and the error codes           |
| `Text`      | The S-expression parser, the printer, and `canonicalize`                                 |
| `Graph*`    | Graph algorithms: reachability, depth-first search, and strongly connected components    |
| `Deps`      | The inference of port dependencies                                                       |
| `Typed`     | Intrinsically typed terms: `Expr : Ctx → Ty → Type`                                      |
| `Check`     | `WellFormed` as a `Prop`, and `check`, which elaborates the AST into a `Typed` design    |
| `Semantics` | Values, state, solutions, and the `step` function on `Typed` designs                     |
| `Interp`    | The interpreter, which computes each value once per cycle in graph order, and `namedRun` |
| `Canonical` | The proofs that `canonicalize` keeps a design well-formed and keeps its semantics        |
| `Mlir`      | The AST of the MLIR subset that `Lower` emits, its printer, and its semantics            |
| `MemModel`  | The memory model of each memory configuration, as MLIR                                   |
| `Lower`     | The reference lowering to `hw`, `comb`, and `seq` MLIR                                   |
| `Vectors`   | The input and output lines of `run` (section 6.4.3)                                      |
| `Main`      | The executable `silicon-check` with `check`, `run`, `lower`, and `lower --models`        |
| `Proof`     | The proofs of `mem_model_correct`, `lower_wellFormed`, and `lower_correct`               |

`Check` uses helper modules for its completeness proof: `Order`, `StatementOrder`, `Reassemble`, `Complete`, and `DependencyTable`. `Semantics`, `Interp`, and `Canonical` are directories of submodules. `Semantics` imports nothing from `Interp` or `Canonical`. Phase 4a (#5) adds the `Mlir` AST and printer, `MemModel`, `Lower`, `Vectors`, and `Main`.

The semantics works only on `Typed` designs. An ill-typed design thus cannot reach the semantics. `check` returns a typed design or an error code.

The `Mlir` subset has these operations: `hw.module`, `hw.instance`, `hw.output`, `hw.constant`, the `comb` operations of section 4.1, `seq.compreg` with a reset, `hw.array_get`, `hw.array_inject`, and `hw.module.extern` for black boxes.

The unit tests are in `lean/Silicon/Core/Test/`. They use `#guard` and `example ... := by decide`.

### 6.3 Theorems

All theorems of the table are proven. No theorem uses `sorry`, a new `axiom`, or `native_decide`.

| Theorem             | Statement                                                                                                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parse_print`       | `parse (print d) = .ok d` up to source positions, for a design with valid names within the limits of section 3                                                                                                                                                                  |
| `check_sound`       | `check d = .ok t → WellFormed d`, and `t` is the elaboration of `d` up to source positions. `check_sound_erase` gives `t.erase = d`.                                                                                                                                            |
| `check_complete`    | `WellFormed d → ∃ t, check d = .ok t`. The checker accepts each well-formed design.                                                                                                                                                                                             |
| `canonicalize_step` | For a design without externs, `canonicalize` keeps `step`: equal named states and one input give equal named outputs and equal named next states                                                                                                                                |
| `canonicalize_sem`  | For a design without externs, `canonicalize` keeps the named outputs of each cycle from the all-zero state                                                                                                                                                                      |
| `deps_sound`        | An output does not change when an input outside its dependency set changes.                                                                                                                                                                                                     |
| `solution_unique`   | A well-formed module has exactly one solution for each state and input.                                                                                                                                                                                                         |
| `interp_correct`    | The interpreter returns that solution.                                                                                                                                                                                                                                          |
| `interp_step`       | `Interp.step = step`. The interpreter computes each value once per cycle.                                                                                                                                                                                                       |
| `mem_model_correct` | Take a configuration, a model state whose words below the depth equal a core memory, and addresses below the depth. The reads equal the core reads. Below the depth, the next model state equals the next core memory.                                                          |
| `lower_wellFormed`  | For a checked design without externs, `(lower t).withModels (memoryConfigs t)` is well-formed MLIR.                                                                                                                                                                             |
| `lower_correct`     | Take a checked design without externs, the top module of `(lower t).withModels (memoryConfigs t)`, corresponding core and MLIR states, and an input. An MLIR solution exists. In each MLIR solution, each output port carries the output of `step`. The next states correspond. |

A named state gives each register and each memory by its instance path and its name. A named state thus does not depend on the statement order. A design with an extern has no `run` (section 6.4.3), so the two `canonicalize` theorems exclude it.

`check_complete` does not cover the choice of error code. The differential tests of the checkers (section 8.3) validate that choice.

`mem_model_correct` covers only addresses in range. The guard muxes for an address out of range are in the parent module, and `lower_correct` covers them.

A memory model stores `2^A` words, and the core memory stores `D` words. The correspondence maps word `i < D` to core word `i`. Words `D` to `2^A - 1` can hold any value.

`lower_correct` covers only designs without externs. One assumption remains: the `Mlir` module must match the meaning that CIRCT gives to the same operations. Two oracles check that assumption. `arcilator` runs the same MLIR in the differential tests, and `circt-lec` reads it in LEC.

### 6.4 The executable and the cross-phase contracts

`silicon-check` is the translation validator. Lake builds it as a `lean_exe`. It has four commands:

- `silicon-check check FILE` checks the design.
- `silicon-check run FILE` reads input vectors from the standard input and prints output vectors.
- `silicon-check lower FILE` prints the reference MLIR.
- `silicon-check lower --models FILE` prints the Lean memory model of each memory configuration of the design, sorted by module name. LEC uses these models on the Lean side (section 8.1).

The compiled checker trusts the Lean compiler, as `native_decide` does. [The trust document](../trust.md) records this.

The Lean side and the Rust side must agree on these contracts. Phases 2, 3, 4a, and 5 use them. This section is their authority.

#### 6.4.1 Error report order

Both checkers apply the rules in this pass order. They stop at the first pass with an error. In that pass, they report the error at the lowest position: the lowest line, then the lowest column.

| Pass | Codes                  |
| ---- | ---------------------- |
| 1    | `E001`                 |
| 2    | `E002`                 |
| 3    | `E003`                 |
| 4    | `E005`                 |
| 5    | `E009`                 |
| 6    | `E011`, `E013`         |
| 7    | `E004`                 |
| 8    | `E006`, `E007`, `E012` |
| 9    | `E010`                 |
| 10   | `E008`                 |

The position of an error is:

- `E001`: the first token that does not match, or the end of the file. An invalid token or a keyword as a name has the position that section 3 gives.
- The end of the file: the line and the column just after the last character. After a final LF, that is the next line, column 1.
- A single name or number that breaks a rule: the position of that atom. Examples are an unresolved name (`E003`), a declared number (`E005`), and a value that reads a clock (`E009`).
- `E002`: the name in the second definition.
- `E004`: a form is an `E004` error only when all its operands are well typed. The checker thus reports the innermost form that breaks a rule. Each `(PORT expr)` connection of an `inst` is its own form.
- `E005` for `V ≥ 2^N`: the value `V`.
- `E006`, `E007`: the second `next` or `assign`. If there is no second one, the `reg` or the output port that has none.
- `E008`: the node with the lowest position on the cycle. A `let` node has the position of its `let`, an output node of its `assign`, and an instance output node of its `inst`.
- `E009` for a second clock input: the second `clock` port.
- `E011` for a `clock` input of an instance: the start of the connected expression.
- `E011` for an input that an instance connects twice: the port name of the second `(PORT expr)` connection.
- `E009`: all cases belong to pass 5. These are two clock inputs, a `clock` output port, and a clock name read as a value. They compete by position, as the other errors of one pass do.
- `E013` for a duplicate input in one `deps` list: the second occurrence. For a `clock` input in a `deps` list: that input.
- `E013` for a second `deps` entry of one output: the output name in the second entry. For an output without an entry: the name of that output port of the extern.
- `E010`: the `inst` with the lowest position among the instances on the cycle.
- `E012`: the second `write` with the same index. If there is no second one, the `mem`.
- All other errors: the start of the form that breaks the rule.

Lines and columns start at 1.

#### 6.4.2 Command-line output

`silicon-check` (Lean) and `silicon` (Rust) give the same exit code, the same error code, and the same error source line number. The column and the message can differ. For `run`, they also print the same `out=` lines. For `lower`, the MLIR text differs, and LEC compares it.

| Command              | Success                                                                         | Design error                             | Exit code |
| -------------------- | ------------------------------------------------------------------------------- | ---------------------------------------- | --------- |
| `check F`            | `ok` on stdout                                                                  | `error[E004]: 12:5: <message>` on stdout | 0 or 1    |
| `run F`              | one `out=` line per input line                                                  | as `check`                               | 0 or 1    |
| `lower F`            | MLIR text on stdout                                                             | as `check`                               | 0 or 1    |
| `lower --models F`   | one Lean memory model for each memory configuration of the design, on stdout    | as `check`                               | 0 or 1    |
| `verilog F`          | Verilog text of the design on stdout                                            | as `check`                               | 0 or 1    |
| `verilog --models F` | one Verilog memory model for each memory configuration of the design, on stdout | as `check`                               | 0 or 1    |

In the error line, `12:5` is the line and the column from section 6.4.1.

- Exit code 0 means success.
- Exit code 1 means a design error.
- Exit code 2 means a usage error or an input or output error.

The test harnesses compare the code and the line. They do not compare the column or the message.

`run` and both `lower` commands check the design first. A design with a checker error gives that error, as `check` does. `lower` accepts a design with an extern and emits `hw.module.extern` for it. Only `run` reports `E014`.

#### 6.4.3 Input and output vectors

- An input line is `in=(`, then pairs of a name and a value, then `)`. It lists each input of the top module that is not a clock, in port order.
- Each run of ASCII spaces or tabs separates two tokens. Whitespace can also come after `(`, before `)`, and at the start and the end of the line. Nothing else can.
- LF ends an input line. The last line can lack its final LF.
- A value is a decimal natural number of any size. It can have leading zeros. Only the width of its port limits it. The limit 4294967295 of section 3 does not apply to a value. For example, `in=(x 1099511627775)` is valid for an input `x` of width 40.
- An output line lists each output of the top module, in port order. It has these bytes, with no other spaces:
  1. `out=(`.
  2. The first name, one space, and its value.
  3. For each further output: one space, the name, one space, and the value.
  4. `)` and LF.
- An output value is decimal without leading zeros. Zero prints as `0`.
- A top module without outputs prints `out=()` and LF for each input line.
- Each input line is one clock cycle. `run` calculates the outputs from the state and the input, and prints them. Then it updates the state.
- The start state is all zero. This start state is a test convention, not semantics (section 5.2).
- `run` reports `E014` only for a design that passes the checker and has an extern. It rejects such a design with `error[E014]: <line>:<col>: no environment for extern` and exit code 1. Section 5.4 gives the reason.
- `E014` is not a checker rule, and the pass table of section 6.4.1 does not contain it. Its position is the start of the `extern` item with the lowest position in the file.
- `run` reports a usage error with exit code 2 for an input line with one of these faults:
  - Bad syntax. This includes an empty line, a line with CR, and each line that does not match the tokenization above.
  - A missing name, an extra name, or an unknown name.
  - A value that does not fit the width of its input, for example `1099511627776` for width 40.
  - Names out of port order.
- `run` stops at the first faulty input line. The `out=` lines that it printed before that line stay on stdout.

#### 6.4.4 Names in `print` and `parse_print`

The AST holds source positions. The theorem `parse_print` erases the positions on both sides before it compares them. It needs two preconditions: the design has valid names, and the design is within the limits of section 3. A valid name matches `[A-Za-z_][A-Za-z0-9_$]*`, and it is not a keyword of the grammar.

## 7. The Rust side

### 7.1 Crates

| Crate           | Layer   | Content                                                                                        |
| --------------- | ------- | ---------------------------------------------------------------------------------------------- |
| `core-ir`       | 6       | The AST, the parser, the canonical printer, the checker, dependency inference, the interpreter |
| `backend-circt` | 7       | The lowering to MLIR text, and the CIRCT pass pipeline to Verilog                              |
| `driver`        | Support | The `silicon` CLI: `check`, `fmt`, `run`, `lower`, `verilog`                                   |

### 7.2 `core-ir`

- The modules `text`, `check`, `deps`, and `interp` mirror the Lean modules. They use the error codes of section 4.2.
- The AST is a tree of `Box` nodes. It does not store nodes in a `Vec` with an index. The AST keeps the names and the source spans, as in Lean. The checker resolves the names once, when it elaborates the AST.
- The checker elaborates the AST into a typed design, as in Lean. A typed index tells a value from a clock, a register, and a memory. Code after the checker cannot mix them, and it uses no string as an identifier.
- The interpreter is the Rust simulator for the differential tests. Its vectors use the format of `silicon-check run`.
- The module `gen` holds a random design generator behind the cargo feature `gen`. Only `xtask` and the tests use this feature.

### 7.3 `backend-circt`

- The crate writes MLIR text. It calls the CIRCT tools as processes. It does not link the MLIR C API, so Cargo needs no C++ build.
- A register lowers to `seq.compreg` with its reset pair. Its MLIR name is `silicon_reg_<name>`.
- A memory lowers to an instance of `hw.module.extern @silicon_mem_<D>x<W>_r<R>w<P>`. These are the parts of the name:
  - `D` is the depth, and `W` is the data width.
  - `R` is the number of `read` forms of that memory in its module. Each `read` form is one read port.
  - `P` is the number of write ports.
- The memory module has these ports, in this order. `A` is the address width, and `W` is the data width:
  1. The clock `clk` of type `!seq.clock`.
  2. For each read port `N`, from 0: the input `rN_addr` of type `iA`, then the output `rN_data` of type `iW`. The read ports come in the order of the `read` forms in the canonical text of the module.
  3. For each write port `N`, from 0: the inputs `wN_addr` of type `iA`, `wN_data` of type `iW`, and `wN_en` of type `i1`.
- The configuration of a memory is its tuple `(D, W, R, P)`. The Lean lowering uses the same module names and the same port order.
- The guard muxes for an access out of range stay in the parent module. A macro flow can replace the memory module.
- The crate also generates one **memory model** for each memory configuration, in MLIR and in Verilog. It is the simulation model for users. A separate LEC compares it with the Lean memory model of the same configuration (section 8.1). The model has these properties:
  - It stores `2^A` words, one for each address of `A` bits. The register `silicon_reg_mem` has the type `!hw.array<2^A x iW>`. Thus a memory of depth 1 gives an array of 2 words.
  - A read port uses `hw.array_get` on the current state. The write ports apply `hw.array_inject` in index order.
  - The model has no guard. The parent module guards each access. Through a guarded parent, no access reaches a word at address `D` or above.
  - Each address is in the range of the array. If a parent has no guard, an access out of range changes an output or the next state, and LEC finds the difference.
- Silicon emits the memory module itself. CIRCT makes an external memory module only for read latency 1, and a core IR memory has read latency 0. Phase 0 showed this.
- An extern lowers to `hw.module.extern`.

### 7.4 Engineering rules

Each Rust task follows these rules. The reviewers check them:

- Each error has a code and a source span. No code panics on user input.
- The parser recovers after an `E001` error, so it reports an exact position.
- Each crate has a small public interface. `core-ir` exports the AST, `parse`, `print`, `canonicalize`, `check`, `deps`, and `interp`.
- Each task starts with a failing test.
- `proptest` covers the parser, the printer, and the interpreter. A `proptest` test also gives arbitrary input to the parser and expects no panic. The project uses no `cargo-fuzz`, because it needs a nightly Rust, and the flake pins a stable Rust.
- An Opus review checks the design quality of each Rust branch. The Codex adversarial review runs too.

## 8. Oracles

### 8.1 LEC

For each file `f.sil` of the corpus:

1. Lean: `silicon-check lower f.sil` writes `ref.mlir`.
2. Rust: `silicon verilog f.sil` writes `out.sv` through the full CIRCT pipeline. `silicon verilog --models f.sil` writes `models.sv`.
3. `circt-verilog --ir-hw --detect-memories=false out.sv models.sv` writes `imp.mlir`. The file `models.sv` holds one Rust memory model for each configuration in the file. The flag keeps the array registers of the models as registers. On the Lean side, the Lean memory model of each configuration (from `silicon-check lower --models f.sil`) replaces the extern declaration with the same name.
4. `circt-opt --hw-flatten-modules --externalize-registers --canonicalize` runs on both sides. A register becomes an input for its current value and an output for its next value. Both sides keep the register names. Both lowerings name each register `silicon_reg_<name>`. The register of a memory model has the name `silicon_reg_mem`. No user name starts with `silicon_` (rule `E002`). The externalized ports of the top module thus cannot collide with user ports. Open point: `--hw-flatten-modules` can put an instance prefix in front of the names of inlined child registers. Phase 7 (issue #9) checks the CIRCT naming and states the final collision rule. Until then, the check of the wrapper for duplicate and unmatched ports is the guard.
5. `cargo xtask lec` writes one wrapper module for each side. A wrapper has the ports of both sides sorted by name, connects them by name, and drives the dead clock port with a constant.
6. `circt-lec --run` on the two wrappers must report `c1 == c2`.

The wrapper rejects a duplicate port name and a port name without a match on the other side.

The wrappers replace text edits of the MLIR. The Verilog import can change the port order, and the flattening adds an instance prefix to port names. A wrapper connects ports by name, so neither change matters.

This LEC uses register correspondence: both sides must have the same registers with the same names. The check is sound. It is not complete: a CIRCT pass that merges or retimes registers gives a false failure, not a false pass.

A second LEC compares `ref.mlir` with the MLIR of the Rust lowering before the CIRCT passes. It finds a bug in the Rust lowering before the passes hide it.

The main LEC uses a different memory model on each side. On the Lean side, the Lean memory model replaces each memory module. On the Verilog side, the Rust memory model in `models.sv` replaces it. The main LEC checks how the parent uses each memory: the addresses, the data, the enables, and the guards.

A third LEC proves each Rust memory model equal to the Lean memory model of the same configuration `(D, W, R, P)`. `mem_model_correct` proves the Lean memory model. These three steps make a chain from the Rust memory model to the semantics of section 5.2.

Phase 0 confirmed this flow on a counter and on an array register of depth 12. Each deliberate bug gave `c1 != c2`: a sub in place of an add, a missing write guard, a missing read guard, and swapped address bits. `circt-lec --run` needs Z3 through `--shared-libs`, so the flake adds `z3`.

### 8.2 Differential tests

Random designs from `gen` and random inputs drive these tools. Each tool starts from the all-zero state:

- The Lean interpreter.
- The Rust interpreter.
- `arcilator` on the Lean reference MLIR.

A disagreement is a failure. The test prints the design and the input vectors. `arcilator` gives a second check of the Lean lowering. LEC covers the emitted Verilog, so this iteration uses no Verilator.

### 8.3 Checkers

Each file of `tests/check/` goes through the Rust checker and the Lean checker. Both must report the expected code at the expected line. This is a differential test of the two checkers.

## 9. Test harness

The tests follow the CIRCT model with `FileCheck` and expected diagnostics. They use no shell `RUN:` lines. The directory selects the command, and a Rust harness with `datatest-stable` runs it.

| Directory       | Command                                       | Expectation in the file                       |
| --------------- | --------------------------------------------- | --------------------------------------------- |
| `tests/check/`  | The Rust checker and the Lean checker         | `; expected-error E004 @+1`                   |
| `tests/lower/`  | `silicon lower`                               | `; CHECK:` lines, which LLVM `FileCheck` runs |
| `tests/run/`    | The Rust interpreter and the Lean interpreter | `; STEP in=(en 1 rst 0) out=(q 3)` lines      |
| `tests/corpus/` | LEC and differential tests                    | None. The oracles decide.                     |

- `@+1` means the next line. A file without `expected-error` must pass the check.
- A file of `tests/check/` has a user module with the name `silicon_mem_12x8`. It expects `E002`.
- A file of `tests/corpus/` has two memories with the same depth and the same data width, but different port counts. They lower to two different memory modules.
- A file of `tests/corpus/` has the input `r_state`, the output `r_next`, and the register `r`. In the mutation, one side gives the register `r` the input `r_state` as its next value, in place of its own expression. LEC must report `c1 != c2`.
- The harness uses the real LLVM `FileCheck` from Nix.
- Rust unit tests cover each module of `core-ir`. `insta` snapshots cover the canonical printer.
- `proptest` checks `parse (print d) = .ok d` in Rust, up to source positions, for valid names, and within the limits of section 3 (section 6.4.4). It also checks that the two interpreters agree on random designs.

These `justfile` recipes are new. Each recipe runs one command:

| Recipe            | Command                  | Oracle                                                                  |
| ----------------- | ------------------------ | ----------------------------------------------------------------------- |
| `just lean-check` | `cargo xtask lean-check` | `silicon-check` meets the expectations of `tests/check` and `tests/run` |
| `just lec`        | `cargo xtask lec`        | `circt-lec` over `tests/corpus`                                         |
| `just diff`       | `cargo xtask diff`       | The differential tests of section 8.2                                   |

`just ci` runs all three recipes from this iteration on. This closes the open question "When LEC joins `just ci`": LEC joins now.

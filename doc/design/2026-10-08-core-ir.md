# Core IR

- Status: accepted
- Date: 2026-10-08

## 1. Purpose and scope

This spec defines the core IR of Silicon and the tools around it. It covers build steps 1 to 3 of [the architecture](../architecture.md):

1. The core IR semantics and a reference interpreter in Lean.
2. The core IR in Rust, the text format, the translation validator, and differential tests.
3. The CIRCT backend with LEC.

The goal: a design in the core IR has one meaning, which the Lean spec defines. Each tool that reads or writes the core IR agrees with that meaning. A mechanical oracle checks each agreement.

These items are out of scope for this iteration. Each item has a follow-up issue (section 12):

- A proof of the Rust implementation against the Lean spec, for example through Aeneas.
- Asynchronous reset, more than one clock domain, and CDC primitives.
- Synchronous memory read ports and write masks.

The source language, elaboration, and the `.si` frontend come after this iteration.

## 3. The text format

The core IR has one text format. A core IR file has the extension `.sil`. A Silicon source file has the extension `.si`.

The format uses S-expressions. A comment starts with `;` and ends at the end of the line. A name matches `[A-Za-z_][A-Za-z0-9_$]*`. A number is a decimal natural number.

### 3.1 Example

```lisp
(design counter
  (module counter
    (input  clk clock)
    (input  rst (bits 1))
    (input  en  (bits 1))
    (output q   (bits 8))
    (reg  r (bits 8) clk (reset sync rst (const 8 0)))
    (let  inc (bits 8) (add r (const 8 1)))
    (next r (mux en inc r))
    (assign q r)))
```

### 3.2 Grammar

```text
design ::= (design TOP item*)
item   ::= module | extern
module ::= (module NAME port* stmt*)
extern ::= (extern NAME port* dep*)
port   ::= (input NAME type) | (output NAME type)
type   ::= clock | (bits N)
dep    ::= (deps OUT (IN*))

stmt   ::= (let NAME (bits N) expr)
         | (reg NAME (bits N) CLK reset?)
         | (next REG expr)
         | (mem NAME (bits N) DEPTH CLK)
         | (write MEM PORT expr expr expr)      ; address, data, enable
         | (inst NAME MODULE (PORT expr)*)
         | (assign OUT expr)
reset  ::= (reset sync expr expr)              ; signal, value

expr   ::= NAME | NAME.PORT
         | (const N VALUE)
         | (UNOP expr) | (BINOP expr expr)
         | (icmp PRED expr expr)
         | (mux expr expr expr)                 ; condition, then, else
         | (extract expr LO N)
         | (replicate expr K)
         | (read MEM expr)

UNOP   ::= not
BINOP  ::= add | sub | mul | and | or | xor | shl | shru | shrs | concat
PRED   ::= eq | ne | ult | ule | ugt | uge | slt | sle | sgt | sge
```

Notes:

- The reset field `sync` is the only reset kind now. Asynchronous reset adds a second kind later, and the format stays compatible.
- A `write` has an explicit port index `PORT`. The order of the statements in a body thus has no meaning.
- An instance input of type `clock` connects to a clock name. `NAME.PORT` reads an output of an instance.
- Each definition states its type: a port, a `let`, a `reg`, and a `mem`. An expression has no annotation, because its operands and section 4.1 fix its type. The declared type is redundant on purpose: a compiler bug then shows at the definition, not at a later use.
- The order of the ports is part of the interface. The order of the statements and the items is not.

### 3.3 Canonical form

The function `canonicalize` sorts the items by name. It sorts the statements by kind, then by name or port index. The kind order is `reg`, `mem`, `inst`, `let`, `next`, `write`, `assign`. The printer `print` keeps the order of its input. The formatter prints `print (canonicalize d)`. Two designs that differ only in statement order thus print to the same bytes. The digest of a semantic artifact needs this property.

## 4. Typing and well-formedness

### 4.1 Operation types

The core IR is fully typed. Each value has a type that the checker knows before a run. The core IR has no implicit conversion: no extension, no truncation, and no signed type. An operation states its signedness, as in `comb`. `clock` is a separate type, and logic cannot read it.

In this table, `w` is the width of the first operand.

| Operation                 | Operand rule                                    | Result width | Meaning                                                            |
| ------------------------- | ----------------------------------------------- | ------------ | ------------------------------------------------------------------ |
| `const N V`               | `N ≥ 1` and `V < 2^N`                           | `N`          | The constant `V`                                                   |
| `add`, `sub`, `mul`       | Equal widths                                    | `w`          | Modulo `2^w`                                                       |
| `and`, `or`, `xor`, `not` | Equal widths                                    | `w`          | Bitwise                                                            |
| `shl`, `shru`, `shrs`     | Equal widths                                    | `w`          | A shift amount of `w` or more gives 0, or the sign fill for `shrs` |
| `icmp P a b`              | Equal widths                                    | `1`          | Unsigned or signed comparison                                      |
| `mux c t e`               | `c` has width 1. `t` and `e` have equal widths. | width of `t` | `t` if `c = 1`, else `e`                                           |
| `concat a b`              | None                                            | `wa + wb`    | `a` gives the high bits                                            |
| `extract x LO N`          | `N ≥ 1` and `LO + N ≤ w`                        | `N`          | The bits `LO` to `LO + N - 1`                                      |
| `replicate x K`           | `K ≥ 1`                                         | `w × K`      | `K` copies of `x`                                                  |
| `read m a`                | `a` has the address width of `m`                | data width   | The current state, or 0 out of range                               |

A memory with depth `D` has the address width `max(1, ⌈log₂ D⌉)`.

### 4.2 Rules and error codes

The checker accepts a design, or it reports the first error with its code and its source line. Rust and Lean use the same codes. A test fails when the two checkers report different codes for one file. Section 6.4.1 gives the order in which the checkers apply the rules.

| Code   | Rule                                                                                                                                          |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `E001` | The file is valid S-expression syntax, and it matches the grammar.                                                                            |
| `E002` | A name is unique in its scope. Modules and externs share one scope. A module body is one scope.                                               |
| `E003` | Each name and each `NAME.PORT` resolves. `TOP` names a module.                                                                                |
| `E004` | The widths obey section 4.1. Each `let`, `next`, reset value, `assign`, `write`, and instance input has the width of its target.              |
| `E005` | A width, a depth, and a replication count are at least 1. A constant fits its width.                                                          |
| `E006` | Each register has exactly one `next`. Each `next` names a register.                                                                           |
| `E007` | Each output has exactly one `assign`. Each `assign` names an output of its module.                                                            |
| `E008` | The combinational graph has no cycle (section 5.3).                                                                                           |
| `E009` | A module or an extern has at most one input of type `clock`. Each `reg` and `mem` names that input. A value expression does not read a clock. |
| `E010` | The instance graph has no cycle.                                                                                                              |
| `E011` | An instance connects each input of its module exactly once, with the correct type.                                                            |
| `E012` | The write ports of a memory have the indices `0` to `k-1`, each exactly once.                                                                 |
| `E013` | A `deps` entry names an output and inputs of its extern. Each output of an extern has exactly one entry.                                      |

Rule `E009` gives decision D2. Each module has at most one clock input, so a design has at most one clock.

## 5. Semantics

### 5.1 Values and state

A value of width `n` is a Lean `BitVec n`. The state of a module has these parts:

- A value for each register.
- A function from `Fin D` to values for each memory of depth `D`.
- A state for each instance.

An input has a value for each input port that is not a clock. An output has a value for each output port.

### 5.2 One clock cycle

The step function has the form `step : State → Input → State × Output`. It has two parts:

1. **Solution.** The equations of the module give a value to each `let`, each output, and each instance output. A solution is an assignment that satisfies all equations for the given state and input.
2. **Update.** The next state comes from the solution:
   - A register with a reset takes the reset value if the reset signal is 1. Otherwise, it takes its `next` value.
   - A memory applies its write ports in index order. A higher port thus overwrites a lower port at the same address. A write with enable 0 or with an address out of range does nothing.
   - An instance takes the next state of its module, with its inputs from the solution.

The initial state is free. A property of a design holds for each start state, or the property states its own reset assumption.

### 5.3 Port dependencies and the combinational graph

The **port dependencies** of a module map each output to the set of inputs that the output can read in the same cycle. The checker infers them from the module body. An extern declares them with `deps`.

The combinational graph of a module has one node for each `let`, each output, and each instance output. It has an edge from `x` to `y` when the expression of `y` reads `x`. These reads make no edge:

- A read of a register.
- A read of a memory, because it reads the old state.
- A connection to an input of instance `u` that is not in the dependencies of the output `u.q`. This read makes no edge to `u.q`.

Rule `E008` requires an acyclic graph. The theorem `solution_unique` shows that such a graph has exactly one solution.

### 5.4 Black boxes

An extern has an assumed contract. The semantics takes an environment. The environment gives each extern a state type, an output function, and a next-state function. The output function must respect the declared `deps`.

Black boxes are on the trusted side of the trust boundary. The interpreters reject a design with an extern, because this iteration has no environment for them. They report the code `E014`. `E014` is not a checker code: only `run` reports it, and `check` accepts a design with an extern. Section 6.4.3 gives the output.

## 6. The Lean spec

### 6.1 Form

The normative modules are literate Lean. Prose blocks `/-! -/` alternate with definitions, and the Lean kernel checks each definition next to its prose. `cargo xtask prose` checks these prose blocks with vale. A Verso book that renders the modules stays in build step 5.

### 6.2 Modules

The modules are under `lean/Silicon/Core/`, in dependency order:

| Module      | Content                                                                                                |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| `Syntax`    | The AST: types, expressions, statements, modules, designs                                              |
| `Text`      | The S-expression parser, the printer, and `canonicalize`                                               |
| `Typed`     | Intrinsically typed terms: `Expr : Ctx → Ty → Type`                                                    |
| `Check`     | `WellFormed` as a `Prop`, the error codes, and `check`, which elaborates the AST into a `Typed` design |
| `Deps`      | The inference of port dependencies                                                                     |
| `Semantics` | Values, state, solutions, and the `step` function on `Typed` designs                                   |
| `Interp`    | The interpreter, which computes the solution in graph order                                            |
| `Mlir`      | A semantics for the MLIR subset that `Lower` emits                                                     |
| `MemModel`  | The memory model of each memory configuration, as MLIR                                                 |
| `Lower`     | The reference lowering to `hw`, `comb`, and `seq` MLIR                                                 |
| `Main`      | The executable `silicon-check` with `check`, `run`, and `lower`                                        |

The semantics works only on `Typed` designs. An ill-typed design thus cannot reach the semantics. `check` returns a typed design or an error code.

The `Mlir` subset has these operations: `hw.module`, `hw.instance`, `hw.output`, `hw.constant`, the `comb` operations of section 4.1, `seq.compreg` with a reset, `hw.array_get`, `hw.array_inject`, and `hw.module.extern` for black boxes.

The unit tests are in `lean/Silicon/Core/Test/`. They use `#guard` and `example ... := by decide`.

### 6.3 Theorems

No theorem uses `sorry`, a new `axiom`, or `native_decide`.

| Theorem             | Statement                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------- |
| `parse_print`       | `parse (print d) = some d` up to source positions, for a design with valid names            |
| `check_sound`       | `check d = .ok t → WellFormed d`, and `t` is the elaboration of `d`                         |
| `check_complete`    | `WellFormed d → ∃ t, check d = .ok t`                                                       |
| `canonicalize_sem`  | `canonicalize` keeps the elaborated design up to statement order, so `step` does not change |
| `deps_sound`        | An output does not change when an input outside its dependency set changes.                 |
| `solution_unique`   | A well-formed module has exactly one solution for each state and input.                     |
| `interp_correct`    | The interpreter returns that solution.                                                      |
| `mem_model_correct` | The `Mlir` semantics of each memory model equals the memory semantics of section 5.2.       |
| `lower_correct`     | The `Mlir` semantics of `lower t`, with its memory models, equals `step` on `t`.            |

`lower_correct` is the largest proof of this iteration. One assumption remains: the `Mlir` module must match the meaning that CIRCT gives to the same operations. Two oracles check that assumption. `arcilator` runs the same MLIR in the differential tests, and `circt-lec` reads it in LEC.

### 6.4 The executable and the cross-phase contracts

`silicon-check` is the translation validator. Lake builds it as a `lean_exe`. It has three commands:

- `silicon-check check FILE` checks the design.
- `silicon-check run FILE` reads input vectors from the standard input and prints output vectors.
- `silicon-check lower FILE` prints the reference MLIR.

The compiled checker trusts the Lean compiler, as `native_decide` does. The trust document records this.

The Lean side and the Rust side must agree on these contracts. Phases 2, 3, 4a, and 5 use them. This section is their authority.

#### 6.4.1 Error report order

Both checkers apply the rules in this pass order. They stop at the first pass with an error. In that pass, they report the error at the lowest position: the lowest line, then the lowest column.

| Pass | Codes                  |
| ---- | ---------------------- |
| 1    | `E001`                 |
| 2    | `E002`                 |
| 3    | `E003`                 |
| 4    | `E005`                 |
| 5    | `E009`                 |
| 6    | `E011`, `E013`         |
| 7    | `E004`                 |
| 8    | `E006`, `E007`, `E012` |
| 9    | `E010`                 |
| 10   | `E008`                 |

The position of an error is:

- `E001`: the first token that does not match, or the end of the file.
- `E002`: the second definition of the name.
- `E006`, `E007`: the second `next` or `assign`. If there is no second one, the `reg` or the output port that has none.
- `E008`, `E010`: the node on the cycle with the lowest position.
- `E012`: the second `write` with the same index. If there is no second one, the `mem`.
- All other codes: the start of the form that breaks the rule.

Lines and columns start at 1.

#### 6.4.2 Command-line output

`silicon-check` (Lean) and `silicon` (Rust) give the same output for these commands:

| Command   | Success                        | Design error                             | Exit code |
| --------- | ------------------------------ | ---------------------------------------- | --------- |
| `check F` | `ok` on stdout                 | `error[E004]: 12:5: <message>` on stdout | 0 or 1    |
| `run F`   | one `out=` line per input line | as `check`                               | 0 or 1    |
| `lower F` | MLIR text on stdout            | as `check`                               | 0 or 1    |

In the error line, `12:5` is the line and the column from section 6.4.1.

- Exit code 0 means success.
- Exit code 1 means a design error.
- Exit code 2 means a usage error or an input or output error.

The test harnesses compare the code and the position. They do not compare the message.

#### 6.4.3 Input and output vectors

- An input line is `in=(NAME VALUE NAME VALUE ...)`. It lists each input of the top module that is not a clock, in port order. A value is a decimal number.
- An output line is `out=(NAME VALUE ...)`. It lists each output of the top module, in port order.
- Each input line is one clock cycle. `run` calculates the outputs from the state and the input, and prints them. Then it updates the state.
- The start state is all zero. This start state is a test convention, not semantics (section 5.2).
- `run` rejects a design with an extern with `error[E014]: <line>:<col>: no environment for extern`. Section 5.4 gives the reason.

#### 6.4.4 Names in `print` and `parse_print`

The AST holds source positions. `parse_print` holds up to these positions: the theorem erases the positions on both sides. It also needs valid names. A valid name matches `[A-Za-z_][A-Za-z0-9_$]*`, and it is not a keyword of the grammar.

## 7. The Rust side

### 7.1 Crates

| Crate           | Layer   | Content                                                                                        |
| --------------- | ------- | ---------------------------------------------------------------------------------------------- |
| `core-ir`       | 6       | The AST, the parser, the canonical printer, the checker, dependency inference, the interpreter |
| `backend-circt` | 7       | The lowering to MLIR text, and the CIRCT pass pipeline to Verilog                              |
| `driver`        | Support | The `silicon` CLI: `check`, `fmt`, `run`, `lower`, `verilog`                                   |

### 7.2 `core-ir`

- The modules `text`, `check`, `deps`, and `interp` mirror the Lean modules. They use the error codes of section 4.2.
- The AST stores its nodes in a `Vec` and refers to them by typed index. The checker resolves the names once, when it elaborates the AST. The AST keeps the names and the source spans, as in Lean.
- The checker elaborates the AST into a typed design, as in Lean. A typed index tells a value from a clock, a register, and a memory. Code after the checker cannot mix them, and it uses no string as an identifier.
- The interpreter is the Rust simulator for the differential tests. Its vectors use the format of `silicon-check run`.
- The module `gen` holds a random design generator behind the cargo feature `gen`. Only `xtask` and the tests use this feature.

### 7.3 `backend-circt`

- The crate writes MLIR text. It calls the CIRCT tools as processes. It does not link the MLIR C API, so Cargo needs no C++ build.
- A register lowers to `seq.compreg` with its reset pair.
- A memory lowers to an instance of `hw.module.extern @silicon_mem_<D>x<W>`, where `D` is the depth and `W` is the data width. The guard muxes for an access out of range stay in the parent module. A macro flow can replace the memory module.
- The crate also generates one **memory model** for each memory configuration, in MLIR and in Verilog. The model is a `seq.compreg` of type `!hw.array`, with `hw.array_get` and `hw.array_inject`. It is the simulation model for users. A separate LEC compares it with the Lean memory model of the same configuration (section 8.1).
- Silicon emits the memory module itself. CIRCT makes an external memory module only for read latency 1, and a core IR memory has read latency 0. Phase 0 showed this.
- An extern lowers to `hw.module.extern`.

### 7.4 Engineering rules

Each Rust task follows these rules. The reviewers check them:

- Each error has a code and a source span. No code panics on user input.
- The parser recovers after an `E001` error, so it reports an exact position.
- Each crate has a small public interface. `core-ir` exports the AST, `parse`, `print`, `canonicalize`, `check`, `deps`, and `interp`.
- Each task starts with a failing test.
- `proptest` covers the parser, the printer, and the interpreter. A `proptest` test also gives arbitrary input to the parser and expects no panic. The project uses no `cargo-fuzz`, because it needs a nightly Rust, and the flake pins a stable Rust.
- An Opus review checks the design quality of each Rust branch. The Codex adversarial review runs too.

## 8. Oracles

### 8.1 LEC

For each file `f.sil` of the corpus:

1. Lean: `silicon-check lower f.sil` writes `ref.mlir`.
2. Rust: `silicon verilog f.sil` writes `out.sv` through the full CIRCT pipeline.
3. `circt-verilog --ir-hw --detect-memories=false out.sv models.sv` writes `imp.mlir`. The file `models.sv` holds the memory models. The flag keeps the array registers of the models as registers. On the Lean side, the Lean memory models replace the extern declarations of the memories.
4. `circt-opt --hw-flatten-modules --externalize-registers --canonicalize` runs on both sides. A register becomes an input for its current value and an output for its next value. Both sides keep the register names.
5. `cargo xtask lec` writes one wrapper module for each side. A wrapper has the ports of both sides sorted by name, connects them by name, and drives the dead clock port with a constant.
6. `circt-lec --run` on the two wrappers must report `c1 == c2`.

The wrappers replace text edits of the MLIR. The Verilog import can change the port order, and the flattening adds an instance prefix to port names. A wrapper connects ports by name, so neither change matters.

This LEC uses register correspondence: both sides must have the same registers with the same names. The check is sound. It is not complete: a CIRCT pass that merges or retimes registers gives a false failure, not a false pass.

A second LEC compares `ref.mlir` with the MLIR of the Rust lowering before the CIRCT passes. It finds a bug in the Rust lowering before the passes hide it.

Both sides use the Lean memory model, and `mem_model_correct` proves it. LEC thus does not check the model. LEC checks how the parent uses each memory: the addresses, the data, the enables, and the guards. A memory is thus a trusted primitive.

A third LEC compares each memory model of the Rust backend with the Lean memory model of the same configuration.

Phase 0 confirmed this flow on a counter and on an array register of depth 12. Each deliberate bug gave `c1 != c2`: a sub in place of an add, a missing write guard, a missing read guard, and swapped address bits. `circt-lec --run` needs Z3 through `--shared-libs`, so the flake adds `z3`.

### 8.2 Differential tests

Random designs from `gen` and random inputs drive these tools. Each tool starts from the all-zero state:

- The Lean interpreter.
- The Rust interpreter.
- `arcilator` on the Lean reference MLIR.

A disagreement is a failure. The test prints the design and the input vectors. `arcilator` gives a second check of the Lean lowering. LEC covers the emitted Verilog, so this iteration uses no Verilator.

### 8.3 Checkers

Each file of `tests/check/` goes through the Rust checker and the Lean checker. Both must report the expected code at the expected line. This is a differential test of the two checkers.

## 9. Test harness

The tests follow the CIRCT model with `FileCheck` and expected diagnostics. They use no shell `RUN:` lines. The directory selects the command, and a Rust harness with `datatest-stable` runs it.

| Directory       | Command                                       | Expectation in the file                       |
| --------------- | --------------------------------------------- | --------------------------------------------- |
| `tests/check/`  | The Rust checker and the Lean checker         | `; expected-error E004 @+1`                   |
| `tests/lower/`  | `silicon lower`                               | `; CHECK:` lines, which LLVM `FileCheck` runs |
| `tests/run/`    | The Rust interpreter and the Lean interpreter | `; STEP in=(en 1 rst 0) out=(q 3)` lines      |
| `tests/corpus/` | LEC and differential tests                    | None. The oracles decide.                     |

- `@+1` means the next line. A file without `expected-error` must pass the check.
- The harness uses the real LLVM `FileCheck` from Nix.
- Rust unit tests cover each module of `core-ir`. `insta` snapshots cover the canonical printer.
- `proptest` checks `parse (print d) = d` in Rust, up to source positions and for valid names (section 6.4.4). It also checks that the two interpreters agree on random designs.

These `justfile` recipes are new. Each recipe runs one command:

| Recipe            | Command                  | Oracle                                                                  |
| ----------------- | ------------------------ | ----------------------------------------------------------------------- |
| `just lean-check` | `cargo xtask lean-check` | `silicon-check` meets the expectations of `tests/check` and `tests/run` |
| `just lec`        | `cargo xtask lec`        | `circt-lec` over `tests/corpus`                                         |
| `just diff`       | `cargo xtask diff`       | The differential tests of section 8.2                                   |

`just ci` runs all three recipes from this iteration on. This closes the open question "When LEC joins `just ci`": LEC joins now.

## 10. Trust boundary

A new document, `doc/trust.md`, holds the trust boundary. It replaces the table in the architecture, and the architecture links to it. The document gives the status and the oracle of each part. It also lists each gap: what no check covers, and which issue closes the gap.

| Part                                                                       | Status        | Oracle or gap                                                                                                                                                    |
| -------------------------------------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The Lean theorems of section 6.3, including the checker in both directions | Proven        | The Lean kernel                                                                                                                                                  |
| The core IR of each compiler run                                           | Validated     | `silicon-check check`                                                                                                                                            |
| The Rust checker and interpreter                                           | Validated     | Differential tests against Lean. Gap: no proof. Issue: Aeneas proof.                                                                                             |

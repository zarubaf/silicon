# Elab

## Purpose

The `elab` crate is the elaborator of the Rust front end. It is layer 6 of the pipeline, after `typeck`. See [the front end design](../../doc/design/2026-10-09-frontend.md), sections 4.4, 4.5, and 5.

## Owns

This crate owns the static values with their canonical serialization, their recursive size, and their depth. The static values include the containers `()`, tuples, arrays, records, and lists, the strings, and the types as values. It also owns SHA-256 for the digest names. It owns the evaluator with the fuel, the nesting depth, the cost model, the table of constants, and the hardware values. It owns the table of instantiations with the checks for each instantiation, the core names, and the emitted module names. It owns the lowering to core IR, the port layout, and the port schema of the source vectors. The Lean modules `Source.Value`, `Source.Sha256`, `Source.Eval`, `Source.Elab`, `Source.Names`, `Source.Layout`, `Source.Flatten`, and `Source.Vectors` are the normative definitions.

The scan keeps the values of the number literals and the symbols of the field names. Their keys are the node ids of the parser, not the positions, because two nodes can have the same position. The call site of a call frame comes from `resolve`.

A hardware value is a node in one arena, so a new node shares its operand trees. A structural path is a node in a second arena, and a user field holds the symbol of its name. Thus a new node or a new name costs constant work and no copy. A static type is an id in a third table, `Types`, with one id for each equal type. An id carries the size and the depth of its type. Thus a copy and an equality of types cost constant work. An array value and a record hold the id of their type. The module `types` holds this table, the type metadata of design section 5.4, and the table of struct specializations. The key of a specialization is its struct item and its static arguments after their typed use. A struct type carries the metadata, so `T()` and `data_bits` never walk the field types. A handle type `Reg[T]`, `Wire[T]`, `Input[T]`, or `Mem[T, N]` is a node with the ids of its parts. `Instance[M, args]` is an entry of a table of instance types (`InstTy`). The table finds it by the fingerprint of its module item and its converted arguments. Thus the key of the index never holds a `Vec<Value>`. A handle type has the metadata of `List[T]` and takes the function flag and the enum flag of `T`. The module `serial` writes the canonical serialization, and `text` writes the bounded text of a type or a value in a message. Both walks keep their own stack. The walk of `text` takes a list of parts one part at a time, so a type with `2^20` parts stops soon after the bound. In the evaluator, `eval/types` evaluates the type expressions, the `type` aliases, and the specializations with their charges and `S019`. `eval/record` evaluates the constructors, the variant constructors, the zero `T()`, the fields, and `data_bits`. A static payload packs into one bit buffer (`BitBuf`). A hardware payload is one `Op::Pack` node of its leaves, and `eval/pack` walks them with its own stack. `eval/arms` holds the arm walk (`arm_walk`) with the leaves of a hardware `if` and `match`. `reinterpret` between an enum and its bits makes `Op::Pack` or two `Op::Extract` nodes. `eval/call` evaluates the calls and the receiver calls, binds the parameters, and runs the write-backs of the `mut` formals. `eval/place` resolves the places of assignments and of `mut` actuals. From phase 5, `eval/types` also evaluates the function types, and a function name is a value. `eval/call` calls a function through a value and counts the windows of the `mut` actuals at run time (`S008`). `eval/string` evaluates the string index, `len`, and `str`. `eval/list` evaluates `list`, `push`, and `pop`. `eval/store` owns the locals with their frames and the table of constants. It also owns the results that wait, the cursors and holds of the reads, and the change log of the locals (`eval/store/history`). The evaluator reaches them only through the methods of `Store`, and it sees no field. Each method that changes the value of a local decides the holds of the waiting reads first. The methods `bind`, `unbind`, and `put_back` do not: `bind` and `unbind` make or end a local that no read waits at, and `put_back` follows a take that decided. The module `limit` holds the size limit of design section 5.4. Each check reads only lengths, and it runs before the charge of its operation. Lean `Eval.over`, `shlBits`, and `sumBits` define it. The module `counters` counts the work of the walks and the operations for each run, by its fuel budget, and only the tests compile it. The same holds for the step count and the copy count of the store: a release build has no counter field and no `Cell`. An enum type (`Ty::Enum`) is nominal and has the size 1. It carries the metadata of a record of `UInt[W]` and `UInt[P]`, without the second part when `P` is 0. `Types` holds each enum by its item in a table of enums. The first use runs the checks of design section 5.6 in their order. It runs one level deeper and in a structural context (`eval/types`). A later use reads the done entry. The id of a type carries the enum flag, as it carries the function flag. Thus `==` and `!=` on a type with an enum are `S010` in constant work. A static enum value is one form, `Value::Enum`. It holds its type, its tag of `W` bits, and its payload of `P` bits. `Types::parts` gives the named parts of a struct type and of an enum type. No other module reads the parts of a type. `eval/matching` evaluates a `match`: the arm checks, the static selection, the binders, and the hardware `match`. `cover` holds its ordered map, and `unpack` makes the static value of a binder from the payload bits. The coverage check compares the count of the keys with `2^W` by `W`. Thus no check loops over the values of a type. A hardware `match` marks its selector and payload leaves by their use counts. Then it evaluates each arm under an `Arm` guard, with its binders first. The arms join as array elements. Each leaf is one `Op::Onehot` node over the selects and the values. The select of `_` is an `Op::Rest` node. `flatten` lowers both to AND-OR rows. It builds their `or` chains in a loop.

The module `agg` holds the hardware aggregate of Lean `Eval.Agg` (design sections 5.1 and 5.4), and `eval/agg` evaluates it:

- An `Agg` is a tree of `Static`, `Hw`, `Ref`, `Array`, `Tuple`, and `Record` parts. Each container `Node` stores its `TyId`, its size, its depth, and its count of hardware leaves. Thus no charge walks the tree. A container without a hardware leaf stays a static `Value`.
- A `Ref` is lazy. A read of an aggregate port, register, wire, or child output gives a `Ref` with no charge. A static selection gives a sub-reference with one node in the path arena (`Base::sub`). A part without a hardware leaf normalizes to a static value, and it charges the zero size from the `TyId` first.
- `Op::Out` and `Base::Out` hold the port name of a child output as a path in the path arena. Thus a step and a leaf read copy no name.
- A read through the nodes of a stored root takes its steps with one cursor, so it walks the path from the root once. An index with no call evaluates before that walk when no part before it is empty. The scan pass records each index with a call, so no evaluation scans the AST. An index with a call can change the root. Thus the first change of the root during that index decides if the read holds the root (`decide_holds`). An index that leaves the root alone walks no path. Each node stores its part with the most hardware leaves (`heavy`). The cursor keeps a witness. This is a path from the root to a hardware leaf along the heavy parts. The cursor also keeps its common prefix with the path of the read. A part on the witness holds a hardware leaf, so its decision walks nothing. Else the decision walks the path once, and a static part holds the root. A walk that finds a hardware part makes a new witness through a part with at most half the leaves of the part before. A node without a hardware leaf is a static value (`Agg::finish` asserts it), so the heavy part of a node leads to a leaf. Thus a read walks at most (log2 L + 1) times its steps, where L counts the hardware leaves of the root. Each change of a local while a read waits at it appends one entry to the history of the local (`eval/store/history`). The changes are a `push`, a `pop`, a write into a part of a static local, and a write that binds the local again. An entry takes work in the length of its path, and it visits no waiting read. The history has an index by path, so a read finds the entries that reach its part by a binary search. A result resolves once, when its read takes it back (`Store::resume`, which every site calls). A part that no entry reached stays a reference. A part that an entry reached gets a copy of its old value. The copy starts from the earliest entry that replaced the part, else from the live part, and it undoes the later entries newest first. A read at a part of an aggregate root that holds no root walks the live root. It resolves at its last step. After a write that bound the root again, it walks the old root in the log (`View`). It then copies only the part where it ends. Such a write moves the old root into the log and builds the new root from a copy of the rest of the old one (`split_root`). That copy costs at most the size of the root. A hardware write pays it in its charge. A static root with a waiting read is held, so its write charges the size of the root first. A write that leaves no hardware leaf turns the root static. A root becomes an aggregate again only by a charge of its new size. Thus the build of the root pays each such copy once. An index that changed the local of its base pays for the copy of its result (#237). A hardware `if` keeps the numbers of each finished part, and the promotion of a static container finds its type once.
- `push` and `pop` into a list part refresh each node on the path in constant work from the stored numbers (`change_at`). `charge_refresh` charges the part counts first (Lean `Agg.pathWidth`).
- `==`, `!=`, and a hardware `if` walk both operands by leaf. `arm_walk` takes the arms of an `if` and of a `match` as a list, with a leaf callback. It charges the number of arms less 1 at each position. A static part with different arms is `S011` (F19). An enum is a container pair of these walks, with the parts `tag` and `payload`. `Op::Share` marks the condition of an `if` with two or more `mux` nodes, and the operand of a hardware unpack. It charges the size of its operand once, and a value that holds it counts a core name. `flatten` binds it at its first lowering in the module.
- `layout` streams the leaves of a port in packing order, and no other module expands a port. An enum has the two leaves `tag` and `payload`, or only `tag` when its payload is empty. `flatten` lowers `Op::Pack` to a `concat` chain that a loop builds from the first leaf, and `Op::Extract` to an `extract`. A hardware enum in a `diagnostic` renders as `(enum <type> <tag> <payload>)`, and its measure charge is 1 for the container. `flatten` charges each leaf before it makes the leaf, and it lowers the left spine of a binary chain in a loop.
- The lowering thread joins the counters of its run, so the tests count the work of `flatten` too.
- `Handle::Mem` is the handle of a `mem` statement. The `Mem` of `Body.mems` holds its path, depth, word type, first requests, and first second call.
- A word reference is `Base::Word(PathId, offset)` or `Op::Word(PathId, offset)`. It holds the path id once, never a copy. `Base::sub` adds `Types::offset`, which reads the stored prefix offset of the type, so a step costs constant work. The counters `offsets`, `chained`, `blocked`, and `seconds` count this work in the tests.
- The prelude item `ReadResponse` comes after the user items, and `Resolved::is_prelude_item` marks it. `spec_of` moves the errors of its specialization to the use position.
- `flatten` lowers each memory as one block after the registers: the core memory, the response registers, the request `let` values, the two `next` statements, and the `write`. Each core node charges before it exists. A leaf of a word is an `extract` of `m$0rdata`. The write data is a `concat` chain that a loop over the leaves builds, so no recursion follows the leaf count. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.

The elaborator core keeps to the Rust subset of design section 4.5: plain owned data, `match`, `Vec`, `Box`, and no `Rc`, no `unsafe`, and no trait object. The module `int` holds the static integer behind a small interface, and only this module computes with `num-bigint`. It also holds each conversion between an integer and a finite value. A finite value uses the bit vector of `core-ir`, as the core semantics does.

## Invariants

- The serialization of a value equals the bytes of `Value.serialize` in Lean. The recursive size equals `Value.size`, and the depth equals `Value.depth`. Check: `cargo nextest run -p elab`.
- The digest equals the test vectors of FIPS 180-4. Check: `cargo nextest run -p elab`.
- The evaluator charges each unit of `Source.Eval` in the same order and at the same node. The charge comes before the work, and each operation keeps its work and its memory in its charge. One exception exists. In `renewed` (`eval/place.rs`), the read copies the old part before the charge of its result. This happens at most once. It happens only on a run that then fails with `S015` at that charge. The charge of the held root paid that size before. Thus the value, the used fuel, and the code and the position of the first error equal those of Lean. Check: `cargo nextest run -p elab` and the comparison with `silicon-check eval`.
- A struct use, an `instance` statement, and the top selection bind their parameters in order (`bind_params`). For each parameter, the type evaluates and the argument gets its typed use. The size of that argument charges, and then a copy of the converted value binds the parameter in the new frame. Thus a read of a parameter in a later parameter type is a local read. A run that fails at a charge has copied at most the units that it charged. Lean `bindParams` has the same order. Check: `cargo nextest run -p elab` and the comparison with `silicon-check cost`.
- A memory port call follows section 6.2 (`eval/mem.rs`). The order is: the copies, the memory check, `S016` in a guard, the typed uses, and the record of the first request of each kind. `read_port` then charges the struct use of `ReadResponse[T]`, its depth, and its zero size. A second call of one kind charges the same and keeps the first request. It records its `S018` in O(1). The response refers to the word of the memory (`Base::Word`) and walks no leaf. The table of types stores the prefix offsets of each tuple and struct type. Thus a step on a word adds one stored number. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.
- The evaluator holds the innermost guard of section 9.4 in `guard: Option<Guard>`, with its kind (`Arm` or `Structural`) and its depth. A hardware `if` and the arms of a hardware `match` set an `Arm` guard. `structural` sets a `Structural` guard in O(1) for each type expression, type index, `[T; N]`, function type, struct use, first use of a constant, and `mem` depth. The innermost guard wins. A `push`, a `pop`, or a write-back of a binding of the depth of the guard is `S016`, and so is a memory port call. The texts of `Guard` equal those of Lean. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.
- `diagnostic` follows section 5.4 and Lean `Eval.diagnose` (`eval/observe.rs`): the guard, the message, the waiting value, the measure charge, the byte charge, and then the record. The render walk is pure. It has its own stack, it runs into a `Len` sink for the byte charge and then into the string, and it never calls `normalize`. A `Ref` renders from the metadata of its type. A record names its instantiation by an index into the emitted names. A domain handle is the id of its declaration, and the evaluator keeps the text in a table. Thus a read of a domain copies no text. The length pass builds no name text, and it needs no list of types to measure first. The evaluator keeps a cache. It holds the length of each type that a record measured and the powers of ten of the digit counts. A type nobody records costs no length. The length pass counts the digits of an integer from its bit length (`Int::decimal_len`) and formats none. A frame, a handle, a module, a port, and a message write from borrowed fields. A call pushes its frame in O(1) and a done instantiation makes no record again, so the frames cost only their charged bytes. `observe` returns `Observed { records, outcome }`, with the records of an error too. `elaborate` is its projection. The counters `rendered`, `rendered_leaves`, `framed`, `recorded`, `guarded`, and `text_bytes` count this work. Check: `cargo nextest run -p elab` and the comparison with `silicon-check observe`.
- A handle type family follows Lean `Eval.handleTy` and `Eval.instanceTy` (`eval/types.rs`). The arguments evaluate from left to right. The checks read the metadata and charge nothing. The first argument is a type, and `T` is hardware data. `Mem` runs the word and depth checks of a `mem` statement. Then the type checks its depth and charges its size, before the table holds it. `Instance[M, args]` binds its arguments with the typed uses of an `instance` statement (`arguments`), one level deeper. The table interns it by its module item and its converted arguments. A handle type where a position needs hardware data is `S010` (`not_handle`). At a static position it is `S011` (`static_handle`). The join of a handle type with another type charges the sum of the two sizes. It needs one type, else `S010` stops the walk (`clash_fault`). A typed `let` and an assignment to a `let mut` local at a handle type follow Lean `handleUse`. The copy charges first, and a handle has the size 1. Then the handle type of the value must equal the declared type, by id, with no charge and no read. A handle holds the id of its data type, so the handle type reads no type. An `instance` statement stores its instance type, which it interns from the converted arguments with no extra charge. An assignment to a local without a type uses the handle type of the held handle (`held_use`). Another typed use at a handle type is `S010` until #278 (`later_handle`). Check: `cargo nextest run -p elab` and the comparison with `silicon-check cost`.
- The elaboration charges each unit of `Source.Elab` in the same order and at the same node. The units of each instantiation, the emitted names, and the code and the position of the first error equal those of Lean `Elab.elaborate`. Check: `cargo nextest run -p elab` and the comparison with `silicon-check cost`.
- `decode(encode(p)) == Some(p)` for each valid name `p`, and each encoded name is a legal core name. Check: `cargo nextest run -p elab`.
- An error message prints at most 256 bits of an integer, 64 characters of a string, and 1024 bytes of the text of a type. Check: `cargo nextest run -p elab`.
- The evaluator recurses, so it runs through `parse::NestedStack`, and it only finds the heights of the AST. A call, a constant, a function name used as a value, and an instantiation each start a nesting level. Each thread runs a group of nesting levels, so any nesting depth is safe. A design and an error hold no recursive value, so they drop safely on any stack. No walk over a value, a type, or an aggregate recurses. Each keeps an explicit stack, so a value of any depth is safe on any stack, also in the driver. `Parts` drops with its own stack. A result that refers to a local or a constant copies nothing until a copy pays for it. An assignment to a place with an index copies only the containers on the path of the place. Check: `cargo nextest run -p elab`.
- `push`, `pop`, and a `mut` write-back change the live root in one walk down the path of the place. A `pop` of a held root walks the path twice, and the charge of the root pays for the second walk. They copy no list and no root. A string operation charges the size of the string before it scans, and `s = s + t` makes one new string. Check: `cargo nextest run -p elab`.
- A result keeps the value that its expression read. A result that refers to a local waits in the store while a later operand, argument, or index evaluates. A waiting reference to a static value holds its local (design section 5.4). A waiting result that a change reached (`Out::Kept`) keeps its copy and still holds its local, as Lean keeps its root. A mutation of a held local first charges the size of the local. Then it appends its entry to the history, and it copies nothing. A waiting result copies its part when it resumes, and only if an entry reached the part. A `push` or `pop` reaches the lists at or below the part. A `pop` of a list above the part reaches it when the `pop` took out the element of the part. A write into a part reaches the parts above it and below it. A write that binds the local again reaches all parts. Each copy is at most the size of the local. One expression of the source holds the waiting results. Thus k waiting reads and m changes of one local take work in k plus m, up to the logarithm of the path lengths. The copies of the parts that a change reached come on top. Reads of one part share the undo. A batch of results resolves the latest mark first. The log keeps one memo for each path. Each read then continues the undo of the read of its part before it (`Memo` in `eval/store/history`). A new entry clears the memos, and they leave with the log. Check: `cargo nextest run -p elab` and the comparison with `silicon-check eval`.
- A waiting read copies at most the part where it ends. It records the numbers of its steps, and it walks the live local. After a write that bound the local again, it walks the old local in the log. The exceptions have three cases. First, a step goes into a list or a part that a change reached. An index in the old range of a list copies only the element. The log gives the old length (`Store::old_len`). Else the read copies that list or part, and not the rest of the local, and the check of the step fails on it. An index that changed the local of its base then charges the size of its result as the last step of the read. A count of the mutations of each local, compared around the index, finds this. The result is a new value, so a binding of it copies nothing. A string index is exempt. The tests `k_reads_that_cross_a_changed_list_copy_only_that_list` and `the_copies_of_an_old_list_that_a_read_finds_are_paid` cover it. Second, a write that binds an aggregate root again copies the rest of the root once. A hardware write pays it in its charge. A write that leaves no hardware leaf turns the root static, and only a charge of the new size builds it again. The test `k_reads_and_a_static_write_over_the_hardware_part` covers it. Third, a write that binds a static root again with a hardware leaf copies the root, and the held root charges its size first. The test `k_reads_and_a_hardware_write_into_a_static_local` covers it. Check: `cargo nextest run -p elab`.
- A `mut` actual binds its formal only at the type of its place, with no typed use. The write-backs run after the result binds, in the order of the parameters, at the position of the call. Each checks `S016`, then the depth of the root, then charges, then writes. Check: `cargo nextest run -p elab` and the comparison with `silicon-check run`.
- The signature of a function value evaluates in the scope of its function, with no locals, and it takes one nesting level. A function type has no metadata charge. A call through a value compares the number of arguments before the arguments evaluate. The windows of a place open after its root resolves and before its steps. A root with an open window gives `S008` at the next `mut` actual or assignment. A `mut` actual that is not a place gives `S008` in a call through a value. Check: `cargo nextest run -p elab` and the comparison with `silicon-check run`.
- The non-test code of the crate keeps to the Rust subset of design section 4.5. It has no `Cell`, `RefCell`, `OnceCell`, `LazyCell`, `UnsafeCell`, `Rc`, `Arc`, `Weak`, `Mutex`, `RwLock`, `OnceLock`, `LazyLock`, an `Atomic` type, `std::thread`, `dyn`, `unsafe`, `static mut`, `HashMap`, `HashSet`, `FnMut`, the macros `thread_local!`, `include!`, `include_str!`, `include_bytes!`, and `macro_rules!`, `#[path]` on a module, a glob of a crate root, or an alias of a standard crate. A function gets mutable state as a parameter. The tests and `counters` can use them. Check: `cargo xtask check` (rule `elab-subset`).
- Non-test code has no `unwrap`, no `expect`, and no panic on user input. Check: `just clippy`.

## Dependencies

This crate reads a `Resolved` that passed `typeck`. It uses `resolve` for the targets of names, and `parse` for the AST and the front-end thread. It uses `core-ir` for the operations on finite values and the keywords of core names. The tests use `typeck` and `proptest`. The `driver` calls it.

## How to test

Run `cargo nextest run -p elab`, then `just check` from the repository root.

# Elab

## Purpose

The `elab` crate is the elaborator of the Rust front end. It is layer 6 of the pipeline, after `typeck`. See [the front end design](../../doc/design/2026-10-09-frontend.md), sections 4.4, 4.5, and 5.

## Owns

This crate owns the static values with their canonical serialization, their recursive size, and their depth. In slice 2, the static values include the containers `()`, tuples, arrays, records, and lists, the strings, and the types as values. It also owns SHA-256 for the digest names. It owns the evaluator with the fuel, the nesting depth, the cost model, the table of constants, and the hardware values. It owns the table of instantiations with the checks for each instantiation, the core names, and the emitted module names. It owns the lowering to core IR, the port layout, and the port schema of the source vectors. The Lean modules `Source.Value`, `Source.Sha256`, `Source.Eval`, `Source.Elab`, `Source.Names`, `Source.Layout`, `Source.Flatten`, and `Source.Vectors` are the normative definitions.

The scan keeps the values of the number literals and the symbols of the field names. Their keys are the node ids of the parser, not the positions, because two nodes can have the same position. The call site of a call frame comes from `resolve`.

A hardware value is a node in one arena, so a new node shares its operand trees. A structural path is a node in a second arena, and a user field holds the symbol of its name. Thus a new node or a new name costs constant work and no copy. A static type is an id in a third table, `Types`, with one id for each equal type. An id carries the size and the depth of its type. Thus a copy and an equality of types cost constant work. An array value and a record hold the id of their type. The module `types` holds this table, the type metadata of design section 5.4, and the table of struct specializations. A specialization is keyed by its struct item and its static arguments after their typed use. A struct type carries the metadata, so `T()` and `data_bits` never walk the field types. The module `serial` writes the canonical serialization, and `text` writes the bounded text of a type or a value in a message. Both walks keep their own stack. In the evaluator, `eval/types` evaluates the type expressions, the `type` aliases, and the specializations with their charges and `S019`. `eval/record` evaluates the constructors, the zero `T()`, the fields, and `data_bits`. `eval/call` evaluates the calls and the receiver calls, binds the parameters, and runs the write-backs of the `mut` formals. `eval/place` resolves the places of assignments and of `mut` actuals. From phase 5, `eval/types` also evaluates the function types, and a function name is a value. `eval/call` calls a function through a value and counts the windows of the `mut` actuals at run time (`S008`). `eval/string` evaluates the string index, `len`, and `str`. `eval/list` evaluates `list`, `push`, and `pop`. The module `counters` counts the work of the walks and the operations for each run, by its fuel budget, and only the tests compile it.

The module `agg` holds the hardware aggregate of Lean `Eval.Agg` (design sections 5.1 and 5.4), and `eval/agg` evaluates it:

- An `Agg` is a tree of `Static`, `Hw`, `Ref`, `Array`, `Tuple`, and `Record` parts. Each container `Node` stores its `TyId`, its size, its depth, and its count of hardware leaves. Thus no charge walks the tree. A container without a hardware leaf stays a static `Value`.
- A `Ref` is lazy. A read of an aggregate port, register, wire, or child output gives a `Ref` with no charge. A static selection gives a sub-reference with one node in the path arena (`Base::sub`). A part without a hardware leaf normalizes to a static value, and it charges the zero size from the `TyId` first.
- `Op::Out` and `Base::Out` hold the port name of a child output as a path in the path arena. Thus a step and a leaf read copy no name.
- A read through the nodes of a stored root takes its steps with one cursor, so it walks the path from the root once. An index with no call evaluates before that walk when no part before it is empty. The scan pass records each index with a call, so no evaluation scans the AST. An index with a call can change the root. Thus the first change of the root during that index decides if the read holds the root (`decide_holds`). An index that leaves the root alone walks no path. Each node stores its part with the most hardware leaves (`heavy`). The cursor keeps a witness. This is a path from the root to a hardware leaf along the heavy parts. The cursor also keeps its common prefix with the path of the read. A part on the witness holds a hardware leaf, so its decision walks nothing. Else the decision walks the path once, and a static part holds the root. A walk that finds a hardware part makes a new witness through a part with at most half the leaves of the part before. Thus a read walks at most log2 of the leaves plus one times its steps. A `push` or `pop` into a list part of an unheld aggregate root appends one entry to its undo log (`eval/undo`). This takes constant work. No waiting read of the root copies for it. The read resolves the entries of its window once at its result. A part that no entry reaches stays a reference. A part at or above a changed list gets a copy of its old value, and the copy undoes the entries first. No charge pays for that copy (#237). A hardware `if` keeps the numbers of each finished part, and the promotion of a static container finds its type once.
- `push` and `pop` into a list part refresh each node on the path in constant work from the stored numbers (`change_at`). `charge_refresh` charges the part counts first (Lean `Agg.pathWidth`).
- `==`, `!=`, and a hardware `if` walk both operands by leaf. In an `if`, a static pair with different sides is `S011` (F19). `Op::Share` marks the condition of an `if` with two or more `mux` nodes, and `flatten` binds it at its first lowering in the module.
- `layout` streams the leaves of a port in packing order, and no other module expands a port. `flatten` charges each leaf before it makes the leaf, and it lowers the left spine of a binary chain in a loop.
- The lowering thread joins the counters of its run, so the tests count the work of `flatten` too.
- `Handle::Mem` is the handle of a `mem` statement. The `Mem` of `Body.mems` holds its path, depth, word type, first requests, and first second call.
- A word reference is `Base::Word(PathId, offset)` or `Op::Word(PathId, offset)`. It holds the path id once, never a copy. `Base::sub` adds `Types::offset`, which reads the stored prefix offset of the type, so a step costs constant work. The counters `offsets`, `chained`, `blocked`, and `seconds` count this work in the tests.
- The prelude item `ReadResponse` comes after the user items, and `Resolved::is_prelude_item` marks it. `spec_of` moves the errors of its specialization to the use position.
- `flatten` lowers each memory as one block after the registers: the core memory, the response registers, the request `let` values, the two `next` statements, and the `write`. Each core node charges before it exists. A leaf of a word is an `extract` of `m$0rdata`. The write data is a `concat` chain that a loop over the leaves builds, so no recursion follows the leaf count. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.

The elaborator core keeps to the Rust subset of design section 4.5: plain owned data, `match`, `Vec`, `Box`, and no `Rc`, no `unsafe`, and no trait object. The module `int` holds the static integer behind a small interface, and only this module computes with `num-bigint`. It also holds each conversion between an integer and a finite value. A finite value uses the bit vector of `core-ir`, as the core semantics does.

## Invariants

- The serialization of a value equals the bytes of `Value.serialize` in Lean. The recursive size equals `Value.size`, and the depth equals `Value.depth`. Check: `cargo nextest run -p elab`.
- The digest equals the test vectors of FIPS 180-4. Check: `cargo nextest run -p elab`.
- The evaluator charges each unit of `Source.Eval` in the same order and at the same node. The charge comes before the work, and each operation keeps its work and its memory in its charge. Thus the value, the used fuel, and the code and the position of the first error equal those of Lean. Check: `cargo nextest run -p elab` and the comparison with `silicon-check eval`.
- A memory port call follows section 6.2 (`eval/mem.rs`). The order is: the copies, the memory check, `S016` in a guard, the typed uses, and the record of the first request of each kind. `read_port` then charges the struct use of `ReadResponse[T]`, its depth, and its zero size. A second call of one kind charges the same and keeps the first request. It records its `S018` in O(1). The response refers to the word of the memory (`Base::Word`) and walks no leaf. The table of types stores the prefix offsets of each tuple and struct type. Thus a step on a word adds one stored number. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.
- The evaluator holds the innermost guard of section 9.4 in `guard: Option<Guard>`, with its kind (`Arm` or `Structural`) and its depth. A hardware `if` sets an `Arm` guard. `structural` sets a `Structural` guard in O(1) for each type expression, type index, `[T; N]`, function type, struct use, first use of a constant, and `mem` depth. The innermost guard wins. A `push`, a `pop`, or a write-back of a binding of the depth of the guard is `S016`, and so is a memory port call. The texts of `Guard` equal those of Lean. Check: `cargo nextest run -p elab` and the comparison with `silicon-check elab`.
- `diagnostic` follows section 5.4 and Lean `Eval.diagnose` (`eval/observe.rs`): the guard, the message, the waiting value, the measure charge, the byte charge, and then the record. The render walk is pure. It has its own stack, it runs into a `Len` sink for the byte charge and then into the string, and it never calls `normalize`. A `Ref` renders from the metadata of its type. The emitted name and the name of a domain handle are an `Arc<str>`, so a read of a domain copies no text. The length pass builds no name text, and it needs no list of types to measure first. The evaluator keeps a cache. It holds the length of each type that a record measured and the powers of ten of the digit counts. A type nobody records costs no length. The length pass counts the digits of an integer from its bit length (`Int::decimal_len`) and formats none. A frame, a handle, a module, a port, and a message write from borrowed fields. A call pushes its frame in O(1) and a done instantiation makes no record again, so the frames cost only their charged bytes. `observe` returns `Observed { records, outcome }`, with the records of an error too. `elaborate` is its projection. The counters `rendered`, `rendered_leaves`, `framed`, `recorded`, `guarded`, and `copied` count this work. Check: `cargo nextest run -p elab` and the comparison with `silicon-check observe`.
- The elaboration charges each unit of `Source.Elab` in the same order and at the same node. The units of each instantiation, the emitted names, and the code and the position of the first error equal those of Lean `Elab.elaborate`. Check: `cargo nextest run -p elab` and the comparison with `silicon-check cost`.
- `decode(encode(p)) == Some(p)` for each valid name `p`, and each encoded name is a legal core name. Check: `cargo nextest run -p elab`.
- An error message prints at most 256 bits of an integer, 64 characters of a string, and 1024 bytes of the text of a type. Check: `cargo nextest run -p elab`.
- The evaluator recurses, so it runs through `parse::NestedStack`, and it only finds the heights of the AST. A call, a constant, a function name used as a value, and an instantiation each start a nesting level. Each thread runs a group of nesting levels, so any nesting depth is safe. A design and an error hold no recursive value, so they drop safely on any stack. No walk over a value, a type, or an aggregate recurses. Each keeps an explicit stack, so a value of any depth is safe on any stack, also in the driver. `Parts` drops with its own stack. A result that refers to a local or a constant copies nothing until a copy pays for it. An assignment to a place with an index copies only the containers on the path of the place. Check: `cargo nextest run -p elab`.
- `push`, `pop`, and a `mut` write-back change the live root in one walk down the path of the place. A `pop` of a held root walks the path twice, and the charge of the root pays for the second walk. They copy no list and no root. A string operation charges the size of the string before it scans, and `s = s + t` makes one new string. Check: `cargo nextest run -p elab`.
- A result keeps the value that its expression read. A result that refers to a local waits in the store while a later operand, argument, or index evaluates. A waiting reference to a static value holds its local (design section 5.4). A waiting result that a mutation copied (`Out::Kept`) keeps its copy and still holds its local, as Lean keeps its root. A mutation of a held local first charges the size of the local, then copies each waiting reference to it. A `push` or `pop` copies only the references that its path reaches, and only those that hold the root or that no cursor follows. A write that binds the root again copies all, after it undoes the log entries of each copy. Each copy is at most that size, and one expression of the source holds the waiting references. Check: `cargo nextest run -p elab` and the comparison with `silicon-check eval`.
- A `mut` actual binds its formal only at the type of its place, with no typed use. The write-backs run after the result binds, in the order of the parameters, at the position of the call. Each checks `S016`, then the depth of the root, then charges, then writes. Check: `cargo nextest run -p elab` and the comparison with `silicon-check run`.
- The signature of a function value evaluates in the scope of its function, with no locals, and it takes one nesting level. A function type has no metadata charge. A call through a value compares the number of arguments before the arguments evaluate. The windows of a place open after its root resolves and before its steps. A root with an open window gives `S008` at the next `mut` actual or assignment. A `mut` actual that is not a place gives `S008` in a call through a value. Check: `cargo nextest run -p elab` and the comparison with `silicon-check run`.
- The crate uses no `HashMap` and no `HashSet`. Check: `just clippy`.
- Non-test code has no `unwrap`, no `expect`, and no panic on user input. Check: `just clippy`.

## Dependencies

This crate reads a `Resolved` that passed `typeck`. It uses `resolve` for the targets of names, and `parse` for the AST and the front-end thread. It uses `core-ir` for the operations on finite values and the keywords of core names. The tests use `typeck` and `proptest`. The `driver` calls it.

## How to test

Run `cargo nextest run -p elab`, then `just check` from the repository root.
